# 검증 실행

검증을 돌리고 결과를 읽는 절차. 규칙을 만드는 절차는 `core/rules.md` 에 있다.

## 실행 절차

1. `engine/verify.py` 를 실행한다. 무엇을 검사할지는 매니페스트가 정한다
2. 일부만 보려면 `--path <경로>` 로 좁힌다
3. `error` 와 `확정 필요` 가 둘 다 없으면 통과다
4. 결함이 있으면 각 항목의 `고침` 을 따라 고친다
5. 확정할 후보가 있으면 하나씩 판정해 `--verdicts` 가 가리키는 JSON 에 적는다
6. 2 로 돌아간다

어댑터가 위임을 제공하면 4단계를 나눠 돌려도 된다. 제공하지 않아도 절차는 그대로 완주한다.

화면에는 사람이 읽는 요약이 나온다. `warn` 은 수만 세고 목록은 `--warn` 을 줄 때 낸다.
기계가 읽을 산출물이 필요하면 `--json <파일>` 로 쓰거나 `--format json` 으로 바꾼다.

## 매니페스트

`verify.json` 이 규칙 셋 목록과 종류별 경로를 갖는다. 규칙을 늘려도 이 파일은 안 바뀌고,
새 종류를 만들거나 경로가 옮겨질 때만 바뀐다.

```
{
  "rulesets": ["<규칙 디렉토리>", ...],
  "kinds": {"<종류>": {"granularity": "file" 또는 "dir", "paths": [...]}},
  "kinds": {"<규칙 셋 종류>": {"granularity": "dir", "from_rulesets": true}},
  "names": {"<이름 종류>": {"from_dirs": "<디렉토리>"}},
  "verdicts": "<확정 기록 경로>",
  "timeout": <판정기 하나에 주는 초>
}
```

`granularity` 는 판정기가 무엇을 받는지다. `file` 은 파일 하나씩, `dir` 은 디렉토리 통째다.

`names` 는 판정기가 써야 할 이름 목록의 출처다. 목록을 매니페스트에 나열하지 않고 디렉토리에서
뽑는다. 나열하면 실제와 어긋나도 드러날 자리가 없다.

`rulesets` 항목을 `{"path": ..., "checks": ...}` 로 적으면 그 셋의 판정기를 다른 자리에서 찾는다.
스킬이 자기 규칙을 가질 때 쓴다. 문자열로 적으면 엔진 아래에서 찾는다.

`from_rulesets` 인 종류는 경로를 적지 않는다. `rulesets` 목록이 그대로 대상이 된다. 같은 목록을
두 곳에 적으면 한쪽만 늘어나고, 그러면 새 규칙 셋이 검사 대상에서 조용히 빠진다.

`timeout` 은 판정기 하나에 주는 시간이다. 끝나지 않는 판정기 하나가 검증 전체를 세우면
무엇이 세웠는지도 안 남는다.

## 판정기 인터페이스

| granularity | 첫 인자 | 둘째 인자 |
|---|---|---|
| `file` | 파일 경로 | 그 파일 본문 |
| `dir` | 디렉토리 경로 | 그 안의 규칙 목록 |

결함 목록을 낸다. 각 항목은 `line` 과 `snippet` 과 `message` 를 갖는다.

문맥이 필요한 판정기만 셋째 인자를 더 받는다. `names` 가 만든 이름 목록이 거기 들어온다.

판정기가 `fix` 를 함께 두면 `--fix` 가 그것을 부른다. 인자는 `check` 와 같고, 무엇을 고쳤는지
한 줄씩 낸다.

## 자동 수정

`--fix` 는 결함에 `autofixable` 이 붙은 것만 고친다. 붙일 수 있는 것은 **생성물**뿐이다 --
고칠 결과가 판단 없이 하나로 정해지고 그것을 만드는 생성기가 이미 있는 경우다.
지금은 인덱스 하나가 그렇다.

나머지 결함은 `--fix` 를 줘도 그대로 낸다. 방향이 하나로 정해진다는 것과 기계가 그 방향으로
갈 수 있다는 것은 다르다.

커밋 훅은 `--fix` 를 쓰지 않는다. 훅이 파일을 고치면 방금 스테이지한 내용과 어긋난 채로
커밋된다.

## 종료 코드

| 코드 | 뜻 | 할 일 |
|---|---|---|
| 0 | 통과 | 끝낸다 |
| 1 | 결함 있음 | 고치고 다시 돌린다 |
| 2 | 헛돎 | 멈추고 사람에게 넘긴다 |
| 3 | 미확정 후보 있음 | 후보를 확정하고 다시 돌린다 |

## 후보 확정

`hybrid` 규칙의 후보는 확정되기 전까지 통과가 아니다. 확정은 후보의 `id` 별로 적는다.

```
{"<id>": {"verdict": "ok" 또는 "defect", "evidence": "왜 그렇게 판정했는가"}}
```

근거가 비면 확정으로 세지 않는다. 판정했다는 표시만 받으면 후보를 훑고 넘어간 것과
구분되지 않는다. `id` 는 대상 스니펫의 해시를 담으므로, 그 자리를 고치면 지난 확정은
매칭되지 않고 다시 후보로 올라온다.

반대쪽도 막는다. 확정은 있는데 그 대상이 이번 검사에 없으면 결함이다. 미확정을 통과로 세지
않는 것과 같은 이유다 -- 남겨두면 무엇을 위한 확정인지 알 수 없게 되고 그 파일을 못 믿는다.
지우는 데 판단이 필요 없으므로 `--fix` 대상이다.

이 판정은 전체를 볼 때만 한다. `--path` 로 좁히면 멀쩡한 확정이 낡아 보인다.

## 회차 비교

`--out-dir` 를 주면 회차가 쌓이고 직전 회차와의 비교가 `delta` 에 담긴다.
`--path` 와 함께 쓸 수 없다. 부분만 본 회차는 안 본 결함을 사라진 것으로 세어, 헛돎 판정이
리셋되고 루프가 거짓 진전으로 끝난다.

| 항목 | 뜻 | 할 일 |
|---|---|---|
| `resolved` | 지난 회차에 있었고 이번에 없다 | 진전이다 |
| `persisted` | 양쪽에 있다 | 그 결함은 아직 안 고쳐졌다 |
| `new` | 이번에만 있다 | 수정이 새 결함을 만들었다. 되돌리고 다른 방향으로 고친다 |

`resolved` 도 `new` 도 없이 `persisted` 만 남은 회차가 두 번 연속이면 헛도는 것이다.
엔진이 종료 코드 2 를 내며, 이때는 멈추고 사람에게 넘긴다.

## 반복 자동화

`scripts/loop.py` 가 검증 명령을 반복해 돌린다. 완료 판정을 종료 코드로만 하므로
실행 모델이 완료를 선언해도 검증이 통과하지 못하면 끝나지 않는다.

반복을 무엇이 촉발하는지는 어댑터가 정한다. 종료를 막을 수단이 있는 툴은 그것으로 돌리고,
없으면 사람이 다시 호출한다. 어느 쪽이든 판정은 같다.

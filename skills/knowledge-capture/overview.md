# 지식 캡처

논의에 필요한 지식을 감지하고 문서로 누적하는 스킬.

활성된 동안 메인 LLM 이 매 발화에서 아래 점수표를 기준으로 자동 감지를 수행하고,
임계 도달 시 wip 파일 작성을 `knowledge-writer` 에이전트에 위임한다.
wip 를 확정지식으로 올리는 승급(지식화) 단계는 별도 독립 스킬 `knowledge-promote` 가 담당한다. 본 스킬은 캡처(wip 누적)까지만 다룬다.

---

## 활성 조건

`knowledge-capture` 는 사용자가 `/knowledge-capture` 슬래시 명령으로 명시적으로 호출했을 때만 활성된다.
활성 여부의 판단은 사용자에게만 있다.

<RICOCHET>
LLM 자가판단으로 스킬을 활성하거나 점수 계산을 시작하지 않는다.
</RICOCHET>

## 저장 경로 설정

활성 직후, wip 파일을 저장할 디렉토리 경로를 사용자에게 입력받는다.
경로를 코드에 고정하지 않으며, 매 활성마다 새로 입력받는다.

입력 경로는 Herbarium 저장소 하위여야 한다. 디렉토리명은 동명 저장소가 있을 수 있어 신뢰할 수 없으므로, 검증은 git origin remote 조회로 한다.

### 검증 절차

1. 입력 경로에서 origin remote 를 조회한다. 입력 경로가 아직 없으면 존재하는 가장 가까운 상위 디렉토리에서 조회한다.
   `git -C <입력경로> remote get-url origin`
2. 결과가 아래 기대 remote URL 과 정확히 일치하면 채택한다.
3. 일치하지 않거나 조회에 실패하면 사유를 한 줄로 알리고 경로를 다시 입력받는다. 일치할 때까지 반복한다.
4. 채택한 경로가 아직 없으면 `mkdir -p` 로 생성한다.

#### 기대 remote URL

이 값이 저장 경로 검증의 단일 기준이다.

```
git@github.com:Olbbemi/Herbarium.git
```

채택한 저장 경로는 점수표와 마찬가지로 메인 LLM 컨텍스트에만 유지하며(세션 휘발), 별도 파일 · 인덱스에 저장하지 않는다.

<PENETRATE>
활성 직후 wip 저장 디렉토리 경로를 사용자에게 입력받는다.
</PENETRATE>

<PENETRATE>
입력 경로의 git origin remote 가 기대 remote URL 과 정확히 일치할 때만 저장 경로로 채택한다.
</PENETRATE>

<RICOCHET>
origin remote 가 기대 remote URL 과 일치하지 않는 경로를 저장 경로로 채택하지 않는다.
</RICOCHET>

<RICOCHET>
wip 저장 경로를 코드에 고정 리터럴로 박지 않는다.
</RICOCHET>

## 하위 스킬

| 스킬 | 파일 | 역할 |
|------|------|------|
| `knowledge-writer` 에이전트 | `agents/knowledge-writer.md` | 임계 도달 시 메인의 입력을 받아 wip 본문을 작성하고 메인에 반환 (저장은 메인이 수행) |

---

## 실행 순서

1. 활성 (슬래시 명령). 활성 직후 저장 경로를 설정한다 (`저장 경로 설정` 섹션)
2. 매 발화마다 두 트리거 동시 감시
   - 자동 감지: 점수표 임계(3점) 도달
   - 명시 지시: 사용자의 직접 저장 요청
3. 트리거 발생 시 호출 입력 구성
4. `knowledge-writer` 서브에이전트 백그라운드 호출 (Task 도구)
5. writer 가 외부 조사 + wip 본문 작성 후, 본문 전체를 최종 메시지로 반환 (파일 저장 안 함)
6. 메인이 완료 통지를 받아 반환 본문을 wip 파일로 저장 (HTML 엔티티 원복) 후 흐름 종료

에이전트가 한 종류라 에이전트 간 병렬 처리는 해당 없음. 각 단계의 세부 규칙·강제 사항은 후속 섹션에 정의한다.

---

## 자동 감지 점수표

자동 감지 점수표는 **개념 지식**(패턴·아키텍처·라이브러리)에만 적용한다.
코드/문법 지식은 자동 감지하지 않는다. 모르는 문법은 눈앞에 코드가 있어야 물어볼 수 있어 자동 감지가 사실상 불가능하기 때문이다.
코드 지식은 사용자 명시 요청으로만 캡처한다(아래 "사용자 명시 지시 트리거").

<RICOCHET>
코드/문법 지식을 점수표로 자동 감지하지 않는다.
</RICOCHET>

<PENETRATE>
활성된 동안 메인 LLM 은 매 발화마다 점수표를 적용해 자동 감지를 수행한다.
</PENETRATE>

<RICOCHET>
활성된 동안 발화를 점수 계산 없이 그냥 흘려보내지 않는다.
</RICOCHET>

> 초기값. 사용하면서 기준과 점수를 조정할 것.

| # | 기준 | 점수 | 예시 |
|---|---|---|---|
| A | 처음 등장하는 개념이고 wiki 캐시에 미존재 | +1 | RUDP 가 갑자기 언급됨 |
| B | 해당 개념 없이 현재 논의 판단 자체가 불가 | +2 | RUDP 설계인데 UDP 를 모르면 진행 불가 |
| C | 논의 방향이 인접 계층 / 개념으로 반복 이탈 | +2 | UDP 논의 중 계속 IP 계층으로 빠짐 |
| D | 같은 잘못된 가정이 2회 이상 반복 | +3 | "UDP 는 연결을 맺고 나서..." 류 오해 반복 |
| E | 서로 다른 개념을 같은 것처럼 혼용 | +2 | "패킷" 과 "세그먼트" 를 같은 의미로 씀 |

A 기준은 wiki 정의 후 실제 동작과 함께 적용된다. wiki 미정의 상태에서는 A 기준 자체를 점수 계산에서 보류한다.

### 임계값

| 합계 점수 | 동작 |
|----------|------|
| 3점 미만 | 무시 |
| 3점 이상 | 즉시 `knowledge-writer` 에이전트 호출 (`임계 도달 이후 처리` 섹션 참조) |

<RICOCHET>
현재 작업과 직접 연관 없는 주제는 점수 계산 대상으로 삼지 않는다.
</RICOCHET>

## 사용자 명시 지시 트리거

사용자가 특정 주제에 대해 knowledge 저장을 직접 요청한 경우, 점수와 무관하게 즉시 위임한다.

### 인정 발화 패턴

저장 의도가 드러난 발화는 모두 명시 지시로 인정한다.

- "이거 knowledge 로 남겨줘"
- "이 부분 wip 로 저장해줘"
- "이 정보 기억해둬" (knowledge 맥락)
- 기타 사용자가 명시적으로 저장 의도를 표한 표현

<PENETRATE>
명시 지시가 감지되면 점수 누적 상태와 무관하게 즉시 `knowledge-writer` 에이전트를 호출한다.
</PENETRATE>

<RICOCHET>
명시 지시 발화를 "점수 3점 미만이라 무시" 로 처리하지 않는다.
</RICOCHET>

### 처리 규칙

- 호출 형식은 자동 감지 경로와 동일 (`임계 도달 이후 처리` 섹션 재사용)
- `triggered_by` 필드에 점수 코드(A~E) 대신 `user-request` 를 적는다
- `trigger_summary` 에 어떤 발화로 지시가 발생했는지 한 줄 기술
- 묶음 / 분리 판단은 메인 LLM 자율
- 동일 세션 내 같은 주제 중복 위임 방지 규칙은 동일 적용

---

## 점수 계산 주체와 휘발성

- 점수표 비교와 누적 계산은 메인 LLM (Claude) 의 작업이다.
- 점수표 · 누적값은 메인 LLM 컨텍스트 안에만 존재하며 별도 파일 · 인덱스에 저장하지 않는다.
- 세션 종료 · 컴팩 시 자연히 초기화된다 (세션 단위 휘발).

<RICOCHET>
점수표 자체나 누적 점수를 별도 파일 · 인덱스에 저장하지 않는다.
</RICOCHET>

<PENETRATE>
모든 점수 상태는 메인 LLM 컨텍스트 안에서만 유지한다.
</PENETRATE>

---

## 누적 규칙

- 점수는 세션 내에서만 유효하다. 세션이 바뀌면 모든 주제 점수 리셋.
- 다른 주제는 독립적으로 점수 계산한다.
- 사용자가 이미 알고 있다고 명시한 주제는 해당 세션의 점수 계산 · 위임 대상에서 제외한다 (세션이 바뀌면 다시 적용).
- 여러 주제가 동시에 임계를 넘는 경우 모두 위임 대상에 포함한다 (하나만 선택하지 않는다).
- 임계를 넘어 `knowledge-writer` 에이전트로 위임된 주제는 해당 세션에서 추가 점수 누적 및 중복 위임 대상에서 제외한다 (락).
- wiki 에 이미 등재된 주제는 점수 계산 대상에서 제외한다 (요약 비교로 의미적 중복 판단). 본 규칙은 wiki 정의 후 실제 동작과 함께 적용된다.

## 임계 도달 이후 처리 (wip 단계)

임계 점수를 넘긴 주제는 메인 LLM 이 즉시 `knowledge-writer` 에이전트를 호출해 wip 파일 작성을 위임한다.
사용자 확인 없이 자동 진행되며, 같은 사안의 여러 측면을 한 항목으로 묶을지 별 항목으로 쪼갤지의 판단도 메인 LLM 의 자율에 맡긴다.
호출 명세는 아래 서브섹션 참조.

<PENETRATE>
임계 도달 시 메인 LLM 은 사용자 확인 없이 즉시 `knowledge-writer` 에이전트를 호출한다.
</PENETRATE>

이 자동 진행은 wip 단계에 한정된다. wip -> wiki 승급 단계는 별도 사용자 확인 규약을 따른다.

<RICOCHET>
wip 단계에서 위임 여부 · 묶음 · 분리 여부를 사용자에게 묻지 않는다.
</RICOCHET>

### 호출 형태

| 항목 | 값 |
|------|----|
| 호출 도구 | Task |
| `subagent_type` | `knowledge-writer` |
| `run_in_background` | `true` (백그라운드) |
| writer 출력 | wip 파일 전체 본문을 최종 메시지로 반환 (Write 안 함) |
| 저장 | 메인 에이전트가 통지를 받아 활성 시 설정한 저장 경로 하위 `<저장경로>/<topic>.md` (또는 suffix) 로 직접 저장 |

<PENETRATE>
`knowledge-writer` 호출은 백그라운드(`run_in_background: true`)로 한다. 메인은 완료 통지 도착까지 사용자 논의를 계속한다.
</PENETRATE>

<PENETRATE>
작업(조사·작문)은 백그라운드 서브에이전트 writer 에 위임하고, wip 파일 저장은 메인 에이전트가 완료 통지 도착 시 직접 수행한다.
</PENETRATE>

<PENETRATE>
반환 본문의 `&`/`<`/`>` HTML 엔티티는 저장 전 원복한다.
</PENETRATE>

<RICOCHET>
백그라운드 writer 에게 Write/Edit 으로 wip 파일을 직접 저장하게 하지 않는다.
</RICOCHET>

### `knowledge-writer` 에이전트 호출 입력 포맷

Task 도구의 prompt 파라미터에 아래 라벨 + 콜론 구조화 텍스트로 전달한다. JSON 형식은 사용하지 않는다.

| 필드 | 의미 | 비고 |
|------|------|------|
| `save_path` | 활성 시 확정한 wip 저장 디렉토리 절대경로 | `저장 경로 설정` 에서 채택한 경로. writer 가 충돌 검사·파일명 결정 기준으로 사용 |
| `topic` | 주제 식별자 (kebab-case) | wip 파일명 기반 |
| `triggered_by` | 발동된 기준 코드 (A~E 또는 `user-request`) | 복수 가능 |
| `trigger_summary` | 한 줄 사유 | 1~2 문장 |
| `user_known` | 사용자가 안다고 명시한 인접 지식 | 에이전트의 출발 지식 수준 결정 기준 |
| `discussion_context` | 임계가 발생한 큰 논의 맥락 | 왜 이 주제가 지금 필요한가 (snippets 한 단계 위의 목적 맥락) |
| `snippets` | 대화 발췌 | 화자 표기 권장 |
| `kind` | 지식 종류 | `concept`(기본) 또는 `code`. `code` 면 writer 가 코드 템플릿으로 작성 |
| `language` | 대상 언어 | `kind: code` 일 때만. `python` / `rust` / `cpp` |

#### 입력 예시 (zmq 라이브러리 — 한 항목 묶음)

```
save_path: /home/olbbemi/Project/Herbarium/wip
topic: zmq
triggered_by: A, B
trigger_summary:
  ZMQ 라이브러리 자체에 대한 전제 지식 부재로 라이브러리 선택 논의 진행 불가.
  PUB/SUB 등 메시징 패턴 종류도 전혀 모름.
user_known:
  - TCP/UDP 차이는 알고 있음
  - 메시지 큐 개념은 들어본 정도
discussion_context:
  설계 논의 중 마이크로서비스 간 메시지 큐 라이브러리 후보 선정 중
snippets:
  - Claude: 메시지 큐로 ZMQ 를 검토해볼까요?
  - 사용자: zmq 가 뭐지? 처음 들어봐
  - Claude: PUB/SUB 패턴이 적합할 것 같습니다
  - 사용자: 패턴 종류가 뭐가 있는지 전혀 모르겠어
```

같은 상황을 두 항목으로 쪼갠 예시:

- 항목 1: `topic: zmq` (라이브러리 자체 개요)
- 항목 2: `topic: zmq-messaging-patterns` (PUB/SUB · REQ/REP 등 패턴 종류)

묶음 / 분리 결정은 메인 LLM 의 자율 판단이며 사용자 확인을 받지 않는다.

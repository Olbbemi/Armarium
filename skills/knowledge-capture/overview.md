# 논의 감시 캡처

활성된 동안 대화를 지켜보며 개념 공백을 자동 감지하고, 사용자의 명시 저장 요청도 함께 받아 wip 로 캡처하는 스킬.

활성 후 매 발화마다 배후에서 도는 상시 감시가 이 스킬의 성격이다. 명령 한 번에 시작해 끝나는 단발 작업(`knowledge-scan` 의 코드 스캔, `knowledge-study` 의 로드맵 학습)은 수명주기가 달라 별도 스킬로 나뉘어 있다.

wip 를 확정지식으로 올리는 승급은 별도 스킬 `knowledge-promote` 가 담당한다. 본 스킬은 캡처까지만 다룬다.

---

## 활성 조건

이 스킬은 두 방식으로 활성된다. 어느 쪽이든 활성 후 동작은 같다.

| 활성 방식 | 촉발 |
|------|------|
| 자동 활성 | SessionStart 훅(`hooks/session-skill-list.sh`)이 매 세션 이 overview 를 주입한다 |
| 명시 호출 | 사용자가 `/knowledge-capture` 슬래시 명령으로 부른다 |

자동 활성은 이 스킬만의 예외다. 논의 중 지식 부재는 사용자가 스킬을 부를 생각을 못 하는 순간에 드러나므로, 명시 호출에만 의존하면 잡을 시점을 놓친다. 형제 스킬인 `knowledge-scan` 과 `knowledge-study` 는 사용자가 목적을 갖고 시작하는 단발 작업이라 자동 활성 대상이 아니다.

자동 활성은 사용자가 훅을 설치해 미리 내린 결정이지 LLM 의 자가판단이 아니다.

<FORBIDDEN>
훅 주입도 슬래시 명령도 없는 세션에서 LLM 자가판단으로 이 스킬을 활성하거나 점수 계산을 시작하지 않는다.
</FORBIDDEN>

## 공용 프로토콜

저장 경로 검증 · `knowledge-writer` 호출 형태 · 입력 포맷 · 반환 본문 저장은 아래 공용 파일이 단일 출처다.

    references/knowledge-wip-protocol.md

캡처가 확정되면 이 파일을 Read 툴로 로드해 따른다. 본 스킬이 받는 경로는 wip 저장 디렉토리 하나이며, 공용 파일 1절의 검증 절차를 그 경로에 적용한다.

### 저장 경로 확보 시점

경로는 활성 시점이 아니라 **첫 캡처가 확정되는 순간**에 처음 묻는다. 자동 활성이 기본이라 활성 시점에 물으면 knowledge 와 무관한 세션까지 전부 경로 질문으로 시작하기 때문이다. 감지는 경로 없이도 돌고, 경로가 실제로 필요한 것은 저장 단계뿐이다.

- 세션에서 첫 캡처가 확정되면 그때 경로를 입력받아 검증한다. writer 호출은 경로 확정 뒤에 한다.
- 한 번 확정한 경로는 그 세션 동안 재사용한다.
- 캡처가 한 번도 일어나지 않는 세션은 경로를 묻지 않는다.

캡처가 확정되면 `references/knowledge-wip-protocol.md` 를 Read 툴로 로드하고, wip 저장 디렉토리 경로를 입력받아 그 파일의 검증 절차를 적용한다.

<FORBIDDEN>
캡처가 확정되지 않은 상태에서 wip 저장 경로를 미리 묻거나, 세션에서 한 번 확정한 경로를 다시 묻지 않는다.
</FORBIDDEN>

## 하위 스킬

| 파일 | 역할 |
|------|------|
| `references/knowledge-wip-protocol.md` | 세 knowledge 스킬 공용 -- 경로 검증 · writer 호출 · 저장 규칙 |

에이전트는 `knowledge-writer` 하나를 쓴다. 정의 파일은 플러그인 루트 `agents/` 에 있다.

| 에이전트 | 파일 | 역할 |
|----------|------|------|
| `knowledge-writer` | `agents/knowledge-writer.md` | 메인의 입력을 받아 wip 본문을 작성하고 반환 (저장은 메인이 수행) |

점수표와 트리거 규칙은 이 파일 안에 직접 둔다. 이 스킬은 모드가 하나뿐이라 하위 파일로 쪼개지 않는다.

## 두 갈래 트리거

캡처는 두 트리거로 시작된다. 둘은 활성된 동안 동시에 감시된다.

이 문서에서 "경로" 는 파일시스템 경로만 가리킨다. 캡처가 어느 쪽으로 들어왔는지는 "트리거" 로 쓴다.

| 트리거 | 촉발 | 대상 지식 |
|--------|------|----------|
| 자동 감지 | LLM 이 대화를 점수표로 판정해 발동 | 개념만 |
| 명시 요청 | 사용자가 저장을 직접 지시 | 개념 + 코드/문법(지명) |

코드/문법은 눈앞에 코드가 있어야 물어볼 수 있어 자동 감지 대상이 아니다. 그래서 코드/문법은 명시 요청으로만 들어오며, 코드베이스를 훑어 뽑는 일은 별도 스킬 `knowledge-scan` 이 담당한다.

---

## 실행 순서

1. 활성 (훅 주입 또는 슬래시 명령)
2. 매 발화마다 두 트리거를 동시 감시한다 (`자동 감지 점수표` / `사용자 명시 지시 트리거`)
3. 캡처가 확정되면 경로를 확보한다 -- 세션 첫 캡처면 공용 프로토콜을 로드해 경로를 입력받아 검증하고, 이미 확정돼 있으면 그것을 재사용한다 (`저장 경로 확보 시점`)
4. 이미 정리한 주제인지 대조한다 (`기존 정리분 대조`). 중복이면 트리거에 따라 건너뛰거나 보강으로 전환한다
5. `knowledge-writer` 를 호출한다 -- 백그라운드 (`run_in_background: true`). 입력: `writer 위임` 의 값. 출력: wip 본문을 반환 -> 메인이 `<저장경로>/<권장파일명>` 으로 저장

### 단계 시각화 (TaskCreate)

이 스킬은 발화마다 배후에서 도는 상시 감지라 매 발화를 task 로 만들지 않는다. 임계 도달이나 명시 요청으로 writer 위임이 발생하는 시점만 표시한다 -- 백그라운드 에이전트 호출이므로 호출 즉시 completed 로 닫고, subject 는 "knowledge-writer 에이전트 호출" 형식으로 쓴다.

## 자동 감지 점수표

자동 감지 점수표는 개념 지식(패턴·아키텍처·라이브러리)에만 적용한다.
모르는 문법은 눈앞에 코드가 있어야 물어볼 수 있어 자동 감지가 사실상 불가능하다.

활성된 동안 메인 LLM 은 매 발화마다 점수표를 적용해 자동 감지를 수행한다.

<FORBIDDEN>
코드/문법 지식을 점수표로 자동 감지하지 않는다.
</FORBIDDEN>

점수표는 그룹별로 나뉜다. 각 행은 점수 외에 역할 태그와 드러나는 `user_known` 을 갖는다. 역할 태그로 "발동 판정(게이트)" 과 "깊이 보정(user_known)" 을 한 표에서 갈라 뽑는다 (아래 `역할 태그와 추출` 참조).

### 공백 (개념 부재 신호)

| # | 기준 | 점수 | 역할 | 드러나는 user_known | 예시 |
|---|---|---|---|---|---|
| A1 | 처음 등장하는 개념이고 wiki 캐시에 미존재 | +1 | gate | - | RUDP 가 갑자기 언급됨 |
| A2 | 해당 개념 없이 현재 논의 판단 자체가 불가 | +2 | gate | - | RUDP 설계인데 UDP 를 모르면 진행 불가 |
| A3 | 이름조차 생소한 개념을 "모른다 / 뭐지?" 로 자기보고 | +2 | both | 그 개념 자체를 모름 | "zmq 가 뭐지? 처음 들어봐" |
| A4 | 이름은 익숙한데(들어봤다·써봤다) 용도·역할을 말하지 못함 | +1 | user_known | 이름만 알고 용도 모름 | "RUDP 들어는 봤는데 뭐 하는진 모름" |

### 오해 (잘못 아는 신호)

| # | 기준 | 점수 | 역할 | 드러나는 user_known | 예시 |
|---|---|---|---|---|---|
| M1 | 두 개념을 (환원 선언 없이) 용어로 구분 없이 섞어 씀 | +2 | both | 두 개념의 경계를 모름 | "패킷" 과 "세그먼트" 를 같은 의미로 |
| M2 | "항상 / 절대" 같은 절대화로 단정 | +2 | both | 예외·조건을 모름 | "락은 항상 느리다" |
| M3 | 옛 버전 정의를 현재 사실로 단정 | +2 | both | 버전에 따라 바뀐 걸 모름 | "view 는 항상 비소유" (DR 로 깨짐) |

오해는 종류만 행으로 두고, 반복은 가산으로 얹는다. M1/M2/M3 중 한 행에 해당하는 같은 오해가 2회 이상 반복되면 그 행 점수에 +1 한다. "잘못된 가정 반복" 을 독립 행으로 두면 종류 행과 포함관계가 되어 같은 오해를 이중계산하므로, 반복성은 독립 행이 아니라 수식어로만 쓴다.

### 앵커 (잘못된 기준점 신호)

| # | 기준 | 점수 | 역할 | 드러나는 user_known | 예시 |
|---|---|---|---|---|---|
| C1 | (개념 동일시가 아니라) 화제가 인접 계층으로 반복 이탈 | +2 | both | 경계 인접 개념과 혼동 | UDP 논의 중 계속 IP 계층으로 빠짐 |
| C2 | "결국 ~같은 거" 식 명시적 환원·동일시 선언 | +2 | both | 친숙 개념으로 잘못 동일시 | "코루틴? 결국 스레드 같은 거잖아" |
| C3 | 하위 요소를 전체로 착각 | +1 | user_known | 부분-전체 관계 오인 | "views 가 곧 Ranges" |

M1·C1·C2 는 겹치기 쉬우니 행위로 가른다: 명시적 "결국 ~같은 거" 환원 선언이면 C2, 선언 없이 용어를 섞으면 M1, 동일시가 아니라 화제가 다른 계층으로 흐르면 C1. 한 발화는 셋 중 하나로만 친다.

A1 기준은 wiki 정의 후 실제 동작과 함께 적용된다. wiki 미정의 상태에서는 A1 자체를 점수 계산에서 보류한다.

### 역할 태그와 추출

각 행의 역할 태그는 켜진 내역을 두 군데로 갈라 쓰기 위한 것이다.

- `gate` -- 발동 판정(점수 합산)에만 기여. 깊이엔 쓰지 않는다. "사용자가 모른다" 가 아니라 "개념이 중요·생소하다" 신호라 `user_known` 으로는 약하다
- `user_known` -- 깊이 보정에만 기여. 발동 점수에도 합산되지만, 본업은 writer 출발 수준 신호다
- `both` -- 발동·깊이 양쪽에 기여

발동 판정(게이트): 켜진 모든 행의 점수를 합산해 임계 이상이면 발동한다. 어느 한 행이 켜졌다고 점수와 무관하게 즉시 발동하지 않는다(단독 발동 룰 없음).

`user_known` 구성(깊이 보정): 켜진 행 중 `user_known`·`both` 태그 행만 추려, 그 "드러나는 user_known" 을 모아 writer 입력 `user_known` 을 구성한다. `gate` 행은 깊이에 넣지 않는다.

켜진 행이 전부 `gate` 면 `user_known` 이 빈다. A1 + A2 가 그 조합이다. 이때는 `그 개념 자체를 모름` 을 기본값으로 채워 writer 를 부르고, 되묻지 않는다. 되묻기는 명시 요청 트리거에만 둔다 (`user_known 보충 되묻기`).

### 행 판정 우선순위

행마다 판정 난이도가 다르다. 아래 순서로 본다.

- A3 · C2 · M2 를 먼저 본다. 셋은 사용자 말에 글자로 드러나므로(자기보고 "모른다", "결국 ~같은 거", "항상 / 절대") LLM 자기지식 없이 판정된다.
- M1 · M3 는 LLM 이 그 주제의 정답을 알 때만 켠다. 오해를 감지하려면 무엇이 맞는지 알아야 하기 때문이다.
- 나머지 행은 위 판정을 마친 뒤 보탠다.

<FORBIDDEN>
LLM 이 정답을 모르는 주제에서 M1 · M3 를 추측으로 켜지 않는다.
</FORBIDDEN>

### 임계값

| 합계 점수 | 동작 |
|----------|------|
| 3점 미만 | 무시 |
| 3점 이상 | 즉시 `knowledge-writer` 호출 (`임계 도달 이후 처리` 참조) |

임계는 3~4점 범위로 유지한다. 너무 높이면 감지가 안 되고, 너무 낮추면 과적된다.

<FORBIDDEN>
현재 작업과 직접 연관 없는 주제는 점수 계산 대상으로 삼지 않는다.
</FORBIDDEN>

## 사용자 명시 지시 트리거

사용자가 특정 주제에 대해 knowledge 저장을 직접 요청한 경우, 점수와 무관하게 즉시 위임한다.
이 트리거는 대화 중 "이거 남겨줘" 류의 지시다. 코드베이스를 훑어 문법을 뽑는 명령은 `knowledge-scan` 스킬 소관이다.

### 인정 발화 패턴

저장 의도가 드러난 발화는 모두 명시 지시로 인정한다.

- "이거 knowledge 로 남겨줘"
- "이 부분 wip 로 저장해줘"
- "이 정보 기억해둬" (knowledge 맥락)
- 기타 사용자가 명시적으로 저장 의도를 표한 표현

user_known 이 비면 수준 보충 질문을 한 뒤 knowledge-writer 를 호출한다.

<FORBIDDEN>
명시 지시 발화를 "점수 3점 미만이라 무시" 로 처리하지 않는다.
</FORBIDDEN>

### 처리 규칙

- 호출 형식은 자동 감지 트리거와 동일하다 (공용 프로토콜 2절)
- `triggered_by` 필드에 점수표 코드 대신 `user-request` 를 적는다
- `trigger_summary` 에 어떤 발화로 지시가 발생했는지 한 줄 기술한다
- 묶음 / 분리 판단은 메인 LLM 자율이다
- 동일 세션 내 같은 주제 중복 위임 방지 규칙을 동일 적용한다
- writer 호출 전에 `user_known` 이 얇으면 수준 보충 질문을 한다 (아래 `user_known 보충 되묻기`). 캡처 자체는 자동 확정이라 "남길까요"·묶음·분리는 여전히 묻지 않는다 -- 묻는 건 오직 사용자 수준이다

### user_known 보충 되묻기

명시 요청은 점수표를 우회해 발동하므로 켜진 행이 없고, 따라서 행이 주는 `user_known` 도 없다. `user_known` 이 비면 writer 가 깊이를 못 잡아 개요부터 심화까지 과하게 깐다. 그래서 writer 호출 전에 수준을 보충한다.

되묻기는 이 트리거에만 둔다. 자동 감지도 `user_known` 이 빌 수 있지만(A1 + A2), 그쪽은 사용자를 붙잡지 않고 기본값으로 채운다 (`역할 태그와 추출`).

- 되묻기는 `user_known` 이 얇을 때만 한다. 요청에 수준이 이미 묻어나면(사용자가 인접 지식·목적을 이미 말함) 생략한다 -- 귀찮음을 최소화한다.
- probe 2종을 쓴다.
  - 인접 지식 probe: "관련된 X 는 아시나요?" (예: UDP 면 TCP) -- 출발 수준을 잡는다.
  - 목적 probe: "왜·어디에 쓰려고 남기나요?" -- 목적이 깊이를 정한다.
- 받은 답을 `user_known` 과 `discussion_context` 에 실어 writer 를 호출한다.
- "모른다" 는 답도 "그 개념 자체를 모름" 신호로 `user_known` 에 실어 writer 가 기초부터 깔게 한다(A3 와 같은 취지). 사용자가 응답하지 않으면 `user_known` 을 빈 채로 두고 그대로 writer 를 호출한다 -- 캡처 확정이 우선이다.

<FORBIDDEN>
수준 보충 probe 를 두 번 이상 반복하지 않는다.
</FORBIDDEN>

두 트리거 모두 `user_known` 을 채운 채 writer 를 부른다 -- 자동 감지는 기본값으로, 명시 요청은 되묻기로 채운다.

## 점수 계산 주체와 휘발성

- 점수표 비교와 누적 계산은 메인 LLM 의 작업이다.
- 점수표 · 누적값은 메인 LLM 컨텍스트 안에만 존재하며 별도 파일 · 인덱스에 저장하지 않는다.
- 세션 종료 · 컴팩 시 자연히 초기화된다 (세션 단위 휘발).

<FORBIDDEN>
점수표 자체나 누적 점수를 별도 파일 · 인덱스에 저장하지 않는다.
</FORBIDDEN>

## 누적 규칙

- 점수는 세션 내에서만 유효하다. 세션이 바뀌면 모든 주제 점수 리셋.
- 다른 주제는 독립적으로 점수 계산한다.
- 사용자가 이미 알고 있다고 명시한 주제는 해당 세션의 점수 계산 · 위임 대상에서 제외한다 (세션이 바뀌면 다시 적용).
- 여러 주제가 동시에 임계를 넘는 경우 모두 위임 대상에 포함한다 (하나만 선택하지 않는다).
- 임계를 넘어 `knowledge-writer` 로 위임된 주제는 해당 세션에서 추가 점수 누적 및 중복 위임 대상에서 제외한다 (한 번 위임되면 그 세션 동안 고정).
- `기존 정리분 대조` 에서 중복으로 판정돼 건너뛴 주제도 위임된 것과 동일하게 해당 세션의 추가 점수 누적 · 위임 대상에서 제외한다. 그러지 않으면 같은 세션에서 임계를 넘을 때마다 대조를 반복한다.
- 위 두 규칙은 세션 안에서만 유효하다. 세션을 넘는 중복은 `기존 정리분 대조` 가 담당한다.
- wiki 에 이미 등재된 주제는 점수 계산 대상에서 제외한다 (요약 비교로 의미적 중복 판단). 본 규칙은 wiki 정의 후 실제 동작과 함께 적용된다. 그전까지 세션 밖 중복 방지는 `기존 정리분 대조` 가 대신한다.

## 기존 정리분 대조

`누적 규칙` 의 중복 방지는 세션 안에서만 듣는다. 이 스킬은 매 세션 자동 활성되고 점수는 세션마다 리셋되므로, 그것만으로는 어제 캡처한 주제가 오늘 다시 임계를 넘는다. writer 는 기존 파일을 덮어쓰지 않고 suffix 파일을 만들 뿐이라 중복이 그대로 쌓인다.

세션을 넘는 중복은 저장된 파일로 막는다. 대조 시점은 경로를 확보한 뒤 writer 를 호출하기 전이다. 점수 계산 시점에는 아직 저장 경로가 없어(`저장 경로 확보 시점`) 대조할 수 없다.

### 대조 방법

- wip 디렉토리와 확정지식 디렉토리를 Glob 해 파일명 목록을 얻는다. 확정지식 디렉토리는 wip 경로가 속한 저장소 루트의 `knowledge/` 다.
- 파일명 목록과 이번 `topic` 을 문자열 일치가 아니라 같은 주제인지로 판단한다. 이 스킬의 `topic` 은 메인이 그때그때 정해 같은 개념이 다른 슬러그로 나온다(`lock-contention` 과 `mutex-contention`). 문자열 대조만으로는 샌다.
- 파일명만으로 판단이 서지 않으면 후보 파일을 Read 해 확인한다.

### 판정 후 동작

중복으로 판정되면 어느 트리거로 들어왔는지에 따라 갈린다.

| 트리거 | 동작 |
|--------|------|
| 자동 감지 | writer 를 호출하지 않고 건너뛴다. 어느 파일과 겹쳐 건너뛰었는지 한 줄만 알린다 |
| 명시 요청 | 겹치는 파일을 제시하고 보강할지 새로 쓸지 묻는다 |

보강을 택하면 `triggered_by` 를 `user-request-reinforce` 로 보내고 기존 파일의 절대경로를 `discussion_context` 에 함께 적는다. 새로 쓰기를 택하면 `user-request` 그대로다. 어느 쪽이든 기존 파일을 덮어쓰지 않고 suffix 파일을 만든다 -- 누적된 파일의 병합은 승급 단계 소관이다.

writer 를 호출하기 전에 기존 wip · 확정지식 파일명과 이번 topic 을 대조한다.

<FORBIDDEN>
자동 감지로 발동한 캡처가 중복으로 판정되면 보강 여부를 사용자에게 묻지 않는다.
</FORBIDDEN>

## 임계 도달 이후 처리

임계 점수를 넘긴 주제는 메인 LLM 이 즉시 `knowledge-writer` 를 호출해 wip 파일 작성을 위임한다.
사용자 확인 없이 자동 진행되며, 같은 사안의 여러 측면을 한 항목으로 묶을지 별 항목으로 쪼갤지의 판단도 메인 LLM 의 자율에 맡긴다.
개념(무엇·왜)과 코드 사용법(어떻게)이 한데 섞인 주제는 concept wip 와 code wip 두 개로 나눠 캡처한다(kind 가 다르면 다른 wip -- promote `2. 형식 변환` 의 kind 결정 규칙 참조).

이 자동 진행은 wip 단계에 한정된다. wip -> 확정지식 승급 단계는 별도 사용자 확인 규약을 따른다.

명시 요청 트리거의 두 질문은 아래 금지에 해당하지 않는다 -- user_known 이 빌 때의 수준 보충 질문(묻는 대상이 사용자 수준이다)과, 기존 정리분과 겹칠 때의 보강 여부 질문(`기존 정리분 대조`)이다.

<FORBIDDEN>
wip 단계에서 위임 여부 · 묶음 · 분리 여부를 사용자에게 묻지 않는다.
</FORBIDDEN>

## writer 위임

호출 형태·입력 포맷·저장 책임은 공용 프로토콜 2절·3절을 그대로 따른다. 이 스킬이 채우는 입력값은 다음과 같다.

| 필드 | 이 스킬의 값 |
|------|-------------|
| `save_path` | `저장 경로 확보 시점` 에서 확보한 저장 경로 |
| `topic` | 주제 식별자 (kebab-case). 메인이 정한다 |
| `triggered_by` | 아래 `triggered_by 값` |
| `trigger_summary` | 어떤 발화·판정으로 발동했는지 한 줄 |
| `user_known` | 자동 감지는 켜진 `user_known`·`both` 행에서. 켜진 행이 전부 `gate` 면 `그 개념 자체를 모름`. 명시 요청은 보충 probe 답에서 |
| `discussion_context` | 캡처가 발생한 논의 맥락. 보강이면 기존 파일의 절대경로도 함께 (`기존 정리분 대조`) |
| `snippets` | 대화 발췌 |
| `kind` | `concept` 기본. 사용자가 코드/문법을 지명했으면 `code` |
| `language` | `kind: code` 일 때만 |

### triggered_by 값

이 스킬의 `triggered_by` 는 점수표 코드 또는 명시 요청 코드다. 복수 가능하다.

| 값 | 뜻 |
|----|-----|
| `A1` ~ `A4` | 공백 그룹에서 켜진 행 |
| `M1` ~ `M3` | 오해 그룹에서 켜진 행 |
| `C1` ~ `C3` | 앵커 그룹에서 켜진 행 |
| `user-request` | 사용자 명시 저장 요청 (점수표 우회) |
| `user-request-reinforce` | 명시 요청인데 기존 정리분과 겹쳐 사용자가 보강을 택함. 기존 노트를 읽고 빠진 부분 위주로 쓴다 |

writer 는 이 코드로 깊이와 정정 타깃을 잡는다. 특히 M 계열(오해)이 켜졌으면 기초부터 깔지 않고 그 오해를 정조준해 정정한다.

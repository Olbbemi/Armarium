# 지식 캡처

논의에 필요한 지식을 감지하고 문서로 누적하는 스킬.

활성된 동안 메인 LLM 이 매 발화에서 아래 점수표를 기준으로 자동 감지를 수행하고,
임계 도달 시 wip 파일 작성을 `knowledge-writer` 에이전트에 위임한다.
wip 를 확정지식으로 올리는 승급(지식화) 단계는 별도 독립 스킬 `knowledge-promote` 가 담당한다. 본 스킬은 캡처(wip 누적)까지만 다룬다.

---

## 활성 조건

`knowledge-capture` 는 사용자가 `/knowledge-capture` 슬래시 명령으로 명시적으로 호출했을 때만 활성된다.
활성 여부의 판단은 사용자에게만 있다.

<RICOCHET>
LLM 자가판단으로 스킬을 활성하거나 점수 계산을 시작하지 않는다.
</RICOCHET>

---

## 저장 경로 설정

활성 직후, wip 파일을 저장할 디렉토리 경로를 사용자에게 입력받는다.
경로를 코드에 고정하지 않으며, 매 활성마다 새로 입력받는다.

입력 경로는 Herbarium 저장소 하위여야 한다. 디렉토리명은 동명 저장소가 있을 수 있어 신뢰할 수 없으므로, 검증은 git origin remote 조회로 한다.

### 검증 절차

1. 입력 경로에서 origin remote 를 조회한다.
   `git -C <입력경로> remote get-url origin`
2. 결과가 아래 기대 remote URL 과 정확히 일치하면 채택한다.
3. 일치하지 않거나 조회에 실패하면(존재하지 않는 경로 포함) 사유를 한 줄로 알리고 경로를 다시 입력받는다. 일치할 때까지 반복한다.

#### 기대 remote URL

이 값이 저장 경로 검증의 단일 기준이다.

```
git@github.com:Olbbemi/Herbarium.git
```

채택한 저장 경로는 점수표와 마찬가지로 메인 LLM 컨텍스트에만 유지하며(세션 휘발), 별도 파일 · 인덱스에 저장하지 않는다.

<PENETRATE>
활성 직후 wip 저장 디렉토리 경로를 사용자에게 입력받는다.
</PENETRATE>

<PENETRATE>
입력 경로의 git origin remote 가 기대 remote URL 과 정확히 일치할 때만 저장 경로로 채택한다.
</PENETRATE>

<RICOCHET>
origin remote 가 기대 remote URL 과 일치하지 않는 경로를 저장 경로로 채택하지 않는다.
</RICOCHET>

<RICOCHET>
wip 저장 경로를 코드에 고정 리터럴로 박지 않는다.
</RICOCHET>

## 하위 스킬

| 스킬 | 파일 | 역할 |
|------|------|------|
| `knowledge-writer` 에이전트 | `agents/knowledge-writer.md` | 임계 도달 시 메인의 입력을 받아 wip 본문을 작성하고 메인에 반환 (저장은 메인이 수행) |

---

## 실행 순서

1. 활성 (슬래시 명령). 활성 직후 저장 경로를 설정한다 (`저장 경로 설정` 섹션)
2. 매 발화마다 두 트리거 동시 감시
   - 자동 감지: 점수표 임계(3점) 도달
   - 명시 지시: 사용자의 직접 저장 요청
3. 트리거 발생 시 호출 입력 구성 (명시 지시 경로에서 `user_known` 이 비면 수준 보충 되묻기 후 구성 -- `user_known 보충 되묻기` 참조)
4. `knowledge-writer` 서브에이전트 백그라운드 호출 (Task 도구)
5. writer 가 외부 조사 + wip 본문 작성 후, 본문 전체를 최종 메시지로 반환 (파일 저장 안 함). writer 는 백그라운드라 미허용 도메인 WebFetch 가 자동 거부되므로, 막힌 조사는 `조사 보류 목록` 으로 남겨 포그라운드 승급(`knowledge-promote`) 검증 단계로 넘긴다
6. 메인이 완료 통지를 받아 반환 본문을 wip 파일로 저장 (HTML 엔티티 원복) 후 흐름 종료

에이전트가 한 종류라 에이전트 간 병렬 처리는 해당 없음. 각 단계의 세부 규칙·강제 사항은 후속 섹션에 정의한다.

## 자동 감지 점수표

자동 감지 점수표는 **개념 지식**(패턴·아키텍처·라이브러리)에만 적용한다.
코드/문법 지식은 자동 감지하지 않는다. 모르는 문법은 눈앞에 코드가 있어야 물어볼 수 있어 자동 감지가 사실상 불가능하기 때문이다.
코드 지식은 사용자 명시 요청으로만 캡처한다(아래 "사용자 명시 지시 트리거").

<RICOCHET>
코드/문법 지식을 점수표로 자동 감지하지 않는다.
</RICOCHET>

<PENETRATE>
활성된 동안 메인 LLM 은 매 발화마다 점수표를 적용해 자동 감지를 수행한다.
</PENETRATE>

<RICOCHET>
활성된 동안 발화를 점수 계산 없이 그냥 흘려보내지 않는다.
</RICOCHET>

> 초기값(실사용 전 잠정). 사용하면서 기준·점수·행 구성을 조정할 것.

점수표는 그룹별로 나뉜다. 각 행은 점수 외에 **역할 태그**와 **드러나는 user_known** 을 갖는다. 역할 태그로 "발동 판정(게이트)" 과 "깊이 보정(user_known)" 을 한 표에서 갈라 뽑는다 (아래 `역할 태그와 추출` 참조).

#### 공백 (개념 부재 신호)

| # | 기준 | 점수 | 역할 | 드러나는 user_known | 예시 |
|---|---|---|---|---|---|
| A1 | 처음 등장하는 개념이고 wiki 캐시에 미존재 | +1 | gate | - | RUDP 가 갑자기 언급됨 |
| A2 | 해당 개념 없이 현재 논의 판단 자체가 불가 | +2 | gate | - | RUDP 설계인데 UDP 를 모르면 진행 불가 |
| A3 | 이름조차 생소한 개념을 "모른다 / 뭐지?" 로 자기보고 | +2 | both | 그 개념 자체를 모름 | "zmq 가 뭐지? 처음 들어봐" |
| A4 | 이름은 익숙한데(들어봤다·써봤다) 용도·역할을 말하지 못함 | +1 | user_known | 이름만 알고 용도 모름 | "RUDP 들어는 봤는데 뭐 하는진 모름" |

#### 오해 (잘못 아는 신호)

| # | 기준 | 점수 | 역할 | 드러나는 user_known | 예시 |
|---|---|---|---|---|---|
| M1 | 두 개념을 (환원 선언 없이) 용어로 구분 없이 섞어 씀 | +2 | both | 두 개념의 경계를 모름 | "패킷" 과 "세그먼트" 를 같은 의미로 |
| M2 | "항상 / 절대" 같은 절대화로 단정 | +2 | both | 예외·조건을 모름 | "락은 항상 느리다" |
| M3 | 옛 버전 정의를 현재 사실로 단정 | +2 | both | 버전에 따라 바뀐 걸 모름 | "view 는 항상 비소유" (DR 로 깨짐) |

오해는 종류만 행으로 두고, 반복은 가산으로 얹는다. M1/M2/M3 중 한 행에 해당하는 같은 오해가 2회 이상 반복되면 그 행 점수에 +1 한다. "잘못된 가정 반복" 을 독립 행으로 두면 종류 행과 포함관계가 되어 같은 오해를 이중계산하므로, 반복성은 독립 행이 아니라 수식어로만 쓴다.

#### 앵커 (잘못된 기준점 신호)

| # | 기준 | 점수 | 역할 | 드러나는 user_known | 예시 |
|---|---|---|---|---|---|
| C1 | (개념 동일시가 아니라) 화제가 인접 계층으로 반복 이탈 | +2 | both | 경계 인접 개념과 혼동 | UDP 논의 중 계속 IP 계층으로 빠짐 |
| C2 | "결국 ~같은 거" 식 명시적 환원·동일시 선언 | +2 | both | 친숙 개념으로 잘못 동일시 | "코루틴? 결국 스레드 같은 거잖아" |
| C3 | 하위 요소를 전체로 착각 | +1 | user_known | 부분-전체 관계 오인 | "views 가 곧 Ranges" |

M1·C1·C2 는 겹치기 쉬우니 행위로 가른다: 명시적 "결국 ~같은 거" 환원 선언이면 C2, 선언 없이 용어를 섞으면 M1, 동일시가 아니라 화제가 다른 계층으로 흐르면 C1. 한 발화는 셋 중 하나로만 친다.

A1 기준은 wiki 정의 후 실제 동작과 함께 적용된다. wiki 미정의 상태에서는 A1 자체를 점수 계산에서 보류한다.

#### 역할 태그와 추출

각 행의 역할 태그는 켜진 내역을 두 군데로 갈라 쓰기 위한 것이다.

- `gate` -- 발동 판정(점수 합산)에만 기여. 깊이엔 쓰지 않는다. ("사용자가 모른다" 가 아니라 "개념이 중요·생소하다" 신호라 user_known 으로는 약하다)
- `user_known` -- 깊이 보정에만 기여. 발동 점수에도 합산되지만, 본업은 writer 출발 수준 신호다.
- `both` -- 발동·깊이 양쪽에 기여.

발동 판정(게이트): 켜진 모든 행의 점수를 합산해 임계 이상이면 발동한다. 어느 한 행이 켜졌다고 점수와 무관하게 즉시 발동하지 않는다(단독 발동 룰 없음).

user_known 구성(깊이 보정): 켜진 행 중 `user_known`·`both` 태그 행만 추려, 그 "드러나는 user_known" 을 모아 writer 입력 `user_known` 을 구성한다. `gate` 행은 깊이에 넣지 않는다.

#### 적용 시 유의 (실사용 검증된 특성)

- backbone(감지·타당 모두 높음) = A3 / C2 / M2. 사용자 말에 글자로 드러나 LLM 자기지식 없이도 안정적으로 켜진다. 가장 자주·일관되게 발동한다.
- M1 / M3 는 오해 감지라 LLM 이 정답을 알아야 켜진다. 모르는 새 주제에서는 침묵하며, M3 는 극단이다(정의가 바뀐 걸 모르면 영영 안 켜짐). (M2 는 "항상·절대" 가 글자로 드러나 backbone 에 든다)
- 행이 많을수록 매 발화 적용의 일관성이 떨어지는 긴장이 있다. 안정 발동이 목표면 backbone 위주로 본다.

### 임계값

| 합계 점수 | 동작 |
|----------|------|
| 3점 미만 | 무시 |
| 3점 이상 | 즉시 `knowledge-writer` 에이전트 호출 (`임계 도달 이후 처리` 섹션 참조) |

임계는 3~4점 범위로 유지한다. 너무 높이면 감지가 안 되고, 너무 낮추면 과적된다.

<RICOCHET>
현재 작업과 직접 연관 없는 주제는 점수 계산 대상으로 삼지 않는다.
</RICOCHET>

## 사용자 명시 지시 트리거

사용자가 특정 주제에 대해 knowledge 저장을 직접 요청한 경우, 점수와 무관하게 즉시 위임한다.

### 인정 발화 패턴

저장 의도가 드러난 발화는 모두 명시 지시로 인정한다.

- "이거 knowledge 로 남겨줘"
- "이 부분 wip 로 저장해줘"
- "이 정보 기억해둬" (knowledge 맥락)
- 기타 사용자가 명시적으로 저장 의도를 표한 표현

<PENETRATE>
명시 지시가 감지되면 점수 누적 상태와 무관하게 캡처를 확정한다. 다만 user_known 이 비면 수준 보충 질문을 한 뒤 knowledge-writer 에이전트를 호출한다.
</PENETRATE>

<RICOCHET>
명시 지시 발화를 "점수 3점 미만이라 무시" 로 처리하지 않는다.
</RICOCHET>

### 처리 규칙

- 호출 형식은 자동 감지 경로와 동일 (`임계 도달 이후 처리` 섹션 재사용)
- `triggered_by` 필드에 점수표 코드 대신 `user-request` 를 적는다
- `trigger_summary` 에 어떤 발화로 지시가 발생했는지 한 줄 기술
- 묶음 / 분리 판단은 메인 LLM 자율
- 동일 세션 내 같은 주제 중복 위임 방지 규칙은 동일 적용
- writer 호출 *전에*, `user_known` 이 얇으면 수준 보충 질문을 한다 (아래 `user_known 보충 되묻기`). 캡처 자체는 자동 확정이라 "남길까요"·묶음·분리는 여전히 묻지 않는다 -- 묻는 건 오직 사용자 수준이다

### user_known 보충 되묻기

명시 요청은 점수표를 우회해 발동하므로, 자동 감지 경로와 달리 켜진 행이 주는 `user_known` 이 없다. `user_known` 이 비면 writer 가 깊이를 못 잡아 개요부터 심화까지 과하게 깐다. 그래서 writer 호출 전에 수준을 보충한다.

- 되묻기는 `user_known` 이 얇을 때만 한다. 요청에 수준이 이미 묻어나면(사용자가 인접 지식·목적을 이미 말함) 생략한다 -- 귀찮음을 최소화한다.
- probe 2종:
  - 인접 지식 probe: "관련된 X 는 아시나요?" (예: UDP 면 TCP) -- 출발 수준을 잡는다.
  - 목적 probe: "왜·어디에 쓰려고 남기나요?" -- 목적이 깊이를 정한다.
- 받은 답을 `user_known` 과 `discussion_context` 에 실어 writer 를 호출한다.
- probe 는 한 번만 한다(무한 되묻기 금지). "모른다" 는 답도 "그 개념 자체를 모름" 신호로 `user_known` 에 실어 writer 가 기초부터 깔게 한다(자동 경로의 A3 와 같은 취지). 사용자가 응답하지 않으면 `user_known` 을 빈 채로 두고 그대로 writer 를 호출한다 -- 캡처 확정이 우선이다.

명시 요청은 사용자의 의도적 행동이라 수준 질문 한둘은 정당하다(귀찮을 일이면 애초에 자동 감지에 맡겼을 것이다). 이로써 자동·명시 두 경로가 양쪽 다 `user_known` 을 채우는 대칭이 된다.

- 세션 종료 · 컴팩 시 자연히 초기화된다 (세션 단위 휘발).

</PENETRATE>

## 누적 규칙

- 점수는 세션 내에서만 유효하다. 세션이 바뀌면 모든 주제 점수 리셋.
- 다른 주제는 독립적으로 점수 계산한다.
- 사용자가 이미 알고 있다고 명시한 주제는 해당 세션의 점수 계산 · 위임 대상에서 제외한다 (세션이 바뀌면 다시 적용).
- 여러 주제가 동시에 임계를 넘는 경우 모두 위임 대상에 포함한다 (하나만 선택하지 않는다).
- 임계를 넘어 `knowledge-writer` 에이전트로 위임된 주제는 해당 세션에서 추가 점수 누적 및 중복 위임 대상에서 제외한다 (락).
- wiki 에 이미 등재된 주제는 점수 계산 대상에서 제외한다 (요약 비교로 의미적 중복 판단). 본 규칙은 wiki 정의 후 실제 동작과 함께 적용된다.

## 임계 도달 이후 처리 (wip 단계)

임계 점수를 넘긴 주제는 메인 LLM 이 즉시 `knowledge-writer` 에이전트를 호출해 wip 파일 작성을 위임한다.
사용자 확인 없이 자동 진행되며, 같은 사안의 여러 측면을 한 항목으로 묶을지 별 항목으로 쪼갤지의 판단도 메인 LLM 의 자율에 맡긴다.
개념(무엇·왜)과 코드 사용법(어떻게)이 한 주제에 섞인 straddle 주제는 concept wip 와 code wip 두 개로 나눠 캡처한다(kind 가 다르면 다른 wip -- promote `2. 형식 변환` 의 kind 결정 규칙 참조).
호출 명세는 아래 서브섹션 참조.

<PENETRATE>
임계 도달 시 메인 LLM 은 사용자 확인 없이 즉시 `knowledge-writer` 에이전트를 호출한다.
</PENETRATE>

이 자동 진행은 wip 단계에 한정된다. wip -> wiki 승급 단계는 별도 사용자 확인 규약을 따른다.

<RICOCHET>
wip 단계에서 위임 여부 · 묶음 · 분리 여부를 사용자에게 묻지 않는다. 단 명시 요청 경로에서 user_known 이 빌 때의 수준 보충 질문은 묻는 대상이 위임·묶음·분리가 아니라 사용자 수준이라 이 금지에 해당하지 않는다.
</RICOCHET>

### 호출 형태

| 항목 | 값 |
|------|----|
| 호출 도구 | Task |
| `subagent_type` | `knowledge-writer` |
| `run_in_background` | `true` (백그라운드) |
| writer 출력 | wip 파일 전체 본문을 최종 메시지로 반환 (Write 안 함) |
| 저장 | 메인 에이전트가 통지를 받아 활성 시 설정한 저장 경로 하위 `<저장경로>/<topic>.md` (또는 suffix) 로 직접 저장 |

<PENETRATE>
`knowledge-writer` 호출은 백그라운드(`run_in_background: true`)로 한다. 메인은 완료 통지 도착까지 사용자 논의를 계속한다.
</PENETRATE>

<PENETRATE>
작업(조사·작문)은 백그라운드 서브에이전트 writer 에 위임하고, wip 파일 저장은 메인 에이전트가 완료 통지 도착 시 직접 수행한다.
</PENETRATE>

<PENETRATE>
반환 본문의 `&`/`<`/`>` HTML 엔티티는 저장 전 원복한다.
</PENETRATE>

<RICOCHET>
백그라운드 writer 에게 Write/Edit 으로 wip 파일을 직접 저장하게 하지 않는다.
</RICOCHET>

### `knowledge-writer` 에이전트 호출 입력 포맷

Task 도구의 prompt 파라미터에 아래 라벨 + 콜론 구조화 텍스트로 전달한다. JSON 형식은 사용하지 않는다.

| 필드 | 의미 | 비고 |
|------|------|------|
| `save_path` | 활성 시 확정한 wip 저장 디렉토리 절대경로 | `저장 경로 설정` 에서 채택한 경로. writer 가 충돌 검사·파일명 결정 기준으로 사용 |
| `topic` | 주제 식별자 (kebab-case) | wip 파일명 기반 |
| `triggered_by` | 발동된 점수표 코드 (A1~A4 / M1·M2·M3 / C1~C3, 또는 `user-request`) | 복수 가능. writer 가 깊이·정정 타깃 산정에 사용 |
| `trigger_summary` | 한 줄 사유 | 1~2 문장 |
| `user_known` | 사용자가 안다고 명시한 인접 지식 | 에이전트의 출발 지식 수준 결정 기준 |
| `discussion_context` | 임계가 발생한 큰 논의 맥락 | 왜 이 주제가 지금 필요한가 (snippets 한 단계 위의 목적 맥락). 이 값들은 writer 의 작성 참고용 입력이며 wip "캡처 맥락" 섹션에 전사하지 않는다 (writer 골격의 `서술 톤` 참조) |
| `snippets` | 대화 발췌 | 화자 표기 권장 |
| `kind` | 지식 종류 | `concept`(기본) 또는 `code`. 노트가 답하는 질문으로 정함(무엇·왜=concept / 어떻게 쓰나=code). 코드 예제가 있다고 `code` 인 것은 아니다. `code` 면 writer 가 코드 템플릿으로 작성. 결정 규칙 상세는 promote `2. 형식 변환` 의 kind 결정 규칙 |
| `language` | 대상 언어 | `kind: code` 일 때만. `python` / `rust` / `cpp` |

#### 입력 예시 (zmq 라이브러리 — 한 항목 묶음)

```
save_path: /home/olbbemi/Project/Herbarium/wip
topic: zmq
triggered_by: A1, A2, A3
trigger_summary:
  ZMQ 라이브러리 자체에 대한 전제 지식 부재로 라이브러리 선택 논의 진행 불가.
  PUB/SUB 등 메시징 패턴 종류도 전혀 모름.
user_known:
  - TCP/UDP 차이는 알고 있음
  - 메시지 큐 개념은 들어본 정도
discussion_context:
  설계 논의 중 마이크로서비스 간 메시지 큐 라이브러리 후보 선정 중
snippets:
  - Claude: 메시지 큐로 ZMQ 를 검토해볼까요?
  - 사용자: zmq 가 뭐지? 처음 들어봐
  - Claude: PUB/SUB 패턴이 적합할 것 같습니다
  - 사용자: 패턴 종류가 뭐가 있는지 전혀 모르겠어
```

같은 상황을 두 항목으로 쪼갠 예시:

- 항목 1: `topic: zmq` (라이브러리 자체 개요)
- 항목 2: `topic: zmq-messaging-patterns` (PUB/SUB · REQ/REP 등 패턴 종류)

묶음 / 분리 결정은 메인 LLM 의 자율 판단이며 사용자 확인을 받지 않는다.

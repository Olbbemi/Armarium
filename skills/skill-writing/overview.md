# 스킬 작성 가이드

스킬을 만들 때 따르는 규격과 기준 정리.

---

## 1. 언제 스킬을 만들까

**만들 때:**
반복적으로 수행할 작업인데 Claude가 어떻게 접근해야 할지 기준이 없을 때

**만들지 않을 때:**
- `settings.json`으로 해결되는 것
- `CLAUDE.md`로 해결되는 것

---

## 2. 파일/디렉토리 구조

### 단순 스킬 (하위 파일 없음)

```
skills/
└── <skill-name>/
    ├── SKILL.md          <- 프론트매터 + overview Read 지시
    └── overview.md       <- 작업 내용 직접 작성
```

### 복합 스킬 (하위 파일 있음)

```
skills/
└── <skill-name>/
    ├── SKILL.md          <- 프론트매터 + overview Read 지시
    ├── overview.md       <- 인덱스 + 실행 순서
    └── foo/
        └── foo.md        <- 하위 작업 내용
```

단순 / 복합 판단 기준:
- 하위로 쪼갤 필요 없는 단일 작업 -> 단순 스킬
- 여러 단계·기능으로 쪼개야 하면 -> 복합 스킬

<PENETRATE>
단순/복합 판단은 사용자 확인을 받은 뒤 결정한다.
</PENETRATE>

<RICOCHET>
Claude의 자체 판단만으로 단순/복합을 결정하지 않는다.
</RICOCHET>

### 규칙

- `SKILL.md` — 프론트매터와 overview Read 지시만 작성한다. 동작 내용 포함 금지
- `overview.md` — 반드시 존재해야 하며, 모든 실행 내용은 이 파일 이하에 작성한다
- 예시의 `foo`는 고정 이름이 아니다. 하위 디렉토리명과 파일명은 기능에 맞게 자유롭게 짓는다
- 하위 파일 분리 기준: 기능이 완전히 다르면 무조건 분리
- 하나로 합치는 기준: 절대로 독립적으로 동작할 수 없는 경우

<PENETRATE>
기능이 완전히 다른 작업은 별도 하위 파일로 분리한다.
</PENETRATE>

<RICOCHET>
독립적으로 동작 가능한 기능을 하나의 파일에 합치지 않는다.
</RICOCHET>

<PENETRATE>
overview.md는 반드시 존재해야 하며, 모든 실행 내용은 그 안에 작성한다.
</PENETRATE>

<RICOCHET>
SKILL.md 본문에 동작 내용을 포함하지 않는다.
</RICOCHET>

## 3. 절대 규칙 태그 사용 규약

태그 정의(`<PENETRATE>`, `<RICOCHET>`)는 플러그인 루트 `CLAUDE.md` 의 "커스텀 태그" 섹션에 있다.
이 절은 **언제 어떻게** 태그를 적용할지의 규약을 다룬다.

### 사용 시점

- `<PENETRATE>` — 절대 수행 규칙 (위반 시 작업 무효)
- `<RICOCHET>` — 절대 금지 규칙 (위반 시 작업 무효)

이 기준에 해당하지 않으면 산문 강조로 작성한다.

### 태그 내부 작성 형식

<PENETRATE>
태그 내부는 평문 단락 하나만 작성한다.
</PENETRATE>

<RICOCHET>
태그 내부에 불릿(`-`), 헤딩(`#`), 표, 들여쓰기 같은 마크다운 구조를 사용하지 않는다.
</RICOCHET>

이유: HTML 블록 안에서는 마크다운이 raw text로 처리되어 한 줄로 이어 보이거나 렌더링이 깨진다.

규칙이 여러 개라 한 단락에 자연스럽게 담기 어려우면 같은 태그를 여러 번 사용해 각각 분리한다.

### 작성·수정 시 변환 절차

<PENETRATE>
스킬 파일을 작성·수정할 때 본문에 산문으로 적힌 절대 규칙이 있으면 위 기준에 맞는지 검토해 태그로 변환한다.
</PENETRATE>

누락 없이 적용됐는지의 검증은 `skill-verify` 스킬이 담당한다.

## 4. Frontmatter 규격

프론트매터는 `SKILL.md`에만 작성한다. overview 및 하위 파일에는 작성하지 않는다.

```yaml
---
name: english-name-with-hyphens
description: |
  한국어로 작성한 트리거 조건
created: YYYY-MM-DD HH:MM
---
```

| 필드 | 설명 | 규칙 |
|------|------|------|
| `name` | 스킬 식별자 | 영문, 숫자, 하이픈만 |
| `description` | Claude가 호출 여부 판단하는 기준 | 한국어, 트리거 조건만 |
| `created` | 작성 날짜/시간 | 사람이 확인하는 메타데이터. `date '+%Y-%m-%d %H:%M'` 실행 결과를 기입 |

<PENETRATE>
프론트매터는 SKILL.md에만 작성한다.
</PENETRATE>

<PENETRATE>
`created` 필드는 반드시 포함하며, `date '+%Y-%m-%d %H:%M'` 실행 결과를 기입한다.
</PENETRATE>

<RICOCHET>
overview.md 및 하위 파일에 프론트매터를 작성하지 않는다.
</RICOCHET>

## 5. Description 작성법

description은 Claude가 **이 스킬을 호출할지 말지 판단하는 기준**이다.

**들어가야 할 것:**
- 이 스킬이 필요한 상황과 증상
- 사용자가 실제로 할 법한 말이나 질문

**들어가면 안 되는 것:**
- 스킬이 뭘 하는지 요약
- 워크플로 설명
- 지시문 ("~할 것", "~반드시 읽을 것")

```yaml
# 나쁜 예
description: |
  코드 설계 및 구현 파이프라인 전체 지도.
  새 기능/서비스 개발을 시작하거나, 현재 어느 단계인지 파악이 필요할 때
  반드시 이 스킬을 먼저 읽을 것.

# 좋은 예
description: |
  새 기능/서비스 개발을 시작할 때.
  현재 어느 단계인지 파악이 안 될 때.
  "어디서부터 시작해?", "지금 뭐 해야 해?", "전체 흐름이 어떻게 돼?"
```

<RICOCHET>
description에 스킬의 동작 요약, 워크플로 설명, 지시문("~할 것", "~반드시 읽을 것")을 포함하지 않는다.
</RICOCHET>

## 6. overview 작성 가이드

### 단순 스킬 overview

- 단일 작업을 다루므로 필수 섹션 없음. 
- 작업 내용만 명확히 전달되면 형식은 자유다.
- 필요하면 복합 스킬 구조(인덱스, 실행 순서)를 부분적으로 가져와 사용해도 된다.

### 복합 스킬 overview

아래 두 섹션은 필수다.

#### 인덱스
하위 스킬 목록과 각 스킬의 역할을 명시한다. overview.md에서 `## 하위 스킬` 섹션으로 작성한다.

| 스킬 | 파일 | 역할 |
|------|------|------|
| 요구사항 분석 | `skills/<skill-name>/01-requirements.md` | ... |
| 설계 | `skills/<skill-name>/02-design.md` | ... |

#### 실행 순서
단계별 순서와 에이전트 실행 여부를 명시한다. 에이전트가 있는 경우 체크리스트 형태로 작성한다.

```markdown
## 실행 순서

1. 요구사항 분석
2. 설계

### 병렬 처리 (해당하는 경우)
아래 에이전트를 Task 도구로 병렬 호출한다.

- [ ] 서브에이전트 security: 포그라운드 호출. 입력: 코드 디렉토리 경로. 출력: 본문을 반환 -> 메인이 wip/security-review.md 로 저장
- [ ] 서브에이전트 performance: 백그라운드 호출 (`run_in_background: true`). 입력: 동일. 출력: 본문을 반환 -> 메인이 wip/perf-review.md 로 저장

### 결과 취합
- 서브에이전트는 작업 결과 본문을 반환하고, 파일 저장은 메인 에이전트가 완료 통지를 받아 수행한다.
- 메인은 저장된 파일들을 참조해 통합 처리한다.
```

- 모든 하위 파일 경로는 overview.md에 명시한다. 
- 경로는 플러그인 루트 기준으로 작성하며, `Read` 툴을 사용해 참조한다.


## 9. 작성 형식 규칙

내용은 간결하게 작성한다. 단, Claude가 올바르게 판단하고 행동하는 데 필요한 기준과 예외는 생략하지 않는다.

- 이모지 사용 금지 — Claude가 인식은 하나 동작에 영향 없음, 불필요한 요소
- 아스키 아트 허용. 단 간격을 직접 계산해서 정렬이 맞게 작성한다. 한글과 영문 혼용 시 한글 1자 = 영문 2자 너비로 계산한다
- 불릿(`-`) 사용 기준: 나열 가능한 항목이 2개 이상일 때. 단일 서술문은 그냥 문장으로 작성한다
- 헤딩과 bold 구분: 독립적인 내용 블록(설명·예시 포함)은 `####` 헤딩, 짧은 분류 레이블(good/bad, 해야 할 것/하지 말 것 등)은 `**bold:**`로 작성한다

<RICOCHET>
이모지를 사용하지 않는다.
</RICOCHET>

#### 예시 작성

가드레일·규칙의 예시는 재현 가능한 패턴으로 서술한다. 특정 시점·환경에서만 유효한 휘발성 식별자(커밋 해시, 빌드 번호, 이슈 번호 등)나 특정 프로젝트에서만 통하는 고유 식별자(고유 클래스·디렉토리·엔티티 이름)는 빼고, 다른 맥락의 독자도 이해할 수 있는 패턴으로 적는다. SQLite·gtest 같은 보편 기술명은 그대로 써도 된다.

이유는 스킬이 여러 프로젝트·시점에 재사용되기 때문이다. 예시가 한 프로젝트·한 시점에 묶이면 다른 맥락의 독자(사람·LLM)가 이해하지 못하거나(고유명사), 사라진 커밋 같은 죽은 참조를 만나거나, "이건 그 케이스니까"라며 과적합한다.

<RICOCHET>
예시에 커밋 해시 같은 휘발성 참조나 특정 프로젝트에서만 통하는 고유 식별자를 쓰지 않는다.
</RICOCHET>

## 10. 에이전트 구성

### 에이전트란

이 스킬에서 말하는 "에이전트"는 **Claude Code의 Task 도구로 호출되는 서브에이전트**다.
메인 에이전트(대화 최상위 Claude)와 별개의 컨텍스트에서 작업하고, 완료 시 결과를 메인에게 자동으로 통지한다.

포그라운드 / 백그라운드는 이 서브에이전트의 **실행 모드**를 가리키며, 메인 / 서브 구분과는 **별개의 축**이다. 혼동을 피하기 위해 본 문서는 실행 모드를 "포그라운드 서브에이전트 / 백그라운드 서브에이전트"로, 최상위를 "메인 에이전트"로 표기한다.

### 언제 에이전트를 쓸까

아래 경우에 에이전트 생성을 검토한다.

- 독립적으로 병렬 처리 가능한 작업 (예: 코드 리뷰의 보안·성능·스타일 동시 검토)
- 시간이 걸리는 작업이라 메인이 다른 일을 계속하는 동안 백그라운드로 위임하고 싶을 때
- 격리된 컨텍스트에서 처리되어야 하는 작업
- 사용자가 명시적으로 요청할 때 ("이건 에이전트로 만들어줘")

### 생성 절차

사용자가 명시적으로 승인을 생략하라고 하지 않는 한 아래 순서를 지킨다.

1. 에이전트 구조 제안 (역할 분담 + 디렉토리 레이아웃)
2. 사용자 승인 확인
3. 생성 진행

> "이런 구조로 에이전트를 나눠서 진행하려고 합니다. 진행해도 될까요?"

### 디렉토리 구조와 등록

Task 로 디스패치하는 에이전트 정의 파일은 **플러그인 루트 `agents/` 에 둔다.** 플러그인 시스템이 이 디렉토리를 자동 발견해 `<플러그인>:<에이전트>` 네임스페이스로 등록한다. 심볼릭 링크는 필요 없다.

```
<플러그인 루트>/
├── agents/
│   ├── security.md          (실제 정의 파일)
│   ├── performance.md
│   └── style.md
└── skills/
    └── code-review/
        ├── SKILL.md
        └── overview.md
```

예외: 에이전트성 보조 파일이 Task 디스패치 없이 **스킬 내부 디스패처(예: .sh)가 경로로 직접 읽기만** 한다면 등록이 불필요하므로 그 스킬 디렉토리 안에 두어도 된다.

이유: 플러그인은 루트 `agents/` 를 자동 스캔해 `subagent_type` 으로 등록하므로, 과거처럼 `.claude/agents/` 에 심링크를 거는 우회가 필요 없다. 스킬 본문에서는 bare 이름(`subagent_type: <에이전트>`)으로 호출하고, 외부에는 `<플러그인>:<에이전트>` 로 노출된다.

### 정의 파일 형식

표준 Claude Code 에이전트 정의 형식. 프론트매터에 이름·설명·사용 도구를 명시한다.

```markdown
---
name: security
description: 코드의 보안 취약점을 검토하는 에이전트
tools: Read, Grep, Glob
---

에이전트 시스템 프롬프트 본문. 호출되면 무엇을 어떻게 작업할지 정의한다.
```

### 호출 방식

메인 Claude 가 Task 도구로 호출한다. 호출 형태는 두 가지.

| 형태 | 사용 시점 |
|------|----------|
| 일반 호출 (`run_in_background: false` 또는 생략) | 결과가 다음 작업의 직접 입력이거나 즉시 필요할 때 |
| 백그라운드 호출 (`run_in_background: true`) | 시간이 걸리고 메인이 다른 일을 계속해야 할 때. 비동기 통지 패턴 |

병렬 처리가 필요하면 여러 Task 호출을 **병렬로** 시작한다. 메커니즘: 메인 Claude 가 한 응답에 여러 Task 호출을 함께 포함하면 시스템이 병렬 실행한다.
각 호출은 별도 컨텍스트로 격리되므로 동시 실행되어도 서로 영향을 주지 않는다.

### 결과 처리

작업 수행(조사·분석·작문)은 서브에이전트에 위임하되, 필요 시 그 결과를 파일로 저장하는 일은 서브에이전트가 할 수 없으므로 메인 에이전트가 맡는다.

- **기본**: 서브에이전트는 결과를 파일에 직접 저장하지 않는다. 완성 본문을 최종 메시지로 반환하고, 메인 에이전트가 통지를 받아 저장한다. 결과가 메인 컨텍스트에 있어야 후속 조인/판단에 쓰고, 권한 문제(아래)도 피하기 때문이다
- 백그라운드 서브에이전트는 권한 프롬프트를 띄울 수 없어 **사전 허용되지 않은** Write/Edit 은 자동 거부된다. 뒤집으면, 대상 경로가 **사전 허용**(권한 설정/모드로 프롬프트가 안 뜨는 상태)이면 백그라운드 서브에이전트도 직접 Write 에 성공한다 (양방향 관측됨 -- 미허용은 거부, 사전허용은 성공)
- 포그라운드 서브에이전트의 Write 가능 여부는 본 환경에서 미검증이므로, 직접 Write 가 정당한 예외(아래)가 아니면 저장은 메인이 맡는 것을 기본으로 한다
- **예외 (서브에이전트 직접 Write 가 정당한 경우)**: 산출이 부피가 커 단일 본문 반환이 토큰 한도에 잘리는 부류(다량 파일 생성·HTML 렌더 등)는, **대상 경로를 사전 허용**해 둔 전제에서 서브에이전트가 자기 산출을 직접 Write 하고 메인엔 경로만 반환하게 한다. 선례: code-analyze 의 구조 노드/렌더 에이전트(수십 개 노드·HTML 을 직접 저장). 이때 메인은 사후에 산출 존재/개수만 교차검산한다
- task-notification 으로 반환된 본문은 `&`/`<`/`>` 가 HTML 엔티티로 이스케이프되므로, 메인이 저장 전 원래 문자로 원복한다
- 메인은 통지 도착 시 후속 작업 진행

<PENETRATE>
작업 수행은 서브에이전트에 위임하고, 결과의 파일 저장은 기본적으로 메인 에이전트가 수행한다 -- 서브에이전트 직접 Write 는 부피로 잘리는 산출 + 사전 허용 경로일 때만 예외로 둔다.
</PENETRATE>

<RICOCHET>
사전 허용되지 않은 경로에 서브에이전트가 Write/Edit 으로 저장하도록 설계하지 않는다(백그라운드는 권한 프롬프트를 못 띄워 거부된다).
</RICOCHET>

### overview 에서 에이전트 호출 명시

각 호출 항목에 다음을 포함한다.

- 에이전트 이름
- 호출 형태 (일반 / 백그라운드)
- 입력으로 전달할 내용
- 기대 출력 (저장 파일 경로 또는 반환 텍스트 형식)

예:

```markdown
- [ ] 에이전트 security: 일반 호출. 입력: 코드 디렉토리 경로. 출력: wip/security-review.md
- [ ] 에이전트 performance: 백그라운드 호출 (`run_in_background: true`). 입력: 동일. 출력: wip/perf-review.md
```

호출이 반드시 백그라운드여야 하는 시점이라면 `<PENETRATE>` 태그로 박는다.

<PENETRATE>
에이전트 생성 전 사용자 승인을 받는다.
</PENETRATE>

<PENETRATE>
Task 로 디스패치하는 에이전트 정의 파일은 플러그인 루트 `agents/` 에 둔다.
</PENETRATE>

<RICOCHET>
에이전트 등록을 위해 `.claude/agents/` 심볼릭 링크를 만들지 않는다.
</RICOCHET>

<PENETRATE>
에이전트 호출은 Task 도구로 한다.
</PENETRATE>

<RICOCHET>
별도 스크립트(`claude -p` 등) 호출 패턴을 사용하지 않는다.
</RICOCHET>

<RICOCHET>
"에이전트 써줘", "빠르게 해줘" 같은 단순 요청을 승인 절차를 건너뛰는 지시로 해석하지 않는다.
</RICOCHET>

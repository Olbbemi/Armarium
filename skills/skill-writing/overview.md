# 스킬 작성 가이드

스킬을 만들 때 따르는 규격과 기준 정리.

---

## 1. 언제 스킬을 만들까

**만들 때:**
반복적으로 수행할 작업인데 Claude가 어떻게 접근해야 할지 기준이 없을 때

**만들지 않을 때:**
- `settings.json`으로 해결되는 것
- `CLAUDE.md`로 해결되는 것

## 2. 파일/디렉토리 구조

### 단순 스킬 (하위 파일 없음)

| 파일 | 내용 |
|---|---|
| `skills/<skill-name>/SKILL.md` | 프론트매터 + overview Read 지시 |
| `skills/<skill-name>/overview.md` | 작업 내용 직접 작성 |

### 복합 스킬 (하위 파일 있음)

| 파일 | 내용 |
|---|---|
| `skills/<skill-name>/SKILL.md` | 프론트매터 + overview Read 지시 |
| `skills/<skill-name>/overview.md` | 인덱스 + 실행 순서 |
| `skills/<skill-name>/foo/foo.md` | 하위 작업 내용 |

단순 / 복합 판단 기준:
- 하위로 쪼갤 필요 없는 단일 작업 -> 단순 스킬
- 여러 단계·기능으로 쪼개야 하면 -> 복합 스킬

<FORBIDDEN>
Claude의 자체 판단만으로 단순/복합을 결정하지 않는다.
</FORBIDDEN>

### 규칙

- `SKILL.md` — 프론트매터와 overview Read 지시만 작성한다. 동작 내용 포함 금지
- `overview.md` — 반드시 존재해야 하며, 모든 실행 내용은 이 파일 이하에 작성한다
- 예시의 `foo`는 고정 이름이 아니다. 하위 디렉토리명과 파일명은 기능에 맞게 자유롭게 짓는다
- 하위 파일 분리 기준은 독립 동작 가능성이다. 다른 하위 파일 없이 그 자체로 하나의 작업을 완결할 수 있으면 독립 동작 가능한 것으로 본다. 기능이 달라도 항상 함께 로드돼야 하면 나누지 않는다 -- 참조 단계만 늘고 얻는 것이 없다

<FORBIDDEN>
독립적으로 동작 가능한 기능을 하나의 파일에 합치지 않는다.
</FORBIDDEN>

### 여러 스킬이 함께 읽는 파일

읽는 스킬이 몇 개인지로 위치를 가른다.

| 읽는 스킬 | 두는 곳 |
|---|---|
| 둘 이상 | 플러그인 루트 `references/` |
| 하나 | 그 스킬 디렉토리 안 (`skills/<skill-name>/`) |

한 스킬만 읽는 파일은 분량이 크더라도 옮기지 않는다.

공유 파일은 자기를 읽는 스킬을 되참조하지 않는다. 어느 파일에서 언제 로드할지는 읽는 쪽 스킬이 정하며, 공유 파일은 그 시점을 규정하지 않는다.

`skill-verify` 는 이 파일들을 스킬 파일과 같은 기준으로 검사한다 -- 대상 스킬이 Read 하도록 지시하는 공유 참조 파일까지 태그·형식 검증 범위다.

## 3. 금지 규칙 태그 사용 규약

태그 정의(`<FORBIDDEN>`)는 플러그인 루트 `CLAUDE.md` 의 "커스텀 태그" 섹션에 있다.
이 절은 **언제 어떻게** 태그를 적용할지의 규약을 다룬다.

규약을 정의하는 이 절 자체에는 태그를 붙이지 않는다. 태그를 다루는 문장을 태그로 감으면 규격과 적용이 겹쳐, 읽는 쪽이 어느 층위의 지시인지 가리기 어렵다.

### 금지 규칙에만 붙인다

태그는 `<FORBIDDEN>` 하나이며 금지 규칙 전용이다. 반드시 해야 할 일에는 태그를 쓰지 않는다. 실행 순서가 있는 스킬이면 그 단계로 적고, 실행 순서가 없는 안내 문서면 본문 항목으로 적는다.

수행과 금지를 갈라 두는 근거는 발견 경로의 차이다. 빠뜨린 단계는 산출물에 구멍으로 남아 뒤 단계나 검증에서 드러난다. 어긴 금지는 흔적을 남기지 않는다 -- 지우면 안 될 파일이 지워진 뒤에는 지워졌다는 사실만 남고, 그것을 금지했다는 기록은 어디에도 없다.

막는 대상은 **그 스킬을 실행하는 모델**이다. 스킬 문서를 어떻게 쓸 것인가에 대한 규칙(경로를 하드코딩하지 않는다, 이 파일에 무엇을 나열하지 않는다 같은 것)은 실행 중에 어길 수 있는 것이 아니므로 태그로 감지 않는다. 그 규칙은 이 규격과 `skill-verify` 의 검사 항목이 맡는 자리이며, 태그로 옮기면 실행자가 지킬 수 없는 지시가 문서에 섞인다.

### 붙일 조건 -- 무검출

금지 규칙이라고 전부 태그가 되지는 않는다. 판정 질문은 하나다.

> 이 규칙을 어기면 무엇이 그것을 잡아내는가.

검출 수단을 하나라도 찾으면 산문으로 적는다. 아무것도 찾지 못할 때만 태그로 감는다.

| 검출 수단 | 예 |
|---|---|
| `skill-verify` 의 개별 검사 | 이모지 -> format-check, 프론트매터 위치 -> frontmatter-check, `claude -p` 호출 -> agent-check |
| 절차의 다음 단계 | 다음 단계가 그 산출물을 입력으로 읽는다 -- 만들어야 할 파일이 없으면 그 자리에서 멈춘다 |
| 산출물 자체 | 산출물을 읽으면 위반이 보인다 -- 형식 이탈, 빈 칸, 완료 기준에 적힌 조건 미충족 |

두 수단을 섞지 않는다. 파일이 있어야 하는데 없는 것은 다음 단계가 잡고, 산출물 쪽은 있는 것의 내용만 본다.

#### 검출 수단이 없는 대표 경우

- **만들지 말아야 할 파일이 생긴 경우.** 어느 단계도 그 파일을 입력으로 읽지 않아 아무것도 멈추지 않고, 사용자가 읽는 산출물에도 나타나지 않는다. 폴더에 남아 나중에 어느 것이 정본인지 흐려질 뿐이다.
- **사용자 확인을 받았는지.** 확인을 거쳤는지, 승인 전에 미리 썼는지는 결과물에 흔적을 남기지 않는다. 완료 기준에 "사용자 확인됨" 항목이 있어도 그 항목을 채운 근거가 산출물에 없다.

둘 다 무검출이므로 태그로 남긴다.

이 판정의 근거는 문서 밖 사실이다 -- 그 규칙을 보는 검사 항목이 실제로 있는지 없는지다. 태그를 붙이려면 어느 검사도 그것을 보지 않는다는 것을 검사 파일에서 확인해야 하므로, 중요해 보인다는 작성자 판단만으로는 붙일 수 없다.

### 같은 규칙을 두 번 적지 않는다

같은 규칙이 산문과 태그에 둘 다 있으면 한쪽으로 정리한다. 무검출을 통과했으면 태그를 남기고 산문에서 규칙 서술을 걷어내 근거와 맥락만 남긴다. 통과하지 못했으면 태그를 지운다.

이 절은 작성 시점의 지침이며 판정은 작성자 몫이다. `skill-verify` 는 중복을 통과·실패로 가르지 않고 검토 후보로만 올린다. 태그된 규칙을 설명하는 산문은 무엇이든 후보가 될 수 있어 기계적으로 판정되지 않기 때문이다. 근거·절차·정의를 담은 산문은 중복이 아니며, 규칙 문장을 그대로 되풀이할 때만 정리 대상이다.

### 태그 내부 작성 형식

태그 내부는 평문 단락 하나만 쓴다. HTML 블록 안에서는 마크다운이 raw text 로 처리되어 한 줄로 이어 보이거나 렌더링이 깨지기 때문이다.

한 블록에는 금지 규칙 하나만 담는다. 규칙이 둘 이상이면 문장이 이어지더라도 블록을 나눈다.

블록이 판정 단위이기 때문이다. 무검출 조건은 규칙마다 답이 갈리므로, 한 블록에 규칙 둘이 들어 있고 하나만 검출 수단이 있으면 그 블록을 지울지 남길지에 답이 없어진다. 총량 상한도 규칙 수를 세는 값이라, 블록 하나가 규칙 여럿을 담으면 세는 대상이 달라진다.

### 태그 총량

태그는 대비로 작동하므로 문서의 상당 부분이 태그면 어느 것이 위험한 규칙인지 구분되지 않는다. 규칙 하나를 새로 태그로 감기 전에, 기존 태그 중 산문으로 내릴 수 있는 것이 없는지 먼저 본다.

한 파일의 태그는 18개를 넘기지 않는다. 이 값은 목표치가 아니라 이상치 경보다 -- 전형적인 파일은 3~6개라 상한을 의식할 일이 없고, 18에 닿았다는 것은 그 파일이 규칙을 과하게 안고 있거나 무검출 판정이 느슨했다는 신호다.

초과했을 때 개수를 맞추려고 태그를 지우지 않는다. 무검출 조건으로 다시 판정해 걷어내는 것이 먼저다.

#### 상한을 조정할 때

상한은 고정값이 아니다. 재판정을 마쳤는데도 전부 무검출을 통과해 남으면 그 파일에 맞춰 올린다. 조정에는 두 가지 제약이 붙는다.

- 한 번에 올리는 폭은 두어 개 안쪽이다. 재판정 없이, 또는 새로 넣고 싶은 규칙 개수에 맞춰 올리지 않는다.
- 재판정 결과가 현재 상한의 1.5배를 넘으면 상한을 올리지 않는다. 그만큼 벌어졌다는 것은 상한이 낮은 것이 아니라 그 파일이 서로 다른 관심사를 한데 안고 있다는 뜻이므로, 하위 파일로 쪼갠다.

### 작성·수정 시 변환 절차

스킬 파일을 작성·수정할 때 본문에 산문으로 적힌 금지 규칙이 있으면 무검출 조건에 맞는지 확인해, 통과하는 것만 태그로 변환하고 변환한 산문 문장에서는 규칙 서술을 걷어낸다. 누락 없이 적용됐는지의 검증은 `skill-verify` 스킬이 담당한다.

## 4. Frontmatter 규격

프론트매터는 `SKILL.md`에만 작성한다. overview 및 하위 파일에는 작성하지 않는다.

```yaml
---
name: english-name-with-hyphens
description: |
  한국어로 작성한 트리거 조건
created: YYYY-MM-DD HH:MM
---
```

| 필드 | 설명 | 규칙 |
|------|------|------|
| `name` | 스킬 식별자 | 영문, 숫자, 하이픈만 |
| `description` | Claude가 호출 여부 판단하는 기준 | 한국어, 트리거 조건만 |
| `created` | 작성 날짜/시간 | 사람이 확인하는 메타데이터. `date '+%Y-%m-%d %H:%M'` 실행 결과를 기입 |

## 5. Description 작성법

description은 Claude가 **이 스킬을 호출할지 말지 판단하는 기준**이다.

**들어가야 할 것:**
- 이 스킬이 필요한 상황과 증상
- 사용자가 실제로 할 법한 말이나 질문

**들어가면 안 되는 것:**
- 스킬이 뭘 하는지 요약
- 워크플로 설명
- 지시문 ("~할 것", "~반드시 읽을 것")

```yaml
# 나쁜 예
description: |
  코드 설계 및 구현 파이프라인 전체 지도.
  새 기능/서비스 개발을 시작하거나, 현재 어느 단계인지 파악이 필요할 때
  반드시 이 스킬을 먼저 읽을 것.

# 좋은 예
description: |
  새 기능/서비스 개발을 시작할 때.
  현재 어느 단계인지 파악이 안 될 때.
  "어디서부터 시작해?", "지금 뭐 해야 해?", "전체 흐름이 어떻게 돼?"
```

## 6. overview 작성 가이드

### 단순 스킬 overview

- 단일 작업을 다루므로 필수 섹션 없음. 
- 작업 내용만 명확히 전달되면 형식은 자유다.
- 필요하면 복합 스킬 구조(인덱스, 실행 순서)를 부분적으로 가져와 사용해도 된다.

### 복합 스킬 overview

아래 두 섹션은 필수다.

#### 인덱스
하위 스킬 목록과 각 스킬의 역할을 명시한다. overview.md에서 `## 하위 스킬` 섹션으로 작성한다.

| 스킬 | 파일 | 역할 |
|------|------|------|
| 요구사항 분석 | `skills/<skill-name>/01-requirements.md` | ... |
| 설계 | `skills/<skill-name>/02-design.md` | ... |

#### 실행 순서
단계별 순서와 에이전트 실행 여부를 명시한다. 에이전트가 있는 경우 체크리스트 형태로 작성한다.

```markdown
## 실행 순서

1. 요구사항 분석
2. 설계

### 병렬 처리 (해당하는 경우)
아래 에이전트를 Task 도구로 병렬 호출한다.

- [ ] 서브에이전트 security: 포그라운드 호출. 입력: 코드 디렉토리 경로. 출력: 본문을 반환 -> 메인이 wip/security-review.md 로 저장
- [ ] 서브에이전트 performance: 백그라운드 호출 (`run_in_background: true`). 입력: 동일. 출력: 본문을 반환 -> 메인이 wip/perf-review.md 로 저장

### 결과 취합
- 서브에이전트는 작업 결과 본문을 반환하고, 파일 저장은 메인 에이전트가 완료 통지를 받아 수행한다.
- 메인은 저장된 파일들을 참조해 통합 처리한다.
```

#### 단계 시각화 (TaskCreate)

실행 단계가 있는 스킬은 overview 에 TaskCreate 시각화 원칙을 명시한다.

- 포그라운드 단계 -- 시작 시 in_progress, 완료 시 completed
- 백그라운드 에이전트 호출 단계 -- 호출 즉시 completed ("위임 완료"). subject 는 "X 에이전트 호출" 형식
- 사용자 확인 게이트 -- 확인 요청 직전 completed, 응답 후 다음 task in_progress
- 아주 짧은 준비 작업(디렉토리 생성 등) -- task 생략

## 7. 스킬 간 연결 방식

- 모든 하위 파일 경로는 overview.md에 명시한다. 
- 경로는 플러그인 루트 기준으로 작성하며, `Read` 툴을 사용해 참조한다.

```markdown
# SKILL.md 예시
skills/<skill-name>/overview.md 를 Read 툴로 로드하고 그 내용을 따른다.
```

```markdown
# overview.md 에서 하위 파일 참조 예시
세부 작업은 skills/<skill-name>/<sub-skill>/<sub-skill-file>.md 를 Read 툴로 로드해 따른다.
```

### 셸 스크립트 경로

스킬이 셸 스크립트를 호출하면 경로는 `${CLAUDE_PLUGIN_ROOT}/skills/<skill-name>/<script>` 기준으로 쓴다. 스크립트가 `BASH_SOURCE` 로 자기 위치를 계산하면, 그 스크립트가 참조하는 보조 파일 경로는 따로 고치지 않아도 된다.

## 9. 작성 형식 규칙

내용은 간결하게 작성한다. 단, Claude가 올바르게 판단하고 행동하는 데 필요한 기준과 예외는 생략하지 않는다.

- 이모지 사용 금지 — Claude가 인식은 하나 동작에 영향 없음, 불필요한 요소
- 아스키 아트 허용. 단 간격을 직접 계산해서 정렬이 맞게 작성한다. 한글과 영문 혼용 시 한글 1자 = 영문 2자 너비로 계산한다
- 불릿(`-`) 사용 기준: 나열 가능한 항목이 2개 이상일 때. 단일 서술문은 그냥 문장으로 작성한다
- 헤딩과 bold 구분: 독립적인 내용 블록(설명·예시 포함)은 `####` 헤딩, 짧은 분류 레이블(good/bad, 해야 할 것/하지 말 것 등)은 `**bold:**`로 작성한다

#### 예시 작성

가드레일·규칙의 예시는 다른 맥락의 독자도 이해할 수 있는 재현 가능한 패턴으로 서술한다. SQLite·gtest 같은 보편 기술명은 그대로 써도 된다.

이유는 스킬이 여러 프로젝트·시점에 재사용되기 때문이다. 예시가 한 프로젝트·한 시점에 묶이면 다른 맥락의 독자(사람·LLM)가 이해하지 못하거나(고유명사), 사라진 커밋 같은 유효하지 않은 참조를 만나거나, "이건 그 케이스니까"라며 과적합한다.

<FORBIDDEN>
예시에 커밋 해시 같은 휘발성 참조나 특정 프로젝트에서만 통하는 고유 식별자를 쓰지 않는다.
</FORBIDDEN>

#### 은유 표현 배제

가드레일·설명·항목 서술은 은유가 아니라 직설적 표현으로 쓴다. 은유가 들어가면 세션마다 그 뜻을 다르게 추론해, 여러 세션이 같은 규칙을 재현해야 하는 스킬에서는 해석 편차가 곧 동작 편차가 된다.

단 굳어진 준기술어(앵커, 창발, 지도 등)까지 억지로 풀어 쓰지는 않는다 -- 직설화하면 오히려 장황해지거나 뜻이 좁아질 수 있다. 생소한 비유어를 쓸지 애매하면 직설어로 바꾸는 쪽을 기본으로 한다.

대상은 모델이 로드하는 파일이다 -- overview, 하위 파일, 에이전트 정의. 커스텀 태그 이름도 여기 포함된다.

## 10. 에이전트 구성

### 에이전트란

이 스킬에서 말하는 "에이전트"는 **Claude Code의 Task 도구로 호출되는 서브에이전트**다.
메인 에이전트(대화 최상위 Claude)와 별개의 컨텍스트에서 작업하고, 완료 시 결과를 메인에게 자동으로 통지한다.

포그라운드 / 백그라운드는 이 서브에이전트의 **실행 모드**를 가리키며, 메인 / 서브 구분과는 **별개의 축**이다. 혼동을 피하기 위해 본 문서는 실행 모드를 "포그라운드 서브에이전트 / 백그라운드 서브에이전트"로, 최상위를 "메인 에이전트"로 표기한다.

### 언제 에이전트를 쓸까

아래 경우에 에이전트 생성을 검토한다.

- 독립적으로 병렬 처리 가능한 작업 (예: 코드 리뷰의 보안·성능·스타일 동시 검토)
- 시간이 걸리는 작업이라 메인이 다른 일을 계속하는 동안 백그라운드로 위임하고 싶을 때
- 격리된 컨텍스트에서 처리되어야 하는 작업
- 사용자가 명시적으로 요청할 때 ("이건 에이전트로 만들어줘")

### 생성 절차

사용자가 명시적으로 승인을 생략하라고 하지 않는 한 아래 순서를 지킨다.

1. 에이전트 구조 제안 (역할 분담 + 디렉토리 레이아웃)
2. 사용자 승인 확인
3. 생성 진행

> "이런 구조로 에이전트를 나눠서 진행하려고 합니다. 진행해도 될까요?"

### 디렉토리 구조와 등록

Task 로 디스패치하는 에이전트 정의 파일은 **플러그인 루트 `agents/` 에 둔다.** 플러그인 시스템이 이 디렉토리를 자동 발견해 `<플러그인>:<에이전트>` 네임스페이스로 등록한다.

에이전트 셋을 쓰는 `code-review` 스킬이라면 이렇게 놓인다.

| 경로 | 내용 |
|---|---|
| `agents/security.md` | 에이전트 정의 파일 |
| `agents/performance.md` | 에이전트 정의 파일 |
| `agents/style.md` | 에이전트 정의 파일 |
| `skills/code-review/SKILL.md` | 스킬 진입점 |
| `skills/code-review/overview.md` | 호출 항목이 여기 적힌다 |

경로는 모두 플러그인 루트 기준이다.

예외: 에이전트성 보조 파일이 Task 디스패치 없이 **스킬 내부 디스패처(예: .sh)가 경로로 직접 읽기만** 한다면 등록이 불필요하므로 그 스킬 디렉토리 안에 두어도 된다.

스킬 본문에서는 bare 이름(`subagent_type: <에이전트>`)으로 호출하고, 외부에는 `<플러그인>:<에이전트>` 로 노출된다.

### 정의 파일 형식

표준 Claude Code 에이전트 정의 형식. 프론트매터에 이름·설명·사용 도구를 명시한다.

```markdown
---
name: security
description: 코드의 보안 취약점을 검토하는 에이전트
tools: Read, Grep, Glob
---

에이전트 시스템 프롬프트 본문. 호출되면 무엇을 어떻게 작업할지 정의한다.
```

### 호출 방식

메인 Claude 가 Task 도구로 호출한다. 호출 형태는 두 가지.

| 형태 | 사용 시점 |
|------|----------|
| 일반 호출 (`run_in_background: false` 또는 생략) | 결과가 다음 작업의 직접 입력이거나 즉시 필요할 때 |
| 백그라운드 호출 (`run_in_background: true`) | 시간이 걸리고 메인이 다른 일을 계속해야 할 때. 비동기 통지 패턴 |

병렬 처리가 필요하면 여러 Task 호출을 **병렬로** 시작한다. 메커니즘: 메인 Claude 가 한 응답에 여러 Task 호출을 함께 포함하면 시스템이 병렬 실행한다.
각 호출은 별도 컨텍스트로 격리되므로 동시 실행되어도 서로 영향을 주지 않는다.

### 결과 처리

작업 수행(조사·분석·작문)은 서브에이전트에 위임하되, 필요 시 그 결과를 파일로 저장하는 일은 서브에이전트가 할 수 없으므로 메인 에이전트가 맡는다.

- **기본**: 서브에이전트는 결과를 파일에 직접 저장하지 않는다. 완성 본문을 최종 메시지로 반환하고, 메인 에이전트가 통지를 받아 저장한다. 결과가 메인 컨텍스트에 있어야 후속 조인/판단에 쓰고, 권한 문제(아래)도 피하기 때문이다
- 백그라운드 서브에이전트는 권한 프롬프트를 띄울 수 없어 **사전 허용되지 않은** Write/Edit 은 자동 거부된다. 뒤집으면, 대상 경로가 **사전 허용**(권한 설정/모드로 프롬프트가 안 뜨는 상태)이면 백그라운드 서브에이전트도 직접 Write 에 성공한다
- 포그라운드 서브에이전트의 Write 가능 여부는 보장되지 않으므로, 직접 Write 가 정당한 예외(아래)가 아니면 저장은 메인이 맡는 것을 기본으로 한다
- **예외 (서브에이전트 직접 Write 가 정당한 경우)**: 다음 둘 중 하나에 해당하고 **대상 경로가 사전 허용**돼 있으면, 서브에이전트가 자기 산출을 직접 Write 하고 메인엔 경로만 반환하게 한다 -- (a) 산출이 부피가 커 단일 본문 반환이 토큰 한도에 잘리는 부류(다량 파일 생성·HTML 렌더 등), (b) 병렬 팬아웃에서 각 에이전트가 자기 출력 파일을 독립 소유해 본문 반환이 직렬화·비효율인 경우. 선례: code-analyze 의 구조 노드/렌더 에이전트(부피, a), skill-verify 의 2단계 5에이전트(각자 wip 파일 소유, b). 이때 메인은 사후에 산출 존재/개수만 교차검산한다
- task-notification 으로 반환된 본문은 `&`/`<`/`>` 가 HTML 엔티티로 이스케이프되므로, 메인이 저장 전 원래 문자로 원복한다
- 메인은 통지 도착 시 후속 작업 진행

사전 허용되지 않은 경로에 서브에이전트가 Write/Edit 으로 저장하도록 설계하지 않는다. 직접 Write 를 쓰기로 했다면 그 경로가 사전 허용임을 overview 에 명시하거나, 사전 준비 단계에서 쓰기 가능 여부를 확인하는 절차를 둔다. `skill-verify` 의 `agent-check` 가 이 두 가지를 검사한다.

### overview 에서 에이전트 호출 명시

각 호출 항목에 다음을 포함한다.

- 에이전트 이름
- 호출 형태 (일반 / 백그라운드)
- 입력으로 전달할 내용
- 기대 출력 (저장 파일 경로 또는 반환 텍스트 형식)

예:

```markdown
- [ ] 에이전트 security: 일반 호출. 입력: 코드 디렉토리 경로. 출력: wip/security-review.md
- [ ] 에이전트 performance: 백그라운드 호출 (`run_in_background: true`). 입력: 동일. 출력: wip/perf-review.md
```

호출이 반드시 백그라운드여야 하는 시점이라면 그 이유와 함께 호출 항목에 명시한다.

## 11. 본문에 넣지 않는 것

스킬 문서는 실행 지시서다. 읽는 쪽은 규격을 심사하는 사람이 아니라 규칙을 실행할 모델이다. 실행에 쓰이지 않는 서술은 넣지 않는다.

적용 대상은 모델이 로드하는 파일이다 -- `SKILL.md`, `overview.md`, 하위 파일, 그리고 그 스킬이 쓰는 `agents/` 정의. `README.md` 는 사람이 읽는 문서라 대상이 아니며, 여기서 빼는 근거와 배경이 갈 자리이기도 하다.

| 넣지 않는 것 | 갈 곳 |
|---|---|
| 결정의 정당화 -- 왜 이렇게 정했는가 | 커밋 메시지, PR 본문 |
| 시점 서사 -- 제작 이력, 미검증·잠정 표기, 예전에는 이랬다 | 메모리 |
| 이미 적은 규칙의 재진술 | 지운다 |

시점 서사를 빼는 데는 이유가 하나 더 있다. "이건 아직 잠정값이다" 는 규칙을 따라야 할 모델에게 그 규칙을 느슨하게 봐도 된다는 신호로 읽힌다.

### 삭제 테스트

근거로 보이는 문장은 지워 보고 정한다. 지웠을 때 규칙만으로는 판정이 갈리지 않는 상황이 생기면 남기고, 모든 경우가 똑같이 판정되면 지운다.

남긴다: "코드/문법은 눈앞에 코드가 있어야 물어볼 수 있어 자동 감지가 불가능하다" -- 목록에 없는 상황이 자동 감지 대상인지 이 문장이 가른다.

지운다: "자동 감지에서 묻지 않는 이유는 사용자가 요청한 적 없는 발동이기 때문이다" -- 묻지 않는다는 규칙이 이미 있고, 이 문장이 갈라 주는 경우가 없다.

판정이 서지 않으면 남긴다. 근거를 잘못 지우면 판단 기준 자체가 사라지므로, 군더더기 한 줄보다 손실이 크다.

**남기기로 정한 문장에는 한 단계가 더 있다.** 근거가 필요해서 남기더라도, 그 안에 시점 표기("미검증", "관측됨", "아직", "예전에는")가 섞여 있으면 그 표기만 걷어낸다. 근거는 판정을 가르지만 시점 표기는 가르지 않으며, 남아 있으면 규칙을 잠정적인 것으로 읽히게 한다.

예: "포그라운드 서브에이전트의 Write 가능 여부는 본 환경에서 미검증이므로" -> "포그라운드 서브에이전트의 Write 가능 여부는 보장되지 않으므로". 판정을 가르는 부분(보장되지 않는다)은 남고, 시점 표기(미검증)만 빠진다.

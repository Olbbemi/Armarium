# CLAUDE.md 검증

그 프로젝트의 CLAUDE.md 품질을 16개 항목으로 검증하고, 각 결함에 고침 제안을 붙여 보고서로 낸다.
에이전트 없이 메인이 직접 수행한다. 파일을 직접 고치지 않는다 -- 적용은 사용자 몫이다.

## 대상 파일 판정

대상은 그 프로젝트의 CLAUDE.md 다. 위치는 프로젝트마다 갈린다.

두 위치 중 존재하는 것을 대상으로 한다. 둘 다 있으면 각각 검사한다.

## 검증 항목

메인이 대상 파일을 전부 읽고 아래 16개 항목을 전수 평가한다. 발견한 각 결함에는 구체적
고침 제안을 붙인다. 판정 기준은 이 스킬이 자체 소유한다 -- 다른 스킬(skill-writing 등)의
규칙을 근거로 삼지 않는다. 근거는 CLAUDE.md 자체의 성질이다. 그 프로젝트의 여러 세션이 항상
읽고 따르는 지시문이라, 구조가 흐트러지거나 표현이 모호·은유적이면 세션마다 해석이 갈려
동작 편차가 난다.

### 형식 / 구조

- F1 마크다운 구조화: 주제가 헤딩 계층으로 나뉘는가, 여러 주제가 구분 없이 한 곳에 섞여 있지 않은가.
- F2 개행 / 문단 분리: 규칙 사이 개행·문단 분리가 되어 있는가. 한 줄·한 문단에 여러 규칙을 몰아넣지 않는가.
- F3 나열은 리스트로: 여러 항목이 산문에 섞이지 않고 리스트로 스캔되는가.
- F4 섹션 밀도: 한 섹션이 지나치게 길어 읽기 어렵지 않은가.
- F5 이모지 배제: 이모지를 쓰지 않았는가.
- F6 불릿 남용: 나열 항목 2개 이상일 때만 불릿을 쓰고, 단일 서술문은 문장으로 두었는가.
- F7 헤딩 vs bold 용도 구분: 독립 내용 블록은 헤딩, 짧은 분류 레이블은 bold 로 구분했는가.

### 언어 / 표현

- L1 은유 표현 배제: 다른 사물에 빗댄 은유·비유를 쓰지 않았는가. 단 굳어진 준기술어(앵커·창발·지도 등)는 예외.
- L2 모호 / 집행 불가: 무엇을 하라는지 불명확하거나 지킬 수 없는 서술이 있는가.
- L3 직설 / 간결: 장황하거나 돌려 말하지 않는가. 단 필요한 기준·예외는 생략하지 않는다.

### 의미 / 논리

- S1 규칙 충돌: 서로 모순되는 지시가 있는가.
- S2 중복 / 겹침: 같은 규칙이 여러 곳에 흩어져 표현이 어긋나는가.
- S3 근거(왜) 유무: 맨 명령만 있고 이유가 없어 오적용 위험이 있는가.
- S4 자기완결성: 그 규칙·참조만 읽어도 이해·적용되는가. 특히 구조 참조(디렉토리 배치·컴포넌트 표·경로 예시)가 문서만으로 해석되는가 -- 그 경로가 단순 디렉토리인지, 브랜치·워크트리별로만 존재하는 경로인지 등을 repo 를 직접 봐야만 알 수 있으면 자기완결성 결함이다. 문서가 그 자리에서 밝혀야 한다.
- S5 적용 범위 / 트리거 명확성: 규칙이 언제·어디서 적용되는지 분명한가.

### 정합성

- C1 프로젝트 실제와 정합: 실제로 따라가야 하는 지시/의존 참조(예: "자세한 건 X 를 본다", "X 로 빌드한다")가 존재하지 않는 경로·도구·파일을 가리키는가. 특정 시점에만 유효한 참조(커밋 해시·이슈 번호 등)도 stale 로 본다. 이런 지시/의존 참조에 한해 파일 시스템으로 실재를 확인한다. 구조 참조(디렉토리 배치·컴포넌트 표·경로 예시)는 현재 브랜치에 없어도 C1 에서 stale 로 보지 않는다 -- 그 적정성(문서만으로 해석되는가)은 S4 가 본다.

CLAUDE.md 는 그 프로젝트 전용이라 고유 경로·도구·엔티티를 쓰는 것 자체는 정상이며 결함이
아니다. C1 은 지시/의존 참조가 실제와 맞는지(stale 여부)만 본다.

## 결과 조립 / 저장

1. 16항목 평가 결과를 결함 목록으로 정리한다. 결함 1건은 항목 코드(F1~C1), 위치(섹션 또는 원문 인용), 문제, 사유, 고침 제안을 포함한다.
2. `<프로젝트 루트>/claude-md/` 디렉토리를 만들고 결과를 `result.md` 로 저장한다. 대상이 둘(루트 + `.claude/`)이면 파일별 섹션으로 한 보고서에 합쳐 저장한다.
3. 콘솔에는 항목별 결함 수 요약 표와 저장 경로만 출력한다.

# 0단계: 구상

무엇을 왜 만들지 -- 또는 만들지 말지 -- 방향을 정하는 발산 단계.
이 단계의 출력(확정 방향)이 1단계(요구사항 명세)의 입력이 된다.

1단계 이후가 "정해진 것을 좁혀가는 수렴"이라면, 이 단계는 그 앞에서 "무엇을 풀지·풀 가치가 있는지·어느 방향으로 풀지"를 펼쳐 보는 발산이다.

---

## 공통 원칙

이 단계의 모든 동작은 `skills/code-design/principles.md` 의 공통 원칙을 따른다.

특히 명확화 질문(모호하면 한 번에 하나씩 되묻기)은 원칙 1 이 이 단계 전반을 관통하므로 작업 흐름에 별도 스텝으로 두지 않는다.

---

## 진입 조건

다음 중 하나라도 해당되면 이 단계로 진입:
- 무엇을 만들지, 또는 만들지 말지가 미정임
- 현 상태가 불만족스러운데 원인이 불명확함 (진단이 필요함)
- 여러 방향이 경합해 비교와 선택이 필요함

방향이 이미 명확한 작업이어도 이 단계를 건너뛰지 않고, 아래 "fast-path" 로 가볍게 통과한다.

<RICOCHET>
방향이 명확해 보인다는 이유로 0단계를 생략하고 1단계로 직행하지 않는다.
</RICOCHET>

## fast-path — 방향이 이미 명확할 때

발산이 불필요할 만큼 방향이 명확하면, 아래 작업 흐름 5스텝을 전부 무겁게 밟지 않고 빠르게 통과한다.

- 진단(스텝 2)과 발산(스텝 3)은 약식 또는 N/A 로 처리할 수 있다.
- 확정 방향(스텝 5)은 약식이어도 사용자 확인으로 못박는다.
- 단계 자체를 건너뛰지는 않는다. 산출물에 "방향이 자명함"을 근거와 함께 기록해, 1단계가 받을 전제가 비지 않게 한다.

이유: 단순해 보이는 작업일수록 점검되지 않은 전제가 가장 큰 낭비를 만든다. fast-path 는 그 점검을 "가볍게라도 반드시" 거치게 하는 장치다.

<PENETRATE>
fast-path 로 통과해도 확정 방향은 사용자 확인을 받아 산출물에 기록한다.
</PENETRATE>

---

## 단계 시작 시 — 사전 조사

발산은 빈 손이 아니라 현 상태를 딛고 한다. 방향을 펼치기 전에 지금이 어떤 상태인지부터 파악한다. 이 사전 조사 결과가 작업 흐름 스텝 1(컨텍스트 탐색)의 입력이 된다.

기존 코드 구조 파악에 code-analyze facet 산출물이 있으면 1차 입력으로 활용한다 -- 공통 원칙 6 (`principles.md`) 참조. 수작업 도구(ripgrep, fd, tree, universal-ctags 등 `references/tools.md`)는 facet 이 없거나 특정 지점을 더 깊이 파야 할 때 보완으로 쓴다.

처음 다루는 도메인이거나 방향 판단에 근거가 필요하면 외부 검색으로 보완한다. 검색 깊이는 공통 원칙 2 를 따르며, 찾은 근거는 그대로 인용하지 않고 프로젝트 맥락에 맞게 재해석한다.

---

## 작업 흐름

### 1. 컨텍스트 탐색

기존 코드 / 문서 / git / facet 을 보고 "지금 상태가 어떤지"를 파악한다.

**작성 규칙:**
- 관련 코드 위치, 현재 동작 방식, 무엇이 갖춰져 있고 무엇이 비어 있는지를 사실 그대로 기록한다.
- 신규 착안(기존 상태와 무관하게 새로 만드는 것)이면 N/A 로 표기한다 (공통 원칙 3).

### 2. 문제 / 근본원인 진단

현 상태의 무엇이 불만인지(증상), 그 진짜 원인이 무엇인지를 가설과 검증으로 진단한다.

**작성 규칙:**
- 증상 -> 원인 가설들 -> 검증(코드/문서/검색으로) -> 결론 순으로 적는다.
- 증상과 원인을 섞지 않는다. "UI 가 빈약하다"(증상)와 "전역 스타일 정의가 없다"(원인)는 다른 칸이다.
- 신규 착안이라 진단할 현 불만이 없으면 약식 또는 N/A 로 처리한다.

이 스텝은 조건부다 -- 진단할 현 상태가 있을 때 핵심이 되고, 순수 신규 착안이면 가벼워진다.

<RICOCHET>
검증하지 않은 원인 가설을 확정 원인으로 기록하지 않는다.
</RICOCHET>

### 3. 방향 발산 + 비교 + 권고

문제를 풀 해결 방향을 2~3개로 펼치고(발산), 각 방향의 트레이드오프를 비교한 뒤 권고안을 제시한다.

**비교 항목:**
- 가치: 이 방향이 주는 효용
- 비용 / 리스크: 구현 부담, 부작용, 실패 가능성
- 수명: 이 방향의 가치가 얼마나 오래 가는지 (다른 계획/방향 전환에도 살아남는지)

**작성 규칙:**
- 방향은 2~3개를 기본으로 한다. 같은 도메인을 반복해 다루면 공통 원칙 2 에 따라 더 넓게 펼친다.
- 권고안과 그 근거를 먼저 제시한다. 단 채택 결정은 사용자 몫이다 (스텝 5).

<RICOCHET>
하나의 방향만 제시하고 비교 없이 그 방향으로 굳히지 않는다.
</RICOCHET>

### 4. go / no-go 판단

발산한 방향들을 놓고 "이걸 만들 가치가 있는가"를 판단한다. go(만든다) / no-go(만들지 않는다) / 보류 중 하나로 귀결한다.

**판단 규칙:**
- go/no-go 는 "갈지 말지"(투자 판단)이고, 스텝 5 의 방향 확정은 "간다면 어느 방향으로"(안 선택)다. 다른 결정이므로 섞지 않는다.
- no-go 면 파이프라인에 진입하지 않고 이 단계에서 종료한다. 산출물에 no-go 사유를 남긴다.
- 지금 결정할 수 없으면 보류한다 -- `code-design/00-ideation-deferrals.md` 에 사유와 재개 조건을 등재한다 (공통 원칙 4).

<PENETRATE>
go/no-go 는 사용자 확인을 받은 결과만 기록한다.
</PENETRATE>

<RICOCHET>
go/no-go 를 Claude 가 임의로 결정하지 않는다.
</RICOCHET>

### 5. 방향 확정

go 결정 후, 발산한 방향 중 어느 것으로 갈지 최종 선택해 명문화한다. 이 확정 방향이 1단계로 넘어가는 핵심 산출이다.

**작성 규칙:**
- 확정 방향은 한 문장으로 분명하게 적는다. "무엇을 왜 만든다"까지만 담고, "어떻게 만든다"(설계)는 2단계 소유이므로 넘기지 않는다.
- 1단계가 명세할 때 꼭 정해야 할 항목이 보이면 "1단계 위임 항목"에 힌트로 남긴다.
- 사용자 승인은 이 스텝에서 받지 않고 완료 기준 체크리스트 게이트에서 받는다.

<RICOCHET>
이 단계에서 설계(어떻게 만들지) 결정을 내리지 않는다 -- 그것은 2단계 소유다.
</RICOCHET>

## 산출물 형식

구상 결과는 다음 형식의 문서로 작성한다.
모든 섹션은 비워두지 않는다. 채울 데이터가 없으면 명시적으로 N/A 로 표기한다 (공통 원칙 3).

이 산출물은 핸드오프 파일(`handoff.md`)에 그대로 저장된다 — "다음 단계로 전달할 것" 섹션 참조.

```markdown
# 구상: {주제}

## 배경 / 현재 상태
(스텝 1. 기존 코드/문서/facet 으로 파악한 현황. 신규 착안이면 N/A)

## 문제 + 근본원인 진단
(스텝 2. 증상 / 가설 / 검증 / 결론. 신규 착안이면 약식 또는 N/A)

## 검토한 방향들
(스텝 3. 방향별 트레이드오프 + 권고)
| 방향 | 가치 | 비용/리스크 | 수명 |
|------|------|------------|------|
| ...  | ...  | ...        | ...  |
- 권고: (어느 방향을 왜 권고하는지)

## go / no-go 결정
(스텝 4. go / no-go / 보류 중 하나 + 근거. 보류면 00-ideation-deferrals.md 참조)

## 확정 방향
(스텝 5. 채택한 방향을 한 문장으로. no-go 면 "미진입")

## 1단계 위임 항목
(1단계가 명세할 때 꼭 정해야 할 항목 힌트. 없으면 N/A)

## 가정 사항
(사용자 확인을 받은 가정만 기록. 임의 가정 금지)

## 참고 자료
- 외부: (검색으로 참고한 공식 문서, 표준 등)

## 사용자와의 명확화 기록
- 모호했던 항목과 그 해소 과정
- 피드백 협의 과정 (피드백이 있었던 경우)
  - 사용자 의견: ...
  - LLM 반문: ...
  - 합의 결과: ...
```

## 완료 기준

단계 종료 시 아래 형식으로 제시한다.

**저장 경로:** `{프로젝트 루트}/code-design/00-ideation/checklist.md`
- 공통 원칙 5("단계 산출물 저장 정책")에 따른다.
- 단일 파일을 회차마다 갱신하며, 회차 이력은 git 이 보존한다.

```markdown
## 완료 기준
- [ ] 현재 상태가 파악되어 기록됨 (신규 착안이면 N/A 명시)
- [ ] 문제와 근본원인이 진단됨 (증상/가설/검증/결론. 신규 착안이면 약식/N/A 명시)
- [ ] 2~3개 방향이 발산되고 트레이드오프로 비교됨 (fast-path 면 약식 + 자명 근거 기록)
- [ ] go / no-go 가 사용자 확인으로 결정됨 (보류면 보류 파일에 등재 — 원칙 4)
- [ ] (go인 경우) 확정 방향이 한 문장으로 명문화되고 사용자 확인됨
- [ ] 1단계 위임 항목이 식별됨 (없으면 N/A 명시)
- [ ] 모호한 항목이 없거나, 보류 항목은 보류 파일에 등재됨 (원칙 4)
- [ ] 임의로 추정한 가정 사항이 없음 (모든 가정은 사용자 확인됨)
- [ ] 설계(어떻게 만들지) 결정을 내리지 않음 (2단계 소유)
- [ ] N/A로 표기된 항목이 모두 사용자 확인을 받음
- [ ] 피드백 영역이 채워짐 (없어도 N/A 명시)

## N/A 항목 확인
다음 항목이 N/A로 표기됨. 정말 해당 없음이 맞는지 확인 부탁드립니다:
- (예) 배경 / 현재 상태: N/A (신규 착안)
- (예) 1단계 위임 항목: N/A
(N/A 항목이 없으면 "없음"으로 표기)

## 피드백
(피드백을 작성. 없으면 N/A 명시)
```

### 피드백 처리 절차

피드백 처리(반문 -> 협의 -> 기록 -> 재제시)와 자동 수용 금지 대상은 1단계(`01-requirements.md` 의 "피드백 처리 절차")와 동일한 규칙을 따른다. 협의 결과는 산출물의 "사용자와의 명확화 기록"에 남긴다.

<RICOCHET>
사용자와 합의에 도달하기 전에 다음 단계로 진행하지 않는다.
</RICOCHET>

**저장 경로:** `{프로젝트 루트}/code-design/00-ideation/handoff.md`
- 공통 원칙 5("단계 산출물 저장 정책")에 따른다.

<PENETRATE>
핸드오프는 완료 기준 체크리스트가 사용자 승인을 받은 직후에만 작성한다.

**내용 계약:**

- 1단계는 이 핸드오프에서 "확정 방향 / 배경·현재상태 / 문제+진단"을 읽어, 자기 산출물 상단의 "전제" 섹션에 요약 인용한다 (통째 복사가 아니라 핵심 압축).
- 1단계가 더 깊은 맥락이 필요하면 이 핸드오프 원본을 직접 참조한다. 요약과 원본이 어긋나면 원본을 신뢰한다.

**no-go 경로:**

<RICOCHET>
go/no-go 가 no-go 면 핸드오프를 작성하지 않고 파이프라인에 진입하지 않는다.
</RICOCHET>

no-go 면 핸드오프 대신, 산출물의 "go / no-go 결정"과 "확정 방향(= 미진입)"에 사유를 남기고 단계를 종료한다.

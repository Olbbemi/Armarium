# 구상 (ideation)

무엇을 왜 만들지 -- 또는 만들지 말지 -- 방향을 정하는 발산 단계.
이 산출물(확정 방향)이 01-requirements 의 입력이 된다.

01-requirements 이후가 "정해진 것을 좁혀가는 수렴"이라면, 00-ideation 은 그 앞에서 "무엇을 풀지·풀 가치가 있는지·어느 방향으로 풀지"를 펼쳐 보는 발산이다.

---

## 공통 원칙

이 단계의 모든 동작은 `skills/code-design/principles.md` 의 공통 원칙을 따른다.

특히 명확화 질문(모호하면 한 번에 하나씩 되묻기)은 원칙 1 이 이 단계 전반을 관통하므로 작업 흐름에 별도 스텝으로 두지 않는다.

---

## 진입 조건

다음 중 하나라도 해당되면 이 단계로 진입:
- 무엇을 만들지, 또는 만들지 말지가 미정임
- 현 상태가 불만족스러운데 원인이 불명확함 (진단이 필요함)
- 여러 방향이 경합해 비교와 선택이 필요함

방향이 이미 명확한 작업이어도 이 단계를 건너뛰지 않고, 아래 "fast-path" 로 가볍게 통과한다.

<RICOCHET>
방향이 명확해 보인다는 이유로 00-ideation 을 생략하고 01-requirements 로 직행하지 않는다.
</RICOCHET>

## 이 단계가 만드는 파일

이 단계는 두 종류의 파일을 만든다.

| 파일 | 내용 | 저장 시점 |
|------|------|----------|
| `handoff.md` | 00-ideation 산출물(문서) -- "산출물 형식" 섹션의 템플릿이 그대로 채워진 형태. 01-requirements 입력으로 사용됨 | 사용자 승인 서명 확인 직후 |
| `checklist.md` | 완료 기준 점검 결과 -- "완료 기준" 섹션의 템플릿이 채워진 형태. **제시 전 파일 먼저 작성**, 회차마다 갱신(이력은 git), 승인 시 사용자 서명 + 시각 스탬프 (overview "단계 전환 규칙") | 제시 전 (파일 먼저) |

**저장 경로:** `{프로젝트 루트}/code-design/<브랜치>/00-ideation/` (로드맵 마스터는 별도로 `code-design/roadmap.md` -- 아래 스텝 4)

**용어 정리:**
- "산출물" = 00-ideation 문서 본문 = `handoff.md` 의 내용
- "핸드오프" = 다음 단계가 읽을 파일 = `handoff.md`
- "체크리스트" = 완료 기준 점검 결과 = `checklist.md`

진행 판단이 no-go 면 핸드오프를 만들지 않는다 -- "다음 단계로 전달할 것" 참조.

---

## fast-path -- 방향이 이미 명확할 때

발산이 불필요할 만큼 방향이 명확하면, 아래 작업 흐름 5스텝을 전부 무겁게 밟지 않고 빠르게 통과한다.

- 진단(스텝 2)과 발산(스텝 3)은 약식 또는 N/A 로 처리할 수 있다. 로드맵(스텝 4)도 쪼갤 것이 없으면 단일 청크로 둔다.
- 유형 판정(스텝 1)과 확정 방향(스텝 6)은 약식이어도 사용자 확인으로 못박는다.
- 단계 자체를 건너뛰지는 않는다. 산출물에 "방향이 자명함"을 근거와 함께 기록해, 01-requirements 가 받을 전제가 비지 않게 한다.

이유: 단순해 보이는 작업일수록 점검되지 않은 전제가 가장 큰 낭비를 만든다. fast-path 는 그 점검을 "가볍게라도 반드시" 거치게 하는 장치다.

<PENETRATE>
fast-path 로 통과해도 확정 방향은 사용자 확인을 받아 산출물에 기록한다.
</PENETRATE>

---

## 단계 시작 시 -- 사전 조사

발산은 빈 손이 아니라 현 상태를 딛고 한다. 방향을 펼치기 전에 지금이 어떤 상태인지부터 파악한다. 이 사전 조사 결과가 작업 흐름 스텝 1(유형 판정 + 컨텍스트 탐색)의 입력이 된다.

기존 코드 구조 파악에 code-analyze facet 산출물이 있으면 1차 입력으로 활용한다 -- 공통 원칙 6 (`principles.md`) 참조. 수작업 도구(ripgrep, fd, tree, universal-ctags 등 `references/tools.md`)는 facet 이 없거나 특정 지점을 더 깊이 파야 할 때 보완으로 쓴다.

처음 다루는 도메인이거나 방향 판단에 근거가 필요하면 외부 검색으로 보완한다. 검색 깊이는 공통 원칙 2 를 따르며, 찾은 근거는 그대로 인용하지 않고 프로젝트 맥락에 맞게 재해석한다.

## 작업 흐름

### 1. 유형 판정 + 컨텍스트 탐색

먼저 이 작업이 어떤 유형인지 판정한다 -- 이후 배경·문제를 어디까지 채울지가 여기서 갈린다.

**유형:**
- 1 = 기존 코드/문서가 있다 (기존 것에 손대는 작업)
- 2a = 순수 신규 -- 둘러싼 맥락도 거의 없음
- 2b = 신규지만 현 상황/동기는 뚜렷 (코드만 없음)

그다음 현 상태를 파악한다. 유형에 따라 채우는 줄이 다르다.

**작성 규칙:**
- 기존 코드/문서 현황: 유형 1 이면 관련 코드 위치·현재 동작·무엇이 갖춰졌고 무엇이 비었는지를 사실대로 기록한다. 유형 2a·2b 면 "없음(신규)".
- 둘러싼 현 상황 / 맥락: 전 유형 공통. 제품을 둘러싼 생태계, 사용자 맥락, 지금은 어떻게 하고 있는지. 유형 2b 는 코드가 없어도 여기가 살아있다 -- 통째로 N/A 로 떨구지 않는다 (공통 원칙 3).

### 2. 문제 / 동기 + (유형 1) 근본원인 진단

무엇이 불만이고 왜 만드는지(동기)를 밝히고, 기존 시스템이 있으면 그 진짜 원인을 진단한다.

**작성 규칙:**
- 문제 / 동기: 전 유형 공통. 무엇이 불편하고 왜 이걸 만드나. 신규 착안이어도 동기가 또렷하면 또렷하게 적는다 -- "신규라서 N/A" 로 약하게 처리하지 않는다.
- 근본원인 진단: 유형 1 전용. 증상 -> 원인 가설들 -> 검증(코드/문서/검색으로) -> 결론 순으로 적는다. 증상과 원인을 섞지 않는다. "UI 가 빈약하다"(증상)와 "전역 스타일 정의가 없다"(원인)는 다른 칸이다. 유형 2a·2b 는 진단할 기존 시스템이 없어 N/A.

<RICOCHET>
검증하지 않은 원인 가설을 확정 원인으로 기록하지 않는다.
</RICOCHET>

### 3. 방향 발산 + 비교 + 권고

문제를 풀 해결 방향을 2~3개로 펼치고(발산), 각 방향의 트레이드오프를 비교한 뒤 권고안을 제시한다.

**비교 항목:**
- 가치: 이 방향이 주는 효용
- 비용 / 리스크: 구현 부담, 부작용, 실패 가능성
- 수명: 이 방향의 가치가 얼마나 오래 가는지 (다른 계획/방향 전환에도 살아남는지)

**작성 규칙:**
- 방향은 2~3개를 기본으로 한다. 같은 도메인을 반복해 다루면 공통 원칙 2 에 따라 더 넓게 펼친다.
- 권고안과 그 근거를 먼저 제시한다. 단 채택 결정은 사용자 몫이다 (스텝 5).

<RICOCHET>
하나의 방향만 제시하고 비교 없이 그 방향으로 굳히지 않는다.
</RICOCHET>

### 4. 로드맵 큐레이션 (roadmap.md)

로드맵은 전체 작업을 청크(하나의 flow 가 담당하는 작업 범위)로 쪼갠 지도이며, `code-design/roadmap.md` 에 마스터로 유지된다(overview "로드맵", 원칙 5). 00-ideation 이 이 파일의 큐레이터다. (청크 = 프로젝트를 쪼갠 작업 덩어리 -- 파이프라인 단계 00~04 와 다른 축이다.)

**flow 시작 시 (기존 roadmap.md 가 있으면):**
- 열린 `[미정]` 청크를 전부 재검토한다 -- 조건 충족이면 승격, 무의미해졌으면 사용자 확인 후 `[기각]`.
- 이번에 만들 청크를 고르거나 새로 스케치하고 그 청크를 `[진행]`으로 표식한다.

**작성 규칙:**
- 채택 방향이 커서 한 번에 다 만들 수 없으면 청크로 굵게 쪼갠다 -- 청크당 한 줄. 이번에 만들 청크에 `[진행]`, 미래에 할 청크에 `[예정]`(할지 확정) 또는 `[미정]`(할지 미정 + 재검토 조건).
- `[예정]`/`[미정]` 청크는 잠정 스케치다. 한 줄 요지 + 의존만 적고 상세를 미리 짓지 않는다 (막지 마라 != 미리 지어라 -- YAGNI).
- 작업이 작아 쪼갤 것이 없으면 단일 청크(`[진행]` 하나)로 둔다.
- `[진행]` 은 스코프 표식일 뿐 진행 판단(go/no-go) 결과가 아니다 -- 판정은 스텝 5 가 한다. 청크 상태 어휘·전이 규칙은 overview "로드맵"을 단일 출처로 본다. 로드맵 쓰기는 사용자 확인 + 출처 기록.

미래(`[예정]`/`[미정]`) 청크의 진행 판단은 그 청크를 다루는 미래 flow 의 00-ideation 이 내린다. 지금은 로드맵에 한 줄로만 둔다.

### 5. 진행 판단 (go / no-go / 미정)

`[진행]` 청크를 만들 가치가 있는지 판단한다. go(만든다) / no-go(만들지 않는다) / 미정 중 하나로 귀결한다.

**판단 규칙:**
- 판단 대상은 `[진행]` 청크다. 진행 판단은 "이 청크를 갈지 말지"(투자 판단)이고, 스텝 6 의 방향 확정은 "간다면 어느 방향으로"(안 선택)다. 다른 결정이므로 섞지 않는다.
- go: 진행한다. 01-requirements 로 넘어간다.
- no-go: 안 하기로 결론. 로드맵에서 그 청크를 `[기각]`(사유 명시)으로 두고 이 단계에서 종료한다. `[진행]` 청크가 의존 사슬 첫머리면 전체 멈춤을 겸한다.
- 미정: 지금은 못 정한다. 로드맵에서 `[미정]`(재검토 조건 명시)으로 두고 종료한다. 파이프라인 미진입.

<PENETRATE>
진행 판단은 사용자 확인을 받은 결과만 기록한다.
</PENETRATE>

<RICOCHET>
진행 판단을 Claude 가 임의로 결정하지 않는다.
</RICOCHET>

### 6. 방향 확정

go 결정 후, 발산한 방향 중 어느 것으로 갈지 최종 선택해 명문화한다. 이 확정 방향이 01-requirements 로 넘어가는 핵심 산출이다.

**작성 규칙:**
- 확정 방향은 로드맵 `[진행]` 청크를 "무엇을 왜 만드나 + 어디까지가 이번 범위인가(미래 수용 경계)"로 푼 한 문단이다. "어떻게 만든다"(설계)는 02-design 소유이므로 넘기지 않는다.
- 미래 수용 경계를 함께 적어 01-requirements·02-design 이 미래 단계를 미리 닫아버리지 않게 한다.
- 01-requirements 가 명세할 때 꼭 정해야 할 항목이 보이면 "위임 항목"에 힌트로 남긴다. 항목의 성격도 표시한다 -- `[requirements]`(요구에서 정함) / `[design]`(02-design 영역) / `[deferred]`(지금 결정 못함). 성격을 식별해 표시하는 것은 설계 결정이 아니다.
- 사용자 승인은 이 스텝에서 받지 않고 완료 기준 체크리스트 게이트에서 받는다.

<RICOCHET>
이 단계에서 설계(어떻게 만들지) 결정을 내리지 않는다 -- 그것은 02-design 소유다.
</RICOCHET>

## 산출물 형식

00-ideation 결과는 다음 형식의 문서로 작성한다.
모든 섹션은 비워두지 않는다. 채울 데이터가 없으면 명시적으로 N/A 로 표기한다 (공통 원칙 3).

이 산출물은 핸드오프 파일(`handoff.md`)에 그대로 저장된다 -- "다음 단계로 전달할 것" 섹션 참조.

```markdown
# 구상: {주제}

유형: {1 | 2a | 2b}
- 1  = 기존 코드/문서가 있다 (기존 것에 손대는 작업)
- 2a = 순수 신규 -- 둘러싼 맥락도 거의 없음
- 2b = 신규지만 현 상황/동기는 뚜렷 (코드만 없음)

## 배경 / 현재 상태
(스텝 1)
- 기존 코드/문서 현황: (유형 1 이면 적음 / 유형 2a·2b 면 "없음")
- 둘러싼 현 상황 / 맥락: (전 유형 공통 -- 항상 적음. 유형 2b 도 여기는 채운다)

## 문제 + (유형 1) 근본원인 진단
(스텝 2)
- 문제 / 동기: (전 유형 공통 -- 항상 적음)
- 근본원인 진단: (유형 1 전용. 증상 / 가설 / 검증 / 결론. 유형 2a·2b 면 N/A)

## 검토한 방향들
(스텝 3. 방향별 트레이드오프 + 권고)
| 방향 | 가치 | 비용/리스크 | 수명 |
|------|------|------------|------|
| ...  | ...  | ...        | ...  |
- 권고: (어느 방향을 왜 권고하는지)

## 로드맵 (마스터: roadmap.md 참조)
(스텝 4. 청크 상태의 마스터는 roadmap.md. 여기엔 이번 flow 맥락으로 요약 인용)
- [진행] {청크}: (한 줄 요지)
- [예정] {청크}: (한 줄 요지) (의존: ...)
- [미정] {청크}: (한 줄 요지) (재검토 조건: ...)
(미래 [예정]/[미정] 청크는 잠정 -- 미래 flow 소관. 전체 청크 목록·상태는 roadmap.md 가 마스터. [진행] 은 스코프 표식이지 판정 결과가 아니다.)

## 진행 판단 (go / no-go / 미정)
(스텝 5. [진행] 청크에 대한 판단. 셋 중 하나 + 근거)
- go: 진행. 01-requirements 로.
- no-go: 로드맵에서 [기각](사유). [진행] 청크가 첫머리면 전체 멈춤 겸함.
- 미정: 로드맵에서 [미정](재검토 조건). 파이프라인 미진입.
```

- 01-requirements 는 이 핸드오프에서 "유형 / 확정 방향 / 배경·현재상태 / 문제+진단"을 읽고, 로드맵(청크 상태)은 마스터 `roadmap.md` 에서 직접 읽어, 자기 산출물 상단의 "전제" 섹션에 요약 인용한다 (통째 복사가 아니라 핵심 압축).
- 위임 항목([requirements]/[design]/[deferred])과 [잠정] 가정은 전제 인용과 별개로 01-requirements 작업 흐름이 태그별 목적지로 처리한다 (01-requirements 스텝 2). 00-ideation 은 넘기기만 하고, 해소/재라우팅/확정은 01-requirements 소관이다.
- 01-requirements 가 더 깊은 맥락이 필요하면 이 핸드오프 원본을 직접 참조한다. 요약과 원본이 어긋나면 원본을 신뢰한다.

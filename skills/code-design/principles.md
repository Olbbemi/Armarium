# 공통 원칙

모든 파이프라인 단계가 공통으로 참조하는 원칙. (원칙별 적용 범위는 조건부일 수 있다.)

---

## 원칙 1: 대화에서 모호한 표현이 등장하면 반드시 되묻는다

**트리거:** 사용자가 이번 대화에서 하는 모호한 표현 ("대충", "적당히", "알아서" 등). 문서에 이미 적혀 있던 미결 항목은 원칙 4가 다룬다.

**모호함의 예시**
- "빠르게 동작해야 함" -> 구체적인 응답 시간 목표는?
- "보안 신경써줘" -> 어떤 위협 모델? 어떤 데이터 민감도?
- "사용자가 많을 거야" -> 동시 사용자 수, 일일 활성 사용자 수 등 구체 숫자는?
- "기존이랑 비슷하게" -> 기존 어느 부분을 가리키는지?
- "적당히 나눠줘" -> 어떤 기준으로?

**질문 방식**

<FORBIDDEN>
미결 항목이 많아도 한 번에 둘 이상을 묻지 않는다.
</FORBIDDEN>

선택지를 제시할 수 있으면 제시한다 (예: "A안 / B안 / 그 외").

**금지 사항**

<FORBIDDEN>
사용자에게 묻지 않고 "합리적 기본값"이라며 임의 결정하지 않는다.
</FORBIDDEN>

<FORBIDDEN>
"충분히 조사했다"고 자체 판단하고 사용자 확인 없이 넘어가지 않는다.
</FORBIDDEN>

모호한 답변은 되물어 값으로 굳힌 뒤 다음 단계로 넘긴다. 각 결정 단계의 완료 기준이 이 조건을 점검한다.

## 원칙 2: 반복될수록 더 깊이 파고든다

**판단 기준**
- 이번 세션에서 이 도메인을 다루는 게 처음 -> 표준 깊이
- 이미 같은 도메인을 다룬 적이 있고 이번이 두 번째 작업 -> 깊이 +1
- 같은 종류의 버그/이슈/결정이 반복해서 등장 -> 깊이 +2 (근본 원인 조사 모드)

**깊이를 늘린다는 것의 의미**
- 외부 검색의 횟수와 출처 다양성을 늘린다
- 공식 문서까지 web_fetch로 직접 확인한다
- 사용자에게 더 구체적인 질문을 던진다

**정량 단위**
- 구체적 수치(검색 횟수, 출처 개수, 탐색할 케이스 수 등)는 각 단계 스킬이 자기 영역에 맞게 정의한다
- 단계 스킬에 정량 정의가 없으면 사용자에게 묻거나 표준 깊이로 진행한다
- "+1" 의 일반적 의미: 표준 깊이의 행동을 2배 이상 수행 (예: 검색 3회 -> 6회, 출처 2개 -> 3개 이상)
- "+2" 의 일반적 의미: 표준 깊이의 3배 이상 + 근본 원인 추적 모드 (모든 가설 직접 검증, 공식 문서 / RFC / 표준 직접 확인)

반복 작업을 첫 작업과 같은 조사 깊이로 끝내지 않고, "이미 안다"는 판단으로 외부 검색 · 공식 문서 확인을 생략하지 않는다. `01-requirements` · `02-design` 의 완료 기준이 이 깊이 준수를 점검한다.

## 원칙 3: 공란 금지 -- 모든 칸은 명시적으로 채운다

빈 칸은 "사람이 확인하지 않은 칸"으로 해석한다.

**공란 처리 방법**
- 데이터가 있으면 -> 데이터 기록
- 데이터가 없으면 -> N/A 명시
- 항목 자체가 해당 없으면 -> N/A 또는 "없음" 명시
- 피드백 영역에 쓸 말이 없어도 -> N/A 명시

N/A 로 표기한 항목은 사용자 확인을 받는다. 자동 통과시키지 않는다. 각 결정 단계 completion 의 `## N/A 항목 확인` 절과 완료 기준이 이를 점검한다.

## 원칙 4: 보류 -- within-flow 결정 지연은 핸드오프 "열린 보류"로 이어보내고 재개 시점에 해소한다

**정의:** 보류(= TBD, to be determined)는 의식적으로 미뤄둔 미결 *결정*이다. **이 flow 안에서** 뒤따르는 결정 단계에 정하기로 미루는 것이며(within-flow 결정 지연), flow 를 넘기지 않는다. 문서 한 칸 안의 작은 미결은 인라인 마커 `(TBD)` 로 표기한다.

- **원칙 1 과의 구분:** 원칙 1 은 이번 대화에서 막 등장한 모호 표현을 즉시 되묻는 것. 보류는 이미 "미루기로 결정"된 항목이다.
- **원칙 3 과의 양립:** 결정은 미뤄도 되지만 그 사실을 핸드오프 "열린 보류"에 기록한다. 칸을 빈 채로 두는 것(원칙 3 위반)과 다르다.
- **미래 청크 일과의 구분:** "이번 flow 에서 아예 안 하고 다음 flow 로"는 보류가 아니라 로드맵 `[예정]`/`[미정]` 청크(범위 결정 -- `cross-flow.md` 참조)다. 보류는 이번 flow 안에서 반드시 해소된다.

### 어디에 기록하나 -- 별도 파일 없음

보류는 별도 파일을 만들지 않고, 그 단계 **핸드오프의 "열린 보류" 섹션**에 표로 남긴다.

```
## 열린 보류
미해소 결정을 추적한다. 재개 시점 단계에서 해소(결정) 또는 로드맵으로 escalation 한다.

| # | 항목 | 사유 | 재개 시점 | 출처 |
|---|------|------|----------|------|
```

- **이어보냄(pass-through):** 다음 단계는 받은 열린 보류 중 재개 시점이 자기 단계가 아닌 것을 자기 핸드오프 "열린 보류"에 **그대로 실어 넘긴다**(누적). 출처는 처음 미룬 단계를 가리킨다.
- 이력은 핸드오프의 git 이력(브랜치 아카이브 -- 원칙 5)이 보존한다.
- 02-design 의 표만 칸 구성이 다르다. 최종 게이트라 미룬 항목이 아니라 **해소 결과**를 적기 때문이다.
  - `사유` · `재개 시점` 대신 `처리(해소 결정 / 로드맵 escalation)` 칸을 쓴다.
  - 헤딩도 `## 열린 보류 (해소 기록)` 으로 구분한다.

**대상 단계 (결정 단계 전용)**
- 발생: 00-ideation / 01-requirements / 02-design. 재개(해소): 01-requirements / 02-design. **최종 게이트 = 02-design** -- 02-design 을 닫을 때 열린 보류가 0 이어야 한다.
- **03-implementation 진입 시 열린 보류 = 0** (모든 결정이 02-design 까지 확정). 03-implementation·04-verification 은 보류 메커니즘 밖이다 -- 03-implementation 진행 중 갈림길은 보류가 아니라 원칙 1 / G4 로 그 자리에서 확인한다.

**처리 절차**

- **발생 시** -- 미루는 결정을 핸드오프 "열린 보류"에 사유 · 재개 시점 · 출처와 함께 등재한다. 문서 해당 지점에는 `(TBD)` 마커를 남길 수 있다.
- **재개 시점 단계에서** -- 재개 시점이 자기 단계인 열린 보류를 사용자 확인으로 **해소**한다.
  - 해소 = 결정을 내려 값을 채우고 `(TBD)` 를 지운 뒤 열린 보류에서 뺀다.
  - 못 정하면 사용자 확인 하에 **로드맵 `[예정]`/`[미정]` 로 escalation** 한다 (`cross-flow.md` 참조).
- **게이트** -- 각 결정 단계 완료 기준이 "재개 시점 = 자기 단계인 열린 보류가 남아 있으면 완료 불가"를 강제한다. 02-design 게이트가 최종이다.

모호한 칸을 "나중에 채운다"로 두지 않는다. 미루는 결정은 반드시 핸드오프 "열린 보류"에 등재한 뒤 다음 단계로 넘긴다.

### escalation 사유에는 실측 선행이 포함된다

판단에 필요한 사실을 아직 재보지 않았을 때는 **크기**로 가른다. 측정 결과가 아니라 측정 방법이 서 있는지가 기준이다.

- 재는 방법이 이미 서 있다 -> escalation 이 아니다. 그 자리에서 재고 결과를 자기 핸드오프에 남긴 뒤 계속 간다.
- 재는 방법부터 세워야 한다 -> 로드맵에 **선행 청크**로 올리고, 이 청크는 그 flow 가 끝날 때까지 멈춘다.
  - 멈춘 청크는 브랜치를 유지한다. 선행 flow 가 끝나 그 사실이 cross-flow 층에 오르면 이어서 진행하므로 같은 flow 다.
  - 이 멈춤은 원칙 4 가 정의하는 보류(미결 결정)가 아니라 청크 단위의 대기다.

잰 값을 어디에 남길지는 이 판단과 무관하게 갈린다. 이번 flow 가 코드를 바꾼 뒤에도 참인 사실이면 cross-flow 층으로 올리고, 아니면 그 단계 핸드오프에 둔다 (`cross-flow.md` 참조).

<FORBIDDEN>
열린 보류를 사용자 확인 없이 임의 해석해 해소하지 않는다.
</FORBIDDEN>

<FORBIDDEN>
열린 보류를 사용자 확인 없이 로드맵으로 escalation 하지 않는다.
</FORBIDDEN>

## 원칙 5: 단계 산출물 저장 정책

핸드오프(다음 단계로 넘기는 산출물)도 같은 경로에 두되, 그 형태는 단계마다 다르다 -- 아래 "핸드오프는 단계별로 형태가 다르다" 참조.

### 저장 경로

    {프로젝트 루트}/code-design/<브랜치 슬러그>/{단계}/   (within-flow 산출물)
    {프로젝트 루트}/code-design/{cross-flow 파일}         (cross-flow 층)

- `{프로젝트 루트}` 는 git 최상위(= CWD, code-design 은 루트에서만 실행 -- overview "프로젝트 루트 확인" 참조)
- `<브랜치 슬러그>` 는 이 작업(= 이 flow)을 진행하는 git 브랜치 이름을 슬러그화한 것(`/` 를 `_` 로 치환, 예: `feature/x` -> `feature_x`) -- 브랜치가 곧 버전 키이고 그 슬러그가 폴더 이름이다. within-flow 산출물(핸드오프·체크리스트·검증 틀)을 이 아래에 브랜치별로 격리 누적한다.
- `{단계}` 는 단계 디렉토리 이름 (예: `00-ideation`, `01-requirements`, `02-design`)
- cross-flow 층 파일은 브랜치 폴더 밖 code-design 루트에 flat 하게 둔다. 파일 목록과 각 파일의 규격은 `skills/code-design/cross-flow.md` 가 단일 출처다.

### 파일 패턴

| 종류 | 파일명 | 갱신 방식 | 위치 / 대상 단계 |
|------|--------|----------|----------|
| 체크리스트 | `checklist.md` | 단일 -- 핸드오프 뒤 · 제시 전 파일로 작성, 회차마다 갱신(이력은 git 이 보존), 승인 시 사용자 서명 + Claude 시각 스탬프 | `<브랜치 슬러그>/{단계}/`, 전 단계 (00-ideation ~ 04-verification) |
| 핸드오프 | `handoff.md` | 단일 -- checklist 보다 먼저 작성, 갱신 시 사용자 확인 | `<브랜치 슬러그>/{단계}/`, 핸드오프가 문서인 단계만 (아래 참조) |
| cross-flow 층 | `roadmap.md` · `architecture.md` · `decisions.md` · `qa-checklist.md` | flow 를 넘어 누적 -- 갱신 규칙은 `cross-flow.md` | `code-design/` 루트 (flow 공유) |

체크리스트와 핸드오프의 역할·내용 계약은 아래 세 소절에서 정한다 -- "역할 분담", "결정 요약은 자립한다", "`handoff.md` 는 결정 + 근거까지".

### 역할 분담 -- 갈림은 "누가 읽나"가 아니라 "무엇에 사인하나"

두 문서는 독자로 갈리지 않는다. `handoff.md` 는 그 단계의 **산출물 실물**이고, `checklist.md` 는 그 실물에 사인하는 **사인오프 문서**다.

사용자는 checklist 만 읽고도 승인할 수 있어야 하지만, 더 보고 싶으면 handoff 를 연다. 그래서 handoff 도 사람이 읽을 수 있는 형태로 쓴다(원칙 10).

**`handoff.md` -- 산출물 실물**

- 그 단계가 만든 것 전부를 담는다. 각 단계의 `## 산출물 형식` 템플릿이 곧 이 파일의 내용이다.
- 사람이 읽는 부분(설계 · 명세 · 흐름)과 Claude 가 읽는 메타 정보(전제 요약 · 범례 · 출처 표기)를 섞지 않는다. 메타 정보는 `## 전제` 한 절에 몰고, 나머지 절은 사람이 읽는 순서로 둔다.
- 무엇을 담고 무엇을 빼는지는 아래 "`handoff.md` 는 결정 + 근거까지" 가 정한다.

**`checklist.md` -- 사인오프 문서**

- 상단 `## 결정 요약` = 그 단계가 내린 **결정의 값**. 사용자는 이 단락만 읽고 사인오프할 수 있어야 한다.
- 하단 `## 완료 기준` = **절차 점검**(규격대로 했나). 결정 요약과 겹치지 않는다 -- 요약은 "무엇을 정했나", 체크박스는 "규격대로 정했나"에 답한다.
- 보장 규칙: `handoff.md` 안의 "사용자 승인이 필요한 항목"은 빠짐없이 결정 요약에 값으로 등장한다. 근거 · 외부 출처 · 협의 과정처럼 승인 단위가 아닌 것은 `handoff.md` 에만 둔다.

### 결정 요약은 자립한다 -- 출처가 값을 대신하지 못한다

각 줄은 `{항목} = {값} ({출처})` 꼴로 쓴다. 예: `저장소 = PostgreSQL (decisions.md #12)`

- **출처를 지워도 값이 읽혀야 한다.** 출처만 있고 값이 없는 줄(`저장소 = handoff.md 참조`)은 미충족이다.
- 출처는 항목 성격으로 갈린다.
  - 설계 결정 -> `decisions.md`
  - 시스템 제약 · 기술 스택 -> `architecture.md`
  - 나머지 -> 그 단계의 `handoff.md`
- 판정 규칙: 값과 출처가 어긋나면 **출처가 맞다**. 결정 요약은 사인오프용 발췌이고 값의 소유자가 아니다.

### 단계 전환 규칙 -- checklist.md 가 사인오프 문서다

`checklist.md` 는 사용자가 보는 문서일 뿐 아니라 **사인오프하는 문서**다. `## 완료 기준` 의 `[x]` 는 완료 기준 충족 여부이고, 승인 증거는 사용자가 checklist.md 를 직접 편집한 흔적이다 -- 이 둘은 별개다. 이 절이 단계 전환·완료 기준 검증·승인 서명 절차의 단일 출처다.

#### 제시 순서 -- 핸드오프 먼저, 그다음 checklist

`handoff.md` 를 먼저 쓰고, 그 내용에서 발췌해 `checklist.md` 를 만든다.

    작업 -> handoff.md -> checklist.md -> 완료 기준 동반 검증 -> 사용자 서명 -> 다음 단계

- 순서가 뒤집히면 결정 요약이 아직 없는 파일을 출처로 가리키게 되고, 아래 "완료 기준 동반 검증"의 "실제 저장 위치·근거" 칸도 채울 수 없다.
- 서명 없는 핸드오프가 파일로 존재해도 승인 게이트는 그대로 선다. 다음 단계는 서명 없이 진입하지 못하고, 진입 판정도 checklist 의 서명으로만 완료를 인정한다(overview "단계 진입 판단").
- checklist.md 는 사용자에게 제시하기 전에 파일로 존재해야 한다. 터미널에 먼저 찍고 나중에 파일로 옮기지 않는다.

각 단계 종료 시 checklist.md 는 아래 골격을 갖는다. **이 골격이 단일 출처다** -- 각 단계 파일은 골격을 다시 그리지 않고 `## 결정 요약` 에 넣을 항목과 `## 완료 기준` 항목만 정의한다. 나머지 세 절의 문안은 이 자리에서만 고친다.

```
## 결정 요약   (사용자는 이 단락만 보면 됩니다)
(각 줄에 값의 출처를 단다. 값과 출처가 어긋나면 출처가 맞다 -- 아래 "결정 요약은 자립한다")
- {항목} = {값} ({출처})

## 완료 기준
- [x] 항목 1 -- {근거 위치}
- [x] 항목 2 -- {근거 위치}

## N/A 항목 확인
다음 항목이 N/A로 표기됨. 정말 해당 없음이 맞는지 확인 부탁드립니다:
- {항목}: N/A ({사유})
(N/A 항목이 없으면 "없음"으로 표기)

## 피드백
<!-- 피드백이 있으면 이 주석을 지우고 내용을 적으세요.
     없으면 이 주석을 지우고 N/A 로 확정하세요.
     주석이 남아 있으면 아직 확인 안 한 것으로 봅니다. -->

## 사용자 승인
<!-- 승인하려면 이 주석 줄을 지우고 아래에 "승인" 한 줄을 직접 남기세요.
     이 주석이 남아 있으면 미승인입니다 -- Claude 는 이 줄을 대신 지우지 않습니다. -->
<!-- 승인 확인 시각(Claude 가 승인 감지 후 채움): -->
```

`## 피드백` · `## 사용자 승인` 두 절을 주석 가이드로 준비하는 것은 골격의 일부이므로 단계별 완료 기준 항목으로 다시 세우지 않는다 -- 준비가 안 되면 아래 승인 게이트가 그 자리에서 막는다.

#### 완료 기준 동반 검증

항목을 한 개씩 왕복하면 느리므로 **약 5개씩 배치**로 묶어 아래 표로 제시하고, 배치마다 사용자와 확인하며 넘어간다.

```
| # | 완료 기준 항목 | 실제 저장 위치·근거 | 판정 |
|---|----------------|---------------------|------|
| 1 | ...            | `<파일>:<섹션>` 에 ... 로 저장됨 | [x] |
| 2 | ...            | (근거 없음 -- 미충족)            | [ ] |
```

"실제 저장 위치·근거" 칸은 그 항목이 충족됐다는 근거가 **실제로 어디에 있는지**를 가리킨다.

- 이 칸이 실제 위치로 채워질 때만 `[x]` 다. 근거 없이 체크박스만 채우는 것은 허위 표기다.
- 아직 만들지 않은 파일은 위치가 아니다. 그 칸에 적힌 경로는 그 시점에 실재해야 한다.
- 표에서 확인한 근거는 checklist.md 의 해당 완료 기준 항목에도 남겨(항목 뒤 `-- 근거`) 파일만 봐도 자립하게 한다.

배치 검증 중 근거가 비는(미충족) 항목이 나오면 성격에 따라 처리한다.

- 명세된 빈칸을 메우는 수준(공통 원칙 1 / G4 로 그 자리에서 채울 수 있는 것)이면, 실제 산출물/섹션을 채워 근거를 만든 뒤 그 위치를 표에 찍고 `[x]` 로 넘어간다.
- 사용자 결정이 필요한 항목이면 임의로 채우지 않고, 갭을 사용자에게 알려 확인받는다(공통 원칙 1). 결정이 미뤄지면 열린 보류로 처리한다(원칙 4).

모든 배치의 `[x]` 가 실제 근거로 뒷받침된 뒤에 승인 서명(아래)으로 간다.

#### 승인 서명 = 사용자의 직접 편집

`[x]` 는 완료 기준 충족 여부일 뿐(동반 검증으로 근거까지 확인됐더라도) 다음 단계로 넘어가도 좋다는 승인은 아니다. 승인 증거는 **사용자가 checklist.md 를 직접 편집한 흔적**이다.

- `## 피드백` · `## 사용자 승인` 두 칸은 처음엔 `<!-- -->` 주석(가이드)으로 채워 둔다 = 미확인 상태.
- 사용자가 그 주석을 지우고 내용을 남기면 = 사용자가 파일을 직접 손댄 것 = 확인/서명 (보지 않고 지웠더라도 그건 사용자 책임).
- 두 칸이 **모두** 주석 해제되어야 진행한다 (AND 게이트). 하나라도 주석이 남아 있으면 미승인으로 보고 재요청한다.

| 사용자 승인 | 피드백 | 판정 |
|-------------|--------|------|
| 주석 | 주석 | 미승인 -- 재요청 |
| 주석 | 해제 | 미승인 -- (피드백 있으면 반영 후 재제시) |
| 해제 | 주석 | 미승인 -- 피드백 칸도 정리(N/A든 내용이든) 요청 |
| 해제 | 해제 | 승인 -> 다음 단계 진입 |

<FORBIDDEN>
Claude 는 `## 피드백` · `## 사용자 승인` 의 주석을 스스로 지우지 않는다.
</FORBIDDEN>

<FORBIDDEN>
Claude 는 승인 · 피드백 내용을 사용자 대신 써넣지 않는다.
</FORBIDDEN>

승인이 확인되면(두 칸 모두 주석 해제) Claude 는 `date '+%Y-%m-%d %H:%M:%S'` 결과를 `## 사용자 승인` 의 "승인 확인 시각" 자리에 채워 그 시점을 픽스하고 다음 단계로 넘어간다.<br>
이 시각은 Claude 가 승인을 감지해 스탬프한 시점이며(사용자가 실제로 주석을 지운 시점과 미세한 갭이 있을 수 있음), 실제 편집 시점은 git/파일 이력이 보존한다.<br>
승인 확인 시각을 채우는 것은 위 `<FORBIDDEN>` 의 예외가 아니다 -- Claude 는 시각만 스탬프할 뿐 사용자 서명 자체(주석 해제)는 건드리지 않는다.

### 핸드오프는 단계별로 형태가 다르다

핸드오프는 한 단계가 다음 단계로 넘기는 것이다. 모든 단계가 같은 `handoff.md` 문서를 내는 게 아니라, 그 단계의 자연스러운 산출물이 그 역할을 한다.

- **00-ideation · 01-requirements · 02-design** -> `handoff.md` 문서 (구상 방향 / 요구사항 명세 / 설계). 다음 단계가 이 문서를 입력으로 읽는다.
- **03-implementation** -> 별도 `handoff.md` 를 만들지 않는다.
  - 04-verification 으로 넘기는 핸드오프는 코드(소스 트리) + 검증 산출물 틀이다.
  - 설계 이탈은 G12 에 따라 02-design `handoff.md` 에 동기화하므로 별도 핸드오프 문서가 필요 없다.
- **04-verification** -> 하류 단계가 없어 핸드오프가 필수가 아니다. 04-verification 뒤에 단계가 생기면 그 단계에 맞는 형태로 둘 수 있고, 반드시 `handoff.md` 형식일 필요는 없다.

**핸드오프(`handoff.md`) 갱신 절차** (00-ideation / 01-requirements / 02-design 에 적용)
- 파일이 없으면 -> 새로 작성 (확인 없이)
- 파일이 있으면 -> 사용자에게 "덮어쓸까요?" 확인
  - OK -> 갱신
  - NO -> 사용자에게 처리 방향을 다시 묻는다

<FORBIDDEN>
핸드오프를 사용자 확인 없이 덮어쓰지 않는다.
</FORBIDDEN>

### `handoff.md` 는 결정 + 근거까지, 군더더기는 뺀다

`handoff.md` 는 다음 단계 실행에 필요한 만큼 자세히 적되, 실행에 안 쓰이는 내용으로 컨텍스트를 늘리지 않는다.

- 결정의 "왜"(근거)는 한 줄로 남긴다 -- 하류 단계의 재논쟁을 막는다.
- 협의 **과정 전문**(사용자 의견 / 반문 / 합의 스텝)은 `handoff.md` 에 넣지 않는다. 그 이력은 git(checklist 회차)이 보존한다.
- 외부 출처는 본문 여기저기 두지 말고 하단 "출처" 부록에 `링크 + 한 줄 결론` 쌍으로 모은다. 결정을 실제로 뒷받침한 출처만 남긴다 -- 맨 링크 나열은 저밀도라 피한다.

### 버전은 브랜치별 아카이브, 이어지는 것은 cross-flow 층

within-flow 산출물(핸드오프·체크리스트·검증 틀)은 이 flow 를 진행하는 브랜치 폴더 `code-design/<브랜치 슬러그>/` 아래에 둔다. 새 작업은 새 브랜치에서 진행하므로(한 작업 = 한 브랜치 = 한 버전), 산출물이 브랜치별로 자연히 격리·누적된다. 브랜치명이 곧 버전 키라, 과거 flow 의 설계 문서가 버전별로 브라우징 가능하게 남는다(git diff 로만 보는 게 아니라 폴더로 열린다).

flow 를 넘어 이어지는 것은 cross-flow 층 파일 넷뿐이다. 브랜치 폴더 밖 루트에 두고 커밋한다(규격은 `cross-flow.md`). 새 flow 의 입력은 자기 브랜치 폴더 + cross-flow 층으로 닫혀 있어, flow 격리가 구조로 강제된다.

<FORBIDDEN>
새 flow 에서 다른 브랜치 폴더의 핸드오프·체크리스트를 입력으로 참고하지 않는다.
</FORBIDDEN>

#### 병행 불가

같은 청크에 대해 둘 이상의 flow(브랜치)를 동시에 진행하지 않는다.

사용자가 별도 세션에서 강제로 병행 실행해 발생하는 충돌은 사용자 책임 범위로 둔다.

## 원칙 6: 코드 분석 산출물(facet)이 있으면 우선 활용 (선택)

기존 코드 구조를 파악해야 하는 단계(00-ideation · 01-requirements · 02-design · 03-implementation)에서, 프로젝트에 코드 분석 산출물(facet)이 있으면 수작업 탐색보다 먼저 1차 입력으로 삼을 수 있다. 필수는 아니다.

facet 은 코드에서 파생된 분석 문서다 -- 코드와 어긋나 보이면 코드를 신뢰한다(stale 가능성). **facet 의 유무·종류·저장 경로·갱신 정책은 이 스킬이 정의하지 않고 각 프로젝트의 `CLAUDE.md` 를 따른다** -- 어떤 도구가 어디에 facet 을 남기는지는 프로젝트마다 다른 연결 방식이라, 범용 스킬에 박으면 어긋난다. 이 스킬은 "있으면 참고한다"는 원칙만 둔다.

**절차**
- 프로젝트 `CLAUDE.md` 가 가리키는 facet 경로가 있으면 "분석 산출물(facet)을 이번 작업에 활용할까요?"를 사용자에게 한 번 묻는다
- 그 경로에 여러 벌(예: 브랜치별)이 나란히 있으면 어느 것을 쓸지 사용자에게 확인받는다
- 활용하기로 하면 그 경로에 **실제로 있는** facet 문서를 1차 입력으로 삼는다 -- 특정 facet 이름을 여기 박아두지 않고 있는 파일을 그대로 쓴다. 수작업 도구는 facet 이 없거나 특정 지점을 더 깊이 파야 할 때 보완으로 쓴다

<FORBIDDEN>
facet 산출물의 활용 여부를 사용자 확인 없이 정하지 않는다.
</FORBIDDEN>

## 원칙 7: 단계 내 진행도 -- 구조적 체크포인트가 여럿인 단계는 TaskCreate 로 시각화한다

각 단계는 여러 턴에 걸치므로, 내부에 구조적 체크포인트가 여럿인 단계는 TaskCreate 로 단계 내 진행도를 시각화한다. 공통 규칙은 다음과 같다.

- 태스크는 그 단계의 구조적 체크포인트지 대화 턴이 아니다. 사용자와의 논의 / 검색 / 피드백 왕복은 해당 체크포인트 task 안에서 처리하고, 턴마다 목록을 바꾸지 않는다.
- 체크포인트에 진입하면 in_progress, 그 체크포인트의 완료 조건이 충족되면 completed 로 닫는다.
- 사용자 확인 게이트는 확인 요청 직전 completed 로 닫고, 응답 후 다음 체크포인트를 in_progress 로 연다.
- 체크포인트가 사실상 하나뿐이거나 fast-path 로 가볍게 통과하는 단계(예: 00-ideation 의 fast-path)는 task 를 만들지 않는다.

구체적 체크포인트 목록은 각 단계 파일이 정의한다. 도입 단계는 02-design(고정 체크포인트 시퀀스), 03-implementation(진입 + 동적 슬라이스 루프), 04-verification(고정 체크포인트 시퀀스), 05-coverage(고정 체크포인트 시퀀스)이다.

## 원칙 8: 피드백 처리 -- 반문 -> 협의 -> 기록 -> 재제시

체크리스트를 제시한 뒤 사용자가 "피드백" 섹션에 남긴 입력을 처리하는 공통 절차다. 결정 단계(00-ideation / 01-requirements / 02-design)가 이 절차를 따른다. 단계별 특이점(자기 도메인의 자동 수용 금지 대상, 협의 과정·사유를 남기는 위치)은 각 단계 파일이 지정한다.

**처리 절차**
1. 반문한다 -- 왜 그렇게 판단했는지, 어떤 영향이 있는지 확인.
2. 협의한다.
3. 기록한다 -- 합의 결과를 산출물 결정값에 반영하고, 협의 과정·사유는 그 단계가 지정한 위치에 남긴다.
4. 합의된 변경을 산출물에 반영한 뒤 재제시한다.

**자동 수용 금지**

각 단계는 자기 도메인의 구조적 변경 요청도 자동 수용 금지에 추가한다(각 단계 파일이 지정).

<FORBIDDEN>
사용자 피드백을 협의 없이 자동 수용하지 않는다.
</FORBIDDEN>

<FORBIDDEN>
합의에 도달하기 전에 피드백 내용을 산출물에 반영하지 않는다.
</FORBIDDEN>

## 원칙 9: 산출물은 파이프라인 코드값을 자체 정의한다

**정의**
- 파이프라인이 약속한 코드값 -- 유형(`1`/`2a`/`2b`), 청크 상태 플래그(`[완료]`/`[진행]`/`[예정]`/`[미정]`/`[기각]`) -- 은 값만으로는 뜻이 안 통하고 상류 단계의 정의를 봐야 풀린다.
- 이런 코드값을 산출물에 쓸 때는 그 값을 쓰는 산출물 안에 뜻을 한 줄 인라인 정의로 붙인다.
- 핸드오프는 다음 단계가 단독으로 인수하는 파일이라(원칙 5) 이 자체완결이 특히 중요하다.

**대상과 비대상**
- 대상: 상류 정의를 봐야 풀리는 파이프라인 코드값(유형, 청크 플래그).
- 비대상: 그 프로젝트의 도메인 내용과 보편 기술어. 이건 인라인 정의 대상이 아니다 -- 억지로 풀어 쓰면 오히려 장황해진다.

**정의 어긋남 방지 -- 복제가 아니라 한 줄 정의**
- 정의 전문을 복사하지 않고 한 줄 요약만 붙이며, 상세 정의의 단일 출처(유형은 00-ideation, 청크 플래그는 `cross-flow.md`)를 함께 가리킨다.
- 전제 인용이 이미 따르는 "통째 복사 아님, 상세는 원본, 어긋나면 원본 신뢰" 관례(원칙 5)와 같은 방식이다.

## 원칙 10: 산출물 작성 형식 -- 사람이 훑을 수 있게, 사실은 그대로

이 원칙의 대상은 파이프라인이 만드는 **산출물**(`handoff.md` · `checklist.md` · cross-flow 층 파일)이다. 각 단계의 `## 산출물 형식` 템플릿도 이 형식을 따라 짜서, 채워진 결과가 자연히 이 형태가 되게 한다.

가독성을 해치는 것은 분량이 아니라 **한 줄에 담는 사실의 개수**다. 한 줄에 여러 사실을 이어 붙이면 사용자는 훑지 못하고, Claude 는 부분만 인용하지 못한다. 같은 양을 표나 중첩 불릿으로 재배치하면 양쪽이 함께 나아진다.

**한 줄에 담는 사실의 개수**

- 한 줄 = 한 사실. 콤마 · 슬래시로 여러 사실을 이어 붙이지 않는다.
- 같은 축의 항목이 셋 이상이면 표로 낸다.
- 표로 안 되는 것은 중첩 불릿으로 층위를 드러낸다.
  - 항목마다 칸 구성이 다르거나 깊이가 제각각이라 열이 안 서는 경우다.
  - 평평한 나열로 뭉개지 않는다. 무엇이 무엇에 딸린 것인지가 사라진다.

**한 줄 안**

- 값이 앞, 근거 · 출처는 뒤. 사용자가 왼쪽만 훑어도 결정이 읽혀야 한다.
- `--` 부연은 그 줄이 한 줄에 담기는 선까지만 쓴다.
  - 넘으면 중첩 불릿 한 단 아래로 내린다.
  - 한 줄에 `--` 를 두 번 쓰지 않는다.

**관계:** 의존 · 흐름 · 상태 전이는 다이어그램으로 낸다. 산문으로 서술하지 않는다.

**총량:** 짧게 만들 때 사실을 지우지 않고 형태를 바꿔 줄인다 -- 하류 단계가 이 문서를 유일한 입력으로 읽기 때문이다.

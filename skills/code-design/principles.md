## 원칙 1: 대화에서 모호한 표현이 등장하면 반드시 되묻는다

**트리거:** 사용자가 이번 대화에서 하는 모호한 표현 ("대충", "적당히", "알아서" 등). 문서에 이미 적혀 있던 미결 항목은 원칙 4가 다룬다.

<PENETRATE>
사용자의 표현이 모호하면 추측하지 않고 즉시 질문한다.
</PENETRATE>

<RICOCHET>
"충분히", "적절히", "합리적 기본값" 같은 회피성 표현으로 모호함을 덮고 넘어가지 않는다.
</RICOCHET>

**모호함의 예시:**
- "빠르게 동작해야 함" -> 구체적인 응답 시간 목표는?
- "보안 신경써줘" -> 어떤 위협 모델? 어떤 데이터 민감도?
- "사용자가 많을 거야" -> 동시 사용자 수, 일일 활성 사용자 수 등 구체 숫자는?
- "기존이랑 비슷하게" -> 기존 어느 부분을 가리키는지?
- "적당히 나눠줘" -> 어떤 기준으로?

**질문 방식:**

<PENETRATE>
한 번에 1개만 묻는다. 미결 항목이 많아도 대화에서는 하나씩만 꺼낸다.
</PENETRATE>

선택지를 제시할 수 있으면 제시한다 (예: "A안 / B안 / 그 외").

<PENETRATE>
사용자 답변이 또 모호하면 명확해질 때까지 다시 되묻는다.
</PENETRATE>

**금지 사항:**

<RICOCHET>
사용자에게 묻지 않고 "합리적 기본값"이라며 임의 결정하지 않는다.
</RICOCHET>

<RICOCHET>
"충분히 조사했다"고 자체 판단하고 사용자 확인 없이 넘어가지 않는다.
</RICOCHET>

<RICOCHET>
사용자 답변이 모호한 채로 다음 단계에 진입하지 않는다.
</RICOCHET>

## 원칙 2: 반복될수록 더 깊이 파고든다

<PENETRATE>
같은 도메인 / 같은 종류의 작업이 반복되면 조사 깊이를 늘린다.
</PENETRATE>

**판단 기준:**
- 이번 세션에서 이 도메인을 다루는 게 처음 -> 표준 깊이
- 이미 같은 도메인을 다룬 적이 있고 이번이 두 번째 작업 -> 깊이 +1
- 같은 종류의 버그/이슈/결정이 반복해서 등장 -> 깊이 +2 (근본 원인 조사 모드)

**깊이를 늘린다는 것의 의미:**
- 외부 검색의 횟수와 출처 다양성을 늘린다
- 공식 문서까지 web_fetch로 직접 확인한다
- 사용자에게 더 구체적인 질문을 던진다

**정량 단위:**
- 구체적 수치(검색 횟수, 출처 개수, 탐색할 케이스 수 등)는 각 단계 스킬이 자기 영역에 맞게 정의한다
- 단계 스킬에 정량 정의가 없으면 사용자에게 묻거나 표준 깊이로 진행한다
- "+1" 의 일반적 의미: 표준 깊이의 행동을 2배 이상 수행 (예: 검색 3회 -> 6회, 출처 2개 -> 3개 이상)
- "+2" 의 일반적 의미: 표준 깊이의 3배 이상 + 근본 원인 추적 모드 (모든 가설 직접 검증, 공식 문서 / RFC / 표준 직접 확인)

**금지 사항:**

<RICOCHET>
반복 작업인데 첫 작업과 같은 깊이로 종료하지 않는다.
</RICOCHET>

<RICOCHET>
"이미 안다"고 판단해 외부 검색 / 공식 문서 확인을 생략하지 않는다.
</RICOCHET>

<RICOCHET>
깊이 +2 상황(같은 이슈 반복 등장)에서 +1 수준 조사로 종료하지 않는다.
</RICOCHET>

## 원칙 3: 공란 금지 -- 모든 칸은 명시적으로 채운다

<PENETRATE>
산출물의 모든 섹션과 체크리스트의 모든 영역을 명시적으로 채운다.
</PENETRATE>

빈 칸은 "사람이 확인하지 않은 칸"으로 해석한다.

**공란 처리 방법:**
- 데이터가 있으면 -> 데이터 기록
- 데이터가 없으면 -> N/A 명시
- 항목 자체가 해당 없으면 -> N/A 또는 "없음" 명시
- 피드백 영역에 쓸 말이 없어도 -> N/A 명시

<PENETRATE>
N/A 항목을 통과시키기 전에 완료 기준의 "N/A 항목 확인" 단계에서 사용자에게 명시적 확인을 받는다.
</PENETRATE>

**금지 사항:**

<RICOCHET>
빈 칸을 N/A 명시 없이 그대로 두지 않는다.
</RICOCHET>

<RICOCHET>
N/A 항목을 사용자 확인 없이 자동 통과시키지 않는다.
</RICOCHET>

<RICOCHET>
모호한 칸을 "나중에 채운다"로 보류하고 다음 단계에 진입하지 않는다.
</RICOCHET>

## 원칙 4: 보류 -- in-run 결정 지연은 핸드오프 "열린 보류"로 릴레이하고 재개 시점에 해소한다

**정의:** 보류(= TBD, to be determined)는 의식적으로 미뤄둔 미결 *결정*이다. **이 run 안에서** 뒤따르는 결정 단계에 정하기로 미루는 것이며(in-run 결정 지연), run 을 넘기지 않는다. 문서 한 칸 안의 작은 미결은 인라인 마커 `(TBD)` 로 표기한다.

- **원칙 1 과의 구분:** 원칙 1 은 이번 대화에서 막 등장한 모호 표현을 즉시 되묻는 것. 보류는 이미 "미루기로 결정"된 항목이다.
- **원칙 3 과의 양립:** 결정은 미뤄도 되지만 그 사실을 핸드오프 "열린 보류"에 기록한다. 칸을 빈 채로 두는 것(원칙 3 위반)과 다르다.
- **미래 chunk 일과의 구분:** "이번 run 에서 아예 안 하고 다음 flow 로"는 보류가 아니라 로드맵 `[예정]`/`[미정]` 청크(범위 결정 -- overview 참조)다. 보류는 이번 run 안에서 반드시 해소된다.

**어디에 기록하나 -- 별도 파일 없음:**
보류는 별도 파일을 만들지 않고, 그 단계 **핸드오프의 "열린 보류" 섹션**에 표로 남긴다.

    ## 열린 보류
    미해소 결정을 추적한다. 재개 시점 단계에서 해소(결정) 또는 로드맵으로 escalation 한다.

    | # | 항목 | 사유 | 재개 시점 | 출처 |
    |---|------|------|----------|------|

- **릴레이(pass-through):** 다음 단계는 받은 열린 보류 중 재개 시점이 자기 단계가 아닌 것을 자기 핸드오프 "열린 보류"에 **그대로 실어 넘긴다**(누적). 출처는 처음 미룬 단계를 가리킨다.
- 이력은 핸드오프의 git 이력(브랜치 아카이브 -- 원칙 5)이 보존한다.

**대상 단계 (결정 단계 전용):**
- 발생: 00-ideation / 01-requirements / 02-design. 재개(해소): 01-requirements / 02-design. **최종 게이트 = 02-design** -- 02-design 을 닫을 때 열린 보류가 0 이어야 한다.
- **03-implementation 진입 시 열린 보류 = 0** (모든 결정이 02-design 까지 확정). 03-implementation·04-verification 은 보류 메커니즘 밖이다 -- 03-implementation 진행 중 갈림길은 보류가 아니라 원칙 1 / G4 로 그 자리서 확인한다.

**처리 절차:**
- **발생 시** -- 미루는 결정을 핸드오프 "열린 보류"에 사유·재개 시점·출처와 함께 등재한다. 문서 해당 지점에는 `(TBD)` 마커를 남길 수 있다.
- **재개 시점 단계에서** -- 재개 시점이 자기 단계인 열린 보류를 사용자 확인으로 **해소**한다(결정 -> 값 채우고 `(TBD)` 제거, 열린 보류에서 뺌). 못 정하면 사용자 확인 하에 **로드맵 `[예정]`/`[미정]` 로 escalation** 한다(다음 flow 로 -- overview 로드맵 참조).
- **게이트** -- 각 결정 단계 완료 기준이 "재개 시점 = 자기 단계인 열린 보류가 남아 있으면 완료 불가"를 강제한다. 02-design 게이트가 최종이다.

<PENETRATE>
결정을 미루면 핸드오프 "열린 보류"에 사유·재개 시점·출처와 함께 등재한다.
</PENETRATE>

<PENETRATE>
재개 시점 단계에서 그 열린 보류를 사용자 확인으로 해소하거나 로드맵으로 escalation 하며, 02-design 을 닫을 때 열린 보류를 0 으로 만든다.
</PENETRATE>

**금지 사항:**

<RICOCHET>
보류를 핸드오프 "열린 보류"에 기록하지 않고 조용히 넘기지 않는다.
</RICOCHET>

<RICOCHET>
열린 보류를 사용자 확인 없이 임의 해석해 해소하거나, 확인 없이 로드맵으로 escalation 하지 않는다.
</RICOCHET>

<RICOCHET>
열린 보류를 03-implementation 이후로 넘기지 않는다.
</RICOCHET>

## 원칙 5: 단계 산출물 저장 정책

<PENETRATE>
모든 단계는 완료 기준 기록(체크리스트)을 정해진 경로에 정해진 패턴으로 저장한다.
</PENETRATE>

핸드오프(다음 단계로 넘기는 바통)도 같은 경로에 두되, 그 형태는 단계마다 다르다 -- 아래 "핸드오프는 단계별로 형태가 다르다" 참조.

**저장 경로:**

    {프로젝트 루트}/code-design/<브랜치 슬러그>/{단계}/     (within-run 산출물)
    {프로젝트 루트}/code-design/roadmap.md          (cross-run 공유 마스터)

- `{프로젝트 루트}` 는 git 최상위(= CWD, code-design 은 루트에서만 실행 -- overview "프로젝트 루트 확인" 참조)
- `<브랜치 슬러그>` 는 이 작업(= 이 flow)을 진행하는 git 브랜치 이름을 슬러그화한 것(`/` 를 `_` 로 치환, 예: `feature/x` -> `feature_x`) -- 브랜치가 곧 버전 키이고 그 슬러그가 폴더 이름이다. within-run 산출물(핸드오프·체크리스트·검증 틀)을 이 아래에 브랜치별로 격리 누적한다.
- `{단계}` 는 단계 디렉토리 이름 (예: `00-ideation`, `01-requirements`, `02-design`)
- `roadmap.md` 는 flow 를 넘어 공유되는 유일한 파일 -- 브랜치 폴더 밖 code-design 루트에 flat 하게 둔다 (아래 "버전은 브랜치별 아카이브, cross-run 은 roadmap.md" 참조).

<PENETRATE>
브랜치 폴더 이름(`<브랜치 슬러그>`)은 git 브랜치 이름에서 `/` 를 `_` 로 치환해 짓는다.
</PENETRATE>

**파일 패턴:**

| 종류 | 파일명 | 갱신 방식 | 위치 / 대상 단계 |
|------|--------|----------|----------|
| 체크리스트 | `checklist.md` | 단일 -- 제시 전 파일 먼저 작성, 회차마다 갱신(이력은 git 이 보존), 승인 시 사용자 서명 + Claude 시각 스탬프 | `<브랜치 슬러그>/{단계}/`, 전 단계 (00~04) |
| 핸드오프 | `handoff.md` | 단일 -- 갱신 시 사용자 확인 | `<브랜치 슬러그>/{단계}/`, 핸드오프가 문서인 단계만 (아래 참조) |
| 로드맵 | `roadmap.md` | 공유 마스터 -- 청크 상태 갱신(00 큐레이터, 전이 이벤트마다 append) | `code-design/` 루트 (flow 공유) |

체크리스트와 핸드오프의 역할·내용 계약은 아래 두 소절("역할 분담", "handoff 는 결정 + 근거까지")에서 정한다.

### 역할 분담 -- 사용자는 checklist 만, handoff 는 Claude 전용

`checklist.md` 는 사용자가 보는 유일한 면이다. `handoff.md` 는 다음 Claude 세션이 참고하는 전용 자료이며, 사용자는 열지 않는다(열지 않아도 되게 만든다).

- checklist 상단에 `## 결정 요약` 을 둔다 = 그 단계가 내린 **결정의 값**을 한 줄씩 모은 것. 사용자는 이 단락만 읽고 사인오프할 수 있어야 한다.
- checklist 하단 `## 완료 기준` 은 **절차 점검**(규격대로 했나)이다. 결정 요약과 겹치지 않는다 -- 요약은 "무엇을 정했나", 체크박스는 "규격대로 정했나"에 답한다.
- 보장 규칙: handoff 안의 "사용자 승인이 필요한 항목"은 **빠짐없이** 결정 요약에 값으로 등장한다. 근거 / 외부 출처 / 협의 과정처럼 "승인 단위가 아닌 것"은 handoff 에만 둔다.

<PENETRATE>
checklist 상단 결정 요약에 그 단계의 모든 "사용자 승인 필요" 결정을 값으로 적어, 사용자가 checklist 만 보고 사인오프할 수 있게 한다.
</PENETRATE>

<RICOCHET>
사용자가 handoff 를 열어야만 결정 내용을 알 수 있는 상태로 두지 않는다 (결정 요약에서 승인 필요 항목을 누락하지 않는다).
</RICOCHET>

### 승인 서명 -- checklist.md 가 사인오프 면이다

`checklist.md` 는 사용자가 보는 면일 뿐 아니라 **사인오프하는 면**이다. `## 완료 기준` 의 `[x]` 는 완료 기준 충족 여부이고, 승인 증거는 사용자가 checklist.md 를 직접 편집한 흔적이다. 이 둘은 별개다.

- checklist.md 는 제시 전에 파일로 먼저 작성한다 (터미널에 먼저 찍고 나중에 파일로 옮기지 않는다).
- `[x]` 는 Claude 가 혼자 판정하지 않는다. 각 항목을 실제 저장 위치·근거와 함께 (약 5개씩 배치로) 사용자와 확인하며 체크하고, 실물 근거가 있을 때만 `[x]` 로 둔다 (근거 없는 체크는 위조).
- `## 피드백` · `## 사용자 승인` 두 칸을 `<!-- -->` 주석(가이드)으로 두고, 사용자가 주석을 지워 내용을 남기는 것이 서명이다. Claude 는 이 편집을 대신 하지 않는다.
- 두 칸이 모두 주석 해제될 때만 다음 단계로 넘어가며(AND 게이트), 그 시점 시각을 Claude 가 스탬프한다.

절차·게이트 표·시각 스탬프 규약의 단일 출처는 overview "단계 전환 규칙" 이다.

### 핸드오프는 단계별로 형태가 다르다

핸드오프는 다음 단계가 읽는 바통이다. 모든 단계가 같은 `handoff.md` 문서를 내는 게 아니라, 그 단계의 자연스러운 산출물이 바통 역할을 한다.

- 00-ideation / 01-requirements / 02-design -> `handoff.md` 문서 (구상 방향 / 요구사항 명세 / 설계). 다음 단계가 이 문서를 입력으로 읽는다.
- 03-implementation -> 별도 `handoff.md` 를 만들지 않는다. 04-verification 으로 넘기는 바통은 코드(소스 트리) + 검증 산출물 틀(e2e 리포트 / 수동 QA 체크리스트 / 보안 점검)이다. 구현 산출물이 코드인데 그 위에 별도 설계 문서를 또 내는 건 부자연스럽고, 설계 이탈은 G12 에 따라 02-design handoff 에 동기화하므로 03-implementation 에 별도 핸드오프 문서가 필요 없다.
- 04-verification -> 현재 하류 단계가 없어 핸드오프가 필수가 아니다. 이후 04-verification 뒤에 플로우가 생기면 그 단계에 맞는 형태로 핸드오프를 둘 수 있다 (반드시 `handoff.md` 형식일 필요는 없다).

**핸드오프(`handoff.md`) 갱신 절차** (00-ideation / 01-requirements / 02-design 에 적용):
- 파일이 없으면 -> 새로 작성 (확인 없이)
- 파일이 있으면 -> 사용자에게 "덮어쓸까요?" 확인
  - OK -> 갱신
  - NO -> 사용자에게 처리 방향을 다시 묻는다

### handoff 는 결정 + 근거까지, 군더더기는 뺀다

handoff 는 다음 단계 실행에 필요한 만큼 자세히 적되, 실행에 안 쓰이는 내용으로 컨텍스트를 늘리지 않는다.

- 결정의 "왜"(근거)는 한 줄로 남긴다 -- 하류 단계의 재논쟁을 막는다.
- 협의 **과정 전문**(사용자 의견 / 반문 / 합의 스텝)은 handoff 에 넣지 않는다. 그 이력은 git(checklist 회차)이 보존한다.
- 외부 출처는 본문에 흩지 말고 하단 "출처" 부록에 `링크 + 한 줄 결론` 쌍으로 모은다. 결정을 실제로 뒷받침한 출처만 남긴다 -- 맨 링크 나열은 저밀도라 피한다.

<RICOCHET>
협의 과정 전문이나 결정에 쓰이지 않은 탐색 기록을 handoff 에 늘어놓아 컨텍스트를 잡아먹지 않는다.
</RICOCHET>

### 버전은 브랜치별 아카이브, cross-run 은 roadmap.md

within-run 산출물(핸드오프·체크리스트·검증 틀)은 이 flow 를 진행하는 브랜치 폴더 `code-design/<브랜치 슬러그>/` 아래에 둔다. 새 작업은 새 브랜치에서 진행하므로(한 작업 = 한 브랜치 = 한 버전), 산출물이 브랜치별로 자연히 격리·누적된다. 브랜치명이 곧 버전 키라, 과거 flow 의 설계 문서가 버전별로 브라우징 가능하게 남는다(git diff 로만 보는 게 아니라 폴더로 열린다).

flow 를 넘어 승계되는 것은 `code-design/roadmap.md` 하나뿐이다 -- 청크 상태(overview 로드맵 참조)를 담는 공유 마스터로, 브랜치 폴더 밖 루트에 두고 커밋한다. 새 flow 는 자기 브랜치 폴더 + roadmap.md 만 보고, 다른 브랜치 폴더의 핸드오프는 참고하지 않는다 -- flow 격리가 구조로 강제된다.

<RICOCHET>
새 flow 에서 다른 브랜치 폴더의 핸드오프·체크리스트를 입력으로 참고하지 않는다.
</RICOCHET>

**병행 불가:**

<RICOCHET>
같은 청크에 대해 둘 이상의 flow(브랜치)를 동시에 진행하지 않는다.
</RICOCHET>

within-run 산출물은 브랜치 폴더로 격리되지만, 공유 마스터 roadmap.md 는 하나다 -- 같은 청크를 두 flow 가 동시에 `[진행]`으로 잡으면 로드맵 상태와 산출물이 어긋난다. "한 작업 = 한 브랜치 = 한 청크" 원칙이 이를 막는다. 사용자가 별도 세션에서 강제로 병행 실행해 발생하는 충돌은 사용자 책임 범위로 둔다.

**금지 사항:**

<RICOCHET>
산출물을 위 경로 외 다른 위치에 저장하지 않는다.
</RICOCHET>

<RICOCHET>
핸드오프를 사용자 확인 없이 덮어쓰지 않는다.
</RICOCHET>

## 원칙 6: 코드 분석 산출물(facet)이 있으면 우선 활용 (선택)

기존 코드 구조를 파악해야 하는 단계(00-ideation · 01-requirements · 02-design · 03-implementation)에서, 프로젝트에 코드 분석 산출물(facet)이 있으면 수작업 탐색보다 먼저 1차 입력으로 삼을 수 있다. 필수는 아니다.

facet 은 코드에서 파생된 분석 문서다 -- 코드와 어긋나 보이면 코드를 신뢰한다(stale 가능성). **facet 의 유무·종류·저장 경로·갱신 정책은 이 스킬이 정의하지 않고 각 프로젝트의 `CLAUDE.md` 를 따른다** -- 어떤 도구가 어디에 facet 을 남기는지는 프로젝트마다 다른 접착제라, 범용 스킬에 박으면 어긋난다. 이 스킬은 "있으면 참고한다"는 원칙만 둔다.

**절차:**
- 프로젝트 `CLAUDE.md` 가 가리키는 facet 경로가 있으면 "분석 산출물(facet)을 이번 작업에 활용할까요?"를 사용자에게 한 번 묻는다
- 그 경로에 여러 벌(예: 브랜치별)이 나란히 있으면 어느 것을 쓸지 사용자에게 확인받는다
- 활용하기로 하면 그 경로에 **실제로 있는** facet 문서를 1차 입력으로 삼는다 -- 특정 facet 이름을 여기 박아두지 않고 있는 파일을 그대로 쓴다. 수작업 도구는 facet 이 없거나 특정 지점을 더 깊이 파야 할 때 보완으로 쓴다

<PENETRATE>
facet 산출물의 활용 여부는 임의로 정하지 않고 사용자에게 확인한다.
</PENETRATE>

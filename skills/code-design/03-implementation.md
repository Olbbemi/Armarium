# 구현 (implementation) -- 최소 제약

코드를 작성할 때 *건너뛰면 안 되는 제약*만 둔다.
"어떻게 작성하는지"의 세부 방법은 TDD 스킬 / 언어 reference / 일반 상식에 맡기고,
이 단계는 최소 제약(가드레일)만 둔다.

---

## 공통 원칙

이 단계는 `skills/code-design/principles.md` 를 따른다.

## 단계 내 진행도 (TaskCreate)

이 단계는 수직 슬라이스 반복(G8)이 기본 구조라, 슬라이스를 task 로 시각화한다(principles.md "단계 내 진행도" 원칙).

- 설계 인수 -- 02-design 핸드오프 인수 + TDD 계획을 첫 RED 백로그로 정리 + 열린 보류 0 확인이 끝나면 닫는다.
- 슬라이스 목록 도출 + 확인 -- 설계 인수 직후 TDD 계획 / 기능 분해에서 이번 flow 의 슬라이스를 도출해 각각을 task 로 등록한다(처음부터 전체 개수가 보이게 한다). 이 초기 목록을 사용자에게 한 번 확인받는다 -- 확인 요청 직전 이 도출 task 를 completed 로 닫는다.
- 슬라이스 실행 (각 슬라이스가 task 하나) -- 진입 시 in_progress, 그 슬라이스의 검증 완료선(전체 테스트 green) + 커밋으로 completed 로 닫는다. 슬라이스 내부 RED -> GREEN -> REFACTOR, 가드레일 적용, G4 / G12 확인은 이 슬라이스 task 안에서 처리하고 별도 task 로 쪼개지 않는다.
- 동적 조정 -- 진행 중 G9 로 이번 flow 범위 안의 부차 항목을 발견하면 새 슬라이스 task 를 추가한다. G12 로 설계 항목을 이번에 안 만들기로(descope) 하면 해당 슬라이스 task 를 제거하고 로드맵 `[예정]` 으로 뺀다. 범위 밖 신규 발견은 task 가 아니라 로드맵 `[미정]` 후보다(G9).

| e2e 리포트 | `{프로젝트 루트}/code-design/<브랜치 슬러그>/03-implementation/` | 시나리오 목록(틀) + 슬라이스별 진행 |

## 가드레일

각 가드레일은 **정의 / 왜**로 적고, 사례가 이해를 도우면 **예시**를 덧붙인다 -- 예시는 필수가 아니다. 메인 G1~G15 는 실제 사례에서 와서 대부분 예시를 달지만, 선이 자명한 항목(특히 언어 하위 파일)은 정의+왜 만으로 둔다.
절대 수행/금지(위반 시 단계 무효)에 해당하는 항목만 `<PENETRATE>` / `<RICOCHET>` 로 박고, 나머지는 산문 권고로 둔다.
사용 언어에 고유 가드레일이 있으면 아래 G1~G15 에 더해 함께 로드해 적용한다 -- C++ -> `skills/code-design/03-implementation/languages/cpp.md`.

### G1. 검증 없는 프로덕션 코드 없음 (2축으로 적용)

- **정의**: 프로덕션 코드는 반드시 검증과 짝지어 작성한다. 검증 방식은 한 가지가 아니라 두 축의 조합이다.
  - **순서 축** -- 언제 테스트를 쓰나. 새 동작이면 테스트를 **먼저 쓰고 실패를 본 뒤** 구현한다 (TDD: RED -> GREEN -> REFACTOR). 이미 있는데 미검증인 동작을 노출/변경하면 **회귀(characterization) 테스트로 먼저 고정**한다. 기존 코드를 변경할 때는 손대기 전에 전체 스위트를 돌려 **변경 전 green(baseline)을 먼저 확인**하고 변경 후에도 그 baseline 이 유지되는지 본다 -- 변경 후 red 의 원인을 귀속할 수 있고, baseline 유지가 곧 "회귀 없음"의 정의다. (RED-first 가 "green 이 의미 있으려면 실패를 먼저 본다"라면, baseline-first 는 "나중 red 가 의미 있으려면 green 을 먼저 본다".)
  - **레벨 축** -- 어느 레벨에서 검증하나. 대상은 세 갈래다. **코어**(도메인 / usecase)는 외부와 격리해 **unit** 으로 잡고, 무거운 통합 거동이면 E2E 를 보강한다. **어댑터**(외부 경계 -- DB·네트워크·시계 같은 driven, GUI/TUI·CLI 입력 같은 driving)는 진짜 외부에 닿으므로 **통합·E2E** 로, 자동화가 어려운 인터랙티브 어댑터는 **수동 QA** 로 검증한다 (GUI 는 어댑터의 한 예시일 뿐 특별 범주가 아니다). **조립**(composition root)은 부품을 끼워 맞춘 전체가 실제로 도는지 **E2E** 로 본다.
  - 둘을 곱해 대상 성격에 맞게 조합한다.
- **왜**: 검증 없는 코드는 "동작한다"는 근거가 없다. 특히 RED 를 건너뛰면 테스트가 실제로 그 동작을 잡는지조차 보장 못 한다 (빈 테스트 / 항상 통과). 순서·레벨을 대상에 맞게 골라야 비용 대비 검증력이 선다.
- **예시**: 코어(도메인 + usecase)는 TDD unit 으로, 조립 지점(예: CLI 엔트리)은 실제 바이너리를 직접 실행하는 E2E 로 검증한다 -- 같은 기능을 unit 과 E2E 가 각자의 책임으로 잡는다.

| 대상 | 레벨 | 순서 |
|------|------|------|
| 코어 (도메인 / usecase) | unit 필수 (무거운 통합 거동이면 E2E 보강) | 새 것=TDD / 기존=회귀 |
| 어댑터 (외부 경계: driving / driven) | 통합·E2E, 자동화 어려우면 수동 QA | 기존 동작이면 회귀 |
| 조립 (composition root) | E2E | (단위 TDD 생략) |

참고 지식: `Herbarium/wip/tdd.md` (TDD 정의 / 회귀·E2E 경계).

<RICOCHET>
검증 없이 프로덕션 코드를 작성하지 않는다.
</RICOCHET>

### G2. 의존성은 경계 뒤로 격리(주입)

- **정의**: 외부 라이브러리 / IO / 시간 / 네트워크는 포트(인터페이스) 뒤로 감싸 주입하고, 코어가 가짜(fake)로 테스트되게 한다. 진짜 어댑터는 통합 테스트로 따로 검증한다.
- **왜**: 이것이 G1 의 TDD 를 애초에 가능하게 만드는 전제다. 코어가 DB·시계·네트워크를 직접 알면 단위 테스트가 외부에 묶여 RED 를 빠르게 만들 수 없다. (네트워크 / 외부 의존 코드까지 G1 이 적용되려면 G2 가 선행돼야 한다.)
- **예시**: DB·로거·설정을 포트(인터페이스) 뒤에 두고 어댑터로 구현한다. 코어 usecase 는 in-memory / fake 구현으로 단위 검증한다.

### G3. 기존 코어 재사용

- **정의**: 도메인 / usecase 가 이미 지원하면 재구현하지 말고 엣지만 조립한다. 새로 작성하기 전에 "이미 있는지" 부터 확인한다.
- **왜**: 중복 구현은 동작이 두 갈래로 나뉘어 (한쪽만 고치는 버그) 검증·유지 비용을 배로 만든다. 기존 코어 경로 재사용이 일관성과 회귀 안전을 지킨다.
- **예시**: 조회 기능을 새 로직 없이 기존 포트 메서드를 직접 호출해 처리하고, 같은 일을 하는 재구현(전체 스캔 등)을 없앤다. 새 엔티티의 update/delete 는 이미 다른 엔티티에 선 CRUD 패턴을 그대로 대칭 적용한다.

### G4. 임의 결정 금지

- **정의**: 인터페이스를 정하는 선택(옵션 이름 / 기본값 / 정책)은 임의로 정하지 않는다. 한 번에 하나씩 사용자에게 확인한다 (공통 원칙 1).
- **왜**: 임의로 박은 인터페이스가 사용자 의도와 어긋나면 이미 작성된 코드·테스트까지 되돌려야 한다. 결정 비용이 가장 싼 시점은 "코드 작성 전"이다.
- **예시**: 정책 갈림길(예: 타임존 처리 A/B)에서 임의 디폴트 대신 사용자에게 확인해 결정한 뒤 조립한다. 옵션의 이름·기본값도 임의로 도입하지 않고 기존 패턴에 맞춰 확정한다.

<RICOCHET>
인터페이스를 정하는 선택(옵션 이름, 기본값, 정책)을 사용자 확인 없이 임의로 정하지 않는다.
</RICOCHET>

### G5. 이상하면 근본 원인부터

- **정의**: 동작이 기대와 다르거나 어떤 제약·한계가 의심되면 "고치기/우회하기" 전에 근본 원인·사실을 규명한다. 증상만 덮는 대응·가정 기반 우회 금지.
- **왜**: 증상만 막거나 검증 안 된 가정 위에 우회를 쌓으면, 같은 원인이 다시 문제를 일으키거나 헛수고·재작업이 생기고 구조가 망가진다. 근본 원인·사실을 먼저 잡아야 한 번에 끝난다.
- **예시(반례)**: 컴파일러 / 런타임 버전을 오탐해 특정 표준 API 를 못 쓴다고 *가정*하고 구식 함수로 우회 구현했다가, 나중에 실제 버전을 확인하고 표준 API 로 되돌린 경우. 가정(버전)을 먼저 검증했으면 우회·재작업이 없었다 -- 우회 전에 근본 사실부터 확인.

<RICOCHET>
동작이 기대와 다를 때 원인을 규명하지 않고 증상만 고치지 않는다.
</RICOCHET>

### G6. 엣지 관심사는 엣지에

- **정의**: 타임존 / 파싱 / 포맷 / IO 같은 경계 변환은 어댑터(edge)에, 조립은 composition root 에, usecase / 도메인은 순수하게 유지한다.
- **왜**: 경계 관심사가 도메인에 새면 도메인이 외부 형식에 묶여 G2(격리)·G1(단위 테스트)이 무너진다. 변환을 엣지에 가두면 코어는 순수·테스트 가능 상태로 남는다.
- **예시**: 파싱·출력 포맷 같은 경계 변환을 별도 엣지 모듈로 추출해 단위 테스트를 붙인다. 타임존 변환도 도메인이 아니라 엣지에서 처리한다.

### G7. 실패 / 가드 경로도 검증

- **정의**: 정상(happy path)뿐 아니라 *거부돼야 하는* 입력 · 충돌 · 미발견 같은 부정 경로도 테스트 / E2E 로 확인한다.
- **왜**: 해피패스만 통과시키면 "막아야 할 걸 실제로 막는지"는 모른다. 가드 로직 자체가 동작 안 하면 실패 신호 없이 통과해버린다.
- **예시**: 상호배타 옵션 충돌, 필수 옵션 누락, 대상 not-found 같은 거부 경로를 각각 E2E 로 직접 확인한다.

<PENETRATE>
정상 경로뿐 아니라 거부돼야 하는 입력·충돌·미발견 같은 부정 경로도 검증한다.
</PENETRATE>

### G8. 수직 슬라이스 + 슬라이스마다 커밋

- **정의**: 한 번에 한 도메인 / 기능을 끝까지(도메인 -> usecase -> 엣지 -> 검증) 관통하고, 슬라이스가 끝나면 커밋한다. "전 계층 한꺼번에"는 최후 보류. 슬라이스가 인터랙티브 표면(수동 QA 로만 잡히는 GUI / TUI 등)을 건드리면, 그 슬라이스를 닫기 전에 해당 수동 QA 항목을 그 자리에서 확인한다 -- 인터랙티브 결함을 그것을 만든 슬라이스에 귀속시켜 04-verification 에 누적되지 않게 한다(권고). 진행도 시각화에서는 슬라이스 하나가 task 하나이며, 이 커밋이 그 task 의 completed 신호다.
- **왜**: 작은 단위로 끝내고 커밋하면 회귀 추적 · 되돌리기 · 리뷰가 쉽다. 미완 상태가 누적되지 않는다. 수동 QA 를 맨 끝(04-verification)으로 미루면 인터랙티브 결함이 늦게, 슬라이스 가드 없이 잡힌다. 슬라이스마다 그 자리에서 확인하면 결함이 그것을 만든 슬라이스에 바로 귀속된다.
- **예시**: 기능 하나(예: 한 엔티티의 update/delete, 초기화, 한 화면의 라벨 정정)를 각각 독립 슬라이스로 끝내고 커밋을 하나씩 남긴다.

### G9. 슬라이스 중 범위 확장 금지

- **정의**: 슬라이스 도중 발견한 교차 관심사 / 부차 항목은 그 자리에서 처리하지 않고, 따로 적어 미룬다. 미루는 곳은 범위로 나눈다 -- 이번 flow(현재 청크) 범위 안이면 이 flow 의 별도 슬라이스로 돌리고, 이번 flow 범위를 벗어나는 새 주제면 사용자 확인 후 로드맵 `[미정]` 청크 후보로 뺀다(요구엔 없던 신규 발견이라 미검증 = `[미정]`; 04-verification 의 신규 범위 발견과 같은 결). 이미 합의된 설계 항목을 이번에 안 만드는 '범위 축소'는 G9 가 아니라 G12(로드맵 `[예정]`) 소관이다. 진행도 시각화에서, 이번 flow 슬라이스로 돌리는 것은 새 슬라이스 task 추가이고, 로드맵으로 빼는 것은 task 가 아니다.
- **왜**: 범위가 커지면 슬라이스가 안 끝나고 커밋이 비대해진다. 교차 관심사는 별도 슬라이스가 맞다.
- **예시**: 한 슬라이스에서 내부 문구가 사용자에게 그대로 노출되는 문제를 발견했지만, "친절한 에러 메시지"는 모든 usecase 공통 사안이라 그 슬라이스에서 고치지 않고 따로 미뤘다.

<RICOCHET>
슬라이스 도중 발견한 교차 관심사나 부차 항목을 그 자리에서 처리하지 않는다.
</RICOCHET>

### G10. 기존 패턴 / 관용구에 맞추기

- **정의**: 새 코드는 주변 코드의 명명 · 구조 · 관용구를 따른다. 새 스타일을 끌어들이지 않는다.
- **왜**: 일관성이 읽기 / 유지보수 비용을 낮추고 리뷰 부담도 준다.
- **예시**: 한 엔티티의 update 에서 자리잡은 옵션 패턴(`--no-x` / `--clear-y`)을 다른 엔티티의 update 에도 그대로 동형 적용한다.

### G11. 주석 / 문서는 사실과 일치

- **정의**: 코드가 바뀌거나 가정이 틀리면 주석 · 문서도 즉시 고친다.
- **왜**: 틀린 주석은 없느니만 못하다 -- 다음 사람을 적극적으로 오도한다.
- **예시**: 사용 라이브러리가 키를 정렬해 출력한다는 사실을 확인하고, 틀린 "키 순서 보존" 주석을 사실대로 정정한다. (미사용 변수 제거 등 무경고 유지도 같은 결.)

### G12. 설계에서 이탈하면 설계를 동기화하거나 확인한다

- **정의**: 구현이 합의된 상위 설계(예: 02-design 핸드오프)에서 벗어나면 그대로 진행하지 않는다. 답은 "기록하고 넘어감"이 아니라 설계를 실제에 맞게 맞추는 것이다. (a) 인터페이스나 결정을 바꾸는 이탈이면 사용자 확인을 받고(G4 연결), `handoff.md` 의 "설계 결정 기록"에 새 항목으로 남긴다. (b) 인터페이스가 그대로인 사소한 이탈이면 `handoff.md` 본문(모듈 구조 등)을 사실에 맞게 갱신한다(G11 연결). 설계 항목을 이번에 구현하지 않고 미루는 것은 설계 이탈이 아니라 범위 축소다 -- 로드맵 `[예정]` 청크로 빼고 사용자 확인을 받는다(이미 합의된 설계 항목이라 "할지 확정, 시점만 미래" = `[예정]`; 요구에 없던 신규 발견 = `[미정]` 은 G9 소관. 전이 주체 -- overview "로드맵"). 진행도 시각화에서 이 descope 는 해당 슬라이스 task 제거를 뜻한다. 03-implementation 은 in-run 보류를 만들지 않는다(원칙 4). 여기서 두 경우를 구분한다 -- (1) 명세되지 않은 빈칸을 채우는 결정은 원칙 1 / G4 로 그 자리에서 확인해 채우는 평상 구현 판단이고, (2) 이미 합의·확정된 설계 결정에 반하는 변경은 무게가 다르다. (2)는 (a) 의 사후 `handoff.md` 기록만으로 부족하고, 구현·수정에 **착수하기 전** 사용자 승인을 받는다. 동작 교정 자체가 정당하더라도, 확정된 결정에 반하는 구조 변경(예: 안 하기로 한 표현 seam 추출)은 그 동작 교정과 별개 사안이라 따로 사전 승인 대상이다.
- **왜**: 이탈을 기록만 하고 방치하면 설계 문서와 코드가 어긋난 채 남아 추적성이 끊긴다. 설계를 실제에 맞게 동기화하면(또는 결정을 바꾸는 이탈을 확인 / 기록하면) 설계 문서가 늘 코드의 진실을 반영해, 따로 쌓는 이탈 로그보다 강한 추적성을 준다.
- **예시(반례)**: 빌드 타깃 이름 / UX 패턴 / 라이브러리 선택이 설계에서 벗어났는데 `handoff.md` 갱신도 사용자 확인도 없이 이탈한 경우. 결정을 바꾼 이탈이면 G4 로 확인하고 설계 결정 기록에 남겼어야 하고, 사소한 이탈이면 `handoff.md` 본문을 사실대로 동기화했어야 한다.
- **예시(반례, 확정된 결정 충돌)**: 동작 결함을 고치며 표현 계층의 검증 로직을 별도 seam 클래스로 추출했는데, 이는 "GUI 표현 seam 을 강제 추출하지 않는다"로 이미 확정된 설계 결정에 반하는 구조 변경이었다. 동작 교정은 정당했고 그 동작은 seam 없이도 교정 가능했으므로, 확정된 결정에 반하는 구조 변경 쪽은 착수 전 사용자 승인을 받았어야 했다 -- 사후 이탈 기록만으로는 부족하다.

<PENETRATE>
구현이 합의된 설계에서 벗어나면, 결정을 바꾸는 이탈은 사용자 확인을 받아 설계 결정 기록에 남기고, 사소한 이탈은 `handoff.md` 를 사실에 맞게 갱신한다.
</PENETRATE>

<RICOCHET>
설계에서 벗어난 구현을 설계 동기화도 사용자 확인도 없이 진행하지 않는다.
</RICOCHET>

<RICOCHET>
이미 확정된 설계 결정에 반하는 변경을 착수 전 사용자 승인 없이 진행하거나 사후 기록만으로 끝내지 않는다.
</RICOCHET>

### G13. 스캐폴딩 생명주기 관리

- **정의**: 스캐폴딩이란 본 작업을 시작하기 위해 임시로 두는 최소 설정이다 (진짜 코드가 생기면 제거하는 게 전제). 새 프로젝트 초기처럼 도메인 코드·테스트가 아직 하나도 없을 때, TDD 첫 RED 를 보기 전에 도구 체인(빌드 + 테스트 러너)이 실제로 도는지 확인하는 환경 baseline 용으로 만든다. 첫 실물(도메인 테스트)이 생기는 슬라이스에서 즉시 제거한다 -- "내부 구조가 완성되면"이 아니라, 환경 스모크라면 첫 도메인 테스트가 green 이 되는 순간 그 실제 테스트가 파이프라인 동작을 증명하므로 역할이 끝난다.
- **왜**: 스캐폴딩은 첫 도메인 테스트가 RED 일 때 "환경이 깨져서가 아니라 구현이 없어서"라고 귀속하게 해준다 (G1 baseline-first 의 환경판). 그러나 철거를 "완성"까지 미루면 임시물이 영구물처럼 방치돼, 항상 통과하는 빈 테스트가 스위트에 남아 G1 이 경계하는 무의미 테스트가 된다.
- **예시(반례)**: 빌드 파이프라인 확인용 스모크 테스트(`EXPECT_TRUE(true)` 류)가, 첫 도메인 테스트가 green 된 슬라이스에서 삭제됐어야 하나 많은 테스트가 누적되도록 방치된 경우. 주석은 "도메인 TDD 시작되면 대체/삭제"라 약속했으나 안 지켜진, 눈에 안 띄는 누락.

<PENETRATE>
스캐폴딩은 첫 실물이 생기는 슬라이스에서 제거한다.
</PENETRATE>

### G14. 테스트 파일은 공개 단위로 조직

- **정의**: 테스트 파일은 테스트 대상의 공개 단위(클래스 / 모듈) 하나에 대응시킨다 -- 소스 트리를 미러하듯 "공개 단위 1개 = 테스트 파일 1개". 메서드나 케이스 하나마다 파일을 따로 만들지 않는다(그 단위는 파일 안의 테스트 그룹 / 픽스처로 표현). 로직이 없는 값 타입 · 인터페이스 · DTO 나 자동화 불가한 인터랙티브 어댑터처럼 단위 테스트 대상이 아닌 것은 아예 만들지 않는다.
- **왜**: 대상-파일 1:1 이면 "이 동작의 테스트가 어디 있나"를 구조만 보고 찾는다. 한 파일에 여러 대상을 담으면 탐색이 어렵고, 반대로 메서드별로 잘게 쪼개면 같은 대상의 테스트가 흩어져 그 이점을 깨고 유지 비용만 올린다.
- **예시**: 한 클래스 = 테스트 파일 1개로 소스 트리를 미러한다(`Foo` -> `foo_test`). 로직 없는 값 / 인터페이스 / DTO 와 GUI 어댑터(수동 QA 대상)는 단위 테스트를 만들지 않는다.

<RICOCHET>
한 파일에 여러 공개 단위를 몰거나, 메서드 · 케이스 하나마다 테스트 파일을 따로 만들지 않는다.
</RICOCHET>

### G15. 이름은 의도를 드러낸다

- **정의**: 변수 / 함수 / 타입 이름은 그 역할 · 의도가 이름만으로 읽히게 짓는다. 의미 없는 한 글자(`a`, `b`)나 무엇을 가리키는지 모를 축약(`pl` 이 `play` 인지 `payload` 인지)은 쓰지 않는다. 단 좁은 스코프의 관용적 짧은 이름(루프 인덱스 `i` / `j` 등)은 허용한다 -- 서술성 요구는 스코프에 비례한다.
- **왜**: 이름이 코드의 1차 문서다. 모호한 이름은 읽는 사람이 매번 정의로 돌아가 뜻을 추론하게 만들고 오해를 부른다. (G10 이 "주변 명명 스타일에 맞춰라"라면, G15 는 "이름 자체가 서술적이어야"라는 하한선이다.)
- **예시(반례)**: `pl`, `a`, `tmp2` 처럼 역할을 감춘 이름 -- 각각 `payload` / `player`, 실제 역할 이름으로 바꾼다. 반대로 좁은 루프의 `i` 는 그대로 둔다.

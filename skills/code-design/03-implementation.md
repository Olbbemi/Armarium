# 3단계: 구현

설계가 확정된 후, 그것을 실제 코드로 만드는 단계.
이 단계의 출력이 4단계(정적 분석 / 리팩터링)의 입력이 된다.

---

## 공통 원칙

이 단계는 `skills/code-design/00-principles.md` 를 따른다.

---

## 진입 조건

다음 중 하나라도 해당되면 이 단계로 진입:
- 2단계(설계)가 완료되어 설계 문서가 있음
- 설계는 명확한데 아직 코드가 없음
- 기존 코드 변경 설계가 있고 실제 구현 작업이 필요함

이 단계는 세 종류의 산출물을 만든다.

| 산출물 | 위치 | 내용 | 저장 시점 |
|--------|------|------|----------|
| 실제 코드 | 프로젝트 코드 트리 | 구현된 코드 / 테스트 / 빌드 파일 | 구현 진행 중 |

## 단계 시작 시 — 사전 조사

### 1. 핸드오프 입력 로드

2단계 산출물(`{프로젝트 루트}/code-design/02-design/handoff.md`)을 입력으로 로드한다.
핸드오프 내용 중 모호한 부분이 있으면 즉시 되묻는다 (공통 원칙 1).

### 2. 외부 검색 (필요 시)

**검색이 필요한 경우:**
- 처음 다루는 라이브러리 / 프레임워크의 사용법
- API 스펙 / 시그니처 / 반환 타입 확인
- 외부 시스템 SDK 사용 예제
- 비기능 요구사항 대응 구현 패턴 (성능 / 보안 / 동시성 등)

검색 깊이 — 공통 원칙 2("반복될수록 더 깊이 파고든다")의 정량 단위를 3단계(구현)의 검색 행동으로 구체화:

| 상황 | 검색 횟수 | 출처 다양성 | 공식 문서 확인 |
|------|----------|------------|--------------|
| 처음 다루는 라이브러리/API (표준 깊이) | 3~5회 | 2개 이상 출처 교차 확인 | 핵심 API만 |
| 두 번째 이상 같은 영역 (+1) | 5~8회 | 3개 이상 출처 + 유사 패턴 비교 | 모든 핵심 API |
| 같은 구현 이슈가 반복 등장 (+2) | 8회 이상 | 근본 원인 추적 모드 | 공식 문서 + 표준 / RFC 직접 확인 |

**검색 후 처리:**

<PENETRATE>
이번 구현에 채택한 정보는 산출물의 "구현 결정 기록" 섹션에 명시적으로 반영한다.
</PENETRATE>

<PENETRATE>
검토했으나 채택하지 않은 대안은 산출물의 "구현 결정 기록 — 고려했으나 버린 대안" 에 기록한다.
</PENETRATE>

<PENETRATE>
신뢰할 만한 출처(공식 문서, 표준 문서, RFC)는 산출물의 "참고 자료" 섹션에 링크로 남긴다.
</PENETRATE>

### 3. 사용자 확인 — 모호하면 반드시

외부 검색으로도 결정할 수 없는 항목은 사용자에게 질문한다 (공통 원칙 1).

## 산출물 형식

구현 결과 요약은 다음 형식의 문서로 작성한다.
모든 섹션은 비워두지 않는다. 채울 데이터가 없으면 명시적으로 N/A로 표기한다 (공통 원칙 3).
흐름별로 산출물에 추가할 항목이 있으면 흐름 variant 파일의 "흐름별 산출물 보완" 섹션을 따른다.

이 산출물은 핸드오프 파일(`handoff.md`)에 그대로 저장된다 — "다음 단계로 전달할 것" 섹션 참조.

```markdown
# 구현: {기능명}

## 적용 흐름
A / B 중 어느 것인지 명시.
사용 언어 명시 (C++ / Python / Rust / 그 외).

## 구현 결과
- 작성/변경된 파일 목록 (경로)
- 구현된 인터페이스 (2단계 설계의 어떤 항목과 매핑되는지)
- 사용한 외부 라이브러리 / 의존성 (이름 + 버전)

## TDD 사이클 기록
- 작성한 테스트 목록 (2단계 TDD 계획의 어떤 케이스와 매핑되는지)
- Red -> Green -> Refactor 사이클 진행 요약
- 추가로 발견되어 작성한 테스트 (계획에 없던 케이스)

## 빌드 / 실행 상태
- 빌드 결과: 성공 / 실패
- 빌드 명령:
- 실행 명령:
- 테스트 실행 결과: 전체 통과 / 일부 실패 (실패 케이스 명시)

## TODO / 보류
- (구현 중 발견했으나 이번에 처리하지 않은 항목. 사유 + 처리 시점 명시. 없으면 N/A)

## 구현 결정 기록
- 결정한 것 / 이유 / 고려했으나 버린 대안

## 참고 자료
- 외부: (검색으로 참고한 공식 문서, 표준, 패턴 등)

## 사용자와의 명확화 기록
- 모호했던 항목과 그 해소 과정
- 피드백 협의 과정 (피드백이 있었던 경우)
  - 사용자 의견: ...
  - LLM 반문: ...
  - 합의 결과: ...
```

## 완료 기준

단계 종료 시 아래 형식으로 제시한다.

**저장 경로:** `{프로젝트 루트}/code-design/03-implementation/{YYYY-MM-DD-HHMM}-checklist.md`
- 공통 원칙 5("단계 산출물 저장 정책")에 따른다.
- 매 저장 시 신규 파일이 생성되며 누적된다.

```markdown
## 완료 기준
- [ ] 2단계 설계의 모든 인터페이스가 구현됨
- [ ] 2단계 TDD 계획의 모든 테스트 케이스가 작성됨
- [ ] 모든 테스트가 통과함
- [ ] 빌드가 성공하고 실행 가능함
- [ ] 명백한 TODO / 임시 코드가 없거나 산출물의 "TODO / 보류"에 기록됨
- [ ] 작성한 코드가 2단계 모듈 구조 / 의존 관계와 일치함
- [ ] 사용한 외부 라이브러리 / 의존성이 산출물에 기록됨
- [ ] 흐름 variant 파일의 흐름별 완료 기준이 충족됨
- [ ] 모호한 사용자 표현은 모두 되묻고 명확화됨
- [ ] 임의 결정이 없음 (모든 결정은 사용자 확인됨)
- [ ] 반복 작업의 경우 깊이 +1 / +2 기준에 맞게 조사가 이루어짐
- [ ] N/A로 표기된 항목이 모두 사용자 확인을 받음
- [ ] 피드백 영역이 채워짐 (없어도 N/A 명시)

## N/A 항목 확인
다음 항목이 N/A로 표기됨. 정말 해당 없음이 맞는지 확인 부탁드립니다:
- (예) TODO / 보류: N/A
- (예) 참고 자료 - 외부: N/A
(N/A 항목이 없으면 "없음"으로 표기)

## 피드백
(피드백을 작성. 없으면 N/A 명시)
```

### 피드백 처리 절차

**용어 정리:**
- 체크리스트 파일의 "피드백" 섹션 = 매 회차 사용자가 적는 입력 (회차마다 누적)
- 산출물의 "사용자와의 명확화 기록" 섹션 = 협의 과정과 합의 결과의 영구 이력
- 피드백이 들어오면 협의를 거쳐 그 결과를 영구 이력에 옮긴다.

**자동 수용 금지 피드백:**

<RICOCHET>
"이 인터페이스는 빼자" / "이 테스트는 안 작성해도 됨" 같은 구조 / 검증 범위 축소 요청을 자동 수용하지 않는다.
</RICOCHET>

<RICOCHET>
실패한 테스트를 통과로 만드는 대신 테스트 자체를 약화하는 요청을 자동 수용하지 않는다.
</RICOCHET>

<RICOCHET>
산출물 템플릿 자체에 대한 변경 요청을 자동 수용하지 않는다.
</RICOCHET>

**처리 절차:**
1. 반문한다. 왜 그렇게 판단했는지, 어떤 영향이 있는지 확인
2. 협의한다.
3. 기록한다. 협의 과정과 합의 결과를 산출물의 "사용자와의 명확화 기록"에 남긴다
4. 합의된 변경을 산출물에 반영한 뒤 재제시

<RICOCHET>
협의가 끝나기 전에 자동 수용 금지 피드백을 산출물에 반영하지 않는다.
</RICOCHET>

<RICOCHET>
사용자와 합의에 도달하기 전에 다음 단계로 진행하지 않는다.
</RICOCHET>

피드백이 단순한 N/A (의견 없음) 이거나 명확한 추가 요구사항이면 위 절차 없이 바로 반영해도 된다.

- 구현 결정 기록 + 사용자와의 명확화 기록은 4단계에서 같은 결정이 다시 등장할 때 일관성 유지에 사용된다.
- 외부 참고 자료, 1·2단계로부터 받은 가정 / 보류 항목 — 모두 산출물 안에 포함되므로 별도 파일을 만들지 않는다.

## 가드레일

각 가드레일은 **정의 / 왜 / 실사용**으로 적는다.
절대 수행/금지(위반 시 단계 무효)에 해당하는 항목만 `<PENETRATE>` / `<RICOCHET>` 로 박고, 나머지는 산문 권고로 둔다 (skill-writing §3).
사용 언어에 고유 가드레일이 있으면 아래 G1~G12 에 더해 함께 로드해 적용한다 -- C++ -> `skills/code-design/03-implementation/languages/cpp.md`.

### G1. 검증 없는 프로덕션 코드 없음 (2축으로 적용)

- **정의**: 프로덕션 코드는 반드시 검증과 짝지어 작성한다. 검증 방식은 한 가지가 아니라 두 축의 조합이다.
  - **순서 축** -- 언제 테스트를 쓰나. 새 동작이면 테스트를 **먼저 쓰고 실패를 본 뒤** 구현한다 (TDD: RED -> GREEN -> REFACTOR). 이미 있는데 미검증인 동작을 노출/변경하면 **회귀(characterization) 테스트로 먼저 고정**한다. 기존 코드를 변경할 때는 손대기 전에 전체 스위트를 돌려 **변경 전 green(baseline)을 먼저 확인**하고 변경 후에도 그 baseline 이 유지되는지 본다 -- 변경 후 red 의 원인을 귀속할 수 있고, baseline 유지가 곧 "회귀 없음"의 정의다. (RED-first 가 "green 이 의미 있으려면 실패를 먼저 본다"라면, baseline-first 는 "나중 red 가 의미 있으려면 green 을 먼저 본다".)
  - **레벨 축** -- 어느 레벨에서 검증하나. 단위로 잡히면 **unit**, 배선/통합 지점이라 단위가 번거로우면 **E2E** (실제 바이너리/엔드포인트).
  - 둘을 곱해 대상 성격에 맞게 조합한다.
- **왜**: 검증 없는 코드는 "동작한다"는 근거가 없다. 특히 RED 를 건너뛰면 테스트가 실제로 그 동작을 잡는지조차 보장 못 한다 (빈 테스트 / 항상 통과). 순서·레벨을 대상에 맞게 골라야 비용 대비 검증력이 선다.
- **실사용**: 도메인+application 레이어는 TDD unit (`fb453c2`, 85 green) 으로, CLI 배선 지점은 실제 바이너리 E2E (`1f85e31` todo add/list/done, `46a67fa` goal create/log/show, 둘 다 E2E green) 로 검증.

| 대상 | 순서 | 레벨 |
|------|------|------|
| 핵심 도메인 로직 (새 것) | TDD | unit |
| 이미 있는 usecase 경로 | 회귀 | unit |
| 진입점 배선 (조립) | (단위 TDD 생략) | E2E |

참고 지식: `Herbarium/wip/tdd.md` (TDD 정의 / 회귀·E2E 경계).

<RICOCHET>
검증 없이 프로덕션 코드를 작성하지 않는다.
</RICOCHET>

### G2. 의존성은 경계 뒤로 격리(주입)

- **정의**: 외부 라이브러리 / IO / 시간 / 네트워크는 포트(인터페이스) 뒤로 감싸 주입하고, 코어가 가짜(fake)로 테스트되게 한다. 진짜 어댑터는 통합 테스트로 따로 검증한다.
- **왜**: 이것이 G1 의 TDD 를 애초에 가능하게 만드는 전제다. 코어가 SQLite·시계·네트워크를 직접 알면 단위 테스트가 외부에 묶여 RED 를 빠르게 만들 수 없다. (네트워크 / 외부 의존 코드까지 G1 이 적용되려면 G2 가 선행돼야 한다.)
- **실사용**: SQLite·로거·설정을 `stomata`(ports) 뒤로 두고 `roots`/`rings`/`climate` 어댑터로 구현 (`54e1173`, `0cf06be`). 코어 usecase 는 in-memory / fake repository 로 단위 검증.

### G3. 기존 코어 재사용

- **정의**: 도메인 / usecase 가 이미 지원하면 재구현하지 말고 엣지만 배선한다. 새로 짜기 전에 "이미 있는지" 부터 확인한다.
- **왜**: 중복 구현은 동작이 두 갈래로 갈려 (한쪽만 고치는 버그) 검증·유지 비용을 배로 만든다. 기존 코어 경로 재사용이 일관성과 회귀 안전을 지킨다.
- **실사용**: goal show 를 새 조회 로직 없이 기존 포트 메서드 `findByName` 직접 호출로 처리, 이름->id 전체 스캔 재구현을 제거 (`495f0a9`). todo update/delete 는 event·goal 에 이미 선 CRUD 패턴을 그대로 대칭 적용 (`cb04803`).

### G4. 임의 결정 금지

- **정의**: 인터페이스를 정하는 선택(옵션 이름 / 기본값 / 정책)은 임의로 정하지 않는다. 한 번에 하나씩 사용자에게 확인한다 (공통 원칙 1).
- **왜**: 임의로 박은 인터페이스가 사용자 의도와 어긋나면 이미 작성된 코드·테스트까지 되돌려야 한다. 결정 비용이 가장 싼 시점은 "코드 짜기 전"이다.
- **실사용**: 타임존 처리를 정책 A/B 갈림길에서 임의 디폴트 대신 명시적으로 A 로 결정해 배선 (`81c560b`). CLI 토글 옵션의 이름·의미(`--clear-end` / `--all-day` 등)도 임의 도입이 아니라 기존 패턴에 맞춰 확정.

<RICOCHET>
인터페이스를 정하는 선택(옵션 이름, 기본값, 정책)을 사용자 확인 없이 임의로 정하지 않는다.
</RICOCHET>

### G5. 이상하면 근본 원인부터

- **정의**: 동작이 기대와 다르거나 어떤 제약·한계가 의심되면 "고치기/우회하기" 전에 근본 원인·사실을 규명한다. 증상 땜질·가정 기반 우회 금지.
- **왜**: 증상만 막거나 검증 안 된 가정 위에 우회를 쌓으면, 같은 원인이 또 터지거나 헛수고·재작업이 생기고 구조가 썩는다. 근본 원인·사실을 먼저 잡아야 한 번에 끝난다.
- **실사용(반례)**: GCC 버전을 오탐(실제 13 인데 11.5 로 판단)해 `std::chrono` 타임존 API 를 못 쓴다고 *가정*하고 `mktime` 으로 우회 구현 -> 나중에 실제 버전 확인 후 `chrono` 로 되돌림 (`f0f857e`). 가정(컴파일러 버전)을 먼저 검증했으면 우회·재작업이 없었을 것 -- 우회 전에 근본 사실부터 확인.

<RICOCHET>
동작이 기대와 다를 때 원인을 규명하지 않고 증상만 고치지 않는다.
</RICOCHET>

### G6. 엣지 관심사는 엣지에

- **정의**: 타임존 / 파싱 / 포맷 / IO 같은 경계 변환은 어댑터(edge)에, 조립은 composition root 에, usecase / 도메인은 순수하게 유지한다.
- **왜**: 경계 관심사가 도메인에 새면 도메인이 외부 형식에 묶여 G2(격리)·G1(단위 테스트)이 무너진다. 변환을 엣지에 가두면 코어는 순수·테스트 가능 상태로 남는다.
- **실사용**: 파싱·콘솔 포맷을 `leaves/CliFormat` 으로 추출하고 단위 테스트 부여, 출력 ASCII 화 (`e3f6888`). 타임존 변환도 도메인이 아닌 엣지에서 처리.

### G7. 실패 / 가드 경로도 검증

- **정의**: 정상(happy path)뿐 아니라 *거부돼야 하는* 입력 · 충돌 · 미발견 같은 부정 경로도 테스트 / E2E 로 확인한다.
- **왜**: 해피패스만 통과시키면 "막아야 할 걸 실제로 막는지"는 모른다. 가드 로직 자체가 동작 안 하면 조용히 통과해버린다.
- **실사용**: `--end`+`--clear-end` / `--all-day`+`--no-all-day` 상호배타 에러, 누락 옵션(`--db` 없음), goal·todo not-found 를 각각 E2E 로 직접 확인.

<PENETRATE>
정상 경로뿐 아니라 거부돼야 하는 입력·충돌·미발견 같은 부정 경로도 검증한다.
</PENETRATE>

### G8. 수직 슬라이스 + 슬라이스마다 커밋

- **정의**: 한 번에 한 도메인 / 기능을 끝까지(도메인 -> usecase -> 엣지 -> 검증) 관통하고, 슬라이스가 끝나면 커밋한다. "전 계층 한꺼번에"는 최후 보류.
- **왜**: 작은 단위로 끝내고 커밋하면 회귀 추적 · 되돌리기 · 리뷰가 쉽다. 미완 상태가 누적되지 않는다.
- **실사용**: event clear-end/all-day, goal show, init, todo update/delete, 대시보드 라벨 정정 -- 각각 독립 슬라이스 + 커밋 하나.

### G9. 슬라이스 중 범위 확장 금지

- **정의**: 슬라이스 도중 발견한 교차 관심사 / 곁가지는 그 자리에서 처리하지 않고, 따로 적어 미룬다.
- **왜**: 범위가 번지면 슬라이스가 안 끝나고 커밋이 비대해진다. 교차 관심사는 별도 슬라이스가 맞다.
- **실사용**: goal show 미존재 메시지가 내부 문구로 노출되는 걸 발견했지만, "친절한 에러 메시지"는 모든 usecase 공통 사안이라 그 슬라이스에서 안 고치고 보류.

<RICOCHET>
슬라이스 도중 발견한 교차 관심사나 곁가지를 그 자리에서 처리하지 않는다.
</RICOCHET>

### G10. 기존 패턴 / 관용구에 맞추기

- **정의**: 새 코드는 주변 코드의 명명 · 구조 · 관용구를 따른다. 새 스타일을 끌어들이지 않는다.
- **왜**: 일관성이 읽기 / 유지보수 비용을 낮추고 리뷰 부담도 준다.
- **실사용**: event update 의 `--no-repeat`/`--clear-end` 패턴을 todo update(`--clear-due`/`--clear-tags`)와 all-day(`--all-day`/`--no-all-day`)에 그대로 동형 적용.

### G11. 주석 / 문서는 사실과 일치

- **정의**: 코드가 바뀌거나 가정이 틀리면 주석 · 문서도 즉시 고친다.
- **왜**: 틀린 주석은 없느니만 못하다 -- 다음 사람을 적극적으로 오도한다.
- **실사용**: toml++ 가 키를 정렬 출력하는 걸 확인하고 "키 순서 보존" 주석을 사실대로 정정. (미사용 변수 `kA` 제거 등 무경고 유지도 같은 결.)

### G12. 설계에서 이탈·보류하면 기록 / 확인

- **정의**: 구현이 합의된 상위 설계(예: 02 handoff)에서 벗어나거나, 설계 항목을 이번에 구현하지 않고 미루면(의식적 보류) 조용히 진행하지 않는다. (a) 인터페이스 / 결정을 바꾸는 이탈이면 사용자 확인(G4 와 연결), (b) 이탈·보류 사실을 **그 슬라이스의 커밋 메시지에 한 줄로 남긴다** -- G8 로 어차피 슬라이스마다 커밋하므로 별도 파일이 필요 없다. 사람이 펼쳐볼 통합 목록이 필요하면 별도 상시 파일을 만들지 말고, 복기/마일스톤 같은 체크포인트에 기존 설계 문서의 "이탈/보류 기록" 섹션을 갱신한다.
- **왜**: 이탈·보류 자체는 흔하고 합리적일 수 있으나, *기록되지 않은* 것은 설계-구현 추적성을 끊고 "왜 이렇게 됐지"를 나중에 알 수 없게 만든다. 특히 의식적 보류는 기록이 없으면 "조용한 이탈"과 구분되지 않는다. (이 가드레일의 목적은 "왜 이렇게 됐나"의 추적이다 -- "아직 안 한 보류가 뭐 남았나"의 할 일 추적은 백로그의 몫으로 범위 밖.)
- **실사용(반례)**: Terrarium 의 빌드 타깃 이름·UX 패턴(B->A)·FTXUI·JSON 라이브러리가 02 설계에서 벗어나거나 후속 슬라이스로 보류됐는데 커밋·문서 어디에도 안 적혀 "조용한 이탈"이 됨 -> 이번에 소급 발견해 `02-design/handoff.md` 12장·12-1 에 기록. (G12 가 있었다면 그 슬라이스 커밋에서 잡혔을 것.)

<PENETRATE>
구현이 합의된 상위 설계에서 벗어나거나 설계 항목을 미루면 그 사실을 해당 슬라이스의 커밋 메시지에 남기고, 인터페이스나 결정을 바꾸는 이탈이면 사용자 확인을 받는다.
</PENETRATE>

<RICOCHET>
설계에서 벗어나거나 설계 항목을 미루는 구현을 기록 없이 조용히 진행하지 않는다.
</RICOCHET>

## 검증 완료선 (슬라이스 단위)

- 전체 테스트 green (새 테스트만이 아니라 스위트 전체) -- **필수**
- 슬라이스마다 실제 바이너리 / 실행으로 E2E 한 번 확인 -- 강한 권고
- 컴파일러 무경고 -- 권고

<PENETRATE>
슬라이스를 닫기 전 새 테스트만이 아니라 전체 테스트 스위트가 green 인 것을 확인한다.
</PENETRATE>

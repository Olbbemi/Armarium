# 검증 종류 카탈로그

파이프라인이 다루는 검증 12종의 정의. 각 종류가 무엇이고, 이번 청크에 적용되는지 어떻게 가르고, 무엇을 남기는지를 이 파일이 소유한다.

- 읽는 단계: 01-requirements · 02-design(지정) · 03-implementation(작성) · 04-verification(판정)
- 쓰는 단계: 없음 -- 이 파일은 규격이고, 각 flow 의 판정 결과는 단계 산출물에 남는다

## 이 파일이 소유하지 않는 것

검증에 관한 사실은 세 곳으로 갈라 둔다. 셋은 다른 질문에 답하므로 복제가 아니다.

| 질문 | 소유자 |
|------|--------|
| 어느 단계가 어느 종류를 맡나 | `overview.md` 의 "검증 배치" 표 |
| 각 종류가 무엇이고 언제 적용되나 | 이 파일 |
| 그 언어에서 실제로 무슨 도구를 쓰나 | `03-implementation/languages/{언어}.md` |

## 절단 기준 -- 01-requirements 인가 02-design 인가

가르는 것은 **그 검증이 필요한 근거가 어디 있는가**다.

- 요구사항 문장에 있다 -> 01-requirements 가 지정한다.
- 설계 결정이 만든 위험이다 -> 02-design 이 지정한다.

같은 코드를 보더라도 근거가 다르면 소속이 다르다. "결제가 5초 안에 끝나야 한다" 는 요구사항이라 성능(01-requirements)이고, "그 결제를 두 스레드가 공유 큐로 처리하기로 했다" 는 설계가 만든 위험이라 경합(02-design)이다.

## 적용 판정 -- 재량으로 고르지 않는다

"넣을 수 있는 검증을 다 넣는다" 는 지침만으로는 실행자마다 결과가 달라진다. 그래서 종류마다 **적용 판정**을 둔다. 산출물의 어느 칸을 보면 적용 여부가 갈리는지를 지목하는 규칙이다.

- 01-requirements · 02-design 은 자기 몫 6종 **각각**에 대해 적용 또는 N/A 를 기록한다. 조용히 건너뛴 종류가 없어야 한다(공통 원칙 3).
- N/A 로 판정했으면 그 근거도 함께 적는다. 판정의 근거는 적용 판정이 지목한 칸이다.
- 04-verification 은 지정된 것이 빠짐없이 수행됐는지 대조한다.

## 01-requirements 가 지정하는 6종

### 기능

- **무엇**: 요구사항의 각 승인 기준이 실제로 만족되는지 확인한다.
- **적용 판정**: 01-requirements 의 `핵심 승인 기준` 이 하나라도 있으면 적용. 사실상 항상 적용된다.
- **산출물**: 승인 기준 -> 테스트 케이스 매핑. 자동화 가능한 것은 자동 테스트로, 불가능한 것은 수동 QA 항목으로 보낸다.
- **언어별로 갈리는 곳**: 테스트 러너와 어서션 라이브러리.

### 성능

- **무엇**: 응답 시간 · 처리량 · 자원 사용이 수치 목표를 만족하는지 측정한다.
- **적용 판정**: 01-requirements `비기능 요구사항 > 성능` 에 **수치**가 있으면 적용.
  - "빠르게" 처럼 수치가 없으면 공통 원칙 1 로 수치를 받아낸 뒤 판정한다.
  - 목표치를 세우려면 현재값이 필요할 수 있다. 재는 방법부터 세워야 하면 공통 원칙 4 의 실측 선행으로 간다.
- **산출물**: 측정 시나리오 + 목표치 + 측정 방법. 04-verification 이 실측치를 채운다.
- **언어별로 갈리는 곳**: 프로파일러와 벤치마크 하네스.

### 보안

- **무엇**: 위협 모델에 적힌 공격 경로가 실제로 막혔는지 점검한다.
- **적용 판정**: 아래 중 하나라도 해당하면 적용.
  - 01-requirements `비기능 요구사항 > 보안` 이 N/A 가 아니다.
  - 신뢰 경계를 넘는 입력을 받는다.
  - 인증 · 인가 · 비밀값을 다룬다.
- **산출물**: 보안 점검 기록. 양식은 `04-verification.md` 가 소유한다.
- **언어별로 갈리는 곳**: 취약점 스캐너, 의존성 감사 도구.

### 호환성

- **무엇**: 기존 사용자 · 데이터 · 호출자가 계속 동작하는지 확인한다.
- **적용 판정**: 이번 청크가 **이미 배포된** 인터페이스 · 저장 포맷 · 설정 스키마를 건드리면 적용. 순수 신규(유형 2a)면 건드릴 기존 표면이 없어 N/A.
- **산출물**: 깨질 수 있는 표면 목록 + 각각의 마이그레이션 또는 폴백 확인 항목.
- **언어별로 갈리는 곳**: ABI 안정성 개념의 유무, 직렬화 포맷 도구.

### 수동 QA

- **무엇**: 자동화가 불가한 인터랙티브 거동을 사람이 확인한다.
- **적용 판정**: 자동 e2e 로 재현할 수 없는 경계가 있으면 적용. GUI 조작, 외부 기기 연동, 사람의 판단이 필요한 출력이 여기 해당한다.
- **산출물**: cross-flow `qa-checklist.md`. 03-implementation 이 항목을 더하고 04-verification 이 결과를 채운다.
- **언어별로 갈리는 곳**: N/A -- 사람이 하는 확인이라 언어와 무관하다.

### e2e

- **무엇**: 사용자 관점의 전체 경로가 처음부터 끝까지 도는지 자동으로 확인한다.
- **적용 판정**: 요구사항에 사용자 시나리오가 있고 그것을 자동 실행할 수 있으면 적용. 시나리오는 있는데 자동 실행이 불가하면 e2e 가 아니라 수동 QA 로 보낸다.
- **산출물**: e2e 리포트. 양식은 `04-verification.md` 가 소유한다.
- **언어별로 갈리는 곳**: e2e 러너, 실행 환경 기동 방식.

## 02-design 이 지정하는 6종

### 유닛

- **무엇**: 공개 단위 하나의 동작을 격리해 확인한다.
- **적용 판정**: 02-design `모듈 구조` 의 모듈 중 **로직을 가진 것** 전부. 로직 없는 값 타입 · DTO · 인터페이스는 제외한다(03-implementation G14).
- **산출물**: 02-design 의 TDD 계획(테스트 케이스 목록)이 03-implementation 의 첫 RED 백로그가 된다.
- **언어별로 갈리는 곳**: 테스트 프레임워크, 테스트 파일 배치 관례, 목·페이크 작성 방식.

### 통합

- **무엇**: 실제 어댑터를 붙였을 때 경계가 맞물리는지 확인한다.
- **적용 판정**: 02-design 이 포트 뒤로 격리한 외부 의존(03-implementation G2)이 있으면 **어댑터마다** 적용. DB · 파일시스템 · 네트워크 · 시계가 대표적이다.
- **산출물**: 어댑터별 통합 테스트 목록 + 테스트 더블로 갈 것과 실환경으로 갈 것의 구분.
- **언어별로 갈리는 곳**: 실환경 기동 방식(컨테이너 · 픽스처 · 인메모리 대체물).

### 경합

- **무엇**: 레이스 · 데드락 · 순서 의존처럼 동시 실행에서만 나는 결함을 잡는다.
- **적용 판정**: 02-design `## 동시성 설계` 가 N/A 가 아니면 적용. hazard 표의 **각 행**이 대상이다.
- **산출물**: 03-implementation G16 에 따라 두 갈래로 나뉜다.
  - 대응 수단이 실제 코드 경로에 있는지 -> 유닛 · 정적 분석으로 확인
  - 실제 경합 거동 -> e2e 부하 시나리오 또는 QA 항목으로 등록해 04-verification 이 실행
- **언어별로 갈리는 곳**: sanitizer 유무(TSan 등)와 동시성 테스트 도구. 언어가 경합을 구조로 막으면(소유권 · 액터 모델) 적용 범위 자체가 줄어든다.

### 계약

- **무엇**: 인터페이스 약속을 제공자와 소비자 양쪽이 같은 것으로 알고 있는지 확인한다.
- **적용 판정**: 02-design `인터페이스 명세` 중 **양쪽을 이번 flow 가 다 만들지 않는** 인터페이스가 있으면 적용.
  - 다른 flow 나 외부 팀이 반대편을 구현하는 경우다.
  - 한 flow 안에서 양쪽을 다 만들면 통합 검증으로 충분하다.
- **산출물**: 계약 정의(스키마 또는 시그니처) + 제공자 쪽 · 소비자 쪽 각각의 테스트.
- **언어별로 갈리는 곳**: 계약 테스트 도구, 스키마에서 코드를 뽑는 생성기.

### 경계값

- **무엇**: 입력 범위의 끝 · 넘침 · 빈 값 · 거부돼야 하는 값을 확인한다.
- **적용 판정**: 02-design `인터페이스 명세` 의 입력 중 범위 · 크기 · 널 허용 여부가 정의된 것마다 그 경계가 대상. 03-implementation G6(부정 경로)이 요구하는 것과 같은 축이다.
- **산출물**: 입력별 경계 케이스 목록. 실물은 유닛 테스트로 흡수된다.
- **언어별로 갈리는 곳**: 정수 오버플로 거동(정의됨 · 미정의 · 예외), 없음을 표현하는 방식.

### 정적 분석

- **무엇**: 실행하지 않고 코드에서 잡히는 결함을 도구로 훑는다.
- **적용 판정**: 그 언어에 쓸 만한 정적 분석 도구가 있으면 **항상 적용**. 정할 것은 적용 여부가 아니라 어느 규칙 세트를 켜고 무엇을 통과 기준으로 삼을지다.
- **산출물**: 도구 · 규칙 세트 · 통과 기준(경고 0 인가, 신규 경고 0 인가).
- **언어별로 갈리는 곳**: 12종 중 가장 크게 갈린다. 도구 자체가 언어마다 다르다.

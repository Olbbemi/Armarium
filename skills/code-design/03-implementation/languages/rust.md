# Rust 고유 가드레일과 검증 도구

각 항목이 스켈레톤의 어느 축에서 왔는지는 아래와 같다. 축에 해당 항목이 없으면 그 언어에서 비자명하지 않다는 뜻이다.

| 출처 축 | 해당 항목 |
|---------|----------|
| 자원 · 수명 | RS-G1 · RS-G2 |
| 타입 · 인터페이스 표면 | RS-G3 · RS-G4 · RS-G5 |
| 빌드 · 진단 | RS-G6 · RS-G7 · RS-G8 |
| 동시성 프리미티브 | RS-G9 -- 데이터 경합은 컴파일러가 막으므로 남는 것이 이 하나뿐이다 |
| 테스트 조직 | RS-G10 |
| 12종 > 경계값 | RS-G11 |
| 12종 > 호환성 | RS-G5 |
| 12종 > 나머지 | 아래 "검증 12종 -- Rust 에서 쓰는 도구" |

- **RS-G1. `unsafe` 블록은 최소 범위로 좁히고, 그 블록이 성립하려면 무엇이 참이어야 하는지를 블록 옆에 적는다.**
  `unsafe` 는 컴파일러 검사를 끄는 것이라, 여기서 깨진 전제가 검사를 통과한 나머지 코드까지 UB 로 만든다. 전제를 적지 않으면 나중에 그 전제를 깨뜨린 수정을 알아볼 방법이 없다.

- **RS-G2. 플러시 · 커밋처럼 빠지면 안 되는 마무리는 명시적으로 호출하고 반환값을 확인한다.**
  누수는 Rust 의 안전 정의 밖이라 `mem::forget` 이 안전한 함수이고, `process::exit` 와 panic=abort 에서도 `Drop` 은 건너뛰어진다. 다른 것을 컴파일러가 다 보장하니 이것도 보장된다고 읽기 쉽지만 보장되지 않는다.

빠지면 안 되는 마무리를 `Drop` 실행에만 맡기지 않는다.
</FORBIDDEN>

- **RS-G3. 공개 표면은 `pub(crate)` 를 기본으로 두고, 크레이트 밖으로 낼 것만 `pub` 로 올린다.**
  `pub` 함수의 시그니처에 등장하는 타입은 따로 내보내지 않아도 함께 표면으로 끌려 나와, 의도하지 않은 타입까지 다음 릴리스에서 못 바꾸는 약속이 된다.

- **RS-G4. 크레이트 밖으로 내는 `enum` 과 구조체에는 `#[non_exhaustive]` 를 붙인다.**
  붙이지 않으면 variant 나 필드를 하나 더하는 것만으로 소비자의 `match` 와 구조체 리터럴이 깨져, 더하기가 곧 breaking change 가 된다.

- **RS-G5. 다른 언어나 다른 컴파일 단위와 주고받는 경계는 `extern "C"` + `#[repr(C)]` 로 고정하고, 그 경계를 바꾸면 호환성 검증 대상으로 올린다.**
  Rust 에는 안정된 ABI 가 없어 기본 표현의 레이아웃과 호출 규약이 컴파일러 버전에 따라 달라질 수 있다.

- **RS-G6. `Cargo.toml` 에 edition 과 `rust-version`(MSRV) 을 명시하고, 툴체인이 갈리면 `rust-toolchain.toml` 로 고정한다.**
  edition 은 문법과 기본 동작이 갈리는 단위이고, MSRV 를 적지 않으면 어느 툴체인부터 빌드가 깨지는지가 남의 환경에서만 드러난다.

- **RS-G7. 린터 경고 0 을 완료 조건에 넣는다.**
  컴파일러가 이미 많은 것을 막아 "컴파일되면 맞다" 에서 멈추기 쉬운데, 린터가 잡는 것은 컴파일은 되면서 틀린 관용구다. (검증 완료선 "무경고" 의 Rust 구체화.)

- **RS-G8. 라이브러리 코드에서 `Result` · `Option` 을 `unwrap()` 으로 풀지 않는다 -- 오류는 반환해 호출자에게 넘기고, 되돌릴 수 없는 전제 위반일 때만 `expect` 로 이유를 적어 멈춘다.**
  `unwrap` 은 panic 이라 호출자가 처리할 기회를 없애면서, 무엇이 어긋났는지도 남기지 않는다.

- **RS-G9. `std::sync` 의 락 가드를 보유한 채 `.await` 하지 않는다 -- 대기 구간을 걸쳐 잠가야 하면 async 런타임이 주는 락을 쓴다.**
  가드가 `.await` 를 가로질러 살아 있으면 그 future 가 `Send` 를 잃어 멀티스레드 런타임에 올라가지 않고, 올라가더라도 태스크가 양보한 사이 같은 락을 기다리는 다른 태스크와 맞물려 멈춘다. 컴파일러가 막아 주는 것은 데이터 경합까지고 데드락은 안전한 동작으로 분류되어 그대로 통과하며, `std::sync::Mutex` 는 재진입도 지원하지 않는다.

- **RS-G10. 유닛 테스트는 소스 파일 안 `#[cfg(test)] mod tests` 에, 통합 테스트는 `tests/` 디렉토리에 둔다.**
  `tests/` 의 테스트는 크레이트를 밖에서 링크해 `pub` 표면만 보므로, 어디에 두느냐가 무엇을 검증하는지를 정한다. 비공개 항목에 닿는 것은 소스 안에 둔 테스트뿐이다.

- **RS-G11. 오버플로가 날 수 있는 정수 연산은 의도를 골라 적는다 -- `checked_*` · `saturating_*` · `wrapping_*` 중 하나.**
  기본 연산은 디버그 빌드에서 panic 하고 릴리스 빌드에서 감싸므로, 디버그로만 테스트하면 릴리스에서 조용히 틀린 값이 나오는 경로가 걸리지 않는다.

## 검증 12종 -- Rust 에서 쓰는 도구

`verification.md` 가 각 종류에서 "언어별로 갈리는 곳" 으로 지목한 자리를 Rust 로 채운 것이다. 프로젝트가 이미 쓰는 도구가 있으면 그것을 따르고, 없을 때의 기본값으로 본다.

| 종류 | 도구 | 메모 |
|------|------|------|
| 기능 | 유닛과 같은 러너 | 승인 기준을 유닛과 e2e 로 나눠 담으므로 전용 도구가 없다 |
| 성능 | criterion (마이크로) · flamegraph · perf (프로파일) | 릴리스 프로파일로만 잰다. 디버그 빌드는 최적화가 꺼져 있어 수치가 비교 대상이 되지 않는다 |
| 보안 | cargo-audit (RustSec 자문 DB) · cargo-deny (라이선스 · 금지 크레이트 · 중복 버전) | crates.io 가 중앙 레지스트리라 `Cargo.lock` 만으로 감사가 성립한다 |
| 호환성 | cargo-semver-checks | 공개 표면 변경을 semver 등급과 대조한다. 안정 ABI 가 없어 바이너리 비교 대상은 RS-G5 의 `extern "C"` 경계뿐이다 |
| 수동 QA | N/A | 사람이 하는 확인이라 언어와 무관하다 |
| e2e | 언어 무관 -- 빌드한 바이너리를 프로세스로 띄워 확인한다 | |
| 유닛 | 내장 `#[test]` (`cargo test`) | 프레임워크를 고르는 자리가 아니다. 어서션 출력 보강이 필요하면 pretty_assertions 를 얹는 정도다 |
| 통합 | `tests/` 디렉토리 + 같은 내장 러너 | 배치가 곧 구분이라(RS-G10) 별도 도구가 없다 |
| 경합 | 컴파일러의 `Send` · `Sync` 검사 + loom (인터리빙 모델 검사) | 데이터 경합은 컴파일 단계에서 걸리므로 도구가 맡는 몫은 데드락과 순서 의존이다. RS-G9 는 clippy `await_holding_lock` 이, 메인 G17 의 락 순서는 loom 이 잡는다. `unsafe` 안의 경합은 Miri 가 본다 |
| 계약 | Rust 고유 도구 없음 | 스키마 언어(protobuf 등)를 쓰면 그쪽 생성기를 따른다 |
| 경계값 | 유닛에 흡수 + 릴리스 프로파일 재실행 | RS-G11 대로 거동이 두 프로파일에서 갈리므로 경계 케이스는 양쪽에서 돌린다 |
| 정적 분석 | clippy | 컴파일러가 정적 분석의 큰 몫을 이미 해서 clippy 는 그 위를 본다. `unsafe` 를 쓰면 Miri 를 더한다 -- 실행해서 보는 도구라 엄밀히는 정적 분석이 아니지만 그 자리를 채우는 것이 이것뿐이다 |

도구가 거의 다 `cargo` 서브커맨드라 C++ 처럼 계측 빌드를 몇 벌 만들지 정할 자리가 없다. 대신 Miri 를 비롯한 일부는 nightly 툴체인을 요구하므로, 그 경우 RS-G6 의 `rust-toolchain.toml` 로 어느 툴체인에서 도는지를 못 박는다.

# 흐름 A — 새 프로젝트 신규 구현

---

## 적용 상황

이 variant 는 다음 두 조건을 모두 만족할 때 적용된다.
- 2단계 산출물의 "적용 흐름"이 A (새 프로젝트 / 새 서비스)
- 변경 대상 코드 트리가 비어 있거나, 대상 모듈이 신규임

---

## 흐름별 사전 조사

메인 파일의 사전 조사(핸드오프 로드, 외부 검색, 사용자 확인)가 끝난 뒤 추가로 다음 항목을 확인한다.

### 1. 빌드 시스템 / 패키지 매니저 결정

언어 reference 파일의 기본값을 사용한다.
다른 선택지를 쓸 사유가 있으면 사용자에게 질문 (공통 원칙 1) 후 산출물의 "구현 결정 기록"에 사유를 남긴다.

### 2. 디렉토리 구조 컨벤션 확인

언어 reference 파일의 표준 디렉토리 레이아웃을 따른다.
2단계 모듈 구조와 매핑되지 않는 부분이 있으면 사용자에게 확인 (공통 원칙 1).

### 3. 테스트 프레임워크 결정

언어 reference 파일의 기본값을 사용한다.
다른 선택지를 쓸 사유가 있으면 사용자에게 질문 후 산출물에 기록.

### 4. 의존성 lock 파일 정책

언어별 표준 lock 파일을 사용한다 (예: `poetry.lock`, `Cargo.lock`, `vcpkg.json`).
lock 파일을 커밋할지 여부는 언어 reference 의 권장을 따른다.

---

## 흐름별 작업 흐름

다음 세 단계로 진행한다.

### 단계 1 — 프로젝트 스캐폴딩

1. 디렉토리 구조 생성 (2단계 모듈 구조를 그대로 코드 트리에 펼침)
2. 빌드 / 패키지 매니저 초기화 (언어 reference 의 초기화 명령 사용)
3. 첫 모듈에 빈 골격 + 첫 테스트 파일에 빈 골격 생성
4. 첫 빌드·테스트 실행 — "hello world" 수준 통과 확인

<PENETRATE>
스캐폴딩 직후 첫 빌드·테스트가 통과하는 것을 확인한 뒤 단계 2로 진입한다.
</PENETRATE>

<RICOCHET>
스캐폴딩이 깨진 상태로 단계 2(TDD 사이클)에 진입하지 않는다.
</RICOCHET>

### 단계 2 — TDD 사이클

2단계 TDD 계획의 모든 케이스를 다음 사이클로 처리한다.

1. **Red:** 다음 케이스의 테스트를 작성하고 실패 확인
2. **Green:** 테스트가 통과하는 최소 구현
3. **Refactor:** 2단계 설계 의도에 맞춰 구조 정리, 테스트 재실행으로 통과 유지 확인

<PENETRATE>
Red 단계에서 테스트가 실제로 실패하는 것을 확인한 뒤 Green 으로 진입한다.
</PENETRATE>

<RICOCHET>
테스트 실패 확인 없이 Green 단계로 진입하지 않는다 (의도하지 않은 통과 가능성).
</RICOCHET>

<RICOCHET>
Refactor 단계에서 테스트가 깨지면 즉시 롤백하고 원인 파악 없이 다음 사이클로 진행하지 않는다.
</RICOCHET>

<RICOCHET>
테스트 없이 구현 코드를 작성하지 않는다.
</RICOCHET>

### 단계 3 — 통합 빌드·테스트

모든 TDD 사이클이 끝난 후 전체 빌드·테스트를 실행해 통합 상태로 통과하는지 확인한다.
실패 시 5단계(디버깅) 진입.

메인 파일의 "산출물 형식" 템플릿에 다음 항목을 추가 채운다.

  - 초기 디렉토리 구조 (트리 형태)
  - 첫 빌드·테스트 통과 확인 시각

## 흐름별 완료 기준

메인 파일 완료 기준 체크리스트의 "흐름 variant 파일의 흐름별 완료 기준이 충족됨" 항목은 다음 세부 항목을 모두 충족함을 의미한다.

- [ ] 프로젝트 스캐폴딩이 완료됨 (빌드 시스템 초기화 + 첫 빌드·테스트 통과)
- [ ] 2단계 모듈 구조의 모든 모듈에 대응하는 코드 파일이 존재함
- [ ] TDD 사이클이 모든 케이스에 대해 Red -> Green -> Refactor 순서로 진행됨 (역순 / 생략 없음)
- [ ] 통합 빌드·테스트가 전체 통과함

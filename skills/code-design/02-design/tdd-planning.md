# TDD 계획 작성

02-design 에서 작성하는 것은 **테스트 케이스 목록**이다. 실제 테스트 코드는 03-implementation(Red -> Green -> Refactor)에서 작성한다. 새 프로젝트(흐름 A)와 기존 코드 변경(흐름 B) 양쪽의 TDD 계획이 이 파일을 공유한다.

---

## 1. 공통 작성 규칙

<PENETRATE>
TDD 계획의 테스트 단위는 모듈의 공개 인터페이스(public API) 단위로 쪼갠다.
</PENETRATE>

<RICOCHET>
내부 구현 함수를 테스트 단위로 삼지 않는다.
</RICOCHET>

<PENETRATE>
테스트 케이스는 happy path -> 실패 케이스 -> edge case 순으로 나열한다.
</PENETRATE>

<PENETRATE>
테스트는 이름 + 한 줄 설명으로만 적는다.
</PENETRATE>

<RICOCHET>
TDD 계획에 입출력 예시나 코드 스켈레톤을 포함하지 않는다.
</RICOCHET>

**이유:**
- 공개 인터페이스 기준이면 내부 구현이 바뀌어도 테스트 이름이 안 바뀐다
- happy path 먼저인 이유: 정상 동작이 정의돼야 그 외 케이스가 의미가 있다
- 케이스 목록만 정하면 충분: 03-implementation 에서 Red -> Green -> Refactor 사이클로 실제 코드 작성 시 참조

## 2. 케이스 구분 -- 회귀 가드 유무가 축

케이스의 구체화 수준은 소스 유무가 아니라 **인터페이스 명세 유무**에 달려 있다. 인터페이스 명세는 흐름 A/B 모두 02-design 이 만들어내므로, 소스가 없어도 happy/실패/edge 케이스는 구체적으로 적을 수 있다. 소스가 더해주는 것은 "회귀 가드" 한 축뿐이다.

| 케이스 | 작성할 테스트 |
|------|--------|
| A. 새 프로젝트 | 신규 케이스만 (회귀 가드 없음). 공개 인터페이스별 happy / 실패 / edge |
| B1. 기능 추가 | 새로 추가되는 공개 인터페이스에 대한 신규 케이스 |
| B2. 리팩터링 | 회귀 방지 케이스 -- 기존 동작 중 고정할 항목. 우선순위: 외부 관찰 동작 > 모듈 인터페이스 > 내부 구현. 기존 테스트가 있으면 그것으로 충분한지 검토 |
| B3. 기능 추가 + 리팩터링 | 위 둘 모두 |

흐름 B는 진입 시 식별한 케이스(B1/B2/B3, `extend_or_refactor.md` 0번)를 위 표에 대입한다.

### 회귀 가드의 의미

회귀 방지 케이스는 수동적 방치가 아니라 능동적 감시다. 검증하는 동작(단언)은 바꾸지 않고, 전환(리팩터링)이 진행되는 매 단계 끝에서 계속 통과(green)해야 한다. 리팩터링이 실수로 동작을 깨면 이 케이스가 실패해 잡아준다.

<PENETRATE>
회귀 방지 케이스가 검증하는 동작은 바꾸지 않고, 리팩터링 매 단계 끝에서 통과 상태를 유지한다.
</PENETRATE>

디렉토리/네임스페이스 이동 같은 조립 변경 때문에 테스트 파일의 import 경로나 이름공간은 기계적으로 손볼 수 있다. 그것은 검증 대상이 아니라 조립이므로 케이스 자체는 불변이다.

계약 자체가 바뀐 기존 케이스(시그니처 변경, 제거된 협력자 등)는 가드로 유지할 수 없다. 그 케이스는 폐기하고 바뀐 공개 인터페이스의 신규 케이스로 대체하며, 어떤 케이스가 왜 폐기되는지 함께 기록한다.

## 3. GUI / 외부 경계 어댑터 -- 단위 제외와 수동 검증

공개 API가 인터랙티브 루프 하나뿐인 경계(GUI/TUI 렌더 루프, 대화형 입력 어댑터 등)는 단위 테스트로 쪼개기 어렵다. 헥사고날에서 이런 driving 어댑터는 인프라 경계라, DB 드라이버를 단위 테스트하지 않듯 단위 대상에서 제외하고 수동 QA(인수 테스트)나 E2E로 검증한다.

<RICOCHET>
인터랙티브 렌더/입력 루프 자체를 단위 테스트 단위로 삼지 않는다.
</RICOCHET>

<PENETRATE>
단위 테스트에서 제외한 GUI/외부 경계 거동은 수동 QA 체크리스트나 E2E 시나리오 같은 별도 산출물로 명시해 커버리지가 조용히 누락되지 않게 한다.
</PENETRATE>

표현/매핑 로직이 무거우면(예: 활성 상태에 따라 같은 입력이 다른 동작이 되는 분기) 그 로직을 어댑터 밖의 순수 단위(상태 전이 함수 등)로 빼내 단위 테스트 대상으로 삼을 수 있다. 빼낼지 여부는 로직의 무게로 판단한다 -- 단순 매핑이면 그대로 두고 수동 검증, 실수 나기 쉬운 분기면 추출한다. 추출한 순수 단위는 더 이상 GUI 경계가 아니므로 위 제외 대상이 아니다.

별도 산출물의 위치/형식은 자유다. 수동 QA 체크리스트는 사람이 직접 재현하며 통과/실패를 체크하는 인수 테스트 형태로 두고, 단위로 가드되지 않는 거동만 담는다.

# 기존 코드 변경 설계

기존 코드가 있는 상태에서 기능을 추가하거나 / 구조를 바꾸거나 / 둘 다 수행하는 설계.
세 케이스를 한 파일에서 다룬다.

- **B1. 기능 추가만** — 외부 동작이 확장됨, 기존 동작은 보존
- **B2. 리팩터링만** — 외부 동작은 동일, 내부 구조만 변경
- **B3. 기능 추가 + 리팩터링** — 둘 다 동시에 진행

---

## 0. 케이스 식별

진입 시점에 B1 / B2 / B3 중 어디에 해당하는지 판단하고, 산출물의 "적용 흐름" 섹션에 명시한다.

**판단 기준:**
- 외부에서 관찰 가능한 동작이 새로 생기거나 확장되는가 -> B1 요소 있음
- 외부 동작 변화 없이 내부 구조만 바뀌는 부분이 있는가 -> B2 요소 있음
- 위 둘 다 해당 -> B3

모호하면 사용자에게 확인한다 (공통 원칙 1).

---

## 1. 기존 코드 탐색 (공통)

변경 대상과 영향 범위에 관련된 기존 코드를 파악한다. 모든 케이스 공통.

기존 코드 구조 파악에 code-analyze facet 산출물이 있으면 1차 입력으로 활용한다 -- 공통 원칙 6 (`principles.md`) 참조. 수작업 도구는 facet 이 없거나 특정 지점을 더 깊이 파야 할 때 보완으로 쓴다.

**자주 쓰이는 도구** (`references/tools.md` 의 코드 인텔리전스 참고):
- `tree` — 디렉토리 구조 파악
- `fd` — 관련 파일 빠르게 찾기
- `ripgrep (rg)` — 관련 키워드/패턴 검색
- `universal-ctags` — 함수/클래스/심볼 정의 위치 추적
- `tree-sitter` — AST 기반 구조 분석
- `graphviz`, `pycallgraph2`, `cargo-deps`, `include-what-you-use` — 의존성/호출 그래프 시각화 (사용자 확인용)

**활용 예:**
- 인증 관련 기능 추가 -> `rg "auth|login|session"` 으로 관련 위치 파악
- 특정 모듈 변경 영향 범위 -> 해당 심볼의 호출처 추적
- 순환 의존 여부 점검 -> 모듈 간 호출 그래프 확인

**탐색 범위는 케이스에 따라 다르다:**
- B1: 변경 지점 주변에 한정
- B2: 리팩터링 대상 모듈 전체 + 모든 의존 관계
- B3: 양쪽 모두

---

## 2. 현재 구조 분석 (B2, B3 해당)

리팩터링 대상의 현재 구조를 정확히 파악한다. B1만 해당하는 경우는 이 단계를 건너뛴다.

**작성 내용:**
- 현재 모듈 구조와 의존 관계
- 현재 코드의 문제 지점 (중복, 순환 의존, 단일 책임 위반 등)

<PENETRATE>
현재 모듈 구조와 의존 관계는 다이어그램으로 표현한다.
</PENETRATE>

**다이어그램 도구:**
- `mermaid` — 텍스트로 작성, md 파일에 바로 포함 가능. 간단한 구조에 적합
- `graphviz` — 복잡한 의존 그래프에 적합. dot 출력 -> 사용자 확인용

---

## 3. 영향 범위 파악 (B1, B3 해당)

새 기능이 기존 코드의 어느 부분에 영향을 주는지 명시한다. B2만 해당하는 경우는 이 단계를 건너뛴다.

**작성 내용:**
- 변경 없이 그대로 두는 부분
- 인터페이스만 확장하는 부분 (기존 호출자 영향 없도록)
- 기존 동작이 바뀌는 부분 (있으면 호환성 문제 검토)

### 기존 호출자 영향 검증

인터페이스를 변경하거나 확장할 때, 기존 호출자에게 영향이 없는지 확인한다.

**호출자 목록 수집:**

    rg "함수명|메서드명" --type-add 'lang:*.ext' -l   # 파일 목록
    universal-ctags --list-kinds                        # 심볼 정의 위치 파악 후 역추적

**호환성 체크리스트 (변경 대상 인터페이스별로 작성):**

| 체크 항목 | 확인 내용 |
|---------|---------|
| 파라미터 호환성 | 기존 호출 코드가 추가 파라미터 없이 그대로 동작하는가 (기본값 제공 여부 확인) |
| 반환값 호환성 | 기존 호출자가 기대하는 타입·구조가 유지되는가 |
| 에러 동작 호환성 | 기존 호출자가 처리하던 에러 케이스가 그대로 발생하는가 |
| 부수 효과 호환성 | DB 쓰기, 이벤트 발행 등 기존 부수 효과가 유지되는가 |

**영향이 불가피한 경우 처리:**
- 영향받는 호출자를 모두 열거한다
- 각 호출자에 필요한 변경을 명시한다
- 설계 결정 기록(9번)에 변경 이유와 호환성 파기 결정을 남긴다

<PENETRATE>
호환성을 파기하기 전에 사용자에게 파급 범위를 알리고 확인을 받는다.
</PENETRATE>

---

## 4. 모듈 / 인터페이스 설계 (공통)

설계 대상 모듈과 공개 인터페이스를 정의한다. 케이스별 강조점이 다르다.

| 케이스 | 강조점 |
|------|------|
| B1 | 기존 모듈 위에 새 모듈/인터페이스 얹기. 기존 모듈과의 연결 지점 명시. 의존 방향 단방향 확인 |
| B2 | 목표 구조 정의. 외부 인터페이스는 가능한 한 유지. 변경의 핵심 의도(예: "도메인 로직과 인프라 분리") 명시 |
| B3 | 위 둘을 합쳐 작성 |

**공통 작성 내용:**
- 모듈 목록 + 각 책임
- 모듈 간 의존 관계 (단방향 확인)
- 함수 시그니처 / API 엔드포인트 / 데이터 타입 (언어에 맞게)

<PENETRATE>
모듈 간 의존 관계는 다이어그램으로 표현한다.
</PENETRATE>

<RICOCHET>
순환 의존이 발생한 채로 설계를 종료하지 않는다.
</RICOCHET>

<PENETRATE>
순환 의존이 발견되면 즉시 재설계한다.
</PENETRATE>

**B1 / B3 추가 작성 내용:**
- 기존 모듈에서 새 모듈을 호출하는 지점
- 새 모듈에서 기존 모듈을 호출하는 지점

**외부 시스템 연동 시 추가 작성:**
- 외부 호출의 타임아웃 / 재시도 / 에러 처리 정책
- 테스트 시 mock / stub 대체 방식

다이어그램 도구는 1번 / 2번에서 사용한 것과 동일.

---

## 5. 전환 경로 (B2, B3 해당)

현재 구조에서 목표 구조로 안전하게 옮기는 단계를 정의한다. B1만 해당하는 경우는 이 단계를 건너뛴다.

**작성 내용:**
- 단계별 변경 순서
- 단계별 롤백 가능 여부

<RICOCHET>
리팩터링을 한 번에 다 바꾸지 않는다.
</RICOCHET>

<PENETRATE>
리팩터링은 단계별로 분할해서 적용한다.
</PENETRATE>

<PENETRATE>
각 단계 종료 시점에 시스템이 동작하는 상태여야 한다.
</PENETRATE>

B3의 경우 기능 추가와 리팩터링의 순서도 함께 명시한다 (예: "1) 리팩터링으로 자리 만들기 -> 2) 새 기능 얹기").

---

## 6. 데이터 흐름 (공통)

요청부터 응답까지, 데이터가 어떤 모듈을 거쳐 어떻게 변형되는지 정의한다.

**작성 내용:**
- 주요 시나리오별 데이터 흐름 (다이어그램)
- 상태 변경 지점 (DB 쓰기, 캐시 갱신, 외부 호출 등)
- 에러 발생 시 데이터 흐름

**케이스별 노트:**
- B1: 기존 흐름 위에 새 흐름이 어떻게 얹히는지 표시
- B2: 흐름은 동일해야 함
- B3: 새 흐름 + 리팩터링으로 인한 내부 경로 변화를 모두 표시

<PENETRATE>
B2 에서 데이터 흐름이 바뀌면 리팩터링이 아니라 동작 변경이므로 케이스를 B3 로 재분류한다.
</PENETRATE>

---

## 7. 비기능 요구사항 대응 (공통)

요구사항 문서의 비기능 요구사항 각각을 설계에 어떻게 반영하는지 명시한다.

**작성 내용:**
- 성능: 어느 모듈/지점에서 어떻게 보장하는지 (캐싱, 인덱스, 비동기 등)
- 보안: 인증/인가 위치, 민감 데이터 처리 모듈
- 확장성: 수평 확장 가능 지점, 병목 가능성
- 가용성: 장애 격리 / 복구 전략
- 호환성: 버전 관리 방식
- 운영: 로깅 / 모니터링 / 배포 단위

**케이스별 노트:**
- B1: 기존 코드의 비기능 특성을 깨지 않는지 함께 검토
- B2: 리팩터링이 비기능 특성에 미치는 영향(개선 / 유지 / 악화)을 항목별로 작성
- B3: 위 둘을 모두 검토

## 8. TDD 계획 (공통, 케이스별 차이)

TDD 계획 작성은 `skills/code-design/02-design/tdd-planning.md` 를 Read 툴로 로드해 따른다. 0번에서 식별한 케이스(B1/B2/B3)를 그 파일의 "케이스 구분" 표에 대입한다 — B1=신규, B2=회귀 방지, B3=양쪽.

---

## 9. 설계 결정 기록

주요 설계 결정에 대해 다음을 기록한다:
- 결정한 것
- 이유
- 고려했으나 채택하지 않은 대안과 그 사유

**B2 / B3 추가 항목:** "리팩터링하지 않고 그대로 두는 옵션"을 검토했는지 결과를 함께 기록한다.

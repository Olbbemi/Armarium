# 새 프로젝트 설계

기존 코드가 없는 상태에서 처음부터 구조를 설계한다.

---

## 1. 모듈 구조 정의

모듈 경계와 책임을 정한다.

**작성 내용:**
- 모듈 목록과 각 모듈의 책임 한 줄 요약
- 모듈 간 의존 방향 (단방향 의존이 원칙)
- 모듈 분할 기준 (다음 중 선택 + 사유):
  - 계층 기반 (예: presentation / domain / data) -- 전형적인 3-tier, CRUD 위주
  - 도메인 기반 (예: user / order / payment) -- 도메인 경계가 뚜렷하고 비즈니스 로직이 큰 경우
  - 기능 기반 (예: auth / search / notification) -- 도메인보다 사용자-기능 단위가 자연스러운 경우
  - 어느 쪽이 적합한지 모호하면 공통 원칙 1 에 따라 사용자에게 묻는다
- 디렉토리 배치: top-level 디렉토리 구조 + 모듈 -> 폴더 매핑 (세부 파일 위치는 03-implementation 몫 -- 이 매핑과 모순 안 되는 선)

<FORBIDDEN>
순환 의존이 발생한 채로 설계를 종료하지 않는다.
</FORBIDDEN>

**도구 활용:**

자주 쓰이는 도구 (`references/tools.md` 의 "다이어그램 / 시각화" 참고):
- `mermaid` -- 기본 선택. md 파일에 텍스트로 직접 작성, 별도 렌더링 단계 없음
- `graphviz` -- 의존 그래프 / 콜 그래프 등 복잡한 그래프. dot 출력 -> 사용자 확인용
- `plantuml` -- mermaid 로 표현 힘든 고급 UML(배치, 컴포넌트 등)이 필요하고 별도 파일/참조 형태가 허용될 때만

---

## 2. 인터페이스 명세

각 모듈의 공개 인터페이스를 정의한다.

**작성 내용:**
- 함수 시그니처 (이름, 인자, 반환 타입) -- 언어에 맞게
- API 엔드포인트 (HTTP 메서드, 경로, 요청/응답 형식)
- 데이터 타입 / 스키마 정의

**외부 시스템 연동 시 추가 작성:**
- 외부 호출의 타임아웃 / 재시도 / 에러 처리 정책
- 테스트 시 mock / stub 대체 방식

---

## 3. 데이터 흐름

요청부터 응답까지, 데이터가 어떤 모듈을 거쳐 어떻게 변형되는지를 정의한다.

**작성 내용:**
- 주요 시나리오별 데이터 흐름 (다이어그램)
- 상태 변경 지점 (DB 쓰기, 캐시 갱신, 외부 호출 등)
- 에러 발생 시 데이터 흐름

---

## 4. 동시성 / 통신 설계 (해당 시)

이 설계가 공유 가변 상태에 대한 동시 접근 또는 경계 너머 메시지 통신을 다루면, 02-design 게이트가 로드한 `skills/code-design/02-design/concurrency.md` / `skills/code-design/02-design/communication.md` 의 안내에 따라 산출물의 `## 동시성 설계` / `## 통신 설계` 섹션을 채운다. 해당 없으면 두 섹션 모두 N/A.

---

## 5. 비기능 요구사항 대응

요구사항 문서의 비기능 요구사항 각각을 설계에 어떻게 반영하는지 명시한다.

**작성 내용:**
- 성능: 어느 모듈/지점에서 어떻게 보장하는지 (캐싱, 인덱스, 비동기 등)
- 보안: 인증/인가 위치, 민감 데이터 처리 모듈
- 확장성: 수평 확장 가능 지점, 병목 가능성
- 가용성: 장애 격리 / 복구 전략
- 호환성: 버전 관리 방식
- 운영: 로깅 / 모니터링 / 배포 단위

---

## 6. TDD 계획

TDD 계획 작성은 `skills/code-design/02-design/tdd-planning.md` 를 Read 툴로 로드해 따른다. 새 프로젝트는 회귀 가드가 없으므로 전부 신규 케이스(케이스 구분 표의 A 행)에 해당한다.

---

## 7. 설계 결정 기록

주요 설계 결정에 대해 다음을 기록한다:
- 결정한 것
- 이유
- 고려했으나 채택하지 않은 대안과 그 사유

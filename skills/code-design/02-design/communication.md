# 통신 설계 (communication)

제어하지 못하는 경계 너머로 메시지를 주고받는 설계에서, 놓치면 구현 단계에서 문제가 되는 hazard 를 빠짐없이 짚고 각각의 대응을 설계 시점에 결정하기 위한 파일. 상류(02-design.md)의 게이트가 이 파일을 로드하기로 판정했을 때만 열린다.

대상 범위: 네트워크(HTTP / RPC / 소켓) + 메시지 전달형 IPC(파이프, 도메인 소켓, 로컬 소켓, 메시지 큐) + 상응하는 통신. 공유 가변 상태에 대한 동시 접근(스레드, 공유 메모리)은 이 파일이 아니라 `concurrency.md` 가 담당한다.

---

## 1. 통신 전제 (hazard 판정의 기준선)

hazard 표를 판정하기 전에, 이 설계의 통신이 어떤 계층을 기반으로 그 위에 무엇을 얹는지를 먼저 확정한다. 아래 hazard 는 전부 "이 계층이 보장해주는가, 내 책임인가"에서 갈리므로, 이 전제가 서야 개별 판정이 일관된다.

- **내가 직접 다루는 최상위 통신 계층 + 그 계층이 보장하는 것 / 내 책임으로 남는 것**
  예: HTTP(S) / gRPC / WebSocket / 원시 TCP · UDP · RUDP / 메시지 큐 · 브로커 / 로컬 IPC(파이프 · 도메인 소켓)
  -- 프로토콜 이름이 아니라, 그 계층이 순서 · 중복 · 유실 · 프레이밍 중 무엇을 보장하고 무엇이 내 책임인가로 판정한다. 스택을 밑까지 나열하지 않는다(HTTP 를 쓰면 그 밑 TCP 는 적지 않는다) -- 내가 직접 만지는 한 계층이 곧 보장의 경계선이다.
- **그 위에 얹는 자체 규약** (있으면): 메시지 타입 / 스키마 / 요청 - 응답 매칭 / 세션 · 핸드셰이크
- **통신 패턴**: 단일 요청 - 응답 / 스트리밍 / pub-sub / 양방향

## 2. hazard 체크리스트

로드 여부는 상류가 이미 정했다. 여기서는 통신 전제 위에서 아래 표의 **각 항목이 이 설계에 해당하는지**를 항목마다 판정한다. 트리거 · 키워드는 대응을 정하기 위한 검토 단서이지 처방이 아니다 -- 구체 값은 이 설계의 요구 · 제약에 맞춰 논의해 정한다.

해당으로 판정한 hazard 는 키워드 나열로 끝내지 않고 대응 결정까지 채운다. 아래 3절의 `대응 결정` 칸이 그 자리다.

| hazard | 언제 걸리나 (트리거) | 검토 키워드 / 패턴 |
|--------|---------------------|---------------------------|
| 부분 실패 / 타임아웃 | 경계 너머 호출이 무한 대기 / 무응답 / 중간 실패 -- 응답을 못 받으면 요청이 처리됐는지조차 알 수 없음(부분 실패) | 타임아웃 예산(deadline), 타임아웃 계층, 취소 전파, 실패 표면화 / 에러 전파 |
| 재시도 안전성 / 멱등성 | 실패에 재시도를 붙이려는데, 부작용 있는 연산이면 중복 위험 -- 멱등하지 않으면 재시도가 결제 / 주문을 중복시킴 | 멱등성 키, at-least-once / at-most-once / exactly-once, 지수 백오프 + 지터, 재시도 상한 / 예산, 재시도 불가 조건(4xx 등) 구분, retry storm 방지 |
| 순서 / 중복 | 여러 메시지 / 이벤트를 주고받는데 계층이 순서 · 중복을 보장 안 함 -- 도착 순서 뒤바뀜 / 중복 도착 (단일 요청 - 응답이면 대체로 해당 없음) | 시퀀스 번호, dedup, ordering 보장 여부, 인과 순서, at-least-once 면 소비 측 dedup / 멱등 처리(재시도 hazard 와 연결) |
| 프레이밍 (메시지 경계) | 스트림 계층(원시 TCP · 도메인 소켓 · 파이프)을 직접 다뤄 메시지 경계가 없음 -- 한 read 가 메시지를 잘라 오거나 여러 개를 붙여 옴 (HTTP · gRPC · 큐 등 메시지 계층이면 해당 없음) | 길이 프리픽스(length-prefix), 구분자(delimiter) 프레이밍, 부분 read 누적 버퍼, 최대 메시지 크기 제한 |
| 직렬화 / 인코딩 | 객체를 바이트로 변환해 주고받음 -- 인코딩 / 엔디안 / 문자셋 불일치, 부분 · 손상 데이터 파싱 | 직렬화 포맷(JSON / protobuf / MessagePack), 엔디안 · 문자셋 명시, 파싱 실패 시 처리, 신뢰 못 할 입력 검증 |
| 스키마 버전 / 호환 | 송신자와 수신자가 서로 다른 버전일 수 있음 -- 독립 배포 / 구버전 클라이언트 잔존 시 필드 추가 · 삭제로 깨짐 (송수신이 한 번에 같이 배포되면 해당 없음) | 하위 호환(backward) / 상위 호환(forward), 필드 추가는 optional, 필드 삭제 · 의미 변경 금지, 스키마 버저닝, tolerant reader |
| 백프레셔 / 흐름 제어 | 지속적 흐름에서 생산 속도 > 소비 속도 -- 버퍼가 무한정 쌓여 OOM / 지연 (단일 요청 - 응답이면 대체로 해당 없음) | 버퍼 한계, 레이트 리밋, flow control, 큐 깊이, 초과 시 정책을 명시(block=역압 전파 / drop=손실 허용 / 무정책=OOM), 유계 버퍼(bounded) |
| 연결 생명주기 | 지속 연결을 열어두고 씀(WebSocket / 스트림 / 큐 컨슈머 / 커넥션 풀) -- 상대가 끊겨도 한동안 감지 못 함, 재연결 시 요청 급증 / 세션 복구 필요 (매번 새로 여닫는 무상태 요청이면 대체로 해당 없음) | 하트비트 / keepalive, graceful close, 재연결 백오프 + 지터(thundering herd 방지), 재연결 후 상태 복구(resume vs 재시작) |
| 장애 격리 / 연쇄 전파 방지 | 여러 원격 의존에 기대는데, 한 의존이 느려지거나 죽으면 그 장애가 호출자로 · 다시 상위로 연쇄 전파(cascading) -- 리소스 고갈로 전체 장애 (단일 의존 / 로컬 완결이면 대체로 해당 없음) | 서킷 브레이커, bulkhead, 폴백(fallback), 타임아웃 격리, fail fast |
| 전달 보장 / 손실 | 메시지가 유실될 수 있는데, 이 통신에 요구되는 전달 보장 등급을 정해야 함 -- at-most-once(유실 허용) / at-least-once(유실 불가, 중복 대비 필요) / exactly-once 근사 (유실돼도 되는 로그성이면 약하게) | ack / 재전송, durable queue, 아웃박스 패턴, 데드레터, 전달 의미론 등급 선택, durable 저장 vs 사후 재처리(dead letter) |
| 분산 트랜잭션 / 일관성 | 하나의 논리적 변경이 여러 서비스 / 저장소에 걸쳐 일어나 부분 커밋 위험 -- 한쪽만 반영되고 다른 쪽은 실패 (단일 저장소 트랜잭션으로 끝나면 해당 없음) | saga, 보상 트랜잭션(compensating), 2PC, 최종 일관성(eventual), 아웃박스, 멱등 소비 |

## 3. 산출물 기록

해당하는 각 hazard 의 대응 결정을 02-design 산출물의 `## 통신 설계` 전용 섹션에 남긴다.

```markdown
## 통신 설계
(communication.md 로드 시. 아니면 N/A)
| hazard | 해당 | 대응 결정 |
|--------|------|----------|
| 부분 실패 / 타임아웃 | 해당 | 외부 API 호출에 3s 데드라인 + 취소 전파 |
| 순서 / 중복 | N-A | 단일 요청 - 응답이라 다중 메시지 순서 문제 없음 |
```

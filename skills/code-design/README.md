# code-design

새 기능·서비스 개발의 설계부터 구현·검증까지를 단계로 나눈 **개발 파이프라인 지도** 스킬.

## 무엇을 하나

전체 개발 흐름을 5단계(`00-ideation` ~ `04-verification`)로 정의하고, 각 단계의 목적·완료 기준·단계 전환 규칙을 제공한다. 지금 어느 단계인지 판단하고, 그 단계의 진입 파일로 안내한다.

## 언제 쓰나

`/code-design` 호출, 또는 "어디서부터 시작해?", "지금 뭐 해야 해?", "전체 흐름이 어떻게 돼?" 처럼 새 개발의 시작점·현재 단계·다음 작업 파악이 필요할 때.

## 구조

**단계 공통 파일**

- `overview.md` -- 파이프라인 지도(진입점). 어느 단계든 **먼저 읽고** 진입
- `principles.md` -- 모든 단계 공통 원칙 10가지 (하위 단계는 여기 원칙을 재기술하지 않고 참조만)
- `cross-flow.md` -- flow 를 넘어 유지되는 파일 넷(`roadmap.md` · `architecture.md` · `decisions.md` · `qa-checklist.md`)의 규격
- `verification.md` -- 검증 12종의 정의 · 적용 판정 · 산출물

**단계별 진입 파일**

- `00-ideation.md` -- 구상 (무엇을 왜 만들지/만들지 말지 방향 정의, go/no-go)
- `01-requirements.md` -- 요구사항 명세 + 검증 6종 지정
- `02-design.md` -- 설계 + 검증 6종 지정 (`02-design/new_project.md` · `02-design/extend_or_refactor.md` 분기, `02-design/tdd-planning.md` TDD 계획, 조건부로 `concurrency.md` · `communication.md`)
- `03-implementation.md` -- 구현. 최소 제약 가드레일(G1~G19) + 검증 틀 작성 (언어 고유 가드레일은 `03-implementation/languages/`)
- `04-verification.md` -- 검증. 지정 12종을 실행해 판정
- `05-coverage.md` -- 실행 커버리지 추출 (순차 흐름의 단계가 아니라 도구 단계). lcov 트레이스를 뷰어용 데이터로 바꾸는 변환기는 `05-coverage/lcov-to-coverage.py`

## 단계와 정상 흐름

```
00-ideation -> 01-requirements -> 02-design -> 03-implementation -> 04-verification
```

`00-ideation` 에서 `01-requirements` 로의 전환도 hard 의존이며, 방향이 명확하면 `00-ideation` 은 fast-path 로 가볍게 통과한다(건너뛰지 않음). `00-ideation` 에서 no-go 면 파이프라인에 진입하지 않는다.

| 단계 | 목적 |
|------|------|
| `00-ideation` | 무엇을 왜 만들지/만들지 말지 방향 정의, go/no-go |
| `01-requirements` | 확정 방향을 검증 가능한 요구사항으로 명세 + 요구 유래 검증 지정 |
| `02-design` | 아키텍처·모듈 구조·인터페이스 확정 (+ TDD 계획) + 설계 유래 검증 지정 |
| `03-implementation` | 설계 기반 동작 코드 작성 + 지정된 검증의 산출물 틀 작성 |
| `04-verification` | 지정 12종을 실행해 판정. 결함은 전수 검증 후 사용자 승인 받아 `03-implementation` 회귀 |

리팩터링은 정규 단계가 아니며, 필요하면 별도 작업으로 뺀다.

## 검증은 지정 -> 작성 -> 판정으로 흐른다

무엇을 검증할지는 검증 단계가 아니라 **상류 두 단계가 정한다**. 재량으로 고르지 않고 산출물의 특정 칸을 보고 가른다.

```
01-requirements (6종 지정) --+
                             +--> 03-implementation (틀 작성) --> 04-verification (실행 · 판정 · 대조)
02-design       (6종 지정) --+
```

| 지정 단계 | 맡는 종류 | 절단 기준 |
|----------|----------|----------|
| `01-requirements` | 기능 · 성능 · 보안 · 호환성 · 수동 QA · e2e | 검증이 필요한 근거가 요구사항 문장에 있다 |
| `02-design` | 유닛 · 통합 · 경합 · 계약 · 경계값 · 정적 분석 | 설계 결정이 만든 위험이다 |

두 단계는 자기 몫 6종 **각각**에 적용 또는 N/A 를 기록하고, `04-verification` 이 그 지정과 실제 수행을 대조한다. 각 종류의 정의·적용 판정·산출물은 `verification.md` 가 단일 출처다.

커버리지는 이 12종에 없다. 검증 종류가 아니라 검증이 충분한지를 보는 지표라, `04-verification` 이 판정을 마친 뒤 그 판정 자체를 평가하는 입력으로 쓴다.

## 단계 전환 규칙

각 단계 종료 시 `handoff.md` 를 **먼저** 쓰고, 그 내용에서 발췌해 `checklist.md` 를 만들어 제시한다.

```
작업 -> handoff.md -> checklist.md -> 완료 기준 동반 검증 -> 사용자 서명 -> 다음 단계
```

`checklist.md` 골격은 `principles.md` 의 "단계 전환 규칙" 이 소유한다 -- 상단 `## 결정 요약`(사용자가 이 단락만 보고 사인오프할 수 있어야 한다), `## 완료 기준`, `## N/A 항목 확인`, 그리고 `<!-- -->` 주석 가이드로 들어가는 `## 피드백` · `## 사용자 승인`. 각 단계 파일은 이 골격을 다시 그리지 않고 앞 두 절에 넣을 항목만 정의한다.

- 승인 서명 = 사용자가 두 칸의 주석을 직접 지우는 것 (Claude 는 대신 안 함)
- 두 칸 모두 주석 해제 -> 승인 -> 다음 단계 진입 (하나라도 주석이면 재요청)
- 승인 확인 시 Claude 가 그 시점 시각을 스탬프

단계별 완료 기준 상세는 각 단계 파일의 완료 기준 섹션(`## 완료 기준`, `04-verification` · `05-coverage` 는 `## 완료선`)을 단일 출처로 본다.

## 산출물 저장 경로

모든 단계 산출물은 **프로젝트 루트(git 최상위)** 기준으로 저장된다. code-design 은 **루트에서만** 실행하고, 작업 대상은 브랜치 + 작업할 경로를 **입력으로 받는다**.

| 구분 | 두는 곳 | 무엇이 가나 |
|------|--------|-----------|
| within-flow | `code-design/<브랜치 슬러그>/` | 그 flow 안에서만 쓰는 산출물 |
| cross-flow | `code-design/` 루트 (flat) | flow 를 넘어 다음 flow 가 입력으로 읽는 것 |

슬러그는 브랜치 이름의 `/` 를 `_` 로 치환한 것이다. 무엇이 cross-flow 로 가는지는 `cross-flow.md` 의 "등재 기준" 이 가른다 -- 이번 flow 가 코드를 바꾼 뒤에도 그 문장이 참인가.

**착수 전 루트·브랜치·작업할 경로·작업 성격·진입 단계를 확인받고, 중간 진입인데 직전 핸드오프가 없으면 진행하지 않는다**(overview "프로젝트 루트 확인"). 구체적 경로 패턴은 `principles.md` 의 "단계 산출물 저장 정책" 참조.

## 코드 분석 산출물(facet) 연계 (선택)

기존 코드를 다루는 단계(`00-ideation` · `01-requirements` · `02-design` · `03-implementation`)에서 코드 분석 산출물(facet)이 있으면, 활용 여부를 물어 1차 입력으로 삼는다(공통 원칙 6). 필수는 아니며, facet 의 유무·종류·경로는 프로젝트 `CLAUDE.md` 를 따른다. 여러 벌(브랜치별 등)이 있으면 어느 것을 쓸지 확인한다.

## 이 스킬을 고칠 때

단계를 새로 추가하면 폴더명·산출물 경로·산문 지칭을 모두 `NN-name` 단일 토큰으로 짓는다(예: `05-coverage`). 진입 게이트·핸드오프 테이블·`roadmap.md` 전이가 전부 단계 이름을 키로 참조하므로, 이 규약을 벗어난 이름은 그 참조들을 깨뜨린다.

산문에서 단계를 `01` · `02` 로 줄여 쓰지 않는다. 항상 `01-requirements` · `02-design` 처럼 전체 토큰으로 쓴다(`.md` 는 안 붙임).

## 주의

개별 단계 파일을 단독 실행하지 않는다. 반드시 `overview.md` 를 먼저 읽고 진입한다.

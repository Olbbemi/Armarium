# code-design

새 기능·서비스 개발의 설계부터 구현·검증까지를 단계로 나눈 **개발 파이프라인 지도** 스킬.

## 무엇을 하나

전체 개발 흐름을 4단계로 정의하고, 각 단계의 목적·완료 기준·단계 전환 규칙을 제공한다. 지금 어느 단계인지 판단하고, 그 단계의 진입 파일로 안내한다.

## 언제 쓰나

`/code-design` 호출, 또는 "어디서부터 시작해?", "지금 뭐 해야 해?", "전체 흐름이 어떻게 돼?" 처럼 새 개발의 시작점·현재 단계·다음 작업 파악이 필요할 때.

## 구조

- `overview.md` — 파이프라인 지도(진입점). 어느 단계든 **먼저 읽고** 진입
- `00-principles.md` — 모든 단계 공통 원칙 (하위 단계는 여기 원칙을 재기술하지 않고 참조만)
- 단계별 진입 파일
  - `01-requirements.md` — 요구사항 분석
  - `02-design.md` — 설계 (`02-design/new_project.md` · `02-design/extend_or_refactor.md` 분기, `02-design/tdd-planning.md` TDD 계획)
  - `03-implementation.md` — 구현. 경량 "최소 제약" 가드레일(G1~G14) 묶음 (언어 고유 가드레일은 `03-implementation/languages/cpp.md`)
  - `04-verification.md` — 검증. 03 산출물로 e2e·수동 QA·보안 판정

## 4단계와 정상 흐름

```
1 요구사항 -> 2 설계 -> 3 구현 -> 4 검증
```

| 단계 | 목적 |
|------|------|
| 1 요구사항 분석 | 해결할 문제와 범위를 명확히 |
| 2 설계 | 아키텍처·모듈 구조·인터페이스 확정 (+ TDD 계획) |
| 3 구현 | 설계 기반 동작 코드 작성 + 검증 산출물 틀 작성 |
| 4 검증 | 03 산출물로 e2e·수동 QA·보안 판정. 결함은 전수 검증 후 사용자 승인 받아 03 회귀 |

정적 분석·리팩터링은 정규 단계가 아니며, 필요하면 별도 작업으로 뺀다.

## 단계 전환 규칙

각 단계 종료 시 완료 기준 체크리스트와 피드백 칸을 제시한다.

- 모든 항목 체크 + 피드백 없음 -> 다음 단계 진입
- 피드백이 있으면 -> 반영 후 재제시

단계별 완료 기준 상세는 `overview.md` 의 "각 단계 요약 및 완료 기준" 참조.

## code-analyze 연계 (선택)

기존 코드를 다루는 단계(요구사항·설계·구현)에서 [`code-analyze`](../code-analyze/README.md) 의 facet 분석 산출물이 있으면, 활용 여부를 물어 1차 입력으로 삼는다(공통 원칙 6). 필수는 아니며, 버전별로 누적된 경우 어느 버전을 쓸지 확인한다.

## 산출물 저장 경로

모든 단계 산출물은 **프로젝트 루트(= Claude 실행 디렉토리 CWD)** 기준으로 저장된다. 프로젝트 루트에 대해 별도 확인을 받지 않는다. 구체적 경로 패턴은 `00-principles.md` 의 "단계 산출물 저장 정책" 참조.

## 주의

- 개별 단계 파일을 단독 실행하지 않는다. 반드시 `overview.md` 를 먼저 읽고 진입한다.

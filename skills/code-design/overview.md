# 코드 설계 및 구현 파이프라인 -- Overview

<FORBIDDEN>
이 파일을 읽지 않은 상태에서 개별 단계 스킬을 단독으로 실행하지 않는다.
</FORBIDDEN>

전체 개발 파이프라인 지도.
어떤 단계들이 있고 지금 어디로 진입할지, 각 단계의 목적이 무엇인지를 안내한다.
완료 기준은 각 단계 파일이, 공통 규약(단계 전환 등)은 principles.md 가 단일 출처다.

이 문서에 명시된 모든 파일 경로는 Read 툴로 로드해 따른다.

## 용어 -- flow

flow 는 이 파이프라인을 한 바퀴 도는 것이다. 청크 하나를 00-ideation 부터 04-verification 까지(중간 진입이면 그 단계부터) 끝까지 진행하는 과정을 가리킨다.

flow 의 경계는 git 브랜치다 -- 한 작업 = 한 브랜치 = 한 청크 = 한 flow. 새 브랜치를 따면 새 flow 이고, 같은 브랜치라면 여러 세션 · 여러 날에 걸쳐 진행해도 한 flow 다. 중간 진입으로 뒤 단계만 돌거나 05-coverage 를 단독 실행해도 그 브랜치의 flow 안이다.

산출물은 이 경계로 갈린다.

| 구분 | 뜻 | 두는 곳 |
|------|-----|--------|
| within-flow | 그 flow 안에서만 쓰는 산출물 | `code-design/<브랜치 슬러그>/` |
| cross-flow | flow 를 넘어 다음 flow 가 입력으로 읽는 것 | `code-design/` 루트 |

within-flow 산출물도 git 에 남는다 -- 두 구분을 가르는 것은 보존 여부가 아니라 다음 flow 가 입력으로 읽어도 되는가다(원칙 5).

cross-flow 파일 넷의 목록은 아래 "cross-flow 층" 절에, 각 파일의 규격과 청크 정의는 `skills/code-design/cross-flow.md` 에 있다.

## 프로젝트 루트 확인 (착수 사전, 필수)

이 파이프라인의 모든 산출물은 **프로젝트 루트** 기준으로 저장된다. 프로젝트 루트는 **git 최상위**이며, code-design 은 **루트에서만** 실행한다. 대상(어느 컴포넌트/서브트리를 작업하는지)은 디렉토리를 옮겨 다니는 대신 **입력으로 받는다**. 착수 전 아래 사전 확인을 반드시 거친다.

**사전 확인 5스텝**

1. **루트 판정** -- `git rev-parse --show-toplevel` 로 최상위를 구해 CWD 와 비교한다. 일치하면 루트로 보고(스텝 5 에서 최종 확인), 불일치(하위에서 실행 중)면 중단하고 루트에서 재시작하도록 안내한다. git 조회가 실패하면(git 레포 아님) 자동 판정을 포기하고 스텝 5 에서 CWD 를 루트로 볼지 확인받는다.
2. **입력 수집** -- 브랜치와 작업할 경로(이 flow 가 대상으로 삼는 소스 서브트리, 루트 기준 상대경로)를 받는다. 작업할 경로가 실제로 존재하는지 확인하고, 없으면 다시 받는다. 작업 성격(새로 만드는가 / 기존 코드를 고치는가)도 함께 받되, 브랜치 폴더나 `architecture.md` 에 이미 적혀 있으면 묻지 않고 읽어서 표시한다.
3. **진입 단계 판정** -- 브랜치 폴더의 산출물을 훑어 어디까지 진행됐는지 판정한다. 판정 규칙과 첫 진입 처리는 "단계 진입 판단" 을 따른다. 00-ideation 진입은 중간 진입이 아니라 신규 진입이다 -- 앞 단계가 없어 읽어들일 직전 핸드오프도 없다.
4. **데이터 존재 검사 (중간 진입 한정)** -- 진입 단계가 읽어야 할 것이 실제로 있는지 확인한다. 없으면 진행하지 않고 노티한다.
   - **직전 핸드오프** -- `{프로젝트 루트}/code-design/<브랜치 슬러그>/` 아래에 있어야 한다. 형태는 단계마다 다르다.
     - 01-requirements 진입 -> `00-ideation/handoff.md`
     - 02-design 진입 -> `01-requirements/handoff.md`
     - 03-implementation 진입 -> `02-design/handoff.md`
     - 04-verification 진입 -> 03-implementation 이 세운 검증 틀. e2e 리포트 · 보안 점검은 `03-implementation/` 에, 수동 QA 체크리스트는 cross-flow 층 `code-design/qa-checklist.md` 에 있다.
   - **핸드오프가 가리키는 cross-flow 파일** -- 핸드오프는 cross-flow 층의 사실을 본문으로 다시 적지 않고 포인터로만 가리킨다(`cross-flow.md` 공통 규칙). 가리키는 파일이 없으면 그 정보가 사라진 것이므로 중단한다.
     - 예: 02-design `handoff.md` 의 `## 설계 결정 기록` 이 `decisions.md #12~#15` 를 가리키는데 `code-design/decisions.md` 가 없으면 중단.
     - 핸드오프가 안 가리키는 cross-flow 파일은 없어도 진행한다. 첫 flow 에는 아직 안 생겼을 수 있다.
5. **되묻기 확인** -- 루트 · 브랜치 · 작업할 경로 · 작업 성격 · 진입 단계 · 진행 상황을 요약해 보여주고, 사용자가 확인해야 진행한다.

## cross-flow 층

flow 를 넘어 유지되는 파일 넷은 `code-design/` 루트에 flat 하게 둔다. 각 파일이 소유하는 사실의 축, 내용 규격, 쓰는 단계와 읽는 단계는 `skills/code-design/cross-flow.md` 가 단일 출처다.

파일 넷은 `roadmap.md`(청크 상태) · `architecture.md`(시스템 제약 + 기술 스택) · `decisions.md`(설계 결정) · `qa-checklist.md`(수동 QA 회귀 확인 항목)다.

무엇을 여기 올리고 무엇을 브랜치 폴더에 두는지는 `cross-flow.md` 의 "등재 기준" 이 가른다 -- 이번 flow 가 코드를 바꾼 뒤에도 참인 문장인가.

청크(하나의 flow 가 통째로 담당하는 작업 범위)와 그 상태 플래그도 `cross-flow.md` 의 "roadmap.md" 절에서 정의한다. 브랜치 폴더의 `handoff.md` 는 이 축들을 다시 적지 않고 참조한다.

## 실행 순서

착수할 때 어떤 순서로 도는지를 본다.

- 정상 흐름은 00-ideation -> 01-requirements -> 02-design -> 03-implementation -> 04-verification 순서로 진행한다.
- 방향이 이미 명확하면 00-ideation 은 fast-path 로 가볍게 통과한다(단계를 건너뛰지는 않는다 -- `00-ideation.md` 참조). 00-ideation 에서 진행 판단이 no-go 면 파이프라인에 진입하지 않고 00-ideation 에서 종료한다.
- 05-coverage(커버리지 추출)는 순차 흐름의 단계가 아니라 두 모드로 실행되는 도구 단계다 -- 04-verification 이 완료 판정에 쓸 수치를 얻으려고 호출하거나, code-design 로드 후 단독으로 실행한다. 단독 실행 시 "중간 진입엔 직전 핸드오프 필수" 규칙의 예외로, 직전 핸드오프 없이 코드/테스트를 직접 읽어 시작한다(선결 게이트: 코드 존재 + 빌드 성공). 상세는 `05-coverage.md`.

## 단계 간 이동

단계를 넘길 때마다 본다. 무엇을 넘기고, 무엇을 입력으로 삼고, 어떤 경로로 되돌아오는지다.

**무엇을 넘기나**

- 전환 절차(checklist.md 먼저 작성 -> 완료 기준 동반 검증 -> 사용자 서명 -> 다음 단계)의 단일 출처는 `principles.md` 원칙 5 의 "단계 전환 규칙" 이다. 각 단계는 그 규약을 따른다.
- 00-ideation 에서 01-requirements 로의 전환도 다른 단계와 같은 hard 의존이다 -- 01-requirements 는 00-ideation 의 핸드오프를 입력으로 받는다.
- 단계 간 핸드오프의 형태는 단계마다 다르다 -- 00-ideation / 01-requirements / 02-design 은 `handoff.md` 문서가, 03-implementation -> 04-verification 은 코드와 검증 산출물 틀이 그 역할을 한다(03-implementation 은 별도 `handoff.md` 를 만들지 않음). 04-verification 은 하류 단계가 없어 핸드오프가 필수가 아니다(상세는 원칙 5 "핸드오프는 단계별로 형태가 다르다" 참조).

**무엇을 입력으로 삼나**

- 각 flow 는 자기 브랜치 폴더(`code-design/<브랜치 슬러그>/`)와 cross-flow 층만 입력으로 삼는다. 다른 브랜치(옛 flow)의 핸드오프는 참고하지 않는다(원칙 5).
- 결정 지연(보류)은 02-design 까지 모두 해소되거나 로드맵으로 escalation 되어, 03-implementation 진입 시 열린 보류가 0 이다(원칙 4).

**어떻게 되돌아오나**

- 진행에 필요한 사실이 없으면 그 단계에서 실측한다. 잰 값을 자기 핸드오프에 둘지 cross-flow 층으로 올릴지는 `cross-flow.md` "등재 기준" 이 가른다. 재는 방법부터 세워야 할 만큼 크면 로드맵에 선행 청크로 올리고 이 청크를 내린다(원칙 4 · `cross-flow.md` "선행 관계"). 브랜치를 유지한 채 선행 flow 뒤에 이어가므로 같은 flow 다.
- 04-verification 은 검증만 하고 끝나지 않고 파이프라인을 되돌릴 수 있다 -- 발견된 결함은 03-implementation 회귀(지금 고침) 또는 로드맵 descope 로, 요구에 없던 신규 범위는 로드맵 후보로 라우팅한다. 커버리지 미달도 같은 되돌림 대상이다 -- 케이스가 모자라면 02-design 으로, 케이스는 있는데 테스트가 없으면 03-implementation 으로 보낸다. 결함 집계·승인 게이트 절차의 상세는 `04-verification.md`.

## 검증 배치

검증은 한 단계에 몰려 있지 않다. 어느 단계가 어느 검증 종류를 맡는지는 이 표가 단일 출처다. 각 종류가 무엇이고 이번 청크에 적용되는지 어떻게 가르는지는 `skills/code-design/verification.md` 가 소유한다.

| 단계 | 검증에서 맡는 일 | 다루는 검증 종류 |
|------|----------------|----------------|
| 00-ideation | 없음 -- 방향을 정할 뿐 검증에 관여하지 않는다 | -- |
| 01-requirements | 요구에서 나오는 검증을 지정하고 수용 기준을 정한다 | 기능 · 성능 · 보안 · 호환성 · 수동 QA · e2e |
| 02-design | 설계에서 나오는 검증을 지정하고 테스트 케이스를 계획한다 | 유닛 · 통합 · 경합 · 계약 · 경계값 · 정적 분석 |
| 03-implementation | 지정된 검증의 틀을 만들고 자동 테스트를 구현한다 | 01-requirements·02-design 이 지정한 전부 |
| 04-verification | 실행해 판정하고, 지정된 검증이 빠짐없이 수행됐는지 대조한다 | 01-requirements·02-design 이 지정한 전부 |

지정은 01-requirements·02-design 이 나눠 갖고, 작성은 03-implementation 이, 판정은 04-verification 이 몰아서 한다. 두 곳에서 지정된 검증이 하나의 실행 경로로 합류한다.

지정과 수행이 어긋나는 것은 04-verification 이 막는다 -- 04-verification 의 완료 기준이 "01-requirements·02-design 이 지정한 검증 중 수행되지 않은 것이 없다" 를 요구하므로, 지정만 하고 빠뜨린 검증은 그 자리에서 드러난다.

01-requirements 와 02-design 을 가르는 기준은 그 검증이 필요한 근거가 어디 있는가다 -- 요구사항 문장에 있으면 01-requirements, 설계 결정이 만든 위험이면 02-design.

커버리지는 이 표에 없다. 검증 종류가 아니라 검증이 충분한지를 보는 지표이므로, 04-verification 이 판정을 마친 뒤 그 판정 자체를 평가하는 입력으로 쓴다(위 "단계 간 이동" 참조).

## 단계 내 진행도 (TaskCreate)

단계 내부 구조적 체크포인트를 TaskCreate 로 시각화하는 공통 규칙의 단일 출처는 `principles.md` 원칙 7("단계 내 진행도")이다. 구체적 체크포인트 목록은 각 단계 파일이 정의한다.

## 단계 진입 판단

진입 단계는 사용자에게 상황을 묻지 않고 **브랜치 폴더의 산출물로 판정한다.** 원칙 5 가 단계 전환을 "checklist.md 작성 -> 완료 기준 동반 검증 -> 사용자 서명" 으로 정의하므로, `checklist.md` 의 사용자 서명이 그 단계의 완료 표지다.

00-ideation 부터 04-verification 까지 차례로 훑는다.

| 브랜치 폴더에서 본 것 | 판정 |
|---------------------|------|
| 브랜치 폴더 자체가 없다 | 첫 진입 -- 아래 "첫 진입" 으로 넘어간다 |
| `{단계}/checklist.md` 에 사용자 서명이 있다 | 그 단계는 완료. 다음 단계로 넘어가 계속 훑는다 |
| `{단계}/checklist.md` 는 있는데 서명이 없다 | 그 단계가 진행 중 -- 여기서 이어간다 |
| `{단계}/` 가 없고 앞 단계가 완료됐다 | 여기가 진입 단계다 |

이 훑기가 착수 확인의 `진행 상황` 줄을 그대로 채운다. 단계마다 완료 / 진행 중 / 미착수 중 하나로 표시한다.

판정 결과는 스텝 5 의 착수 확인에 실어 확인받는다. 사용자가 다른 단계를 지목하면 그쪽을 따른다 -- 04-verification 을 마친 뒤 결함 때문에 02-design 으로 되돌리는 경우가 여기 해당한다.

05-coverage 는 이 훑기에 넣지 않는다. 순차 흐름의 단계가 아니라 04-verification 이 호출하거나 사용자가 단독으로 지목하는 도구 단계다.

### 첫 진입 -- 읽을 산출물이 없을 때

브랜치 폴더가 없으면 판정할 근거가 없으므로 상황으로 정한다.

| 상황 | 진입 단계 |
|------|----------|
| 무엇을 만들지/만들지 말지 미정, 또는 현 상태 불만인데 원인 불명 | 00-ideation |
| 방향은 정해졌고 요구사항을 구체화해야 함 | 01-requirements |
| 요구사항은 있는데 아직 설계가 없음 | 02-design |
| 설계는 있는데 코드가 없음 | 03-implementation |
| 코드가 구현됐고 검증이 필요함 | 04-verification |
| 빌드되는 코드가 있고 실행 커버리지를 뽑아야 함 | 05-coverage |

첫 진입인데 00-ideation 이 아닌 단계로 들어가면 직전 핸드오프가 없다. 스텝 4 의 데이터 존재 검사가 그것을 잡는다.

## 각 단계 요약

각 단계의 목적 요약이다. 완료 기준은 각 단계 파일이 단일 출처로 정의하므로(각 파일의 `## 완료 기준`, 04-verification 은 `## 완료선`), 상세는 아래 목적과 함께 해당 단계 파일을 본다.

### 0. 구상
목적: 무엇을 왜 만들지 -- 또는 만들지 말지 -- 방향을 정한다. 완료 기준은 `00-ideation.md`.

### 1. 요구사항 명세
목적: 00-ideation 의 확정 방향을 받아 검증 가능한 요구사항으로 명세하고, 각 요구사항의 수용 기준과 요구에서 나오는 검증 종류를 지정한다. 완료 기준은 `01-requirements.md`.

### 2. 설계
목적: 구현 전 아키텍처, 모듈 구조, 인터페이스를 확정하고, 설계가 만든 위험에서 나오는 검증 종류를 지정하며 테스트 케이스를 계획한다. 완료 기준은 `02-design.md`.

### 3. 구현
목적: 설계를 바탕으로 동작하는 코드를 작성하고, 04-verification 이 판정할 검증 산출물의 틀을 만든다. 완료 기준은 `03-implementation.md`.

### 4. 검증
목적: 03-implementation 이 세운 검증 틀로 구현이 요구사항을 충족하는지 판정한다. 04-verification 은 새 파일을 만들지 않고 틀에 결과를 채워 판정하며, 01-requirements·02-design 이 지정한 검증이 빠짐없이 수행됐는지 대조한다. 완료 기준은 `04-verification.md`.

### 5. 커버리지 추출
목적: 실행 커버리지(라인/브랜치)를 추출해 04-verification 의 완료 판정 입력과 SPA 뷰어용 데이터로 산출한다(추출·산출까지, 후속 조치는 밖). 04-verification 이 호출하는 모드와 단독 실행 모드가 있다. 완료 기준은 `05-coverage.md`.

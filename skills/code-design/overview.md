## 프로젝트 루트 확인 (착수 사전, 필수)

이 파이프라인의 모든 산출물은 **프로젝트 루트** 기준으로 저장된다. 프로젝트 루트는 **git 최상위**이며, code-design 은 **루트에서만** 실행한다. 대상(어느 컴포넌트/서브트리를 작업하는지)은 디렉토리를 옮겨 다니는 대신 **입력으로 받는다**. 착수 전 아래 사전 확인을 반드시 거친다.

**사전 확인 5스텝**

1. **루트 판정** -- `git rev-parse --show-toplevel` 로 최상위를 구해 CWD 와 비교한다. 일치하면 루트로 보고(스텝 5 에서 최종 확인), 불일치(하위에서 실행 중)면 중단하고 루트에서 재시작하도록 안내한다. git 조회가 실패하면(git 레포 아님) 자동 판정을 포기하고 스텝 5 에서 CWD 를 루트로 볼지 확인받는다.
2. **입력 수집** -- 브랜치와 작업할 경로(이 flow 가 대상으로 삼는 소스 서브트리, 루트 기준 상대경로)를 받는다. 작업할 경로가 실제로 존재하는지 확인하고, 없으면 다시 받는다.
3. **진입 단계 판정** -- "단계 진입 판단"으로 00-ideation 부터 시작하는 신규 진입인지, 그 뒤 단계(01-requirements ~ 04-verification)로 들어가는 중간 진입인지 정한다. 00-ideation 진입은 중간 진입이 아니라 신규 진입이다 -- 앞 단계가 없어 읽어들일 직전 핸드오프도 없다.
4. **데이터 존재 검사 (중간 진입 한정)** -- 진입 단계가 읽어야 할 직전 핸드오프가 `{프로젝트 루트}/code-design/<브랜치 슬러그>/` 아래에 있는지 확인한다. 없으면 진행하지 않고 노티한다. 핸드오프의 형태는 단계마다 다르다 -- 01-requirements 진입은 `00-ideation/handoff.md`, 02-design 진입은 `01-requirements/handoff.md`, 03-implementation 진입은 `02-design/handoff.md`, 04-verification 진입은 `03-implementation/` 의 검증 틀(e2e 리포트 / 수동 QA 체크리스트 / 보안 점검)이다.
5. **되묻기 확인** -- 루트 · 브랜치 · 작업할 경로 · 진입 단계(중간 진입이면 확인된 핸드오프까지)를 요약해 보여주고, 사용자가 확인해야 진행한다. 루트가 자동 판정으로 일치했더라도 예외 없이 확인받는다.

**사용자에게 보이는 형태 (예시)**

정상(중간 진입):

```
[착수 확인]
  프로젝트 루트 : <루트>            (git 최상위와 일치)
  브랜치        : <브랜치 이름>
  작업할 경로   : <대상 경로>
  진입 단계     : 03-implementation (중간 진입)
  직전 핸드오프 : code-design/<브랜치 슬러그>/02-design/handoff.md  [확인됨]
  산출물 위치   : code-design/<브랜치 슬러그>/...
  이대로 진행할까요?
```

중단(하위에서 실행):

```
[착수 확인 -- 중단]
  CWD 가 프로젝트 루트가 아닙니다.
    CWD        : <하위 경로>
    git 최상위 : <루트>
  code-design 은 루트에서만 실행합니다. 루트에서 세션을 다시 시작해 주세요.
```

중단(중간 진입인데 핸드오프 없음):

```
[착수 확인 -- 중단]
  <진입 단계> 진입에 필요한 직전 핸드오프가 없습니다.
    찾은 경로 : code-design/<브랜치 슬러그>/02-design/handoff.md  [없음]
  브랜치/경로가 틀렸거나 앞 단계가 끝나지 않았습니다. 확인해 주세요.
```

**컴포넌트 단위 운용:** 한 레포가 루트 아래 여러 컴포넌트(독립 관리하는 디렉토리)를 담더라도, 실행은 항상 레포 루트에서 하고 **작업할 경로 입력으로 대상 컴포넌트를 지목**한다. 컴포넌트 디렉토리로 옮겨 실행하지 않는다 -- 산출물은 그와 무관하게 루트의 `code-design/<브랜치 슬러그>/` 아래에 저장된다.

<PENETRATE>
프로젝트 루트는 git 최상위(`git rev-parse --show-toplevel`)로 판정하고, CWD 가 그와 일치할 때만 루트로 인정한다.
</PENETRATE>

<PENETRATE>

</PENETRATE>

</RICOCHET>

<RICOCHET>

</RICOCHET>

## 로드맵 (cross-run 작업 지도)

로드맵은 전체 작업을 청크(하나의 flow 가 통째로 담당하는 작업 범위) 단위로 쪼갠 지도다. flow 를 넘어 이어지는 유일한 산출물이며 `{프로젝트 루트}/code-design/roadmap.md` 에 커밋된다(원칙 5).

**청크 vs 파이프라인 단계:** 청크는 "무엇을 만드나"(작업 범위)이고, 파이프라인 단계(00~04)는 한 청크를 처음부터 끝까지 진행하는 과정이다. 한 flow = 한 청크. 플래그는 청크에 붙고 파이프라인 단계에는 붙지 않는다. 로드맵은 청크의 상태 한 줄(이름 + 플래그)만 담는 인덱스이며, 청크의 내용물은 핸드오프·코드에 있다.

**청크 상태 플래그:**

| 플래그 | 뜻 | 다음 flow |
|--------|-----|-----------|
| `[완료]` | 이 청크 구현 끝남 | 참조 |
| `[진행]` | 이번 flow 가 지금 만드는 청크 | -- |
| `[예정]` | 미래 flow 에 할 청크 -- 할지 확정, 시점만 미래 | 승격 |
| `[미정]` | 할지 자체가 미정 -- 재검토 조건 있음 | 조건 충족 시 승격 |
| `[기각]` | no-go, 안 만듦 -- 사유 명시 | 참조(재제안 방지) |

- 승격 가능: `[예정]` / `[미정]`. 참조 전용(종결): `[완료]` / `[기각]`.
- 활성(`[진행]`/`[예정]`/`[미정]`)과 종결(`[완료]`/`[기각]`) 섹션을 나눠 둔다.

**전이 규칙:**
- `[미정]`: 자동 만료 없음. 00-ideation 이 flow 시작마다 전부 재검토 -- 조건 충족이면 승격, 무의미해졌으면 사용자 확인 후 `[기각]`.
- `[기각]` 되살리기: 그냥 재제안 불가. 기각 사유가 무효화됐다는 근거 + 사용자 확인으로만 `[미정]`/`[예정]` 로 되살린다(기각 엔트리에 되살림 이력을 남긴다).
- 청크 단위 기각만 로드맵에 올린다. 발산 중 안 고른 하위 대안은 00-ideation 산출물에만 남긴다.

**전이 주체:** 00-ideation 이 로드맵 관리 주체다(flow 시작 승격 · `[미정]` 재검토 · `[기각]` 되살리기 판단). 그 외 전이도 정해진 이벤트에서 해당 단계가 즉시 쓴다 -- mid-flow 게이트의 보류 escalation(새 `[예정]`/`[미정]` append), 03-implementation 의 범위 축소·신규 범위 발견(G12/G9 -- 발견 시 사용자 확인 후 append), 04-verification 의 descope 결함·신규 범위 발견(flow 종료 시 append), flow 종료 시 `[진행]` -> `[완료]`. 모든 쓰기는 사용자 확인 + 출처 기록.

<PENETRATE>
새 flow 시작 시 00-ideation 은 roadmap.md 를 읽어 다음 청크를 `[진행]`으로 승격하고 열린 `[미정]` 을 전부 재검토한다.
</PENETRATE>

<RICOCHET>
로드맵 청크 상태를 사용자 확인 없이 전이시키거나, 기각 청크를 사유 반박 없이 되살리지 않는다.
</RICOCHET>

## 실행 순서

- 정상 흐름은 00-ideation -> 01-requirements -> 02-design -> 03-implementation -> 04-verification 순서로 진행한다.
- 05-coverage(커버리지 추출)는 이 순차 흐름 밖의 이중 모드 단계다 -- 04-verification 뒤에 이어서도, code-design 로드 후 단독으로도 실행한다. 단독 실행 시 "중간 진입엔 직전 핸드오프 필수" 규칙의 예외로, 직전 핸드오프 없이 코드/테스트를 직접 읽어 시작한다(선결 게이트: 코드 존재 + 빌드 성공). 상세는 `05-coverage.md`.
- 00-ideation 에서 01-requirements 로의 전환도 다른 단계와 같은 hard 의존이다 -- 01-requirements 는 00-ideation 의 핸드오프를 입력으로 받는다.
- 방향이 이미 명확하면 00-ideation 은 fast-path 로 가볍게 통과한다(단계를 건너뛰지는 않는다 -- `00-ideation.md` 참조). 00-ideation 에서 진행 판단이 no-go 면 파이프라인에 진입하지 않고 00-ideation 에서 종료한다.
- 단계 간 핸드오프의 형태는 단계마다 다르다 -- 00-ideation / 01-requirements / 02-design 은 `handoff.md` 문서가, 03-implementation -> 04-verification 은 코드와 검증 산출물 틀이 그 역할을 한다(03-implementation 은 별도 `handoff.md` 를 만들지 않음).
    - 04-verification 은 하류 단계가 없어 핸드오프가 필수가 아니다. 상세는 원칙 5("핸드오프는 단계별로 형태가 다르다") 참조.
- 각 flow 는 자기 브랜치 폴더(`code-design/<브랜치 슬러그>/`)와 공유 roadmap.md 만 입력으로 삼는다.
  - 다른 브랜치(옛 flow)의 핸드오프는 참고하지 않는다(원칙 5).
  - 결정 지연(보류)은 02-design 까지 모두 해소되거나 로드맵으로 escalation 되어, 03-implementation 진입 시 열린 보류가 0 이다(원칙 4).

- 새 단계를 추가할 때는 폴더명·산출물 경로·산문 지칭을 모두 `NN-name` 단일 토큰으로 짓는다(예: `05-<name>`).
- 진입 게이트·핸드오프 테이블·roadmap.md 전이가 전부 단계 이름을 키로 참조하므로, 이 규약을 벗어난 이름은 그 참조들을 깨뜨린다.
- 04-verification 은 검증만 하고 끝나지 않고 파이프라인을 되돌릴 수 있다 -- 발견된 결함은 03-implementation 회귀(지금 고침) 또는 로드맵 descope 로, 요구에 없던 신규 범위는 로드맵 후보로 라우팅한다. 결함 집계·승인 게이트 절차의 상세는 `04-verification.md`.

단계 전환·완료 기준 검증·승인 서명 규약(checklist.md 먼저 작성 -> 완료 기준 동반 검증 -> 사용자 서명 -> 다음 단계)의 단일 출처는 `principles.md` 원칙 5 의 "단계 전환 규칙" 이다. 각 단계는 그 규약을 따른다.

## 단계 진입 판단

현재 상황이 어느 단계인지 모를 때 아래 기준으로 판단한다.

| 상황 | 진입 단계 |
|------|----------|
| 무엇을 만들지/만들지 말지 미정, 또는 현 상태 불만인데 원인 불명 | 0. 구상 |
| 방향은 정해졌고 요구사항을 구체화해야 함 | 1. 요구사항 명세 |
| 요구사항은 있는데 아직 설계가 없음 | 2. 설계 |
| 설계는 있는데 코드가 없음 | 3. 구현 |
| 코드가 구현됐고 검증이 필요함 | 4. 검증 |
| 빌드되는 코드가 있고 실행 커버리지를 뽑아야 함 | 5. 커버리지 추출 |

## 각 단계 요약

각 단계의 목적 요약이다. 완료 기준은 각 단계 파일이 단일 출처로 정의하므로(각 파일의 `## 완료 기준`, 04 는 `## 완료선`), 상세는 아래 목적과 함께 해당 단계 파일을 본다.

### 0. 구상
목적: 무엇을 왜 만들지 -- 또는 만들지 말지 -- 방향을 정한다. 완료 기준은 `00-ideation.md`.

### 1. 요구사항 명세
목적: 00-ideation 의 확정 방향을 받아 검증 가능한 요구사항으로 명세한다. 완료 기준은 `01-requirements.md`.

### 2. 설계
목적: 구현 전 아키텍처, 모듈 구조, 인터페이스를 확정한다. 완료 기준은 `02-design.md`.

### 3. 구현
목적: 설계를 바탕으로 동작하는 코드를 작성하고, 04-verification 이 판정할 검증 산출물의 틀을 만든다. 완료 기준은 `03-implementation.md`.

### 4. 검증
목적: 03-implementation 이 만든 산출물로 구현이 요구사항을 충족하는지 판정한다. 04-verification 은 새 파일을 만들지 않고, 03-implementation 산출물(테스트 · e2e 리포트 · 수동 QA 체크리스트 · 보안 점검 기록)의 결과를 채워 판정만 한다. 완료 기준은 `04-verification.md`.

### 5. 커버리지 추출
목적: 실행 커버리지(라인/브랜치)를 추출해 SPA 뷰어용 데이터로 산출한다(추출·산출까지, 후속 조치는 밖). 04-verification 뒤 순차 / 단독 실행의 이중 모드. 완료 기준은 `05-coverage.md`.

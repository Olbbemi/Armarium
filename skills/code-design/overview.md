## 실행 순서

정상 흐름은 1 -> 2 -> 3 -> 4 -> 7 -> 8 -> 9 순서로 진행한다.
5(디버깅), 6(보안 검토)는 어느 단계에서든 이슈가 발생하면 진입하고, 해결 후 원래 단계로 복귀한다.

## 단계 전환 규칙

<PENETRATE>
모든 단계는 완료 기준 체크리스트가 모두 충족되고 피드백이 없을 때만 다음 단계로 진행한다.
</PENETRATE>

각 단계 종료 시 아래 형식으로 제시한다. 체크리스트 상세 항목은 각 단계 스킬 파일 참고.

```
## 완료 기준
- [x] 항목 1
- [x] 항목 2

## 피드백
(없으면 다음 단계로 진행합니다)
```

- 모든 항목 체크 + 피드백 없음 -> 다음 단계 진입
- 피드백이 있으면 -> 반영 후 재제시

## 단계 진입 판단

현재 상황이 어느 단계인지 모를 때 아래 기준으로 판단한다.

| 상황 | 진입 단계 |
|------|----------|
| 새 기능/서비스를 시작하는데 요구사항이 불명확함 | 1. 요구사항 분석 |
| 요구사항은 있는데 아직 설계가 없음 | 2. 설계 |
| 설계는 있는데 코드가 없음 | 3. 구현 |
| 코드가 있는데 품질/구조 개선이 필요함 | 4. 정적 분석 / 리팩터링 |
| 버그가 있고 원인을 모름 | 5. 디버깅 |
| 보안 이슈가 의심되거나 검토가 필요함 | 6. 보안 검토 |
| 테스트가 없거나 커버리지가 부족함 | 7. 테스트 |
| PR 머지 전 리뷰가 필요함 | 8. 코드 리뷰 |
| 코드는 완성됐는데 문서가 없음 | 9. 문서화 |

## 각 단계 요약 및 완료 기준

### 1. 요구사항 분석
목적: 해결할 문제와 범위를 명확히 한다.

완료 기준:
- 해결할 문제가 한 문장으로 정의됨
- 기능 범위(in/out scope)가 합의됨
- 비기능 요구사항(성능, 보안, 확장성)이 명시됨
- 모호한 항목이 없거나 보류 사유가 기록됨

### 2. 설계
목적: 구현 전 아키텍처, 모듈 구조, 인터페이스를 확정한다.

완료 기준:
- 모듈 경계와 책임이 명확히 정의됨
- 주요 인터페이스(API, 함수 시그니처 등)가 명세됨
- 데이터 흐름이 정의됨
- TDD 계획(테스트 케이스 목록)이 작성됨
- 비기능 요구사항 대응 방안이 설계에 반영됨

### 3. 구현
목적: 설계를 바탕으로 동작하는 코드를 작성한다.

완료 기준:
- 설계에서 정의한 인터페이스가 모두 구현됨
- 코드가 빌드/실행됨
- 명백한 TODO/임시 코드가 없거나 기록됨

### 4. 정적 분석 / 리팩터링
목적: 코드 품질과 구조를 개선한다.

완료 기준:
- 린터/타입 체커 경고가 해소됨
- 중복 코드, 과도한 복잡도가 정리됨
- 코드 구조가 설계 의도와 일치함

### 5. 디버깅
목적: 버그 원인을 파악하고 수정한다.

완료 기준:
- 버그가 최소 재현 케이스로 좁혀짐
- 근본 원인이 파악됨
- 수정 후 동일 버그가 재현되지 않음
- 관련 테스트 케이스가 추가됨

### 6. 보안 검토
목적: 보안 취약점을 탐지하고 해소한다.

완료 기준:
- 보안 스캔 툴이 실행됨
- OWASP Top 10 / LLM Top 10 기준 점검됨
- 발견된 이슈가 해소되거나 수용 사유가 기록됨

### 7. 테스트
목적: 코드가 요구사항을 충족하는지 검증한다.

완료 기준:
- 설계 단계에서 계획한 테스트 케이스가 모두 작성됨
- 핵심 로직의 happy path / edge case / 실패 케이스가 커버됨
- 커버리지 측정 후 누락된 경로가 보완됨
- 모든 테스트가 통과함

### 8. 코드 리뷰
목적: 다른 관점에서 코드 품질과 잠재적 문제를 점검한다.

완료 기준:
- 리뷰 지적 사항이 모두 해소되거나 반영 거부 사유가 기록됨
- 보안 관점 리뷰가 포함됨

### 9. 문서화
목적: 코드와 설계를 사람이 이해할 수 있는 형태로 남긴다.

완료 기준:
- API 문서가 생성됨
- 사용자 가이드 또는 README가 작성됨
- 주요 설계 결정사항이 문서에 기록됨

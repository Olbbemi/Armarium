## 실행 순서

정상 흐름은 0 -> 1 -> 2 -> 3 -> 4 순서로 진행한다.
0(구상)에서 1(요구사항 명세)로의 전환도 다른 단계와 같은 hard 의존이다 -- 1은 0의 핸드오프를 입력으로 받는다. 방향이 이미 명확하면 0은 fast-path 로 가볍게 통과한다(단계를 건너뛰지는 않는다 -- `00-ideation.md` 참조). 0에서 go/no-go 가 no-go 면 파이프라인에 진입하지 않고 0에서 종료한다.
4(검증)에서 결함이 발견되면, 첫 실패에서 멈추지 말고 해당되는 검증 항목을 모두 끝낸 뒤 결함을 집계해 사용자 승인을 받고 3(구현)으로 회귀한다.

## 단계 전환 규칙

<PENETRATE>
모든 단계는 완료 기준 체크리스트가 모두 충족되고 피드백이 없을 때만 다음 단계로 진행한다.
</PENETRATE>

각 단계 종료 시 아래 형식으로 제시한다. 체크리스트 상세 항목은 각 단계 스킬 파일 참고.

```
## 완료 기준
- [x] 항목 1
- [x] 항목 2

## 피드백
(없으면 다음 단계로 진행합니다)
```

- 모든 항목 체크 + 피드백 없음 -> 다음 단계 진입
- 피드백이 있으면 -> 반영 후 재제시

## 단계 진입 판단

현재 상황이 어느 단계인지 모를 때 아래 기준으로 판단한다.

| 상황 | 진입 단계 |
|------|----------|
| 무엇을 만들지/만들지 말지 미정, 또는 현 상태 불만인데 원인 불명 | 0. 구상 |
| 방향은 정해졌고 요구사항을 구체화해야 함 | 1. 요구사항 명세 |
| 요구사항은 있는데 아직 설계가 없음 | 2. 설계 |
| 설계는 있는데 코드가 없음 | 3. 구현 |
| 코드가 구현됐고 검증이 필요함 | 4. 검증 |

## 각 단계 요약 및 완료 기준

### 0. 구상
목적: 무엇을 왜 만들지 -- 또는 만들지 말지 -- 방향을 정한다.

완료 기준:
- 현재 상태가 파악되고 문제/근본원인이 진단됨 (신규 착안이면 약식/N/A)
- 2~3개 방향이 발산되고 트레이드오프로 비교됨
- go/no-go 가 사용자 확인으로 결정됨 (no-go 면 파이프라인 미진입)
- (go인 경우) 확정 방향이 명문화되고 사용자 확인됨

### 1. 요구사항 명세
목적: 0의 확정 방향을 받아 검증 가능한 요구사항으로 명세한다.

완료 기준:
- 0 핸드오프의 확정 방향이 전제로 요약 인용됨
- 기능 범위(in/out scope)가 합의됨
- 비기능 요구사항(성능, 보안, 확장성)이 명시됨
- 모호한 항목이 없거나 보류 항목이 보류 파일에 등재됨 (원칙 4)

### 2. 설계
목적: 구현 전 아키텍처, 모듈 구조, 인터페이스를 확정한다.

완료 기준:
- 모듈 경계와 책임이 명확히 정의됨
- 주요 인터페이스(API, 함수 시그니처 등)가 명세됨
- 데이터 흐름이 정의됨
- TDD 계획(테스트 케이스 목록)이 작성됨
- 비기능 요구사항 대응 방안이 설계에 반영됨

### 3. 구현
목적: 설계를 바탕으로 동작하는 코드를 작성하고, 04가 판정할 검증 산출물의 틀을 만든다.

완료 기준:
- 설계에서 정의한 인터페이스가 모두 구현됨
- 코드가 빌드/실행됨
- 명백한 TODO/임시 코드가 없거나 기록됨
- 검증 산출물 틀(e2e 시나리오, 수동 QA 체크리스트 항목)이 작성됨

### 4. 검증
목적: 03이 만든 산출물로 구현이 요구사항을 충족하는지 판정한다. 04는 새 파일을 만들지 않고, 03 산출물(테스트 · e2e 리포트 · 수동 QA 체크리스트 · 보안 점검 기록)의 결과를 채워 판정만 한다.

완료 기준:
- e2e: 계획한 시나리오가 모두 실행·통과 (happy path + 가드/실패 경로). 자동 e2e가 가능한 대상이 있을 때.
- 수동 QA: (자동화 불가한 인터랙티브 경계가 있으면) 체크리스트 전 항목이 사용자와 확인됨
- 보안 점검: (해당되면) 미해결 취약점이 없거나 수용 사유가 기록됨
- 결함이 있으면 첫 실패에서 멈추지 않고 해당 검증을 모두 끝낸 뒤 집계해 사용자 승인을 받고 3(구현)으로 회귀

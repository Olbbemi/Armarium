## 로드맵 (cross-run 작업 지도)

로드맵은 전체 작업을 청크(하나의 flow 가 통째로 담당하는 작업 범위) 단위로 쪼갠 지도다. flow 를 넘어 승계되는 유일한 산출물이며 `{프로젝트 루트}/code-design/roadmap.md` 에 커밋된다(원칙 5).

**청크 vs 파이프라인 단계:** 청크는 "무엇을 만드나"(작업 범위)이고, 파이프라인 단계(00~04)는 한 청크를 관통하는 과정이다. 한 flow = 한 청크. 플래그는 청크에 붙고 파이프라인 단계에는 붙지 않는다. 로드맵은 청크의 상태 한 줄(이름 + 플래그)만 담는 인덱스이며, 청크의 내용물은 핸드오프·코드에 있다.

**청크 상태 플래그:**

| 플래그 | 뜻 | 다음 flow |
|--------|-----|-----------|
| `[완료]` | 이 청크 구현 끝남 | 참조 |
| `[진행]` | 이번 flow 가 지금 만드는 청크 | -- |
| `[예정]` | 미래 flow 에 할 청크 -- 할지 확정, 시점만 미래 | 승격 |
| `[미정]` | 할지 자체가 미정 -- 재검토 조건 있음 | 조건 충족 시 승격 |
| `[기각]` | no-go, 안 만듦 -- 사유 명시 | 참조(재제안 방지) |

- 승격 가능: `[예정]` / `[미정]`. 참조 전용(종결): `[완료]` / `[기각]`.
- 활성(`[진행]`/`[예정]`/`[미정]`)과 종결(`[완료]`/`[기각]`) 섹션을 나눠 둔다.

**전이 규칙:**
- `[미정]`: 자동 만료 없음. 00 이 flow 시작마다 전부 재검토 -- 조건 충족이면 승격, 무의미해졌으면 사용자 확인 후 `[기각]`.
- `[기각]` 되살리기: 그냥 재제안 불가. 기각 사유가 무효화됐다는 근거 + 사용자 확인으로만 `[미정]`/`[예정]` 로 되살린다(기각 엔트리에 되살림 이력을 남긴다).
- 청크 단위 기각만 로드맵에 올린다. 발산 중 안 고른 하위 대안은 00 산출물에만 남긴다.

**전이 주체:** 00 이 로드맵 큐레이터다(flow 시작 승격 · `[미정]` 재검토 · `[기각]` 되살리기 판단). 그 외 전이도 정해진 이벤트에서 해당 단계가 즉시 쓴다 -- mid-flow 게이트의 보류 escalation(새 `[예정]`/`[미정]` append), 04 검증의 descope 결함·신규 범위 발견(flow 종료 시 append), flow 종료 시 `[진행]` -> `[완료]`. 모든 쓰기는 사용자 확인 + 출처 기록.

<PENETRATE>
새 flow 시작 시 00 은 roadmap.md 를 읽어 다음 청크를 `[진행]`으로 승격하고 열린 `[미정]` 을 전부 재검토한다.
</PENETRATE>

<RICOCHET>
로드맵 청크 상태를 사용자 확인 없이 전이시키거나, 기각 청크를 사유 반박 없이 되살리지 않는다.
</RICOCHET>

## 실행 순서

정상 흐름은 구상 -> requirements -> design -> implementation -> verification 순서로 진행한다.
구상(ideation)에서 requirements(요구사항 명세)로의 전환도 다른 단계와 같은 hard 의존이다 -- requirements 는 구상의 핸드오프를 입력으로 받는다. 방향이 이미 명확하면 구상은 fast-path 로 가볍게 통과한다(단계를 건너뛰지는 않는다 -- `00-ideation.md` 참조). 구상에서 진행 판단이 no-go 면 파이프라인에 진입하지 않고 구상에서 종료한다.
단계 간 바통(핸드오프)의 형태는 단계마다 다르다 -- 00/01/02 는 `handoff.md` 문서가 바통이고, 03->04 는 코드와 검증 산출물 틀이 바통 역할을 한다(03 은 별도 handoff.md 를 만들지 않음). 04 는 하류 단계가 없어 핸드오프가 필수가 아니다. 상세는 원칙 5("핸드오프는 단계별로 형태가 다르다") 참조.
각 flow 는 자기 브랜치 폴더(`code-design/<브랜치>/`)와 공유 roadmap.md 만 입력으로 삼는다 -- 다른 브랜치(옛 flow)의 핸드오프는 참고하지 않는다(원칙 5). 결정 지연(보류)은 02 까지 모두 해소되거나 로드맵으로 escalation 되어, implementation(03) 진입 시 열린 보류가 0 이다(원칙 4).
verification(검증)에서 결함이 발견되면, 첫 실패에서 멈추지 말고 해당되는 검증 항목을 모두 끝낸 뒤 결함을 집계한다. 승인 게이트에서 결함마다 지금 고침(implementation 회귀) 또는 descope(로드맵 `[예정]` 청크로 미루고 현재 청크 범위를 좁힘)로 라우팅하고, 요구엔 없던 신규 범위 발견은 로드맵 `[미정]` 후보로 넘긴다.

## 각 단계 요약 및 완료 기준

### 0. 구상
목적: 무엇을 왜 만들지 -- 또는 만들지 말지 -- 방향을 정한다.

완료 기준:
- 유형(1/2a/2b)이 판정되고 현재 상태·문제/동기가 기록됨 (근본원인 진단은 유형 1 전용, 유형 2a·2b 는 N/A)
- 2~3개 방향이 발산되고 트레이드오프로 비교됨
- roadmap.md 의 청크가 스케치/갱신되고 이번에 만들 청크가 `[진행]`으로 표식됨 (쪼갤 것 없으면 단일 청크)
- 기존 roadmap.md 의 열린 `[미정]` 청크가 전부 재검토됨 (첫 flow 면 N/A)
- `[진행]` 청크의 진행 판단이 사용자 확인으로 결정됨 -- go(진행) / no-go(`[기각]`, 사유) / 미정(`[미정]`, 재검토 조건). no-go·미정이면 파이프라인 미진입
- (go인 경우) 확정 방향이 명문화되고 사용자 확인됨

### 1. 요구사항 명세
목적: 구상의 확정 방향을 받아 검증 가능한 요구사항으로 명세한다.

완료 기준:
- 구상 핸드오프의 확정 방향(+유형·로드맵 전체)이 전제로 요약 인용됨
- 구상 위임 항목이 태그별로 처리되고([requirements] 해소/[design] 재라우팅/[deferred] 재검토), [잠정] 가정이 확정 또는 기각됨
- 기능 범위(in/out scope)가 합의되고, Out of scope 가 로드맵 `[예정]`/`[미정]`과 대조되어 "다음 flow 예정"/"영구 제외"로 구분됨
- 비기능 요구사항(성능, 보안, 확장성)이 명시됨
- 재개 시점 = 01 인 열린 보류가 모두 해소되고, 미해소분은 핸드오프 "열린 보류"로 릴레이됨 (원칙 4)

### 2. 설계
목적: 구현 전 아키텍처, 모듈 구조, 인터페이스를 확정한다.

완료 기준:
- requirements 핸드오프가 전제로 요약 인용되고, [design] 위임 항목이 모두 해소됨(또는 열린 보류 등재)
- 모듈 경계와 책임이 명확히 정의됨
- 주요 인터페이스(API, 함수 시그니처 등)가 명세됨
- 데이터 흐름이 정의됨
- TDD 계획(테스트 케이스 목록)이 작성됨
- 비기능 요구사항 대응 방안이 설계에 반영되고, 설계가 로드맵 `[예정]` 청크를 구조적으로 막지 않음(YAGNI)
- 모든 열린 보류가 해소되거나 로드맵으로 escalation 됨 -- 02 를 닫을 때 열린 보류 0 (원칙 4, 최종 게이트)

### 3. 구현
목적: 설계를 바탕으로 동작하는 코드를 작성하고, 04가 판정할 검증 산출물의 틀을 만든다.

완료 기준:
- 02 handoff(인터페이스·모듈 구조·데이터 흐름·TDD 계획)를 인수해 착수하고, 진입 시 열린 보류가 0 임을 확인
- 02 TDD 계획이 첫 RED 백로그로 모두 커버됨 (하한선 -- 추가 케이스는 정상)
- 설계에서 정의한 인터페이스가 모두 구현됨
- 코드가 빌드/실행됨
- 명백한 TODO/임시 코드가 없거나 기록됨
- 검증 산출물 틀(e2e 시나리오, 수동 QA 체크리스트 항목)이 작성됨

### 4. 검증
목적: 03이 만든 산출물로 구현이 요구사항을 충족하는지 판정한다. 04는 새 파일을 만들지 않고, 03 산출물(테스트 · e2e 리포트 · 수동 QA 체크리스트 · 보안 점검 기록)의 결과를 채워 판정만 한다.

완료 기준:
- e2e: 계획한 시나리오가 모두 실행·통과 (happy path + 가드/실패 경로). 자동 e2e가 가능한 대상이 있을 때.
- 수동 QA: (자동화 불가한 인터랙티브 경계가 있으면) 체크리스트 전 항목이 사용자와 확인됨
- 보안 점검: (해당되면) 미해결 취약점이 없거나 수용 사유가 기록됨
- 결함이 있으면 첫 실패에서 멈추지 않고 해당 검증을 모두 끝낸 뒤 집계해, 승인 게이트에서 결함마다 지금 고침(3 회귀) 또는 descope(로드맵 `[예정]` + 현재 청크 범위 좁힘)로 라우팅
- 결함이 아닌 신규 범위 발견은 사용자 확인 후 로드맵 `[미정]` 후보로 넘김 (04 를 닫는 걸 막지 않음). descope · 신규 범위의 로드맵 append 는 04 종료 시 사용자 확인 + 출처로

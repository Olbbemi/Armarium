# cross-flow 층 -- flow 를 넘어 유지되는 파일들

`code-design/` 루트에 flat 하게 두는 파일 넷의 규격. flow · within-flow · cross-flow 의 정의는 `overview.md` 의 "용어 -- flow" 가 단일 출처다.

각 파일은 사실의 축 하나를 소유한다. 어느 축이 어느 파일 소관인지는 아래 표가 단일 출처이며, 브랜치 폴더의 `handoff.md` 는 이 축들을 다시 적지 않고 참조한다. 각 파일을 쓰고 읽는 단계는 아래 파일별 절이 정한다.

| 파일 | 소유하는 축 | 누적 방식 |
|------|------------|----------|
| `roadmap.md` | 청크 상태 | 상태 전이 -- 같은 청크의 플래그가 옮겨 간다 |
| `architecture.md` | 시스템 제약 + 기술 스택 | 스냅샷 -- 현재 유효한 것만 남기고 덮어쓴다 |
| `decisions.md` | 설계 결정과 그 근거 | append-only -- 지난 항목을 고치지 않는다 |
| `qa-checklist.md` | 수동 QA 회귀 확인 항목 | 누적 -- 항목이 쌓이고 결과가 채워진다 |

## 공통 규칙

- 모든 쓰기는 사용자 확인을 받고 **출처**를 남긴다. 출처는 `{브랜치 슬러그} / {단계}` 형식으로 어느 flow 의 어느 단계에서 나왔는지 지목한다.
- 파일은 flow 를 넘어 누적된다. 새 flow 가 자기 내용으로 갈아엎지 않고 기존 내용 위에 더하거나 고친다.
- 여기 오른 사실은 `handoff.md` 에 본문으로 다시 적지 않는다. handoff 는 해당 파일을 가리키고, 이번 flow 가 더한 범위만 표시한다.
- 네 파일의 작성 형식은 공통 원칙 10("산출물 작성 형식")을 따른다.

### 등재 기준 -- 무엇을 여기 올리나

가르는 질문은 하나다. **이번 flow 가 코드를 바꾼 뒤에도 그 문장이 참인가.**

- 참이다 -> cross-flow 층에 올린다. 그 사실의 대상이 이번 flow 의 수정 범위 **밖**에 있다는 뜻이다.
- 거짓이 된다 -> 그 단계의 `handoff.md` 에 둔다. 대상이 수정 범위 **안**이라 곧 무효가 된다.

실측으로 "현재 p95 = 340ms, 그중 300ms 는 외부 결제 API 대기" 를 얻었다면 두 문장이 갈린다.

- `현재 p95 = 340ms` -> 이번 flow 가 고치려는 값이다. 핸드오프.
- `300ms 는 외부 결제 API 대기` -> 우리가 이번에 안 건드리는 구조다. `architecture.md`.

이 기준은 네 파일 모두에 걸린다. 각 파일 절의 등재 규칙은 이 기준을 통과한 것 중에서 다시 가른다.

## roadmap.md -- 청크 상태

- 쓰는 단계: 00-ideation(주) · 01-requirements · 02-design · 03-implementation · 04-verification
- 읽는 단계: 전 단계 (00-ideation ~ 04-verification)

로드맵은 전체 작업을 청크(하나의 flow 가 통째로 담당하는 작업 범위) 단위로 쪼갠 지도다.

**청크 vs 파이프라인 단계:** 청크는 "무엇을 만드나"(작업 범위)이고, 파이프라인 단계(00-ideation ~ 04-verification)는 한 청크를 처음부터 끝까지 진행하는 과정이다. 한 flow = 한 청크. 플래그는 청크에 붙고 파이프라인 단계에는 붙지 않는다.

로드맵은 인덱스가 아니라 **기록**이다. 아직 flow 를 안 돈 청크(`[예정]`/`[미정]`)는 핸드오프가 없어, 여기 적힌 것 말고는 그 청크의 내용이 어디에도 없다. 이름 한 줄만 적으면 몇 flow 뒤에 그것이 무엇이었는지 복원되지 않는다.

### 청크 상태 플래그

| 플래그 | 뜻 | 다음 flow |
|--------|-----|-----------|
| `[완료]` | 이 청크 구현 끝남 | 참조 |
| `[진행]` | 이번 flow 가 지금 만드는 청크 | -- |
| `[예정]` | 미래 flow 에 할 청크 -- 할지 확정, 시점만 미래 | 승격 |
| `[미정]` | 할지 자체가 미정 -- 재검토 조건 있음 | 조건 충족 시 승격 |
| `[기각]` | no-go, 안 만듦 -- 사유 명시 | 참조(재제안 방지) |

- 승격 가능: `[예정]` / `[미정]`. 참조 전용(종결): `[완료]` / `[기각]`.
- `[진행]` 은 파일 전체에 **하나**다. 병행 불가(공통 원칙 5)가 이를 강제한다.

### 형식 -- 활성은 레코드, 종결은 표 한 줄

활성과 종결은 읽는 목적이 다르다. 활성은 "다음에 뭘 할까" 의 입력이라 범위 · 선행 · 재검토 조건이 필요하고, 종결은 "이미 있다 / 다시 꺼내지 마라" 의 참조라 한 줄이면 된다.

```markdown
# 로드맵 -- {프로젝트}

## 활성

### {청크 이름}  `[진행]`
- 범위: (이 청크가 만드는 것)
- 선행: (먼저 끝나야 하는 청크. 없으면 N/A)
- 출처: {브랜치 슬러그} / {단계}

### {청크 이름}  `[미정]`
- 범위: ...
- 선행: N/A
- 재검토 조건: (무엇이 확인되면 `[예정]` 으로 올리나. `[미정]` 전용)
- 출처: ...

## 종결

| 청크 | 상태 | 출처 | 사유 · 참조 |
|------|------|------|------------|
| ... | `[완료]` | {브랜치 슬러그} | 산출물 = `code-design/{브랜치 슬러그}/` |
| ... | `[기각]` | {브랜치 슬러그} / {단계} | (기각 사유) |
```

### 선행 관계 -- 다른 청크를 기다리는 청크

`선행:` 칸은 이 청크가 시작되기 전에 끝나야 하는 청크를 지목한다. 실측이 선행돼야 하는 경우(공통 원칙 4 "escalation 사유에는 실측 선행이 포함된다")가 대표적이다.

- 선행 청크를 새로 만들 때 진행 중이던 청크는 `[진행]` -> `[예정]` 으로 내리고 `선행:` 에 그 청크를 적는다.
- 브랜치 폴더는 지우지 않는다. 선행 flow 가 끝나면 같은 브랜치로 돌아와 `[진행]` 으로 올리고 이어간다.
- 선행 flow 가 남긴 사실은 cross-flow 층을 통해 전달된다. 남의 브랜치 폴더를 읽지 않으므로 flow 격리(공통 원칙 5)를 어기지 않는다.

### 전이 규칙

- `[미정]`: 자동 만료 없음. 00-ideation 이 flow 시작마다 전부 재검토해, 조건 충족이면 승격하고 무의미해졌으면 사용자 확인 후 `[기각]` 한다.
- `[기각]` 되살리기: 그냥 재제안 불가. 기각 사유가 무효화됐다는 근거 + 사용자 확인으로만 `[미정]`/`[예정]` 로 되살린다. 되살릴 때 종결 표의 그 행을 지우지 않고, 활성 레코드의 `출처:` 아래에 `되살림: {옛 기각 사유} 가 {근거} 로 무효화됨` 을 남긴다.
- 청크 단위 기각만 로드맵에 올린다. 발산 중 안 고른 하위 대안은 00-ideation 산출물에만 남긴다.

**전이 주체:** 00-ideation 이 로드맵 관리 주체다(flow 시작 승격 · `[미정]` 재검토 · `[기각]` 되살리기 판단). 그 외 전이도 정해진 이벤트에서 해당 단계가 즉시 쓴다.

| 단계 | 이벤트 | 전이 |
|------|--------|------|
| 02-design | 보류 escalation | 새 `[예정]`/`[미정]` 레코드 추가 |
| 01-requirements · 02-design | 실측 선행 필요 | 선행 청크 `[예정]` 추가 + 이 청크를 `[예정]` 으로 내림 |
| 03-implementation | 범위 축소 · 신규 범위 발견 (G12/G9) | 사용자 확인 후 레코드 추가 |
| 04-verification | descope 결함 · 신규 범위 발견 | flow 종료 시 레코드 추가 |
| 04-verification | flow 종료 | `[진행]` -> `[완료]`, 활성에서 종결 표로 내림 |

## architecture.md -- 시스템 제약 + 기술 스택

- 쓰는 단계: 02-design(주) · 00-ideation(실측한 관측 사실만) · 03-implementation(동기화만)
- 읽는 단계: 00-ideation · 01-requirements · 02-design · 03-implementation · 05-coverage

시스템 수준에서 여러 청크에 걸쳐 유효한 제약을 담는다. 이번 청크에만 걸리는 모듈 구조 · 인터페이스는 여기가 아니라 02-design `handoff.md` 소관이다.

```markdown
# 아키텍처 -- {프로젝트}

## 시스템 제약

### 경계 · 의존 방향
(다이어그램. 어느 단위가 어느 단위에 의존하는가)

### 통신 원칙
| 단위 쌍 | 통하는 것 | 예외 · 사유 |
|---------|----------|------------|

### 하지 않기로 한 것
(구조적 금지. 한 줄에 하나)
- ...

## 기술 스택

### 언어 배치
| 단위 | 언어 | 근거 |
|------|------|------|

### 핵심 라이브러리
| 라이브러리 | 갇히는 경계 | 근거 |
|-----------|-----------|------|

## 관측 사실
(실측으로 확인한 현 시스템의 성질. 정한 것이 아니라 잰 것)
| 사실 | 잰 방법 | 시점 |
|------|--------|------|

## 출처
| 항목 | 출처 |
|------|------|
| ... | {브랜치 슬러그} / {단계} |
```

- `하지 않기로 한 것` 과 roadmap `[기각]` 은 다르다.
  - 여기는 **구조적 금지** -- 만들더라도 이 방식으로는 안 한다.
  - `[기각]` 은 **안 만들 작업 범위**다.
  - 같은 사안이 둘 다에 걸리면 각각의 축으로 나눠 적는다.
- `언어 배치` 는 03-implementation 이 언어 가드레일 파일을 로드할지, 05-coverage 가 어느 언어 절을 볼지 판정하는 입력이다.
- 03-implementation 은 G12 로 확정된 설계 이탈이 이 파일과 어긋날 때만 쓴다. 새 제약을 03-implementation 에서 세우지 않는다.
- 00-ideation 은 실측으로 확인한 **관측 사실**만 쓴다 -- 무엇을 어떻게 할지 정하는 제약은 02-design 소유다.
  - 00-ideation 진행 판단이 no-go 여도 이 쓰기는 유효하다. 잰 값은 그 청크를 만드는지와 무관하게 참이다.
  - 관측 사실은 `시스템 제약 > 경계 · 의존 방향` 이나 `통신 원칙` 이 아니라 아래 `관측 사실` 절에 넣는다.
- 스냅샷이라 지난 내용을 덮어쓴다. 왜 바뀌었는지는 `decisions.md` 가 소유한다.

## decisions.md -- 설계 결정

- 쓰는 단계: 02-design
- 읽는 단계: 02-design · 03-implementation

설계 결정과 그 근거의 단일 출처. append-only 로 누적한다.

```markdown
## #N  {한 줄 제목}
- 결정: (무엇으로 정했나)
- 근거: (왜)
- 버린 대안:
  - {대안} -- 탈락 사유
- 비용: (채택안이 지고 가는 것 + 완화책. 없으면 N/A)
- 출처: {브랜치 슬러그} / {단계}
- 날짜: {YYYY-MM-DD}
```

- 번호 `#N` 은 단조 증가한다. flow 가 바뀌어도 이어서 매긴다.
- 등재 대상은 위 "등재 기준" 을 통과한 비자명한 결정이다. 이번 flow 가 그 코드를 다시 쓰면 무효가 되는 국소 판단은 올리지 않는다.
- `비용` 칸은 공짜인 결정이 없다는 것을 강제한다. 비용을 못 적으면 대안 비교가 아직 안 된 것이다.
- 결정을 뒤집을 때는 옛 항목을 고치지 않는다. 새 항목을 더하고, 옛 항목에 `#M 로 대체됨` 한 줄만 붙인다.
- 02-design `handoff.md` 의 `## 설계 결정 기록` 은 이번 flow 가 더한 범위를 가리키는 포인터 한 줄이다(예: `이번 flow 의 결정 = ../../decisions.md #12~#15`).

## qa-checklist.md -- 수동 QA 회귀 확인 항목

- 쓰는 단계: 03-implementation(항목 추가) · 04-verification(결과 기입)
- 읽는 단계: 03-implementation · 04-verification

자동 테스트로 가드되지 않는 인터랙티브 거동의 확인 항목. flow 를 넘어 누적된다.

양식은 `04-verification.md` 의 "수동 QA 체크리스트" 를 단일 출처로 하고, cross-flow 파일이므로 아래를 더한다.

- 각 항목에 그것을 더한 출처(`{브랜치 슬러그} / 03-implementation`)를 단다.
- 03-implementation 은 기존 파일에 이번 flow 의 항목을 **더한다**. 파일이 없을 때만 새로 만든다.
- 지난 flow 의 항목은 지우지 않는다. 항목이 자동 테스트로 편입되면 그때 제거하고 02-design TDD 계획으로 이관한다.
- 거동이 바뀌면 해당 항목을 사실에 맞게 고친다.

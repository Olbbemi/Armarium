# 2단계: 설계

요구사항이 확정된 후 구현 전에, 어떻게 만들지를 정의하는 단계.
이 단계의 출력이 3단계(구현)의 입력이 된다.

---

## 공통 원칙

이 단계는 `skills/code-design/00-principles.md` 를 따른다.

---

## 진입 조건

다음 중 하나라도 해당되면 이 단계로 진입:
- 1단계(요구사항 분석)가 완료되어 요구사항 문서가 있음
- 요구사항은 명확한데 아직 모듈 구조 / 인터페이스가 정해지지 않음
- 기존 코드의 구조를 바꿔야 하는데 목표 구조가 없음

---

## 이 단계가 만드는 파일

이 단계는 두 종류의 파일을 만든다.

| 파일 | 내용 | 저장 시점 |
|------|------|----------|
| `handoff.md` | 2단계 산출물(설계 문서) — 아래 "산출물 형식" 섹션의 템플릿이 그대로 채워진 형태. 3단계 입력으로 그대로 사용됨 | 체크리스트 승인 직후 |

**용어 정리:**
- "산출물" = 설계 문서 본문 = `handoff.md` 의 내용

## 분기 판단 및 variant 로드

설계 대상에 따라 시작점과 흐름이 달라진다. 다음 두 가지 중 어디에 해당하는지 먼저 판단하고 해당 variant 파일을 로드한다.

| 상황 | variant 파일 |
|------|--------------|
| A. 새 프로젝트 / 새 서비스 | `skills/code-design/02-design/new_project.md` |
| B. 기존 코드 변경 (기능 추가 / 리팩터링 / 둘 다) | `skills/code-design/02-design/extend_or_refactor.md` |

외부 시스템 연동(API, DB, 메시지 큐 등)은 별도 흐름이 아니라 위 두 흐름의
"인터페이스 명세" 및 "데이터 흐름" 섹션에서 함께 다룬다.

분기 판단(A / B)은 Claude 가 사용자의 요청·컨텍스트를 바탕으로 자율적으로 수행한다.

<PENETRATE>
variant 파일은 분기 판단 직후, 사전 조사 시작 전에 사용자에게 로드 확인을 받은 뒤 로드한다.
</PENETRATE>

<PENETRATE>
분기 근거(사유)는 산출물 "적용 흐름" 섹션의 "사유" 칸으로 그대로 이관한다.
</PENETRATE>

<RICOCHET>
산출물 작성 시 분기 판단을 사용자에게 재차 묻지 않는다.
</RICOCHET>

## 단계 시작 시 — 사전 조사

### 1. 외부 검색 (필요 시)

**검색이 필요한 경우:**
- 처음 다루는 아키텍처 패턴 / 설계 패턴
- 외부 라이브러리 / 프레임워크의 권장 구조
- 업계 표준 인터페이스 명세 (REST 가이드, gRPC 컨벤션 등)
- 비기능 요구사항 대응을 위한 참조 패턴

검색 깊이 — 공통 원칙 2("반복될수록 더 깊이 파고든다")의 정량 단위를 2단계(설계)의 검색 행동으로 구체화:

| 상황 | 검색 횟수 | 출처 다양성 | 공식 문서 확인 |
|------|----------|------------|--------------|
| 처음 다루는 아키텍처/패턴 (표준 깊이) | 3~5회 | 2개 이상 출처 교차 확인 | 핵심 패턴만 |
| 두 번째 이상 같은 영역 (+1) | 5~8회 | 3개 이상 출처 + 인접 패턴 비교 | 모든 핵심 패턴 |
| 같은 설계 이슈가 반복 등장 (+2) | 8회 이상 | 근본 원인 추적 모드 | 공식 문서 + 표준 / RFC 직접 확인 |

**검색 후 처리:**

<PENETRATE>
이번 설계에 적용할 정보는 산출물의 "모듈 구조" / "인터페이스 명세" / "비기능 요구사항 대응" 섹션에 명시적으로 반영한다.
</PENETRATE>

<PENETRATE>
검토했으나 채택하지 않은 대안은 산출물의 "설계 결정 기록 — 고려했으나 버린 대안" 에 기록한다.
</PENETRATE>

<PENETRATE>
신뢰할 만한 출처(공식 문서, 표준 문서, RFC)는 산출물의 "참고 자료" 섹션에 링크로 남긴다.
</PENETRATE>

### 2. 사용자 확인 — 모호하면 반드시

외부 검색으로도 결정할 수 없는 항목은 사용자에게 질문한다 (공통 원칙 1).

### 3. 기존 코드 탐색 (해당되는 경우)

작업 흐름 B(기존 코드 변경) 인 경우, 설계 시작 전에 기존 코드의 모듈 구조와 의존 관계를 파악해야
영향 범위와 변경 지점을 정확히 그릴 수 있다. 흐름 A(새 프로젝트) 는 이 항목이 N/A.

기존 코드 구조 파악에 code-analyze facet 산출물이 있으면 1차 입력으로 활용한다 -- 공통 원칙 6 (`00-principles.md`) 참조. 수작업 도구는 facet 이 없거나 특정 지점을 더 깊이 파야 할 때 보완으로 쓴다.

**자주 쓰이는 도구** (`references/tools.md` 의 코드 인텔리전스 참고):
- ripgrep (rg) — 관련 키워드/패턴이 코드베이스 어디에 있는지 검색
- fd — 관련 파일 빠르게 찾기
- tree — 디렉토리 구조 파악
- universal-ctags — 함수/클래스/심볼 정의 위치 추적

**활용 예:**
- 기능 추가 영향 범위 파악 -> 추가 지점 주변 심볼의 호출처 / 의존 추적
- 리팩터링 대상 의존 관계 파악 -> 해당 모듈을 import 하는 모든 위치 추적
- 순환 의존 여부 점검 -> 모듈 간 호출 그래프 확인

**도구 활용 후:**

<PENETRATE>
파악한 내용은 산출물의 "현재 상태" 섹션에 반영한다.
</PENETRATE>

<PENETRATE>
도구가 이 프로젝트에 부적합하다고 판단되면 그 사실을 산출물의 "사용자와의 명확화 기록"에 남긴다.
</PENETRATE>

## 산출물 형식

설계 결과는 다음 형식의 문서로 작성한다.
모든 섹션은 비워두지 않는다. 채울 데이터가 없으면 명시적으로 N/A로 표기한다 (공통 원칙 3).

이 산출물은 핸드오프 파일(`handoff.md`)에 그대로 저장된다 — "다음 단계로 전달할 것" 섹션 참조.

```markdown
# 설계: {기능명}

## 적용 흐름
A / B 중 어느 것인지 명시 + 사유.
B의 경우 variant 파일의 안내에 따라 세부 케이스를 추가 명시한다.

## 현재 상태
(기능 추가 / 리팩터링에만 해당. 새 프로젝트는 N/A)
- 관련 코드 위치: ...
- 현재 구조 (다이어그램)
- 변경 영향 범위 (기능 추가) 또는 문제 지점 (리팩터링): ...

## 모듈 구조
- 모듈 목록 + 각 책임
- 분할 기준 + 사유
- 의존 관계 (다이어그램)

## 인터페이스 명세
- 함수 시그니처 / API 엔드포인트 / 데이터 타입
- 외부 시스템 연동이 있으면 타임아웃 / 재시도 / 에러 처리 / mock 전략 포함

## 데이터 흐름
- 주요 시나리오별 흐름 (다이어그램)
- 상태 변경 지점
- 에러 발생 시 흐름

## 비기능 요구사항 대응
- 성능: ...
- 보안: ...
- 확장성: ...
- 가용성: ...
- 호환성: ...
- 운영: ...

## 전환 경로
(리팩터링에만 해당. 그 외는 N/A)
- 단계별 변경 순서
- 각 단계의 동작 가능 상태
- 롤백 가능 여부

## TDD 계획
형식: 테스트 이름 + 한 줄 설명.
새 프로젝트 / 기능 추가는 신규 케이스, 리팩터링은 회귀 방지 케이스.

### happy path
- test_xxx: ...

### 실패 케이스
- test_xxx: ...

### edge case
- test_xxx: ...

## 설계 결정 기록
- 결정한 것 / 이유 / 고려했으나 버린 대안
- (리팩터링) 리팩터링하지 않는 옵션 검토 결과

## 참고 자료
- 외부: (검색으로 참고한 공식 문서, 표준, 패턴 등)

## 사용자와의 명확화 기록
- 모호했던 항목과 그 해소 과정
- 피드백 협의 과정 (피드백이 있었던 경우)
  - 사용자 의견: ...
  - LLM 반문: ...
  - 합의 결과: ...
```

## 완료 기준

단계 종료 시 아래 형식으로 제시한다.

**저장 경로:** `{프로젝트 루트}/code-design/02-design/{YYYY-MM-DD-HHMM}-checklist.md`
- 공통 원칙 5("단계 산출물 저장 정책")에 따른다.
- 매 저장 시 신규 파일이 생성되며 누적된다.

```markdown
## 완료 기준
- [ ] 적용 흐름(A/B)이 명시됨. B인 경우 variant 파일의 세부 케이스도 추가 명시됨
- [ ] 모듈 경계와 책임이 명확히 정의됨
- [ ] 모듈 간 의존이 단방향이고 순환 의존이 없음
- [ ] 주요 인터페이스(함수 시그니처, API)가 명세됨
- [ ] 외부 시스템 연동이 있으면 타임아웃/재시도/에러 처리/mock 전략이 명세됨
- [ ] 데이터 흐름이 다이어그램으로 정의됨
- [ ] 비기능 요구사항 각 항목에 대한 설계 반영 방안이 작성됨
- [ ] TDD 계획(테스트 케이스 목록)이 happy path / 실패 / edge case로 분류되어 작성됨
- [ ] 기능 추가인 경우 영향 범위가 파악되어 기록됨
- [ ] 리팩터링인 경우 현재 구조 분석 + 전환 경로 + 회귀 방지 테스트 목록이 작성됨
- [ ] 설계 결정 기록에 채택 사유와 대안 검토가 포함됨
- [ ] 모호한 사용자 표현은 모두 되묻고 명확화됨
- [ ] 임의 결정이 없음 (모든 결정은 사용자 확인됨)
- [ ] 반복 작업의 경우 깊이 +1 / +2 기준에 맞게 조사가 이루어짐
- [ ] N/A로 표기된 항목이 모두 사용자 확인을 받음
- [ ] 피드백 영역이 채워짐 (없어도 N/A 명시)

## N/A 항목 확인
다음 항목이 N/A로 표기됨. 정말 해당 없음이 맞는지 확인 부탁드립니다:
- (예) 현재 상태: N/A (새 프로젝트이므로 해당 없음)
- (예) 비기능 요구사항 - 가용성: N/A
(N/A 항목이 없으면 "없음"으로 표기)

## 피드백
(피드백을 작성. 없으면 N/A 명시)
```

### 피드백 처리 절차

**용어 정리:**
- 체크리스트 파일의 "피드백" 섹션 = 매 회차 사용자가 적는 입력 (회차마다 누적)
- 산출물의 "사용자와의 명확화 기록" 섹션 = 협의 과정과 합의 결과의 영구 이력
- 피드백이 들어오면 협의를 거쳐 그 결과를 영구 이력에 옮긴다.

**자동 수용 금지 피드백:**

<RICOCHET>
"이 모듈은 합치자" / "이 인터페이스는 빼자" 같은 구조 변경 요청을 자동 수용하지 않는다.
</RICOCHET>

<RICOCHET>
산출물의 일부 결정을 뒤집는 요청을 자동 수용하지 않는다.
</RICOCHET>

<RICOCHET>
템플릿 자체에 대한 변경 요청을 자동 수용하지 않는다.
</RICOCHET>

**처리 절차:**
1. 반문한다. 왜 그렇게 판단했는지, 어떤 영향이 있는지 확인
2. 협의한다.
3. 기록한다. 협의 과정과 합의 결과를 산출물의 "사용자와의 명확화 기록"에 남긴다
4. 합의된 변경을 산출물에 반영한 뒤 재제시

<RICOCHET>
협의가 끝나기 전에 자동 수용 금지 피드백을 산출물에 반영하지 않는다.
</RICOCHET>

<RICOCHET>
사용자와 합의에 도달하기 전에 다음 단계로 진행하지 않는다.
</RICOCHET>

피드백이 단순한 N/A (의견 없음) 이거나 명확한 추가 요구사항이면 위 절차 없이 바로 반영해도 된다.

**저장 경로:** `{프로젝트 루트}/code-design/02-design/handoff.md`
- 공통 원칙 5("단계 산출물 저장 정책")에 따른다.

<PENETRATE>
핸드오프는 완료 기준 체크리스트가 사용자 승인을 받은 직후에만 작성한다.
</PENETRATE>

**내용 계약:**
- "산출물 형식" 섹션의 템플릿이 곧 핸드오프 파일의 내용이다 (핸드오프 = 2단계 산출물 그 자체).
- 모듈 구조 + 인터페이스 명세는 3단계가 구현 시 직접 참조한다.
- TDD 계획은 3단계 Red -> Green -> Refactor 사이클의 입력이다.
- 설계 결정 기록 + 사용자와의 명확화 기록은 3단계에서 같은 결정이 다시 등장할 때 일관성 유지에 사용한다.
- 외부 참고 자료, 1단계로부터 받은 가정 사항 / 보류 항목 — 모두 산출물 안에 포함되므로 별도 파일을 만들지 않는다.

**재설계(같은 프로젝트를 다시 설계하는 경우):**

이미 handoff.md 가 있는 프로젝트를 다시 설계하면, 새 버전 파일을 만들지 않고 기존 handoff.md 를 그 자리에서 갱신한다. handoff 는 3단계가 읽는 고정 경로의 단일 파일이라, 버전 파일을 만들면 3단계가 그것을 읽지 못한다.

갱신은 섹션 성격에 따라 둘로 갈린다.

- 본문 섹션(적용 흐름, 현재 상태, 모듈 구조, 인터페이스 명세, 데이터 흐름, 비기능 요구사항, 전환 경로, TDD 계획) — 현재(목표) 설계로 교체한다.
- 원장 섹션(설계 결정 기록, 사용자와의 명확화 기록) — 기존 항목을 지우지 않고 이번 재설계 항목을 아래에 덧붙인다. 과거 결정을 뒤집을 때도 옛 항목은 그대로 두고, 뒤집는 이유를 새 항목으로 추가한다.

본문을 교체해도 변경 이력은 원장 섹션이 보존하므로, 옛 본문 전체를 파일에 남겨둘 필요가 없다.

예외(전환기 as-built 스냅샷): 재설계가 점진 전환이라 옛 본문이 전환 동안 현재 코드(as-built)의 참조로 가치가 있으면, 옛 handoff 전체를 `archive/` 하위로 옮겨 스냅샷으로 보존해도 된다. 이때 archive 파일명은 이동 시점 타임스탬프를 붙여(`handoff-{YYYY-MM-DD-HHMM}.md`, 초 제외) 재설계가 반복돼도 덮어쓰지 않게 한다(체크리스트 누적 컨벤션과 동일). 이 스냅샷은 3단계가 읽는 대상이 아니라 동결된 참조이므로 금지 대상인 '버전 파일'이 아니다. 이 경우에도 원장은 새 handoff.md 로 이어받아 자족적으로 둔다.

<PENETRATE>
archive 스냅샷을 두더라도 canonical handoff.md 는 3단계가 읽는 target 설계만 담는다.
</PENETRATE>

<PENETRATE>
재설계 시 handoff.md 를 같은 파일에서 갱신하며 별도 버전 파일을 만들지 않는다.
</PENETRATE>

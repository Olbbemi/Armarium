# 설계 (design)

요구사항이 확정된 후 구현 전에, 어떻게 만들지를 정의하는 단계.
이 단계의 출력이 03-implementation 의 입력이 된다.

01-requirements 의 핸드오프를 입력으로 받는다(hard 의존). 그 핵심은 전제로 요약 인용하고(전제 정리 스텝 1), 위임 항목([design] 태그)은 전제 인용과 별개로 이번 설계에서 해소한다(스텝 2).

## 단계 내 진행도 (TaskCreate)

이 단계는 체크포인트가 많아 TaskCreate 로 진행도를 시각화한다(principles.md "단계 내 진행도" 원칙). 아래 체크포인트를 순서대로 task 로 두고, 진입 시 in_progress / 완료 조건 충족 시 completed 로 닫는다. 체크포인트 사이의 논의 / 검색 / 피드백은 해당 체크포인트 안에서 처리한다.

- 분기 판단 + variant 로드 -- variant 파일이 로드되면 닫는다 (로드 확인 게이트: 확인 요청 직전 completed).
- 사전 조사 -- cross-flow 층(`architecture.md` · `decisions.md`) 읽기와 검색, (흐름 B) 기존 코드 탐색으로 설계 근거를 확보하면 닫는다 (흐름 A 는 코드 탐색 스킵).
- 전제 정리 + 위임 / 보류 해소 -- 열린 보류가 0 이 되면 닫는다 (최종 게이트).
- 산출물 작성 -- 산출물 형식 템플릿 초안을 다 채우면 닫는다. 모듈 구조 / 인터페이스 / 데이터 흐름 / TDD 계획 등 내부 논의는 이 체크포인트 안에서 처리하고 쪼개지 않는다.
- 완료 기준 승인 -- 사용자 사인오프를 받으면 닫는다 (승인 게이트: 완료 기준 제시 직전 completed, 피드백 협의는 이 체크포인트 안).
- 핸드오프 + cross-flow 층 기록 -- handoff.md 를 쓰고, `architecture.md` 갱신과 `decisions.md` append 를 사용자 확인까지 마치면 닫는다.

## 분기 판단 및 variant 로드

설계 대상에 따라 시작점과 흐름이 달라진다. 다음 두 가지 중 어디에 해당하는지 먼저 판단하고 해당 variant 파일을 로드한다.

| 상황 | variant 파일 |
|------|--------------|
| A. 새 프로젝트 / 새 서비스 | `skills/code-design/02-design/new_project.md` |
| B. 기존 코드 변경 (기능 추가 / 리팩터링 / 둘 다) | `skills/code-design/02-design/extend_or_refactor.md` |

외부 시스템 연동(API, DB, 메시지 큐 등)은 별도 흐름이 아니라 위 두 흐름의
"인터페이스 명세" 및 "데이터 흐름" 섹션에서 함께 다룬다.

분기 판단(A / B)은 Claude 가 사용자의 요청·컨텍스트를 바탕으로 자율적으로 수행한다.

<FORBIDDEN>
사용자에게 로드 확인을 받기 전에 variant 파일을 로드하지 않는다.
</FORBIDDEN>

<FORBIDDEN>
산출물 작성 시 분기 판단을 사용자에게 재차 묻지 않는다.
</FORBIDDEN>

### 조건부 보조 파일 -- 동시성 / 통신 (hazard)

variant(A/B) 와 별개로, 이 설계가 아래 hazard 를 건드리면 해당 보조 파일을 로드해 설계 시점에 대응을 결정한다. 안 건드리면 로드하지 않는다.

| 보조 파일 | 로드 트리거 |
|-----------|------------|
| `skills/code-design/02-design/concurrency.md` | 공유 가변 상태에 둘 이상의 실행 맥락(스레드 / async / 프로세스)이 동시·인터리빙 접근 -- 멀티스레드, async 인터리빙, 공유 메모리형 IPC(shm, mmap, 프로세스 간 동기화) |
| `skills/code-design/02-design/communication.md` | 제어하지 못하는 경계 너머로 메시지를 주고받음 -- 네트워크(HTTP / RPC / 소켓), 메시지 전달형 IPC(파이프, 도메인 소켓, 큐) |

- 판정 시점은 유동적이다 -- 분기 때 이미 명확하면 그때, 아니면 사전 조사 / 설계 본문을 짜다 드러나는 즉시 로드한다.
- 한 설계가 둘 다 걸치면(예: 공유 메모리 큐로 프로세스 간 통신) 두 파일을 모두 로드한다 -- 경계가 애매한 hazard 는 양쪽에서 다뤄 놓치지 않는다.
- 로드는 자율로 하되, 로드 근거(어떤 hazard 때문인지)를 대화 또는 산출물에 남긴다.

## 단계 시작 시 -- 사전 조사

### 1. 외부 검색 (필요 시)

**검색이 필요한 경우**
- 처음 다루는 아키텍처 패턴 / 설계 패턴
- 외부 라이브러리 / 프레임워크의 권장 구조
- 업계 표준 인터페이스 명세 (REST 가이드, gRPC 컨벤션 등)
- 비기능 요구사항 대응을 위한 참조 패턴

검색 깊이 -- 공통 원칙 2("반복될수록 더 깊이 파고든다")의 정량 단위를 02-design 의 검색 행동으로 구체화
| 상황 | 검색 횟수 | 출처 다양성 | 공식 문서 확인 |
|------|----------|------------|--------------|
| 처음 다루는 아키텍처/패턴 (표준 깊이) | 3~5회 | 2개 이상 출처 교차 확인 | 핵심 패턴만 |
| 두 번째 이상 같은 영역 (+1) | 5~8회 | 3개 이상 출처 + 인접 패턴 비교 | 모든 핵심 패턴 |
| 같은 설계 이슈가 반복 등장 (+2) | 8회 이상 | 근본 원인 추적 모드 | 공식 문서 + 표준 / RFC 직접 확인 |

**검색 후 처리**
- 이번 설계에 적용할 정보는 산출물의 "모듈 구조" / "인터페이스 명세" / "비기능 요구사항 대응" 섹션에 반영한다
- 검토했으나 채택하지 않은 대안은 "설계 결정 기록 -- 고려했으나 버린 대안" 에 기록한다
- 신뢰할 만한 출처(공식 문서, 표준 문서, RFC)는 "참고 자료" 섹션에 링크로 남긴다

### 2. 사용자 확인 -- 모호하면 반드시

외부 검색으로도 결정할 수 없는 항목은 사용자에게 질문한다 (공통 원칙 1).

### 3. 기존 코드 탐색 (해당되는 경우)

작업 흐름 B(기존 코드 변경) 인 경우, 설계 시작 전에 기존 코드의 모듈 구조와 의존 관계를 파악해야
영향 범위와 변경 지점을 정확히 그릴 수 있다. 흐름 A(새 프로젝트) 는 이 항목이 N/A.

기존 코드 구조 파악에 코드 분석 산출물(facet)이 있으면 1차 입력으로 활용한다 -- 공통 원칙 6 (`principles.md`) 참조. 수작업 도구는 facet 이 없거나 특정 지점을 더 깊이 파야 할 때 보완으로 쓴다.

**자주 쓰이는 도구** (`references/tools.md` 의 코드 인텔리전스 참고)
- ripgrep (rg) -- 관련 키워드/패턴이 코드베이스 어디에 있는지 검색
- fd -- 관련 파일 빠르게 찾기
- tree -- 디렉토리 구조 파악
- universal-ctags -- 함수/클래스/심볼 정의 위치 추적

**활용 예**
- 기능 추가 영향 범위 파악 -> 추가 지점 주변 심볼의 호출처 / 의존 추적
- 리팩터링 대상 의존 관계 파악 -> 해당 모듈을 import 하는 모든 위치 추적
- 순환 의존 여부 점검 -> 모듈 간 호출 그래프 확인

**도구 활용 후**
- 파악한 내용은 산출물의 "현재 상태" 섹션에 반영한다
- 도구가 이 프로젝트에 부적합하다고 판단되면 그 사실을 "사용자와의 명확화 기록" 에 남긴다

## 전제 정리 + 위임 항목 해소

사전 조사 직후, 설계 본문에 들어가기 전에 01-requirements 핸드오프를 받아 정리하고 넘어온 위임을 해소한다.

### 1. 전제 확인 (요구사항 + cross-flow 층 요약)

01-requirements 핸드오프를 읽고, 확정 방향 / 유형 / 범위 / 우선순위 / 핵심 승인 기준 / 비기능 / 제약 / 로드맵(미래 수용 경계) / 상속 가정의 핵심을 산출물 상단 "전제" 섹션에 요약 인용한다. 통째 복사가 아니라 핵심 압축이다.

전제의 각 줄에는 그 값의 출처를 단다. 출처는 그 값의 단일 출처를 직접 가리킨다 -- 시스템 제약 · 기술 스택은 `architecture.md`, 청크 상태는 `roadmap.md`, 지난 flow 의 설계 결정은 `decisions.md`, 나머지는 01-requirements `handoff.md`. 01-requirements 의 전제 섹션(이미 요약본)을 다시 요약하지 않는다. 요약과 출처가 어긋나면 출처를 신뢰한다.

### 2. 요구사항 위임 항목([design] 태그) 해소

01-requirements 핸드오프의 "위임 항목([design] 태그)"을 빠짐없이 이번 설계에서 결정한다. 여기엔 01-requirements 가 새로 발견한 것과, 00-ideation 이 [design] 으로 태깅해 01-requirements 가 통과시킨 것이 섞여 있다 -- design 이 최종 해소처다.

- 각 항목을 모듈 구조 / 인터페이스 명세 / 데이터 흐름 중 해당하는 곳에서 확정한다.
- 못 정하면 되묻고(공통 원칙 1), 그래도 미정이면 사용자 확인 하에 로드맵 `[예정]`/`[미정]` 로 escalation 한다 -- 02-design 은 마지막 결정 단계라 03-implementation 으로 미룰 수 없다(원칙 4).
- [deferred] 로 넘어온 것 중 이제 설계로 풀 수 있는 게 있으면 함께 해소한다.

### 3. 미래 수용 경계 준수

설계는 `[진행]` 청크 범위만 구현하되, 전제의 `[예정]`/`[미정]` 청크를 구조적으로 차단하지 않는다.

- 인터페이스 / 모듈 경계가 `[예정]`/`[미정]` 확장을 차단하지 않는지 점검한다.
- 단, 미래 청크를 위해 지금 코드를 미리 작성하지 않는다(YAGNI). 확장 여지만 남기고 구현은 `[진행]` 청크까지다.

### 4. 열린 보류 해소 (최종 게이트)

01-requirements 에서 재개 시점 = 02-design 으로 넘어온 열린 보류를 여기서 전부 결판낸다. 02-design 은 마지막 결정 단계다.

- 각 열린 보류를 사용자 확인으로 **해소**(결정 -> 값 확정)하거나, 정할 수 없으면 **로드맵 `[예정]`/`[미정]` 로 escalation**(다음 flow 로) 한다. escalation 은 roadmap.md 에 append 하고 출처를 남긴다(전이 주체 -- `cross-flow.md` "roadmap.md").
- 02-design 을 닫을 때 열린 보류가 **0** 이어야 한다 -- 03-implementation 은 열린 보류를 받지 않는다.

### 5. 실측이 필요한 결정

설계 결정에도 재봐야 아는 것이 섞인다 -- 이 라이브러리가 우리 환경에서 도는지, 현재 구조에서 그 경로가 얼마나 걸리는지. 추측으로 채우지 않고 공통 원칙 4("escalation 사유에는 실측 선행이 포함된다")로 가른다.

- 재는 방법이 서 있다 -> 그 자리에서 재고 산출물 `## 실측` 에 남긴다. 그 값이 결정 근거면 `decisions.md` 의 `근거` 칸에서 이 표를 가리킨다.
- 방법부터 세워야 한다 -> 로드맵에 선행 청크를 올리고 이 청크를 `[예정]` 으로 내린다 (`cross-flow.md` "선행 관계"). 열린 보류로 미루지 않는다 -- 02-design 은 마지막 결정 단계라 뒤 단계가 풀어줄 수 없다.

## 검증 지정 (6종)

02-design 이 맡는 검증 6종 -- 유닛 · 통합 · 경합 · 계약 · 경계값 · 정적 분석 -- 각각에 적용 또는 N/A 를 판정한다. 나머지 6종(기능 · 성능 · 보안 · 호환성 · 수동 QA · e2e)은 01-requirements 가 이미 지정했고, 여기서 다시 판정하지 않는다.

- 각 종류의 정의 · 적용 판정 규칙 · 산출물은 `skills/code-design/verification.md` 를 단일 출처로 본다. 여기서는 그 판정을 실행하고 결과만 기록한다.
- 절단 기준이 01-requirements 와 다르다. 여기 6종은 **설계 결정이 만든 위험**이 근거다 -- 요구사항 문장이 아니라 이번 설계가 무엇을 어떻게 나눴는지가 적용 여부를 가른다.
- 6종 중 하나라도 판정을 빠뜨리지 않는다. N/A 로 판정했으면 그 근거도 함께 적는다 (공통 원칙 3).

판정 입력이 이미 산출물 안에 있는 것이 넷이다. 그 절을 채운 뒤 판정한다.

| 종류 | 판정에 쓰는 절 |
|------|--------------|
| 유닛 | `## 모듈 구조` 의 모듈 중 로직을 가진 것 |
| 통합 | `## 모듈 구조` 가 포트 뒤로 격리한 외부 의존 |
| 경합 | `## 동시성 설계` hazard 표의 각 행 |
| 경계값 | `## 인터페이스 명세` 의 입력 중 범위 · 크기 · 널 허용이 정의된 것 |

유닛 검증의 산출물은 `## TDD 계획` 이다. 별도 목록을 만들지 않고 그 절이 곧 03-implementation 의 첫 RED 백로그가 된다.

## cross-flow 층 갱신

02-design 은 cross-flow 층의 주 갱신자다. 갱신 시점은 완료 기준 승인 이후이며 핸드오프 작성과 함께 처리한다(TaskCreate 의 "핸드오프 + cross-flow 층 기록" 체크포인트). 각 파일의 내용 규격은 `skills/code-design/cross-flow.md` 를 따른다.

**`architecture.md`** -- 이번 설계가 시스템 수준 제약을 새로 세우거나 바꾸면 그 항목을 갱신한다. 대상은 여러 청크에 걸쳐 유효한 것이다 -- 경계 · 의존 방향, 단위 간 통신 원칙, 구조적 금지, 언어 · 핵심 라이브러리 배치. 이번 청크에만 걸리는 모듈 구조 · 인터페이스는 여기가 아니라 `handoff.md` 소관이다.

**`decisions.md`** -- 이번 설계에서 내린 비자명한 결정 중 `cross-flow.md` "등재 기준" 을 통과한 것을 append 한다. 항목마다 결정 · 근거 · 버린 대안 · **비용** · 출처 · 날짜를 채우고, 부여된 번호 범위를 `handoff.md` 의 `## 설계 결정 기록` 에 포인터로 적는다. 비용을 못 적으면 대안 비교가 아직 안 된 것이다.

두 파일 모두 사용자 확인을 받고 출처(`{브랜치 슬러그} / 02-design`)를 남긴다.

### 재설계 (같은 프로젝트를 다시 설계하는 경우)

이미 handoff.md 가 있는 프로젝트를 다시 설계하면 기존 handoff.md 를 그 자리에서 갱신한다. handoff.md 는 03-implementation 이 읽는 고정 경로의 단일 파일이라, 버전 파일을 만들면 03-implementation 이 그것을 읽지 못한다.

갱신은 섹션 성격에 따라 둘로 갈린다.

- 본문 섹션(적용 흐름, 현재 상태, 모듈 구조, 인터페이스 명세, 데이터 흐름, 비기능 요구사항, 실측, 검증 지정, 전환 경로, TDD 계획) -- 현재(목표) 설계로 교체한다.
- 이력 섹션(사용자와의 명확화 기록) -- 이번 재설계 항목을 아래에 덧붙인다.
- 설계 결정 기록은 포인터뿐이므로 이번 재설계가 더한 번호 범위로 갱신한다. 과거 결정을 뒤집는 처리는 `decisions.md` 규격(새 항목 추가 + 옛 항목에 대체 표기)을 따른다.

예외(전환기 as-built 스냅샷): 재설계가 점진 전환이라 옛 본문이 전환 동안 현재 코드(as-built)의 참조로 가치가 있으면, 옛 handoff.md 전체를 `archive/` 하위로 옮겨 스냅샷으로 보존해도 된다. 이때 archive 파일명은 이동 시점 타임스탬프를 붙여(`handoff-{YYYY-MM-DD-HHMM}.md`, 초 제외) 재설계가 반복돼도 덮어쓰지 않게 한다(과거 스냅샷 보존용). 이 스냅샷은 03-implementation 이 읽는 대상이 아니라 동결된 참조이므로 금지 대상인 '버전 파일'이 아니다. 이 경우에도 이력 섹션은 새 handoff.md 로 이어받아 자족적으로 둔다.

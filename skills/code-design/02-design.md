# 설계 (design)

요구사항이 확정된 후 구현 전에, 어떻게 만들지를 정의하는 단계.
이 단계의 출력이 03-implementation 의 입력이 된다.

01-requirements 의 핸드오프를 입력으로 받는다(hard 의존). 그 핵심(범위 / 우선순위 / 승인 기준 / 제약 / 비기능 / 로드맵 경계 / 상속 가정)은 산출물 상단 "전제" 섹션에 요약 인용하고, 위임 항목(design)은 전제 인용과 별개로 이번 설계에서 해소한다.

---

## 공통 원칙

이 단계는 `skills/code-design/principles.md` 를 따른다.

---

## 진입 조건

다음 중 하나라도 해당되면 이 단계로 진입:
- 01-requirements 가 완료되어 요구사항 문서가 있음
- 요구사항은 명확한데 아직 모듈 구조 / 인터페이스가 정해지지 않음
- 기존 코드의 구조를 바꿔야 하는데 목표 구조가 없음

## 이 단계가 만드는 파일

이 단계는 두 종류의 파일을 만든다.

| 파일 | 내용 | 저장 시점 |
|------|------|----------|
| `handoff.md` | design 산출물(설계 문서) — 아래 "산출물 형식" 섹션의 템플릿이 그대로 채워진 형태. 03-implementation 입력으로 그대로 사용됨 | 체크리스트 승인 직후 |

**용어 정리:**
- "산출물" = 설계 문서 본문 = `handoff.md` 의 내용
- "핸드오프" = 다음 단계가 읽을 파일 = `handoff.md`
- "체크리스트" = 완료 기준 점검 결과 = `checklist.md`

## 분기 판단 및 variant 로드

설계 대상에 따라 시작점과 흐름이 달라진다. 다음 두 가지 중 어디에 해당하는지 먼저 판단하고 해당 variant 파일을 로드한다.

| 상황 | variant 파일 |
|------|--------------|
| A. 새 프로젝트 / 새 서비스 | `skills/code-design/02-design/new_project.md` |
| B. 기존 코드 변경 (기능 추가 / 리팩터링 / 둘 다) | `skills/code-design/02-design/extend_or_refactor.md` |

외부 시스템 연동(API, DB, 메시지 큐 등)은 별도 흐름이 아니라 위 두 흐름의
"인터페이스 명세" 및 "데이터 흐름" 섹션에서 함께 다룬다.

분기 판단(A / B)은 Claude 가 사용자의 요청·컨텍스트를 바탕으로 자율적으로 수행한다.

<PENETRATE>
variant 파일은 분기 판단 직후, 사전 조사 시작 전에 사용자에게 로드 확인을 받은 뒤 로드한다.
</PENETRATE>

<PENETRATE>
분기 근거(사유)는 산출물 "적용 흐름" 섹션의 "사유" 칸으로 그대로 이관한다.
</PENETRATE>

<RICOCHET>
산출물 작성 시 분기 판단을 사용자에게 재차 묻지 않는다.
</RICOCHET>

## 단계 시작 시 — 사전 조사

### 1. 외부 검색 (필요 시)

**검색이 필요한 경우:**
- 처음 다루는 아키텍처 패턴 / 설계 패턴
- 외부 라이브러리 / 프레임워크의 권장 구조
- 업계 표준 인터페이스 명세 (REST 가이드, gRPC 컨벤션 등)
- 비기능 요구사항 대응을 위한 참조 패턴

검색 깊이 — 공통 원칙 2("반복될수록 더 깊이 파고든다")의 정량 단위를 02-design 의 검색 행동으로 구체화:

| 상황 | 검색 횟수 | 출처 다양성 | 공식 문서 확인 |
|------|----------|------------|--------------|
| 처음 다루는 아키텍처/패턴 (표준 깊이) | 3~5회 | 2개 이상 출처 교차 확인 | 핵심 패턴만 |
| 두 번째 이상 같은 영역 (+1) | 5~8회 | 3개 이상 출처 + 인접 패턴 비교 | 모든 핵심 패턴 |
| 같은 설계 이슈가 반복 등장 (+2) | 8회 이상 | 근본 원인 추적 모드 | 공식 문서 + 표준 / RFC 직접 확인 |

**검색 후 처리:**

<PENETRATE>
이번 설계에 적용할 정보는 산출물의 "모듈 구조" / "인터페이스 명세" / "비기능 요구사항 대응" 섹션에 명시적으로 반영한다.
</PENETRATE>

<PENETRATE>
검토했으나 채택하지 않은 대안은 산출물의 "설계 결정 기록 — 고려했으나 버린 대안" 에 기록한다.
</PENETRATE>

<PENETRATE>
신뢰할 만한 출처(공식 문서, 표준 문서, RFC)는 산출물의 "참고 자료" 섹션에 링크로 남긴다.
</PENETRATE>

### 2. 사용자 확인 — 모호하면 반드시

외부 검색으로도 결정할 수 없는 항목은 사용자에게 질문한다 (공통 원칙 1).

### 3. 기존 코드 탐색 (해당되는 경우)

작업 흐름 B(기존 코드 변경) 인 경우, 설계 시작 전에 기존 코드의 모듈 구조와 의존 관계를 파악해야
영향 범위와 변경 지점을 정확히 그릴 수 있다. 흐름 A(새 프로젝트) 는 이 항목이 N/A.

기존 코드 구조 파악에 code-analyze facet 산출물이 있으면 1차 입력으로 활용한다 -- 공통 원칙 6 (`principles.md`) 참조. 수작업 도구는 facet 이 없거나 특정 지점을 더 깊이 파야 할 때 보완으로 쓴다.

**자주 쓰이는 도구** (`references/tools.md` 의 코드 인텔리전스 참고):
- ripgrep (rg) — 관련 키워드/패턴이 코드베이스 어디에 있는지 검색
- fd — 관련 파일 빠르게 찾기
- tree — 디렉토리 구조 파악
- universal-ctags — 함수/클래스/심볼 정의 위치 추적

**활용 예:**
- 기능 추가 영향 범위 파악 -> 추가 지점 주변 심볼의 호출처 / 의존 추적
- 리팩터링 대상 의존 관계 파악 -> 해당 모듈을 import 하는 모든 위치 추적
- 순환 의존 여부 점검 -> 모듈 간 호출 그래프 확인

**도구 활용 후:**

<PENETRATE>
파악한 내용은 산출물의 "현재 상태" 섹션에 반영한다.
</PENETRATE>

<PENETRATE>
도구가 이 프로젝트에 부적합하다고 판단되면 그 사실을 산출물의 "사용자와의 명확화 기록"에 남긴다.
</PENETRATE>

## 전제 정리 + 위임 항목 해소

사전 조사 직후, 설계 본문에 들어가기 전에 01-requirements 핸드오프를 받아 정리하고 넘어온 위임을 해소한다.

### 1. 전제 확인 (요구사항 요약)

01-requirements 핸드오프를 읽고, 확정 방향 / 유형 / 범위 / 우선순위 / 핵심 승인 기준 / 비기능 / 제약 / 로드맵(미래 수용 경계) / 상속 가정의 핵심을 산출물 상단 "전제" 섹션에 요약 인용한다. 통째 복사가 아니라 핵심 압축이며, 상세는 01-requirements 핸드오프 원본을 참조한다(요약과 원본이 어긋나면 원본을 신뢰).

### 2. 요구사항 위임 항목(design) 해소

01-requirements 핸드오프의 "위임 항목(design)"을 빠짐없이 이번 설계에서 결정한다. 여기엔 01-requirements 가 새로 발견한 것과, 00-ideation 이 [design] 으로 태깅해 01-requirements 가 통과시킨 것이 섞여 있다 -- design 이 최종 해소처다.

- 각 항목을 모듈 구조 / 인터페이스 명세 / 데이터 흐름 중 해당하는 곳에서 확정한다.
- 못 정하면 되묻고(공통 원칙 1), 그래도 미정이면 사용자 확인 하에 로드맵 `[예정]`/`[미정]` 로 escalation 한다 -- 02-design 은 마지막 결정 단계라 03-implementation 으로 미룰 수 없다(원칙 4).
- [deferred] 로 넘어온 것 중 이제 설계로 풀 수 있는 게 있으면 함께 해소한다.

<PENETRATE>
01-requirements 가 [design] 으로 넘긴 위임 항목은 하나도 빠짐없이 이번 설계에서 결정하거나 로드맵으로 escalation 한다.
</PENETRATE>

### 3. 미래 수용 경계 준수

설계는 `[진행]` 청크 범위만 구현하되, 전제의 `[예정]`/`[미정]` 청크를 구조적으로 닫지 않는다. 미래 청크를 실수로 봉쇄하는 일은 정작 인터페이스/모듈 경계를 굳히는 설계에서 벌어진다.

- 인터페이스 / 모듈 경계가 `[예정]`/`[미정]` 확장을 원천봉쇄하지 않는지 점검한다.
- 단, 미래 청크를 위해 지금 코드를 미리 짓지 않는다(YAGNI). 확장 여지만 남기고 구현은 `[진행]` 청크까지다.

<RICOCHET>
[진행] 청크에 최적화한다는 이유로 전제의 [예정]/[미정] 청크를 구조적으로 봉쇄하는 설계를 하지 않는다.
</RICOCHET>

### 4. 열린 보류 해소 (최종 게이트)

01-requirements 에서 재개 시점 = 02-design 으로 릴레이된 열린 보류를 여기서 전부 결판낸다. 02-design 은 마지막 결정 단계다.

- 각 열린 보류를 사용자 확인으로 **해소**(결정 -> 값 확정)하거나, 정할 수 없으면 **로드맵 `[예정]`/`[미정]` 로 escalation**(다음 flow 로) 한다. escalation 은 roadmap.md 에 append 하고 출처를 남긴다(전이 주체 -- overview "로드맵").
- 02-design 을 닫을 때 열린 보류가 **0** 이어야 한다 -- 03-implementation 은 열린 보류를 받지 않는다.

<PENETRATE>
02-design 을 닫기 전에 모든 열린 보류를 해소하거나 로드맵으로 escalation 해 열린 보류를 0 으로 만든다.
</PENETRATE>

<RICOCHET>
열린 보류를 남긴 채 03-implementation 으로 넘어가지 않는다.
</RICOCHET>

## 산출물 형식

설계 결과는 다음 형식의 문서로 작성한다.
모든 섹션은 비워두지 않는다. 채울 데이터가 없으면 명시적으로 N/A로 표기한다 (공통 원칙 3).

이 산출물은 핸드오프 파일(`handoff.md`)에 그대로 저장된다 — "다음 단계로 전달할 것" 섹션 참조.

```markdown
# 설계: {기능명}

## 전제 (요구사항 요약)
(01-requirements 핸드오프에서 요약 인용 -- 통째 복사 아님. 상세는 code-design/<브랜치>/01-requirements/handoff.md 원본, 로드맵은 roadmap.md, 어긋나면 원본 신뢰)
- 확정 방향 / 유형: ...
- 범위: In scope ... / Out of scope ... (다음 flow 예정 / 영구 제외)
- 우선순위: 필수 ... / 선택 ...
- 핵심 승인 기준: ...
- 비기능 요구사항: 성능 ... / 보안 ... (수치)
- 제약 조건: ...
- 로드맵 / 미래 수용 경계: [진행] 청크 ... / [예정]·[미정] 청크 ... (design 이 닫지 말 것)
- 상속 가정: ... (01-requirements 의 확정 가정. 없으면 N/A)

## 적용 흐름
A / B 중 어느 것인지 명시 + 사유.
B의 경우 variant 파일의 안내에 따라 세부 케이스를 추가 명시한다.

## 현재 상태
(기능 추가 / 리팩터링에만 해당. 새 프로젝트는 N/A)
- 관련 코드 위치: ...
- 현재 구조 (다이어그램)
- 변경 영향 범위 (기능 추가) 또는 문제 지점 (리팩터링): ...

## 모듈 구조
- 모듈 목록 + 각 책임
- 분할 기준 + 사유
- 의존 관계 (다이어그램)

## 인터페이스 명세
- 함수 시그니처 / API 엔드포인트 / 데이터 타입
- 기능이 동등하면 시그니처 / 구조 표면이 더 작은 쪽을 택한다 -- 함께 변하는 값은 별도 인자로 흩뿌리지 말고 하나의 응집된 타입에 모으고(parameter object), 불필요한 중첩이나 중복 시그니처를 만들지 않는다
- 외부 시스템 연동이 있으면 타임아웃 / 재시도 / 에러 처리 / mock 전략 포함

## 데이터 흐름
- 주요 시나리오별 흐름 (다이어그램)
- 상태 변경 지점
- 에러 발생 시 흐름

## 비기능 요구사항 대응
- 성능: ...
- 보안: ...
- 확장성: ...
- 가용성: ...
- 호환성: ...
- 운영: ...

## 전환 경로
(리팩터링에만 해당. 그 외는 N/A)
- 단계별 변경 순서
- 각 단계의 동작 가능 상태
- 롤백 가능 여부

## TDD 계획
형식: 테스트 이름 + 한 줄 설명.
새 프로젝트 / 기능 추가는 신규 케이스, 리팩터링은 회귀 방지 케이스.

### happy path
- test_xxx: ...

### 실패 케이스
- test_xxx: ...

### edge case
- test_xxx: ...

## 설계 결정 기록
- 결정한 것 / 이유 / 고려했으나 버린 대안
- (리팩터링) 리팩터링하지 않는 옵션 검토 결과

## 가정 사항
- (설계 중 사용자 확인을 받은 [확정] 가정만 기록. 임의 가정 금지)
- 01-requirements 에서 받은 확정 가정은 위 "전제"에 인용됨 -- 여기선 design 이 새로 세운 것만 (없으면 N/A)

## 열린 보류 (해소 기록)
(01-requirements 에서 재개 = 02-design 으로 온 열린 보류의 처리 결과. 미해소 0 -- 남으면 03-implementation 진입 불가. 없으면 N/A. 원칙 4)
| # | 항목 | 처리 (해소 결정 / 로드맵 escalation) | 출처 |
|---|------|----------------------------------|------|

## 참고 자료
- 외부: (검색으로 참고한 공식 문서, 표준, 패턴 등)

## 사용자와의 명확화 기록
- 모호했던 항목과 그 해소 과정
- 피드백 협의 과정 (피드백이 있었던 경우)
  - 사용자 의견: ...
  - LLM 반문: ...
  - 합의 결과: ...
```

### 피드백 처리 절차

**용어 정리:**
- 체크리스트 파일의 "피드백" 섹션 = 매 회차 사용자가 적는 입력 (단일 파일 갱신, 회차 이력은 git)
- 산출물의 "사용자와의 명확화 기록" 섹션 = 협의 과정과 합의 결과의 영구 이력
- 피드백이 들어오면 협의를 거쳐 그 결과를 영구 이력에 옮긴다.

**자동 수용 금지 피드백:**

<RICOCHET>
"이 모듈은 합치자" / "이 인터페이스는 빼자" 같은 구조 변경 요청을 자동 수용하지 않는다.
</RICOCHET>

<RICOCHET>
산출물의 일부 결정을 뒤집는 요청을 자동 수용하지 않는다.
</RICOCHET>

<RICOCHET>
템플릿 자체에 대한 변경 요청을 자동 수용하지 않는다.
</RICOCHET>

**처리 절차:**
1. 반문한다. 왜 그렇게 판단했는지, 어떤 영향이 있는지 확인
2. 협의한다.
3. 기록한다. 협의 과정과 합의 결과를 산출물의 "사용자와의 명확화 기록"에 남긴다
4. 합의된 변경을 산출물에 반영한 뒤 재제시

<RICOCHET>
협의가 끝나기 전에 자동 수용 금지 피드백을 산출물에 반영하지 않는다.
</RICOCHET>

<RICOCHET>
사용자와 합의에 도달하기 전에 다음 단계로 진행하지 않는다.
</RICOCHET>

### 재설계 (같은 프로젝트를 다시 설계하는 경우)

이미 handoff.md 가 있는 프로젝트를 다시 설계하면, 새 버전 파일을 만들지 않고 기존 handoff.md 를 그 자리에서 갱신한다. handoff 는 03-implementation 이 읽는 고정 경로의 단일 파일이라, 버전 파일을 만들면 03-implementation 이 그것을 읽지 못한다.

갱신은 섹션 성격에 따라 둘로 갈린다.

- 본문 섹션(적용 흐름, 현재 상태, 모듈 구조, 인터페이스 명세, 데이터 흐름, 비기능 요구사항, 전환 경로, TDD 계획) — 현재(목표) 설계로 교체한다.
- 원장 섹션(설계 결정 기록, 사용자와의 명확화 기록) — 기존 항목을 지우지 않고 이번 재설계 항목을 아래에 덧붙인다. 과거 결정을 뒤집을 때도 옛 항목은 그대로 두고, 뒤집는 이유를 새 항목으로 추가한다.

본문을 교체해도 변경 이력은 원장 섹션이 보존하므로, 옛 본문 전체를 파일에 남겨둘 필요가 없다.

예외(전환기 as-built 스냅샷): 재설계가 점진 전환이라 옛 본문이 전환 동안 현재 코드(as-built)의 참조로 가치가 있으면, 옛 handoff 전체를 `archive/` 하위로 옮겨 스냅샷으로 보존해도 된다. 이때 archive 파일명은 이동 시점 타임스탬프를 붙여(`handoff-{YYYY-MM-DD-HHMM}.md`, 초 제외) 재설계가 반복돼도 덮어쓰지 않게 한다(과거 스냅샷 보존용). 이 스냅샷은 03-implementation 이 읽는 대상이 아니라 동결된 참조이므로 금지 대상인 '버전 파일'이 아니다. 이 경우에도 원장은 새 handoff.md 로 이어받아 자족적으로 둔다.

<PENETRATE>
archive 스냅샷을 두더라도 canonical handoff.md 는 03-implementation 이 읽는 target 설계만 담는다.
</PENETRATE>

<PENETRATE>
재설계 시 handoff.md 를 같은 파일에서 갱신한다.
</PENETRATE>

</RICOCHET>

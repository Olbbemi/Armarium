# 검증 (verification) -- 판정 게이트

03-implementation 이 만든 산출물을 통해 구현이 요구사항을 충족하는지 판정한다.
04-verification 은 새 코드나 새 산출물 파일을 만들지 않는다 -- 03-implementation 이 세운 틀(e2e 시나리오 · 수동 QA 체크리스트 항목)에 실제 검증 결과를 채워 판정만 한다.

04-verification 은 새 파일이나 새 디렉토리를 만들지 않는다 -- 03-implementation 이 세운 검증 틀을 그 자리(`{프로젝트 루트}/code-design/<브랜치>/03-implementation/`)에서 in-place 로 채운다. 04-verification 전용 산출물 디렉토리는 없다. 현재는 하류 단계가 없어 별도 핸드오프도 내지 않는다. 이후 04-verification 뒤에 플로우가 생기면 그 단계에 맞는 형태로 핸드오프를 둘 수 있다 -- 반드시 `handoff.md` 형식일 필요는 없다 (원칙 5 "핸드오프는 단계별로 형태가 다르다").

## 03-implementation 과의 역할 분담 (생성 vs 판정)

검증 산출물의 **틀은 03-implementation 이 만들고, 결과는 04-verification 이 채운다**. 파일 생성은 03-implementation, 결과 기입은 04-verification 이다.

| 축 | 03-implementation (생성) | 04-verification (판정) |
|----|-----------|-----------|
| e2e | 시나리오 목록(틀) 작성, 슬라이스마다 진행 | 전체를 한 번 더 실행해 결과·검증 시각을 채움 |
| 수동 QA | 체크리스트 항목(틀) 작성 | 사용자와 재현하며 `[x]`·결과를 채움 |
| 보안 | (해당 시) 점검 항목 작성 | 점검해 결과를 채움 |

<RICOCHET>
04-verification 에서 새 산출물 파일을 만들지 않는다.
</RICOCHET>

## 검증 축

대상 성격에 따라 해당되는 축만 수행한다 (03-implementation G1 레벨 축과 대응). 수행하지 않는 축은 N/A 로 명시한다(00 원칙 3).

### A. e2e -- 자동 e2e 가능 대상이 있으면 필수

- 빌드된 실제 산출물(바이너리 / 앱)을 시나리오대로 실행한다. 유닛 테스트가 아니라 **조립된 전체를 통째로 돌리는 것**이다.
- happy path 뿐 아니라 거부돼야 할 입력 · 충돌 · 미발견 같은 가드 / 실패 경로(03-implementation G7)도 확인한다.
- 대화형 UI 처럼 자동화가 불가한 경계는 e2e 대신 수동 QA 가 받는다.

### B. 수동 QA -- 자동화 불가한 인터랙티브 경계가 있으면 필수

- 자동 테스트로 가드되지 않는 인터랙티브 거동만 대상으로 한다.
- 수동 QA 항목은 가급적 그것을 만든 슬라이스에서 먼저 확인된다(03-implementation G8). 04-verification 은 전체를 최종 재확인하는 게이트지, 인터랙티브 확인을 처음 몰아서 하는 자리가 아니다 -- 04-verification 에 처음 몰면 결함이 늦게 잡혀 03-implementation <-> 04-verification 왕복이 는다.
- 사용자와 한 항목씩 재현하며 확인한다(티키타카, 00 원칙 1 의 "한 번에 하나").
- 인터랙티브 경계가 없는 순수 코어만이면 이 축은 비는 게 정상이다.
- 관찰 결과가 기대와 어긋나도 단일 관찰로 실패를 단정하지 않는다. 먼저 소스로 그 거동을 대조하거나 사용자에게 한 번 더 재현을 요청하고, 그래도 어긋나면 그때 실패로 판정한다 (사용자 조작 실수로 인한 거짓 실패 방지).

<RICOCHET>
수동 QA 에서 관찰이 기대와 어긋난다고 단일 관찰만으로 실패를 단정하지 않는다.
</RICOCHET>

### C. 보안 점검 -- 해당되면

- 이 프로젝트에 해당하는 위협만 점검한다 -- 비밀정보 노출, 의존성 취약점(CVE), 인증 / 권한 경계 등.
- 악의 / 가드 입력 거부는 e2e(G7)와 겹치므로 새로 검증하지 말고 e2e 리포트 항목을 참조한다.
- 해당 위협이 전혀 없으면 이 산출물 자체를 생략한다.

## 산출물 양식

모든 검증 산출물은 `{프로젝트 루트}/code-design/<브랜치>/03-implementation/` 에 둔다(생성 단계 기준 -- 03-implementation 이 만든 파일을 04-verification 이 그 자리에서 채운다). **단일 파일로 갱신**하며, 각 항목(라인)에 **검증 시각**을 남겨 여러 차례 · 여러 날에 걸친 검증 진행을 추적한다.

### e2e 리포트

```
# E2E 결과 -- {대상}
환경: {빌드 / 바이너리 식별}

| # | 시나리오   | 명령·입력 | 기대   | 결과         | 검증 시각        |
|---|-----------|----------|--------|--------------|------------------|
| 1 | 정상: 추가 | add ...  | 추가됨 | pass         | 2026-06-14-1030 |
| 2 | 목록       | list     | 표시   | pass         | 2026-06-14-1030 |
| 3 | 가드: 중복 | --dup    | 거부   | FAIL: 저장됨 | 2026-06-14-1030 |
요약: 2 pass / 1 fail
```

회귀 후 한 항목을 재검증하면 그 라인의 결과 · 검증 시각만 갱신한다. fail 이면 결과 칸에 증상을 함께 적는다.

### 수동 QA 체크리스트

```
# 수동 QA 체크리스트 -- {대상}

{대상 정의 한 줄: 자동 테스트로 가드되지 않는 인터랙티브 거동만 담는다}

## 사용법
1. {산출물 실행 방법}
2. 항목을 위에서부터 재현하고, 기대대로면 [x] 체크
3. 실패하면 항목 옆에 증상 기록

## {그룹명}
- [ ] **{항목명}** -- {기대 동작}
- [x] **{항목명}** -- {기대 동작} (QA {YYYY-MM-DD-HHMM}: {결과 / 증상})

> 갱신 규칙: 거동이 바뀌면 같이 갱신한다. 항목이 자동 테스트로 흡수되면
>           여기서 제거하고 TDD 계획으로 이관한다.
```

### 보안 점검 기록 (해당 시)

수동 QA 체크리스트 양식을 그대로 재사용하되 항목을 보안 위협으로 채운다.

```
# 보안 점검 -- {대상}

이 프로젝트에 해당하는 위협만 항목으로 둔다.
(해당 위협이 전혀 없으면 이 산출물 자체를 생략)

- [x] **비밀정보 노출** -- 하드코딩된 키 / 토큰 / 비번 없음 (점검 {YYYY-MM-DD-HHMM}: 없음)
- [x] **악의 / 가드 입력** -- 인젝션 · 경계 침범이 거부됨 (e2e 리포트 #3 참조)
- [ ] **의존성 취약점** -- 사용 라이브러리에 알려진 CVE
- [ ] **인증 / 권한 경계** -- 무권한 접근이 차단됨

요약: 미해결 취약점 {N}건  (있으면 03-implementation 으로 회귀)
```

## 발견 처리 (결함 -> 03-implementation 회귀·descope / 신규 범위 -> 로드맵)

04-verification 이 검증 중 발견하는 것은 두 종류다 -- 성격에 따라 처리처가 갈린다. 발견은 검증을 **돌린 결과**로 나온다: 결함은 e2e / 수동 QA / 보안을 실행·재현·점검한 결과의 FAIL 이고, 신규 범위는 검증하다 곁에서 관찰된 것이다.

**(a) 결함 -- 구현이 이번 요구사항을 못 충족(깨짐 / 누락).** 결함이 나와도 거기서 멈춰 곧장 처리로 튀지 않는다 -- 해당되는 검증 축(e2e / 수동 QA / 보안)을 **모두 끝내고**, 발견된 결함을 한데 모아 사용자에게 제시한다. 그다음 **승인 게이트에서 결함마다** 사용자가 경로를 고른다.

- **지금 고침 (기본)** -- 이번 run 안에서 고친다. 03-implementation 으로 회귀한다.
- **descope** -- 지금 제대로 고치려면 이번 run 범위를 넘는 결함을 이번엔 안 고치기로 한다. 미룬 수정을 로드맵 청크(기본 `[예정]` -- 알려진 미충족 요구)로 빼고, 현재 `[진행]` 청크 범위를 그만큼 좁혀 기록한다. 좁힌 청크는 좁혀진 범위로만 `[완료]` 된다.

**왜 모아서 게이트에 올리나:** 첫 실패에서 곧장 수정으로 튀면 나머지 결함을 못 보고 03-implementation <-> 04-verification 왕복만 늘어난다. 한 라운드에 다 모아야 03-implementation 에서 일괄로 고치거나 무엇을 descope 할지 한눈에 판단한다.

**(b) 신규 범위 발견 -- 요구엔 없던 새 아이디어 / 개선("이것도 하면 좋겠다").** 이번 청크 밖이라 이번 run 에서 구현하지 않고, 로드맵 청크(기본 `[미정]` -- 미검증 제안)로 넘긴다.

**로드맵 쓰기 (descope · 신규 범위 공통):** append 는 검증 중 그때그때 하지 않고 **모아뒀다 04-verification 을 닫을 때** 한 번에 한다(기존 "flow 종료 시 `[진행]`->`[완료]`" 와 같은 시점). 모든 append 는 사용자 확인을 받고 **출처**를 남긴다 -- 어느 검증 산출물에서 나왔는지 지목한다(예: `출처: 04-verification 결함 descope -- <브랜치>, e2e #3`, `출처: 04-verification 신규발견 -- <브랜치>, QA "정렬 표시"`). 청크 상태 어휘·행 형식·전이 규칙은 overview "로드맵"을 단일 출처로 보고, 04-verification 은 기본 플래그와 출처 관례만 얹는다. 04-verification 산출물은 브랜치 키 폴더에 남아 미래 flow 가 직접 읽지 않으므로, 미래 flow 가 움직일 요지는 로드맵 행에 압축해 넣는다(raw 증거는 04-verification 폴더 스냅샷에 보존).

<RICOCHET>
04-verification 에서 첫 결함이 나왔다고 곧장 처리로 튀지 않는다. descope 로 현재 청크 범위를 좁힐 때 사용자 확인 없이 조용히 줄이지 않는다.
</RICOCHET>

<PENETRATE>
해당되는 검증을 모두 수행하고 결함을 집계해, 승인 게이트에서 결함마다 지금 고침(03-implementation 회귀) 또는 descope(로드맵으로 미룸 + 범위 좁힘)로 라우팅한다. 로드맵 append 는 04-verification 을 닫을 때 사용자 확인 + 출처로 한다.
</PENETRATE>

## 완료선

- 해당되는 모든 검증 축이 수행됨 (수행하지 않은 축은 N/A 명시 -- 00 원칙 3)
- (a) 결함이 미해결로 남지 않음 -- 각 결함이 지금 고침(03-implementation 회귀) 또는 descope(로드맵으로 미룸 + 현재 청크 범위 좁힘) 중 하나로 처리됨
- (b) 신규 범위 발견은 로드맵 후보로 넘긴 상태 -- 이건 04-verification 을 닫는 걸 막지 않는다
- descope · 신규 범위의 로드맵 append 가 04-verification 을 닫을 때 사용자 확인 + 출처로 완료됨
- 각 산출물의 모든 항목이 결과 · 검증 시각으로 채워짐

</PENETRATE>

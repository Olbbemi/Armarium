# 검증 (verification) -- 판정 게이트

03-implementation 이 만든 산출물을 통해 구현이 요구사항을 충족하는지 판정한다.

04-verification 은 03-implementation 이 세운 검증 틀을 그 자리에서 in-place 로 채워 판정만 한다. 전용 산출물 디렉토리는 없고, 하류 단계가 없어 별도 핸드오프도 내지 않는다(원칙 5 "핸드오프는 단계별로 형태가 다르다").

이 단계는 `skills/code-design/principles.md` 를 따른다.

## 단계 내 진행도 (TaskCreate)

이 단계는 체크포인트가 여럿이라 TaskCreate 로 진행도를 시각화한다(principles.md "단계 내 진행도" 원칙). 아래 체크포인트를 순서대로 task 로 두고, 진입 시 in_progress / 완료 조건 충족 시 completed 로 닫는다. 체크포인트 사이의 논의 / 재현 / 피드백 왕복은 해당 체크포인트 안에서 처리한다.

- 진입 + 지정 대조 -- 진입 조건을 확인하고, 상류 두 `## 검증 지정` 을 합쳐 12종의 적용 / N-A 를 틀과 대조하면 닫는다.
- 검증 축 실행 -- 자동 스위트 · 도구 · 판정 문서 세 경로를 모두 돌려 결과 · 검증 시각을 채우면 닫는다. 종류마다 task 를 따로 만들지 않고 이 체크포인트 안에서 처리한다.
- 완결성 점검 -- 사전 틀(e2e/QA/보안)에 없던 확인할 내용을 찾아 맞는 틀에 추가해 그 자리에서 검증하면 닫는다.
- 추가 검증 게이트 -- "이 외에 더 보고 / 검증할 게 있는지" 사용자에게 물어 응답을 받으면 닫는다 (확인 게이트: 질문 직전 completed, 사용자가 든 항목은 틀에 넣어 검증).
- 발견 처리 -- 모든 축 · 점검 · 게이트에서 나온 결함을 집계해, 승인 게이트에서 결함마다 지금 고침(03-implementation 회귀) 또는 descope 로 라우팅하면 닫는다 (승인 게이트: 결함 제시 직전 completed).
- 마감 -- descope · 신규 범위의 로드맵 append(사용자 확인 + 출처)와 완료선 충족을 확인하면 닫는다.

## 03-implementation 과의 역할 분담 (생성 vs 판정)

검증 산출물의 **틀은 03-implementation 이 만들고, 결과는 04-verification 이 채운다**. 파일 생성은 03-implementation, 결과 기입은 04-verification 이다.

| 구분 | 03-implementation (생성) | 04-verification (판정) |
|----|-----------|-----------|
| e2e | 시나리오 목록(틀) 작성, 슬라이스마다 진행 | 전체를 한 번 더 실행해 결과·검증 시각을 채움 |
| 수동 QA | 체크리스트 항목(틀) 작성 | 사용자와 재현하며 `[x]`·결과를 채움 |
| 보안 | (해당 시) 점검 항목 작성 | 점검해 결과를 채움 |
| 성능 | 측정 시나리오 + 목표치 + 측정 방법 | 실측치와 측정 환경을 채워 목표 대비 판정 |
| 호환성 | 깨질 수 있는 표면 + 마이그레이션·폴백 항목 | 각 항목을 실제로 밟아 결과를 채움 |
| 경합 | (G16 b 갈래) 부하·스트레스 항목을 e2e·QA 틀에 등록 | 반복 실행해 결과와 실행 횟수를 채움 |
| 정적 분석 | 도구·규칙 세트·통과 기준을 설정으로 반영 | 실행해 통과 기준 충족을 확인 |

<FORBIDDEN>
04-verification 에서 새 산출물 파일을 만들지 않는다.
</FORBIDDEN>

## 검증 축 -- 지정 12종을 실행한다

무엇을 검증할지는 여기서 정하지 않는다. 01-requirements 와 02-design 이 `## 검증 지정` 으로 이미 판정했고, 03-implementation 이 그 판정대로 틀을 세웠다. 04-verification 은 그 지정을 **실행하고 대조**한다.

### 대조가 먼저다

축을 돌리기 전에 지정과 틀을 맞춰 본다. 이 대조가 "조용히 건너뛴 검증" 을 잡는 유일한 자리다.

- 두 `## 검증 지정` 표를 합쳐 12종의 `적용` / `N/A` 를 확보한다.
- `적용` 인데 틀이 없으면 03-implementation 누락이다. 그 자리에서 결함으로 올린다.
- `N/A` 인데 틀이 있으면 지정과 어긋난 것이다. 사용자에게 확인한다.
- 12종 중 대조되지 않은 것이 없어야 한다 (원칙 3).

### 종류별 실행 경로

12종은 실행 방식이 셋으로 갈린다. 각 종류가 무엇이고 무엇을 남기는지는 `skills/code-design/verification.md` 가 단일 출처다.

| 실행 경로 | 종류 | 04-verification 이 하는 일 |
|----------|------|------------------------|
| 자동 스위트 | 유닛 · 통합 · 경계값 · 계약 | 전체 스위트를 한 번 더 돌려 green 을 확인하고 결과를 기록 |
| 도구 실행 | 정적 분석 | 규칙 세트로 실행해 통과 기준(경고 0 / 신규 경고 0) 충족을 확인 |
| 판정 문서 | 기능 · 성능 · 보안 · 호환성 · 수동 QA · e2e · 경합 | 아래 축별 절차대로 틀에 결과 · 검증 시각을 채움 |

자동 스위트와 도구 실행은 03-implementation 의 검증 완료선이 슬라이스마다 이미 돌린 것이라, 여기서는 **최종 1회 재확인**이다. 실패하면 결함으로 올린다.

판정 문서 축은 사람이 실행·판정해야 하므로 아래에서 절차를 따로 둔다.

### A. e2e -- 자동 e2e 가능 대상이 있으면 필수

- 빌드된 실제 산출물(바이너리 / 앱)을 시나리오대로 실행한다. 유닛 테스트가 아니라 **조립된 전체를 통째로 돌리는 것**이다.
- happy path 뿐 아니라 거부돼야 할 입력 · 충돌 · 미발견 같은 가드 / 실패 경로(03-implementation G7)도 확인한다.
- 대화형 UI 처럼 자동화가 불가한 경계는 e2e 대신 수동 QA 가 받는다.

### B. 수동 QA -- 자동화 불가한 인터랙티브 경계가 있으면 필수

- 자동 테스트로 가드되지 않는 인터랙티브 거동만 대상으로 한다.
- 수동 QA 항목은 가급적 그것을 만든 슬라이스에서 먼저 확인된다(03-implementation G8). 04-verification 은 전체를 최종 재확인하는 게이트지, 인터랙티브 확인을 처음으로 한꺼번에 하는 자리가 아니다.
- 사용자와 한 항목씩 재현하며 확인한다(원칙 1 의 "한 번에 하나").
- 인터랙티브 경계가 없는 순수 코어만이면 이 축은 비는 게 정상이다.
- 관찰 결과가 기대와 어긋나도 단일 관찰로 실패를 단정하지 않는다. 먼저 소스로 그 거동을 대조하거나 사용자에게 한 번 더 재현을 요청하고, 그래도 어긋나면 그때 실패로 판정한다 (사용자 조작 실수로 인한 거짓 실패 방지).

<FORBIDDEN>
수동 QA 에서 관찰이 기대와 어긋난다고 단일 관찰만으로 실패를 단정하지 않는다.
</FORBIDDEN>

### C. 보안 점검 -- 해당되면

- 이 프로젝트에 해당하는 위협만 점검한다 -- 비밀정보 노출, 의존성 취약점(CVE), 인증 / 권한 경계 등.
- 악의 / 가드 입력 거부는 e2e(G7)와 겹치므로 새로 검증하지 말고 e2e 리포트 항목을 참조한다.
- 해당 위협이 전혀 없으면 이 산출물 자체를 생략한다.

### D. 기능 -- 승인 기준 대조

- 01-requirements 의 `## 요구사항별 승인 기준` 각 행이 실제로 만족되는지 대조한다.
- 자동화된 것은 위 자동 스위트 · e2e 결과를 근거로 인용하고, 여기서 다시 실행하지 않는다.
- 자동화 안 되는 항목은 수동 QA 축이 받는다 -- 같은 항목을 두 축에서 세지 않는다.
- 승인 기준 중 대조되지 않은 행이 남으면 완료선 미충족이다.

### E. 성능 -- 목표치 대 실측치

- 03-implementation 이 세운 측정 시나리오를 실행해 **실측치를 채운다**. 목표치는 01-requirements 소유라 여기서 바꾸지 않는다.
- 판정은 목표치 대비다. 미달이면 결함이고, 목표치 자체가 틀렸다는 판단이면 결함이 아니라 02-design 되돌림 사안이라 사용자에게 확인한다.
- 측정 환경(빌드 · 하드웨어 · 데이터 규모)을 결과와 함께 남긴다. 환경이 다르면 수치를 비교할 수 없다.

### F. 호환성 -- 깨질 수 있는 표면

- 03-implementation 의 호환성 확인 목록 각 항목에 대해 기존 사용자 · 데이터 · 호출자가 계속 동작하는지 확인한다.
- 마이그레이션이나 폴백이 붙은 항목은 그 경로까지 실제로 밟아 본다. 코드에 있다는 것만으로 통과시키지 않는다.

### 커버리지 -- 축이 아니라 충분성 지표

커버리지는 검증 12종에 없다. 검증 종류가 아니라 **검증이 충분한지를 보는 지표**라, 위 축을 다 돌린 뒤 그 판정 자체를 평가하는 입력으로 쓴다.

- 수치가 필요하면 `skills/code-design/05-coverage.md` 를 호출해 추출한다. 05-coverage 는 추출·산출까지만 하고 판정하지 않는다.
- 충분한지 미달인지는 여기서 정한다. 미달이면 되돌림 경로가 둘로 갈린다.
  - 케이스가 모자라다 -> 02-design 으로. TDD 계획에 케이스를 더한다.
  - 케이스는 있는데 테스트가 없다 -> 03-implementation 으로.
- 커버리지 추출을 안 돌려도 04-verification 을 닫을 수 있다. 12종 대조와 달리 필수 게이트가 아니다.

### G. 경합 -- 부하 · 스트레스로만 드러나는 것

- 03-implementation G16 이 (b) 갈래로 넘긴 항목 -- 레이스 · 데드락 · 네트워크 실패 · 부하 하 거동 -- 을 실행한다. 등록 위치는 e2e 시나리오 또는 수동 QA 항목이다.
- 한 번 통과했다고 통과로 적지 않는다. 비결정적 결함이라 반복 실행 횟수를 결과와 함께 남긴다.
- (a) 갈래(대응 수단이 코드 경로에 있는지)는 03-implementation 이 이미 확인했다. 여기서 다시 보지 않는다.

## 산출물의 자리

### 판정선 -- 자동 가드가 이어받는가

검증 산출물이 브랜치 폴더에 남는지 cross-flow 층으로 가는지는 이 질문으로 가른다.

- **자동 테스트 · 도구가 그 검증을 계속 돌려준다** -> 브랜치 폴더. 문서는 그 flow 의 결과 기록이고, 회귀를 막는 실물은 소스 트리의 테스트 코드다.
- **사람이 계속 해야 한다** -> cross-flow 층. 자동 가드가 없어 그 문서가 유일한 회귀 자산이고, 지우면 다음 flow 가 무엇을 확인해야 하는지 복원할 수 없다.

### 산출물별 자리

| 산출물 | 자리 | 판정 근거 |
|--------|------|----------|
| 수동 QA 체크리스트 | cross-flow `code-design/qa-checklist.md` | 사람이 계속 재현해야 한다 |
| e2e 리포트 | 브랜치 폴더 | e2e 테스트 코드가 소스 트리에서 계속 돈다 |
| 보안 점검 기록 | 브랜치 폴더 | 자동화된 항목은 정적 분석 · 의존성 감사가 이어받는다 |
| 성능 측정 틀 | 브랜치 폴더 | 목표치는 요구사항이고 실측치는 그 시점 값이다 |
| 호환성 확인 목록 | 브랜치 폴더 | 이번에 건드린 표면 한정이라 다음 flow 에는 대상이 달라진다 |

보안 점검 항목 중 자동화가 안 되는 것(사람이 눈으로 보는 권한 경계 확인 등)이 있으면 그것만 수동 QA 체크리스트로 보낸다 -- 판정선이 항목 단위로도 같게 걸린다.

### 공통 양식 규칙

브랜치 폴더 산출물은 `{프로젝트 루트}/code-design/<브랜치 슬러그>/03-implementation/` 에 있다(생성 단계 기준 -- 03-implementation 이 만든 파일을 04-verification 이 그 자리에서 채운다). 어느 쪽이든 **단일 파일로 갱신**하며, 각 항목(라인)에 **검증 시각**을 남겨 여러 차례 · 여러 날에 걸친 검증 진행을 추적한다.

### e2e 리포트

```
# E2E 결과 -- {대상}
환경: {빌드 / 바이너리 식별}

| # | 시나리오   | 명령·입력 | 기대   | 결과         | 검증 시각        |
|---|-----------|----------|--------|--------------|------------------|
| 1 | 정상: 추가 | add ...  | 추가됨 | pass         | 2026-06-14-1030 |
| 2 | 목록       | list     | 표시   | pass         | 2026-06-14-1030 |
| 3 | 가드: 중복 | --dup    | 거부   | FAIL: 저장됨 | 2026-06-14-1030 |
요약: 2 pass / 1 fail
```

회귀 후 한 항목을 재검증하면 그 라인의 결과 · 검증 시각만 갱신한다. fail 이면 결과 칸에 증상을 함께 적는다.

### 수동 QA 체크리스트

```
# 수동 QA 체크리스트 -- {대상}

{대상 정의 한 줄: 자동 테스트로 가드되지 않는 인터랙티브 거동만 담는다}

## 사용법
1. {산출물 실행 방법}
2. 항목을 위에서부터 재현하고, 기대대로면 [x] 체크
3. 실패하면 항목 옆에 증상 기록

## {그룹명}
- [ ] **{항목명}** -- {기대 동작}
- [x] **{항목명}** -- {기대 동작} (QA {YYYY-MM-DD-HHMM}: {결과 / 증상})

> 이 파일은 cross-flow 층이다. 항목 누적 · 보존 · 제거 규칙은
> cross-flow.md "qa-checklist.md" 를 따른다.
```

### 보안 점검 기록 (해당 시)

수동 QA 체크리스트 양식을 그대로 재사용하되 항목을 보안 위협으로 채운다.


## 사전 틀을 넘어서는 확인 (완결성 점검 + 사용자 게이트)

03-implementation 이 세운 e2e / 수동 QA / 보안 틀은 구현 착수 시점에 미리 짠 목록이라, 이번 요구사항에 필요한 확인을 다 예측하지 못한다 -- 검증하다 보면 틀에 안 적힌 확인할 내용이 제법 나온다. 해당 축의 틀을 다 채운 뒤, 틀에 없던 확인할 내용을 두 경로로 더 살핀다.

**(1) 완결성 점검 -- 스스로 한 번 더 살피기.** 이번 요구사항이 성립하려면 확인됐어야 하는데 틀에 안 적힌 것을 찾는다 -- 경계값 · 실패 / 가드 경로 · 축 사이 상호작용 · 이번 변경이 건드린 기존 거동의 회귀 등. 발견하면 해당 축 틀(e2e 리포트 / 수동 QA 체크리스트 / 보안 점검)에 **항목으로 추가해 그 자리에서 검증한다**. 새 산출물 파일을 만드는 게 아니라 기존 틀에 라인을 더하는 것이라 "새 파일 금지"에 걸리지 않는다.

**(2) 사용자 게이트 -- 사용자에게 묻기.** 점검을 마친 뒤 사용자에게 **"이 외에 추가로 보고하거나 검증할 게 있는지"** 묻는다. 사용자가 든 것도 해당 축 틀에 넣어 검증한다.

**경계 -- 검증 공백 vs 신규 범위(안 섞는다):** 여기서 나오는 건 "이번 요구사항의 검증 공백"이라 **이번 flow 에서 검증한다**. 검증 결과 FAIL 이면 아래 "발견 처리"의 (a) 결함으로 라우팅한다. 반면 "요구엔 없던 새 아이디어 / 개선(이것도 하면 좋겠다)"은 검증 대상이 아니라 (b) 신규 범위이므로 로드맵 후보로만 넘긴다. 둘을 섞으면 이번 flow 가 새 기능 구현으로 확대된다.

## 발견 처리 (결함 -> 03-implementation 회귀·descope / 신규 범위 -> 로드맵)

04-verification 이 검증 중 발견하는 것은 두 종류다 -- 성격에 따라 처리처가 갈린다. 발견은 검증을 **돌린 결과**로 나온다: 결함은 e2e / 수동 QA / 보안을 실행·재현·점검한 결과의 FAIL 이고, 신규 범위는 검증하다 곁에서 관찰된 것이다.

**(a) 결함 -- 구현이 이번 요구사항을 못 충족(깨짐 / 누락).** 결함이 나와도 거기서 곧장 처리로 넘어가지 않는다 -- 해당되는 검증 축(e2e / 수동 QA / 보안)을 **모두 끝내고**, 발견된 결함을 한데 모아 사용자에게 제시한다. 그다음 **승인 게이트에서 결함마다** 사용자가 경로를 고른다.

- **지금 고침 (기본)** -- 이번 flow 안에서 고친다. 03-implementation 으로 회귀한다.
- **descope** -- 지금 제대로 고치려면 이번 flow 범위를 넘는 결함을 이번엔 안 고치기로 한다. 미룬 수정을 로드맵 청크(기본 `[예정]` -- 알려진 미충족 요구)로 빼고, 현재 `[진행]` 청크 범위를 그만큼 좁혀 기록한다. 좁힌 청크는 좁혀진 범위로만 `[완료]` 된다.

**(b) 신규 범위 발견 -- 요구엔 없던 새 아이디어 / 개선("이것도 하면 좋겠다").** 이번 청크 밖이라 이번 flow 에서 구현하지 않고, 로드맵 청크(기본 `[미정]` -- 미검증 제안)로 넘긴다.

**로드맵 쓰기 (descope · 신규 범위 공통):** append 는 검증 중 그때그때 하지 않고 **모아뒀다 04-verification 을 닫을 때** 한 번에 한다(기존 "flow 종료 시 `[진행]`->`[완료]`" 와 같은 시점). 모든 append 는 사용자 확인을 받고 **출처**를 남긴다 -- 어느 검증 산출물에서 나왔는지 지목한다(예: `출처: 04-verification 결함 descope -- <브랜치 슬러그>, e2e #3`, `출처: 04-verification 신규발견 -- <브랜치 슬러그>, QA "정렬 표시"`). 청크 상태 어휘·행 형식·전이 규칙은 `cross-flow.md` "roadmap.md" 절을 단일 출처로 보고, 04-verification 은 기본 플래그와 출처 관례만 더한다. e2e 리포트와 보안 점검 기록은 브랜치 키 폴더에 남아 미래 flow 가 직접 읽지 않으므로, 미래 flow 가 움직일 요지는 로드맵 행에 압축해 넣는다(raw 증거는 브랜치 폴더 스냅샷에 보존). 수동 QA 항목은 cross-flow `qa-checklist.md` 에 그대로 남아 다음 flow 가 이어 쓴다.

# 요구사항 명세 (requirements)

00-ideation 에서 확정된 방향을 받아, 검증 가능한 요구사항으로 명세하는 단계.
이 산출물이 02-design 의 입력이 된다.

00-ideation 핸드오프(유형 / 확정 방향 / 배경·현재상태 / 문제+진단)와 로드맵 마스터 `roadmap.md`(청크 상태)를 입력으로 받는다(hard 의존). 그 핵심은 산출물 상단 "전제" 섹션에 요약 인용한다 -- 통째 복사가 아니라 핵심 압축이며, 더 깊은 맥락이 필요하면 00-ideation 핸드오프 원본을 직접 참조한다(요약과 원본이 어긋나면 원본을 신뢰). 핸드오프의 위임 항목 · [잠정] 가정 · 열린 보류도 함께 받아, 전제 인용과는 별개로 작업 흐름 스텝 2에서 목적지로 처리한다.

## 진입 조건

00-ideation 에서 go 로 확정되어 방향이 정해졌고, 그 방향을 요구사항으로 구체화할 때 이 단계로 진입한다. 00-ideation 핸드오프(확정 방향)가 입력으로 존재하는 것이 전제다.

무엇을 만들지/만들지 말지가 미정이거나, 현 상태 불만의 원인이 불명확하면 01-requirements 가 아니라 00-ideation 으로 간다.

## 단계 시작 시 — 사전 조사

### 1. 외부 검색

처음 다루는 도메인이거나 결정에 근거가 필요한 항목은 외부 검색으로 보완한다.
검색 결과는 그대로 인용하지 않고, 프로젝트 컨텍스트에 맞게 재해석해서 활용한다.

**검색이 필요한 경우:**
- 처음 다루는 도메인 (예: 결제, OAuth, 메시지 큐 등)
- 일반적인 모범 사례 / 표준 (예: REST API 설계 원칙, OWASP 가이드)
- 외부 시스템 / 라이브러리의 제약 사항 (API 스펙, 라이선스, 호환성)
- 비기능 요구사항 결정에 필요한 업계 기준값

검색 깊이 — 공통 원칙 2("반복될수록 더 깊이 파고든다")의 정량 단위를 01-requirements 의 검색 행동으로 구체화:

| 상황 | 검색 횟수 | 출처 다양성 | 공식 문서 확인 |
|------|----------|------------|--------------|
| 처음 다루는 도메인 (표준 깊이) | 3~5회 | 2개 이상 출처 교차 확인 | 핵심 항목만 |
| 두 번째 이상 다루는 도메인 (+1) | 5~8회 | 3개 이상 출처 + 인접 주제 | 모든 핵심 항목 |
| 같은 이슈가 반복 등장 (+2) | 8회 이상 | 근본 원인 추적 모드 | 공식 문서 + 관련 RFC/표준 |

**검색 후 처리:**
- 찾은 정보 중 이번 프로젝트에 적용할 것은 요구사항 / 제약 / 가정 사항에 명시적으로 반영
- 적용하지 않기로 한 사항도 "Out of scope" 또는 "검토했으나 제외" 형태로 기록
- 신뢰할 만한 출처(공식 문서, 표준 문서)는 산출물의 "출처(부록)" 섹션에 `링크 -- 한 줄 결론` 으로 남긴다

### 2. 사용자 확인 — 모호하면 반드시

외부 검색으로도 결정할 수 없는 항목, 또는 사용자 표현 자체가 모호한 항목은 추측하지 않고 사용자에게 질문한다. 공통 원칙 1을 따른다.

### 3. 기존 코드 탐색 (해당되는 경우)

00-ideation 핸드오프의 "배경/현재 상태"가 기존 구조 파악의 1차 입력이다. 범위(in/out scope)를 더 정확히 그리는 데 보완이 필요하면 아래 도구로 추가 탐색한다.

기존 코드 구조 파악에 code-analyze facet 산출물이 있으면 1차 입력으로 활용한다 -- 공통 원칙 6 (`principles.md`) 참조. 수작업 도구는 facet 이 없거나 특정 지점을 더 깊이 파야 할 때 보완으로 쓴다.

이 단계에서 자주 쓰이는 도구 (`references/tools.md`의 코드 인텔리전스 참고):
- ripgrep (rg) — 관련 키워드/패턴이 코드베이스 어디에 있는지 검색
- fd — 관련 파일 빠르게 찾기
- tree — 디렉토리 구조 파악
- universal-ctags — 함수/클래스/심볼 정의 위치 추적

**활용 예:**
- 기존 인증 로직에 2FA 추가 -> rg "auth|login|session" 으로 관련 위치 파악
- 특정 모듈 변경 영향 범위 파악 -> 해당 심볼의 호출처 추적

**도구 활용 후:**
- 파악한 내용은 산출물의 "현재 상태" 섹션에 반영
- 도구가 이 프로젝트에 부적합하다고 판단되면, 해당 사실은 산출물의 "결정 근거(왜)"에 한 줄로 남긴다

## 작업 흐름

### 1. 전제 확인 (00-ideation 산출 요약)

00-ideation 핸드오프(유형 / 확정 방향 / 배경·현재상태 / 문제+진단)와 로드맵 마스터 `roadmap.md`(청크 상태)를 읽고, 그 핵심을 산출물 상단 "전제" 섹션에 요약 인용한다.

**작성 규칙:**
- 통째 복사가 아니라 핵심만 압축한다. 상세는 00-ideation 핸드오프 원본(`code-design/<브랜치>/00-ideation/handoff.md`)에 있다.
- 요약과 00-ideation 원본이 어긋나면 원본을 신뢰한다.
- fast-path 로 통과한 경우에도 00-ideation 핸드오프는 존재하므로(약식이어도), 전제 섹션은 항상 00-ideation 산출에서 채운다.
- 유형(1/2a/2b)과 로드맵은 범위(in/out scope) 판단의 출발점이다 -- 이번 작업이 `[진행]` 청크를 넘지 않게 하고, `[예정]`/`[미정]` 청크는 Out of scope 에서 "영구 제외"가 아니라 "다음 flow 예정"으로 구분한다(스텝 3).

### 2. 00-ideation 위임 항목 · [잠정] 가정 · 열린 보류 처리

00-ideation 핸드오프가 넘긴 위임 항목 · [잠정] 가정 · 열린 보류를 빠짐없이 목적지로 보낸다. 이 스텝을 건너뛰면 00-ideation 이 넘긴 배턴이 새어나가 02-design 이나 03-implementation 에서 뒤늦게 터진다.

**위임 항목 -- 태그별로 목적지가 다르다:**
- `[requirements]` -> 이번 요구사항에서 직접 해소한다 (범위 / 우선순위 / 승인 기준으로 구체화). 못 정하면 되묻고(공통 원칙 1), 그래도 미정이면 핸드오프 "열린 보류"에 등재한다(재개 시점 = 02-design -- 원칙 4).
- `[design]` -> 01-requirements 가 정하지 않고, 01-requirements 산출물의 "위임 항목(design)"으로 그대로 전달한다(재라우팅).
- `[deferred]` -> 00-ideation 이 미뤄둔 항목이다. 맥락이 더 쌓였으니 다시 검토해, 이제 정할 수 있으면 해소하고 아직이면 핸드오프 "열린 보류"로 넘긴다(재개 시점 명시).

**[잠정] 가정 -- 확정 또는 기각으로 결판낸다:**
- 00-ideation 의 [잠정] 가정은 "사용자가 언급했으나 아직 안 굳은 추정"이다. 여기서 사용자 확인으로 결판낸다.
- 확정되면 -> 01-requirements "가정 사항"에 [확정] 으로 승격한다.
- 뒤집히면 -> 버리고 그 사유를 "결정 근거(왜)"에 한 줄 남긴다.
- [잠정] 은 흔히 위임 항목의 "사용자 기울기"이므로, 짝이 되는 위임 항목을 해소할 때 함께 본다.

**열린 보류 -- 재개 시점대로:**
- 00-ideation 핸드오프의 열린 보류 중 재개 시점 = 01-requirements 인 것은 여기서 사용자 확인으로 해소한다.
- 재개 시점 = 02-design 인 것은 자기 핸드오프 "열린 보류"에 그대로 릴레이한다(pass-through, 출처 유지).

<PENETRATE>
00-ideation 핸드오프의 위임 항목 · [잠정] 가정 · 열린 보류는 하나도 빠짐없이 목적지로 처리한다.
</PENETRATE>

<RICOCHET>
[잠정] 가정을 확정 또는 기각하지 않은 채 그대로 다음 단계로 넘기지 않는다.
</RICOCHET>

### 3. 범위 정의 (in/out scope)

이번 작업에 포함할 것과 제외할 것을 명시적으로 나눈다.

**범위 구분:**

| 구분 | 의미 | 예시 |
|------|------|------|
| In scope | 이번에 구현/변경 | 이메일/패스워드 로그인, 세션 발급 |
| Out of scope | 이번에는 하지 않음 | OAuth, 2FA, 비밀번호 재설정 |

**유의 사항:**
- Out of scope를 명시적으로 적는 이유: 나중에 "왜 이건 빠졌지?" 논쟁을 막기 위함
- Out of scope 는 로드맵 `[예정]`/`[미정]` 청크와 대조해 두 갈래로 구분한다 (미래 flow 를 실수로 닫지 않기 위함):
  - "다음 flow 예정" -- 로드맵 `[예정]`/`[미정]` 에 있는 것. 예: "포트폴리오 분석 -- 이번 아님 (로드맵 [예정] 청크)"
  - "영구 제외" -- 로드맵에도 없고 이번 방향과 무관한 것. 예: "가상화폐 매매 -- 범위 밖"
- 결정을 미루는 범위 항목(예: 세션 만료 시간)은 여기 적지 않고 핸드오프 "열린 보류"에 등재한다 (원칙 4)
- 범위가 모호하면 사용자에게 되묻는다 (공통 원칙 1)

<RICOCHET>
범위를 임의로 좁히거나 넓히지 않는다.
</RICOCHET>

### 4. 비기능 요구사항

기능이 아닌 품질 속성을 정의한다. 해당 없으면 명시적으로 N/A로 표기한다.

**체크할 카테고리:**
- 성능: 응답 시간, 처리량 목표 (예: "p99 < 200ms")
- 보안: 인증/인가 요구, 민감 데이터 처리 방식
- 확장성: 예상 사용자 규모, 데이터 증가율
- 가용성: 다운타임 허용 범위
- 호환성: 지원 OS / 브라우저 / 언어 버전
- 운영: 로깅, 모니터링, 배포 방식 제약

**수치 결정 규칙:**

<PENETRATE>
비기능 요구사항의 최종 수치/기준은 사용자 확인을 받은 값만 기록한다.
</PENETRATE>

- 각 항목의 수치/기준이 사용자 입력에 없으면 추정하지 않고 되묻는다 (공통 원칙 1)
- 업계 일반값을 참고로 제시할 수는 있으나, 최종 값은 사용자 확인을 받는다

### 5. 제약 조건

선택의 자유를 제한하는 외부 조건을 기록한다.

**기록할 항목:**
- 기술 스택 제약 (예: "Python 3.11 이상만 사용")
- 의존 시스템 제약 (예: "기존 PostgreSQL 14 사용 필수")
- 일정 / 인력 제약
- 라이선스 / 컴플라이언스 제약

### 6. 우선순위 분류

모든 요구사항에 우선순위를 부여한다.

**분류 기준:**

| 분류 | 의미 |
|------|------|
| 필수 | 이번 범위에서 반드시 구현. 없으면 기능 자체가 성립 안 됨 |
| 선택 | 있으면 좋지만 없어도 됨. 다음 반복에서 구현 가능 |
| 제외 | 이번에는 하지 않음. Out of scope와 동일하게 기록 |

<PENETRATE>
우선순위는 사용자 확인을 받은 결과만 기록한다.
</PENETRATE>

<RICOCHET>
Claude가 우선순위를 임의로 결정하지 않는다.
</RICOCHET>

**적용 규칙:**
- "필수"가 너무 많으면 사용자에게 재검토를 요청한다. 전부 필수면 우선순위가 없는 것과 같다.
- 우선순위 결정 근거가 불명확하면 되묻는다 (공통 원칙 1)

### 7. 요구사항별 승인 기준

각 요구사항이 충족됐는지 판단할 수 있는 기준을 명시한다.

<PENETRATE>
모든 요구사항에 검증 가능한 승인 기준을 작성한다.
</PENETRATE>

<RICOCHET>
"잘 작동함", "빠르게 응답함" 같은 관찰 불가능한 표현을 승인 기준으로 쓰지 않는다.
</RICOCHET>

**작성 규칙:**
- 기능 요구사항은 입력·행동·기대 결과 형태로 작성한다.
- 비기능 요구사항은 측정 가능한 수치로 작성한다.

**나쁜 예:** "로그인이 잘 동작한다"
**좋은 예:** "유효한 이메일과 패스워드로 POST /auth/login 요청 시 200 상태와 세션 토큰 반환됨"

작성이 어려운 항목은 사용자에게 기대 동작을 질문해 함께 작성한다.

### 8. 모호 항목 처리

위 작성 중 명확하지 않은 항목은 다음 순서로 처리한다.

**처리 절차:**
1. 외부 검색으로 후보값을 찾는다
2. 사용자에게 질문한다 — 외부 검색 결과를 후보로 제시할 수 있다
3. 그래도 사용자가 결정을 미루면 핸드오프 "열린 보류"에 등재한다 (사유 + 재개 시점 명시 -- 원칙 4)

<RICOCHET>
외부 검색으로 찾은 후보값을 사용자 확인 없이 곧바로 채택하지 않는다.
</RICOCHET>

이 절차 전반에 공통 원칙 1의 금지 사항이 그대로 적용된다.

## 산출물 형식

요구사항 명세 결과는 다음 형식의 문서로 작성한다.
모든 섹션은 비워두지 않는다. 채울 데이터가 없으면 명시적으로 N/A로 표기한다 (공통 원칙 3).

이 산출물은 핸드오프 파일(`handoff.md`)에 그대로 저장된다 — "다음 단계로 전달할 것" 섹션 참조.

```markdown
# 요구사항 명세: {기능명}

## 전제 (00-ideation 산출 요약)
(00-ideation 핸드오프에서 요약 인용 -- 통째 복사 아님. 상세는 code-design/<브랜치>/00-ideation/handoff.md 원본, 로드맵은 roadmap.md)
- 유형: {1 | 2a | 2b}
- 확정 방향: ...
- 로드맵: [진행] 청크 ... / [예정]·[미정] ... (마스터 roadmap.md -- Out of scope 대조용)
- 배경 / 현재 상태: ...
- 문제 / 근본원인: ...

## 범위
### In scope
- ...
### Out of scope
(로드맵 [예정]/[미정] 과 대조 -- "다음 flow 예정"과 "영구 제외"를 구분)
- (다음 flow 예정) ... (로드맵 [예정] 청크)
- (영구 제외) ...

## 비기능 요구사항
- 성능: ...
- 보안: ...
- 확장성: ...
- 가용성: ...
- 호환성: ...
- 운영: ...

## 제약 조건
- ...

## 우선순위
| 요구사항 | 분류 |
|---------|------|
| ...     | 필수/선택/제외 |

## 요구사항별 승인 기준
| 요구사항 | 승인 기준 |
|---------|---------|
| ...     | (관찰 가능한 조건) |

## 가정 사항
- (사용자 확인을 받은 [확정] 가정만 기록. 임의 가정 금지)
- 00-ideation 의 [잠정] 가정 중 여기서 확정된 것도 포함한다 (기각된 것은 기록하지 않고 "결정 근거"에 사유만)

## 결정 근거 (왜)
- (비자명한 결정만 한 줄씩. 예: "세션 만료 30분 -- 보안/UX 균형, 업계 일반값")
- 협의 *과정* 전문(사용자 의견/반문/합의 스텝)은 여기 적지 않는다 -- 그 이력은 checklist 피드백 회차가 git 에 보존한다.

## 위임 항목 (design)
- (02-design 이 결정해야 할 항목. 없으면 N/A 명시)
- 두 종류가 섞인다: (1) 01-requirements 이 새로 발견한 것, (2) 00-ideation 이 [design] 으로 넘긴 것을 그대로 전달한 것

## 열린 보류
(재개 시점 = 02-design 인 결정 지연. 00-ideation 에서 릴레이된 것 + 01-requirements 이 새로 미룬 것 누적. 없으면 N/A. 원칙 4)
| # | 항목 | 사유 | 재개 시점 | 출처 |
|---|------|------|----------|------|

## 출처 (부록)
- (결정을 실제로 뒷받침한 외부 출처만. `링크 -- 한 줄 결론` 형식. 없으면 N/A)
```

```markdown
- [ ] 재개 시점 = 01-requirements 인 열린 보류가 모두 해소되고, 재개 = 02-design 은 핸드오프 "열린 보류"로 릴레이됨 (원칙 4)
```

### 피드백 처리 절차

**용어 정리:**
- 체크리스트 파일의 "피드백" 섹션 = 매 회차 사용자가 적는 입력. 협의 *과정*의 이력이 회차마다 여기 쌓이고 git 이 보존한다 (단일 파일 갱신).
- handoff 의 "결정 근거(왜)" 섹션 = 합의된 결정의 사유만 한 줄로. 협의 과정 전문은 담지 않는다.
- 피드백이 들어오면 협의하고, 합의 *결과*를 산출물 결정값에 반영하며 그 "왜"를 handoff 결정 근거에 한 줄로 남긴다. 협의 *과정*은 checklist 피드백 회차(git)에 남는다.

**자동 수용 금지 피드백:**

<RICOCHET>
"이 항목은 이번 작업에서 불필요" / "이건 빼도 됨" 같은 항목 제거 요청을 자동 수용하지 않는다.
</RICOCHET>

<RICOCHET>
산출물 템플릿 자체에 대한 변경 요청을 자동 수용하지 않는다.
</RICOCHET>

<RICOCHET>
산출물의 일부 결정을 뒤집는 요청을 자동 수용하지 않는다.
</RICOCHET>

**처리 절차:**
1. 반문한다. 왜 그렇게 판단했는지, 어떤 영향이 있는지 확인
2. 협의한다.
3. 기록한다. 합의 결과를 산출물 결정값에 반영하고 그 "왜"를 handoff "결정 근거"에 한 줄로 남긴다. 협의 과정 자체는 checklist 피드백 회차(git)에 남는다.
4. 합의된 변경을 산출물에 반영한 뒤 재제시

<RICOCHET>
사용자와 합의에 도달하기 전에 다음 단계로 진행하지 않는다.
</RICOCHET>

피드백이 단순한 N/A (의견 없음) 이거나 명확한 추가 요구사항이면 위 절차 없이 바로 반영해도 된다.

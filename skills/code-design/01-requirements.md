# 1단계: 요구사항 분석

해결할 문제와 범위를 명확히 정의하는 단계.
이 단계의 출력이 2단계(설계)의 입력이 된다.

---

## 공통 원칙

이 단계의 모든 동작은 `skills/code-design/00-principles.md` 의 공통 원칙을 따른다.

---

## 진입 조건

다음 중 하나라도 해당되면 이 단계로 진입:
- 새 기능/서비스를 시작하는데 무엇을 만들지가 모호함
- 사용자 요청이 한 줄짜리 막연한 표현임 ("로그인 기능 만들어줘")
- 이미 코드가 있지만 변경 범위가 불명확함

## 단계 시작 시 — 사전 조사

### 1. 외부 검색

처음 다루는 도메인이거나 결정에 근거가 필요한 항목은 외부 검색으로 보완한다.
검색 결과는 그대로 인용하지 않고, 프로젝트 컨텍스트에 맞게 재해석해서 활용한다.

**검색이 필요한 경우:**
- 처음 다루는 도메인 (예: 결제, OAuth, 메시지 큐 등)
- 일반적인 모범 사례 / 표준 (예: REST API 설계 원칙, OWASP 가이드)
- 외부 시스템 / 라이브러리의 제약 사항 (API 스펙, 라이선스, 호환성)
- 비기능 요구사항 결정에 필요한 업계 기준값

검색 깊이 — 공통 원칙 2("반복될수록 더 깊이 파고든다")의 정량 단위를 1단계(요구사항)의 검색 행동으로 구체화:

| 상황 | 검색 횟수 | 출처 다양성 | 공식 문서 확인 |
|------|----------|------------|--------------|
| 처음 다루는 도메인 (표준 깊이) | 3~5회 | 2개 이상 출처 교차 확인 | 핵심 항목만 |
| 두 번째 이상 다루는 도메인 (+1) | 5~8회 | 3개 이상 출처 + 인접 주제 | 모든 핵심 항목 |
| 같은 이슈가 반복 등장 (+2) | 8회 이상 | 근본 원인 추적 모드 | 공식 문서 + 관련 RFC/표준 |

**검색 후 처리:**
- 찾은 정보 중 이번 프로젝트에 적용할 것은 요구사항 / 제약 / 가정 사항에 명시적으로 반영
- 적용하지 않기로 한 사항도 "Out of scope" 또는 "검토했으나 제외" 형태로 기록
- 신뢰할 만한 출처(공식 문서, 표준 문서)는 산출물의 "참고 자료" 섹션에 링크로 남긴다

### 2. 사용자 확인 — 모호하면 반드시

외부 검색으로도 결정할 수 없는 항목, 또는 사용자 표현 자체가 모호한 항목은 추측하지 않고 사용자에게 질문한다. 공통 원칙 1을 따른다.

### 3. 기존 코드 탐색 (해당되는 경우)

이미 존재하는 코드베이스에 기능을 추가하거나 변경하는 작업이면, 요구사항 정의 전에 기존 구조를 파악해야 범위(in/out scope)를 정확히 그릴 수 있다.

**code-analyze 산출물 우선 확인:**

프로젝트에 code-analyze 스킬이 만든 facet 산출물(`analyze/facet/`)이 있으면, 아래 수작업 도구보다 먼저 읽어 현재 상태 파악의 1차 입력으로 삼는다. `architecture.md`(모듈/의존 레이아웃), `flow.md`(주요 흐름), `summary.md`(모듈별 동작), `types.md`(타입/관계), `externals.md`(외부 의존), `callgraph-cpp.md`(C++ 호출 그래프)가 as-built 구조를 이미 요약해 둔 형태다. 수작업 도구는 facet 이 없거나, 있어도 특정 지점을 더 깊이 파야 할 때 보완으로 쓴다.

<PENETRATE>
code-analyze facet 산출물이 존재하면 수작업 탐색보다 먼저 그것을 현재 상태 파악의 1차 입력으로 삼는다.
</PENETRATE>

이 단계에서 자주 쓰이는 도구 (`references/tools.md`의 코드 인텔리전스 참고):
- ripgrep (rg) — 관련 키워드/패턴이 코드베이스 어디에 있는지 검색
- fd — 관련 파일 빠르게 찾기
- tree — 디렉토리 구조 파악
- universal-ctags — 함수/클래스/심볼 정의 위치 추적

**활용 예:**
- 기존 인증 로직에 2FA 추가 -> rg "auth|login|session" 으로 관련 위치 파악
- 특정 모듈 변경 영향 범위 파악 -> 해당 심볼의 호출처 추적

**도구 활용 후:**
- 파악한 내용은 산출물의 "현재 상태" 섹션에 반영
- 도구가 이 프로젝트에 부적합하다고 판단되면, 해당 사실은 산출물의 "사용자와의 명확화 기록"에 남긴다

## 작업 흐름

### 1. 문제 정의

해결할 문제를 명확하게 작성한다.

**작성 규칙:**
- 솔루션이 아닌 문제를 기술한다 ("JWT 인증 구현" X -> "API 요청자의 신원을 검증할 방법이 없다" O)
- 사용자/시스템 관점에서 어떤 어려움이 있는지 명시한다
- 모호한 형용사("좋게", "빠르게")가 사용자 입력에 있으면 정량 기준으로 바꾸기 위해 되묻는다 (공통 원칙 1)

### 2. 범위 정의 (in/out scope)

이번 작업에 포함할 것과 제외할 것을 명시적으로 나눈다.

**범위 구분:**

| 구분 | 의미 | 예시 |
|------|------|------|
| In scope | 이번에 구현/변경 | 이메일/패스워드 로그인, 세션 발급 |
| Out of scope | 이번에는 하지 않음 | OAuth, 2FA, 비밀번호 재설정 |
| 보류 | 결정 못 함, 사유 기록 | 세션 만료 시간 (운영팀 회의 후 결정) |

**유의 사항:**
- Out of scope를 명시적으로 적는 이유: 나중에 "왜 이건 빠졌지?" 논쟁을 막기 위함
- 범위가 모호하면 사용자에게 되묻는다 (공통 원칙 1)

<RICOCHET>
범위를 임의로 좁히거나 넓히지 않는다.
</RICOCHET>

### 3. 비기능 요구사항

기능이 아닌 품질 속성을 정의한다. 해당 없으면 명시적으로 N/A로 표기한다.

**체크할 카테고리:**
- 성능: 응답 시간, 처리량 목표 (예: "p99 < 200ms")
- 보안: 인증/인가 요구, 민감 데이터 처리 방식
- 확장성: 예상 사용자 규모, 데이터 증가율
- 가용성: 다운타임 허용 범위
- 호환성: 지원 OS / 브라우저 / 언어 버전
- 운영: 로깅, 모니터링, 배포 방식 제약

**수치 결정 규칙:**

<PENETRATE>
비기능 요구사항의 최종 수치/기준은 사용자 확인을 받은 값만 기록한다.
</PENETRATE>

- 각 항목의 수치/기준이 사용자 입력에 없으면 추정하지 않고 되묻는다 (공통 원칙 1)
- 업계 일반값을 참고로 제시할 수는 있으나, 최종 값은 사용자 확인을 받는다

### 4. 제약 조건

선택의 자유를 제한하는 외부 조건을 기록한다.

**기록할 항목:**
- 기술 스택 제약 (예: "Python 3.11 이상만 사용")
- 의존 시스템 제약 (예: "기존 PostgreSQL 14 사용 필수")
- 일정 / 인력 제약
- 라이선스 / 컴플라이언스 제약

### 5. 우선순위 분류

모든 요구사항에 우선순위를 부여한다.

**분류 기준:**

| 분류 | 의미 |
|------|------|
| 필수 | 이번 범위에서 반드시 구현. 없으면 기능 자체가 성립 안 됨 |
| 선택 | 있으면 좋지만 없어도 됨. 다음 반복에서 구현 가능 |
| 제외 | 이번에는 하지 않음. Out of scope와 동일하게 기록 |

<PENETRATE>
우선순위는 사용자 확인을 받은 결과만 기록한다.
</PENETRATE>

<RICOCHET>
Claude가 우선순위를 임의로 결정하지 않는다.
</RICOCHET>

**적용 규칙:**
- "필수"가 너무 많으면 사용자에게 재검토를 요청한다. 전부 필수면 우선순위가 없는 것과 같다.
- 우선순위 결정 근거가 불명확하면 되묻는다 (공통 원칙 1)

### 6. 요구사항별 승인 기준

각 요구사항이 충족됐는지 판단할 수 있는 기준을 명시한다.

<PENETRATE>
모든 요구사항에 검증 가능한 승인 기준을 작성한다.
</PENETRATE>

<RICOCHET>
"잘 작동함", "빠르게 응답함" 같은 관찰 불가능한 표현을 승인 기준으로 쓰지 않는다.
</RICOCHET>

**작성 규칙:**
- 기능 요구사항은 입력·행동·기대 결과 형태로 작성한다.
- 비기능 요구사항은 측정 가능한 수치로 작성한다.

**나쁜 예:** "로그인이 잘 동작한다"
**좋은 예:** "유효한 이메일과 패스워드로 POST /auth/login 요청 시 200 상태와 세션 토큰 반환됨"

작성이 어려운 항목은 사용자에게 기대 동작을 질문해 함께 작성한다.

### 7. 모호 항목 처리

위 작성 중 명확하지 않은 항목은 다음 순서로 처리한다.

**처리 절차:**
1. 외부 검색으로 후보값을 찾는다
2. 사용자에게 질문한다 — 외부 검색 결과를 후보로 제시할 수 있다
3. 그래도 사용자가 결정을 미루면 보류 항목으로 기록 (사유 + 결정 시점 명시)

<RICOCHET>
외부 검색으로 찾은 후보값을 사용자 확인 없이 곧바로 채택하지 않는다.
</RICOCHET>

이 절차 전반에 공통 원칙 1의 금지 사항이 그대로 적용된다.

## 산출물 형식

요구사항 분석 결과는 다음 형식의 문서로 작성한다.
모든 섹션은 비워두지 않는다. 채울 데이터가 없으면 명시적으로 N/A로 표기한다 (공통 원칙 3).

이 산출물은 핸드오프 파일(`handoff.md`)에 그대로 저장된다 — "다음 단계로 전달할 것" 섹션 참조.

```markdown
# 요구사항: {기능명}

## 문제 정의
(해결할 문제를 명확하게 작성)

## 현재 상태
(기존 코드가 있는 경우 작성. 신규 프로젝트면 N/A)
- 관련 코드 위치: ...
- 현재 동작 방식: ...
- 변경 영향 범위: ...

## 범위
### In scope
- ...
### Out of scope
- ...
### 보류
- 항목: ... / 사유: ... / 결정 시점: ...

## 비기능 요구사항
- 성능: ...
- 보안: ...
- 확장성: ...
- 가용성: ...
- 호환성: ...
- 운영: ...

## 제약 조건
- ...

## 우선순위
| 요구사항 | 분류 |
|---------|------|
| ...     | 필수/선택/제외 |

## 요구사항별 승인 기준
| 요구사항 | 승인 기준 |
|---------|---------|
| ...     | (관찰 가능한 조건) |

## 가정 사항
- (사용자 확인을 받은 가정만 기록. 임의 가정 금지)

## 참고 자료
- 외부: (검색으로 참고한 공식 문서, 표준 등)

## 2단계 위임 항목
- (1단계에서 정의하지 않고 2단계가 결정해야 할 항목. 없으면 N/A 명시)

## 사용자와의 명확화 기록
- 모호했던 항목과 그 해소 과정
- 피드백 협의 과정 (피드백이 있었던 경우)
  - 사용자 의견: ...
  - LLM 반문: ...
  - 합의 결과: ...
```

## 완료 기준

단계 종료 시 아래 형식으로 제시한다.

**저장 경로:** `{프로젝트 루트}/code-design/01-requirements/{YYYY-MM-DD-HHMM}-checklist.md`
- 공통 원칙 5("단계 산출물 저장 정책")에 따른다.
- 매 저장 시 신규 파일이 생성되며 누적된다.

```markdown
## 완료 기준
- [ ] 해결할 문제가 명확하게 정의됨
- [ ] 기능 범위(in/out scope)가 합의됨
- [ ] 비기능 요구사항이 구체 수치/기준으로 명시됨
- [ ] 제약 조건이 기록됨
- [ ] 모든 요구사항에 우선순위가 부여되고 사용자 확인됨
- [ ] 모든 요구사항에 검증 가능한 승인 기준이 작성됨
- [ ] 모호한 항목이 없거나, 보류 항목은 사유와 함께 기록됨
- [ ] 모호한 사용자 표현은 모두 되묻고 명확화됨
- [ ] 임의로 추정한 가정 사항이 없음 (모든 가정은 사용자 확인됨)
- [ ] 2단계 위임 항목이 식별되어 기록됨 (없으면 N/A 명시)
- [ ] 반복 작업의 경우 깊이 +1 / +2 기준에 맞게 조사가 이루어짐
- [ ] 기존 코드가 있는 작업이면 "현재 상태"가 파악되어 기록됨
      (신규 프로젝트면 N/A로 명시)
- [ ] N/A로 표기된 항목이 모두 사용자 확인을 받음
- [ ] 피드백 영역이 채워짐 (없어도 N/A 명시)

## N/A 항목 확인
```

### 피드백 처리 절차

**용어 정리:**
- 체크리스트 파일의 "피드백" 섹션 = 매 회차 사용자가 적는 입력 (회차마다 누적)
- 산출물의 "사용자와의 명확화 기록" 섹션 = 협의 과정과 합의 결과의 영구 이력
- 피드백이 들어오면 협의를 거쳐 그 결과를 영구 이력에 옮긴다.

**자동 수용 금지 피드백:**

<RICOCHET>
"이 항목은 이번 작업에서 불필요" / "이건 빼도 됨" 같은 항목 제거 요청을 자동 수용하지 않는다.
</RICOCHET>

<RICOCHET>
산출물 템플릿 자체에 대한 변경 요청을 자동 수용하지 않는다.
</RICOCHET>

<RICOCHET>
산출물의 일부 결정을 뒤집는 요청을 자동 수용하지 않는다.
</RICOCHET>

**처리 절차:**
1. 반문한다. 왜 그렇게 판단했는지, 어떤 영향이 있는지 확인
2. 협의한다.
3. 기록한다. 협의 과정과 합의 결과를 산출물의 "사용자와의 명확화 기록"에 남긴다
4. 합의된 변경을 산출물에 반영한 뒤 재제시

<RICOCHET>
사용자와 합의에 도달하기 전에 다음 단계로 진행하지 않는다.
</RICOCHET>

피드백이 단순한 N/A (의견 없음) 이거나 명확한 추가 요구사항이면 위 절차 없이 바로 반영해도 된다.

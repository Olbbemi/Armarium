# 커버리지 추출 (coverage) -- 실행 커버리지 산출

테스트 스위트를 실행해 실행 커버리지(라인 / 브랜치)를 추출하고, 그 결과를 SPA 뷰어가 소비할 정규화 데이터로 가공해 산출한다.

이 단계의 범위는 **추출과 산출까지**다. 그 뒤의 조치는 별도 단계나 별도 스킬로 다룬다 -- 무엇이 밖인지는 아래 태그가 정한다.

의미 커버리지(불변식 / 요구사항 <-> 테스트 대응으로 "명세됐지만 검증 안 된 영역"을 찾는 것)는 이 단계가 다루지 않는다. code-analyze 산출물을 입력으로 삼아야 하므로 별도 단계 / 스킬로 분리한다.

아직 정하지 않은 세부는 `TBD` 로 표시한다.

## 진입 -- 이중 모드 + 선결 게이트

05-coverage 는 두 방식으로 진입한다.

- **순차 진입** -- 04-verification 이 완료 판정에 쓸 수치를 얻으려고 호출한다. 04-verification 산출물을 참고할 수 있으나 필수 입력은 아니다.
- **단독 진입** -- code-design 을 로드해 05-coverage 만 지목해 실행한다. 앞 단계 없이 코드 / 테스트를 직접 읽어 시작한다.

순차 진입이면 산출한 수치를 04-verification 에 돌려준다. **판정은 하지 않는다** -- 충분한지 미달인지는 04-verification 이 정하고, 미달일 때의 되돌림 경로도 그쪽 소관이다.

단독 진입은 직전 핸드오프가 없어도 진행한다 -- 01-requirements ~ 04-verification 의 "중간 진입엔 직전 핸드오프 필수" 규칙의 예외다(overview "단계 진입 판단" 참조). 05-coverage 의 입력은 직전 핸드오프가 아니라 **빌드 가능한 코드와 테스트 스위트 자체**다.

**선결 게이트:** 진입 모드와 무관하게 매 실행마다 아래를 확인한다. 하나라도 충족되지 않으면 추출을 진행하지 않고 사용자에게 알린다.

- 대상 경로에 코드가 존재한다.
- 코드가 빌드된다(빌드 산출물을 만들 수 있다).

순차 진입(04-verification 뒤)이라도 이 게이트를 다시 확인한다 -- 04-verification 이후 코드가 바뀌었을 수 있다.

세부 판정 방법(빌드 명령 감지, 테스트 러너 감지 등)은 `TBD`.

## 단계 내 진행도 (TaskCreate)

이 단계는 고정 체크포인트 시퀀스라 TaskCreate 로 진행도를 시각화한다(principles.md "단계 내 진행도" 원칙). 아래 체크포인트를 순서대로 task 로 두고, 진입 시 in_progress / 완료 조건 충족 시 completed 로 닫는다.

- **선결 게이트** -- 코드 존재 + 빌드 성공을 확인하면 닫는다(실패면 여기서 차단하고 종료).
- **커버리지 실행** -- 계측을 켜고 테스트 스위트를 실행해 원본 커버리지 출력을 얻으면 닫는다. 빌드 / 테스트 로그는 산출물 디렉토리로 리다이렉트한다.
- **변환 · 쓰기** -- 원본 커버리지 출력을 SPA 뷰어용 정규화 데이터로 가공해 산출물 디렉토리에 쓰면 닫는다.
- **산출물 확인 · 요약** -- 커버리지 요약을 제시하고 산출물 경로를 확인하면 닫는다.

이 단계는 사용자가 서명할 결정이 없고 넘어갈 다음 단계도 없으므로 checklist.md 승인 서명 게이트를 두지 않는다(경량 종료).

## 커버리지 추출 절차 (언어 공통)

큰 틀의 절차는 언어와 무관하게 같다. 언어마다 바뀌는 것은 사용하는 도구, 계측을 켜는 지점, 출력 포맷이며 이는 아래 "언어별" 절에서 정한다.

1. **감지** -- 대상의 빌드 / 테스트 시스템과 언어를 식별한다. cross-flow 층에 `architecture.md` 가 있으면 그 "기술 스택" 절의 언어 배치를 1차 입력으로 삼고, 없으면 코드에서 직접 감지한다. 감지 세부는 `TBD`
2. **계측** -- 언어에 맞는 방식으로 커버리지 계측을 켠다(빌드 플래그 / 실행 래퍼 / 러너 내장 중 하나). `TBD`
3. **실행** -- 테스트 스위트를 실행해 원본 커버리지 출력을 수집한다. 로그는 산출물 디렉토리로 리다이렉트한다. `TBD`
4. **수집 · 변환** -- 원본 출력을 SPA 뷰어용 정규화 데이터로 가공한다. 필요하면 변환 스크립트(파이썬 등)를 쓴다. 변환 스크립트의 위치 / 형태는 `TBD`.

## 언어별

언어별 내용은 몇 항목이라 파일을 쪼개지 않고 이 파일 안 소절로 둔다. 언어가 늘면 소절을 추가한다.

각 언어 소절은 아래를 정한다.

| 항목 | 내용 |
|------|------|
| 커버리지 도구 | 어떤 도구로 커버리지를 재는가 |
| 계측 켜는 지점 | 빌드 플래그 / 실행 래퍼 / 러너 내장 중 무엇인가 |
| 출력 포맷 | 도구가 내는 원본 포맷(lcov / cobertura xml / json 등) |
| 변환 메모 | 정규화 데이터로 가공할 때의 주의점 |

### C++

- 커버리지 도구: gcov 또는 llvm-cov (`TBD` -- 어느 쪽을 기본으로 할지)
- 계측 켜는 지점: 빌드 플래그(gcov 계열 `--coverage`, llvm 계열 `-fprofile-instr-generate -fcoverage-mapping`)
- 출력 포맷: `TBD`
- 변환 메모: `TBD`

### Python

## 산출물

- **위치:** `{프로젝트 루트}/code-design/<브랜치 슬러그>/05-coverage/`. 단독 진입이어도 현재 브랜치 슬러그 폴더에 둔다.
- **형태:** SPA 뷰어가 소비하는 정규화 데이터(code-analyze 의 `window.DATA` / data.js 와 같은 결). 사람이 읽는 마크다운 리포트가 아니다.
- **원본 보존:** 도구가 낸 원본 커버리지 출력(lcov / xml 등)과 빌드 / 테스트 로그도 이 디렉토리에 함께 남긴다.
- **뷰어:** 커버리지 뷰어(SPA)는 05-coverage 밖에서 별도로 만들어 관리한다. 이 단계는 뷰어가 읽을 **데이터 계약(형태)만** 산출한다.

데이터 스키마(정규화 JSON 의 필드 구성)와 산출물 파일명 규약은 `TBD`.

## 완료선

- 선결 게이트(코드 존재 + 빌드 성공)를 통과함
- 테스트 스위트가 계측과 함께 실행되어 원본 커버리지 출력이 수집됨
- 원본 출력이 SPA 뷰어용 정규화 데이터로 가공되어 산출물 디렉토리에 쓰임
- 원본 출력과 빌드 / 테스트 로그가 산출물 디렉토리에 보존됨
- 커버리지 요약이 사용자에게 제시되고 산출물 경로가 확인됨

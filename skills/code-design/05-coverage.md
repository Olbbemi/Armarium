# 커버리지 추출 (coverage) -- 실행 커버리지 산출

테스트 스위트를 실행해 실행 커버리지(라인 / 브랜치)를 추출하고, 그 결과를 SPA 뷰어가 소비할 정규화 데이터로 가공해 산출한다.

이 단계의 범위는 **추출과 산출까지**다. 그 뒤의 조치는 별도 단계나 별도 스킬로 다룬다 -- 무엇이 밖인지는 아래 태그가 정한다.

의미 커버리지(불변식 / 요구사항 <-> 테스트 대응으로 "명세됐지만 검증 안 된 영역"을 찾는 것)는 이 단계가 다루지 않는다. code-analyze 산출물을 입력으로 삼아야 하므로 별도 단계 / 스킬로 분리한다.

05-coverage 에서 커버리지 추출 · 산출 외의 조치(공백을 결함으로 라우팅, 부족한 테스트 채우기, 목표 임계치 판정)를 하지 않는다.

## 진입 -- 이중 모드 + 선결 게이트

05-coverage 는 두 방식으로 진입한다.

- **순차 진입** -- 04-verification 이 완료 판정에 쓸 수치를 얻으려고 호출한다. 04-verification 산출물을 참고할 수 있으나 필수 입력은 아니다.
- **단독 진입** -- code-design 을 로드해 05-coverage 만 지목해 실행한다. 앞 단계 없이 코드 / 테스트를 직접 읽어 시작한다.

순차 진입이면 산출한 수치를 04-verification 에 돌려준다. **판정은 하지 않는다** -- 충분한지 미달인지는 04-verification 이 정하고, 미달일 때의 되돌림 경로도 그쪽 소관이다.

단독 진입은 직전 핸드오프가 없어도 진행한다 -- 01-requirements ~ 04-verification 의 "중간 진입엔 직전 핸드오프 필수" 규칙의 예외다(overview "단계 진입 판단" 참조). 05-coverage 의 입력은 직전 핸드오프가 아니라 **빌드 가능한 코드와 테스트 스위트 자체**다.

### 선결 게이트

진입 모드와 무관하게 매 실행마다 아래를 확인한다. 하나라도 충족되지 않으면 추출을 진행하지 않고 사용자에게 알린다.

- 대상 경로에 코드가 존재한다.
- 코드가 빌드된다(빌드 산출물을 만들 수 있다).

순차 진입(04-verification 뒤)이라도 이 게이트를 다시 확인한다 -- 04-verification 이후 코드가 바뀌었을 수 있다.

게이트를 판정하려면 무엇으로 빌드하는지부터 알아야 하므로, 아래 "커버리지 추출 절차" 의 감지를 먼저 수행하고 거기서 식별한 빌드 명령을 실행해 성공 여부로 가른다.

## 단계 내 진행도 (TaskCreate)

이 단계는 고정 체크포인트 시퀀스라 TaskCreate 로 진행도를 시각화한다(principles.md "단계 내 진행도" 원칙). 아래 체크포인트를 순서대로 task 로 두고, 진입 시 in_progress / 완료 조건 충족 시 completed 로 닫는다.

- **선결 게이트** -- 코드 존재 + 빌드 성공을 확인하면 닫는다(실패면 여기서 차단하고 종료).
- **커버리지 실행** -- 계측을 켜고 테스트 스위트를 실행해 원본 커버리지 출력을 얻으면 닫는다. 빌드 / 테스트 로그는 산출물 디렉토리로 리다이렉트한다.
- **변환 · 쓰기** -- 원본 커버리지 출력을 SPA 뷰어용 정규화 데이터로 가공해 산출물 디렉토리에 쓰면 닫는다.
- **산출물 확인 · 요약** -- 커버리지 요약을 제시하고 산출물 경로를 확인하면 닫는다.

이 단계는 사용자가 서명할 결정이 없고 넘어갈 다음 단계도 없으므로 checklist.md 승인 서명 게이트를 두지 않는다(경량 종료).

## 커버리지 추출 절차 (언어 공통)

큰 틀의 절차는 언어와 무관하게 같다. 언어마다 바뀌는 것은 사용하는 도구, 계측을 켜는 지점, 출력 포맷이며 이는 아래 "언어별" 절에서 정한다.

1. **감지** -- 대상의 빌드 / 테스트 시스템과 언어를 식별한다. cross-flow 층에 `architecture.md` 가 있으면 그 "기술 스택" 절의 언어 배치를 1차 입력으로 삼고, 없으면 대상 경로의 마커 파일로 감지한다. 마커가 여럿이면 어느 것을 대상으로 삼을지 사용자에게 확인한다.

   | 마커 파일 | 빌드 시스템 | 테스트 러너를 읽는 곳 |
   |----------|-----------|---------------------|
   | `CMakeLists.txt` | CMake | `enable_testing` · `add_test` 선언 |
   | `Cargo.toml` | Cargo | 내장 (`cargo test`) |
   | `package.json` | npm 계열 | `scripts.test` |
   | `pyproject.toml` · `setup.py` | Python 패키징 | `[tool.pytest]` 등 러너 설정 절 |

2. **계측** -- 감지한 언어의 소절이 지정한 지점에서 계측을 켠다(빌드 플래그 / 실행 래퍼 / 러너 내장 중 하나). 소절이 없는 언어면 여기서 멈추고 사용자에게 알린다.
3. **실행** -- 테스트 스위트를 계측과 함께 실행해 원본 커버리지 출력을 수집한다. 실행 명령 자체는 프로젝트의 빌드 / 러너 설정에서 읽는다. 로그는 산출물 디렉토리로 리다이렉트한다.
4. **수집 · 변환** -- 원본 출력을 먼저 lcov 트레이스로 통일하고, 그 트레이스를 아래 스크립트에 넘겨 정규화 데이터를 얻는다. 중간 포맷을 하나로 고정해야 언어가 늘어도 정규화하는 쪽이 언어마다 갈라지지 않는다.

   ```
   ${CLAUDE_PLUGIN_ROOT}/skills/code-design/05-coverage/lcov-to-coverage.py \
       --root <프로젝트 루트> --target <대상 경로> --branch <브랜치 슬러그> \
       --tool <도구 이름> --exclude '<제외 패턴>' \
       --out <산출물 디렉토리>/coverage.js <lcov 파일>...
   ```

   변환은 결정적이라 매번 이 스크립트를 쓴다. 그때그때 변환 코드를 새로 짜면 같은 lcov 에서 실행할 때마다 다른 산출물이 나온다. 테스트 코드와 서드파티 경로는 `--exclude` 로 빼고, 프로젝트 루트 밖의 파일(시스템 헤더 등)은 스크립트가 제외한다. lcov 파일을 여러 개 넘기면 같은 소스 파일의 레코드를 합산한다.

## 언어별

언어별 내용은 몇 항목이라 파일을 쪼개지 않고 이 파일 안 소절로 둔다. 언어가 늘면 소절을 추가한다.

각 언어 소절은 아래를 정한다.

| 항목 | 내용 |
|------|------|
| 커버리지 도구 | 어떤 도구로 커버리지를 재는가 |
| 계측 켜는 지점 | 빌드 플래그 / 실행 래퍼 / 러너 내장 중 무엇인가 |
| 출력 포맷 | 그 도구에서 lcov 트레이스를 뽑는 방법. 직접 못 내면 무엇을 거쳐 변환하는가 |
| 변환 메모 | 그 언어에서 수치가 틀어지는 지점과 대응 |

### C++

- 커버리지 도구: 빌드에 쓰는 컴파일러를 따른다 -- GCC 면 gcov 계열, Clang 이면 llvm-cov. 컴파일러와 다른 계열을 고르면 계측 데이터를 읽지 못하므로 선택의 여지가 없다.
- 계측 켜는 지점: 빌드 플래그. gcov 계열은 `--coverage`, llvm 계열은 `-fprofile-instr-generate -fcoverage-mapping`.
- 출력 포맷: 계열과 무관하게 **lcov 트레이스로 통일해 수집한다**. gcov 계열은 `gcovr` 또는 `lcov` 로, llvm 계열은 `llvm-profdata merge` 로 `.profraw` 를 합친 뒤 `llvm-cov export -format=lcov` 로 뽑는다. 원본(`.gcda` / `.profraw`)도 함께 보존한다.
- 변환 메모:
  - 계측 빌드는 최적화를 낮춘다(`-O0` 또는 `-Og`). 인라인·루프 변환이 일어나면 라인 번호가 소스와 어긋나 정규화 데이터의 라인 키가 맞지 않는다.
  - 헤더에 있는 인라인 함수와 템플릿은 그것을 포함한 번역 단위마다 따로 계상된다. 파일 경로를 키로 병합하지 않으면 같은 줄이 여러 번 나타난다.
  - 경로가 빌드 디렉토리 기준으로 나오므로 프로젝트 루트 기준 상대경로로 정규화한다.
  - 테스트 코드 자체와 시스템·서드파티 헤더는 제외한다. 제외하지 않으면 분모가 부풀어 수치가 실제보다 낮게 나온다.
  - gcov 계열의 `.gcda` 는 실행할 때마다 누적되므로, 재실행 전에 이전 산출물을 지운다.

### Python

- 커버리지 도구: coverage.py. pytest 를 쓰면 그 래퍼인 pytest-cov 로 붙인다.
- 계측 켜는 지점: 실행 래퍼(`coverage run -m pytest`) 또는 러너 플러그인(`pytest --cov`). 빌드 단계가 없어 빌드 플래그로 켜는 자리가 없다.
- 출력 포맷: `coverage lcov` 로 lcov 트레이스를 뽑는다(coverage.py 7 이상). 원본 `.coverage` 데이터 파일도 함께 보존한다.
- 변환 메모:
  - 브랜치 커버리지가 기본으로 꺼져 있으므로 `--branch` 를 켠다. 켜지 않으면 라인 수치만 나와, 브랜치 칸이 비었는지 0 인지 구분되지 않는다.
  - 테스트를 병렬로 돌리면 데이터 파일이 프로세스별로 쪼개지므로 `coverage combine` 으로 합친 뒤 변환한다.
  - 서브프로세스를 띄우는 테스트는 자동으로 계측되지 않는다. `COVERAGE_PROCESS_START` 를 걸어 자식 프로세스에서도 계측이 시작되게 한다.
  - 경로가 실행 위치 기준으로 기록되므로 설정의 `[paths]` 로 프로젝트 루트 기준으로 정규화한다.
  - 테스트 코드와 가상환경 디렉토리는 `omit` 으로 제외한다. 제외하지 않으면 분모가 부풀어 수치가 실제보다 낮게 나온다.

### Rust

- 커버리지 도구: cargo-llvm-cov. rustc 가 LLVM 기반이라 소스 기반 계측이 툴체인에 들어 있고, 이 도구는 그것을 cargo 에서 쓰게 감싼 래퍼다.
- 계측 켜는 지점: 도구가 대신 건다 -- `cargo llvm-cov` 가 `-C instrument-coverage` 를 `RUSTFLAGS` 로 걸어 테스트를 돌린다.
- 출력 포맷: `cargo llvm-cov --lcov --output-path <파일>` 로 직접 뽑는다. 원본 `.profraw` · `.profdata` 도 함께 보존한다.
- 변환 메모:
  - 제네릭과 `#[inline]` 함수는 단형화로 인스턴스마다 따로 계상된다. 파일 경로를 키로 병합하지 않으면 같은 줄이 여러 번 나타난다.
  - 워크스페이스는 크레이트마다 따로 돌리면 데이터가 갈라지므로 `--workspace` 로 한 번에 돌린다.
  - 의존 크레이트 소스(`~/.cargo/registry` 아래)까지 섞여 나오므로 `--ignore-filename-regex` 로 제외한다. 제외하지 않으면 분모가 부풀어 수치가 실제보다 낮게 나온다.
  - doctest 는 기본 수집 범위 밖이라 켜지 않으면 그 몫이 미커버로 잡힌다. 켤지 말지를 정하고 산출물에 어느 쪽인지 남긴다.
  - 이전 실행의 `.profraw` 가 남으면 섞이므로 `cargo llvm-cov clean` 으로 지우고 시작한다.

## 산출물

- **위치:** `{프로젝트 루트}/code-design/<브랜치 슬러그>/05-coverage/`. 단독 진입이어도 현재 브랜치 슬러그 폴더에 둔다.
- **형태:** SPA 뷰어가 소비하는 정규화 데이터(code-analyze 의 `window.DATA` / data.js 와 같은 결). 사람이 읽는 마크다운 리포트가 아니다.
- **원본 보존:** 도구가 낸 원본 커버리지 출력(lcov / xml 등)과 빌드 / 테스트 로그도 이 디렉토리에 함께 남긴다.
- **뷰어:** 커버리지 뷰어(SPA)는 05-coverage 밖에서 별도로 만들어 관리한다. 이 단계는 뷰어가 읽을 **데이터 계약(형태)만** 산출한다.

### 파일명 규약

| 파일 | 내용 |
|------|------|
| `coverage.js` | 정규화 데이터. `window.COVERAGE = { ... };` 전역 대입 한 줄 |
| `raw/` | 도구가 낸 원본 -- lcov 트레이스와 그 앞 단계 산출물(`.gcda` · `.profraw` · `.coverage` 등) |
| `logs/build.log` · `logs/test.log` | 계측 빌드와 테스트 실행 로그 |

`fetch` 가 아니라 `<script src>` 로 주입하므로 전역 대입 형태여야 한다. `file://` 로 연 뷰어에서 fetch 는 CORS 로 막힌다(code-analyze `viewer/SCHEMA.md` 와 같은 제약).

### 데이터 스키마

필드는 lcov 레코드가 정한다. 뷰어는 이 중 무엇을 어떻게 그릴지만 고르며, 표시 방식이 바뀌어도 필드는 바뀌지 않는다.

```js
window.COVERAGE = {
  meta: {
    target,       // 대상 경로 (프로젝트 루트 기준)
    branch,       // 브랜치 슬러그
    languages,    // 배열. 예: ["cpp", "python"]
    tool,         // 커버리지를 뽑은 도구. 예: "llvm-cov"
    generatedAt   // 추출 시각 (ISO 8601)
  },
  summary: {      // files 를 합산한 값
    lines,        // { found, hit }
    branches,     // { found, hit } 또는 null
    functions     // { found, hit } 또는 null
  },
  files: [
    {
      path,         // 프로젝트 루트 기준 상대경로 = 유일 키
      language,     // 예: "cpp"
      lines,        // { found, hit }
      branches,     // { found, hit } 또는 null
      functions,    // { found, hit } 또는 null
      lineHits,     // { "<라인번호>": <실행 횟수> }
      branchHits,   // [{ line, block, branch, taken }]
      functionHits  // [{ name, line, hit }]
    }
  ]
}
```

세 가지를 지킨다.

- `path` 는 프로젝트 루트 기준 상대경로로 정규화한다. code-analyze 의 노드 경로와 같은 기준이라야 나중에 두 산출물을 조인할 수 있다.
- `lineHits` 에는 **실행 가능한 줄만** 넣는다. 값 `0` 은 실행 가능한데 한 번도 안 탄 줄이고, 키가 없는 줄은 주석 · 선언처럼 계측 대상이 아닌 줄이다. 둘을 합치면 미커버 줄을 셀 수 없다.
- 도구가 그 계측을 아예 내지 않았으면 `null`, 냈는데 항목이 없으면 빈 배열 또는 `{ found: 0, hit: 0 }` 이다. 브랜치 계측을 켜지 않은 것과 브랜치가 없는 것은 다른 상태다.

## 완료선

- 선결 게이트(코드 존재 + 빌드 성공)를 통과함
- 테스트 스위트가 계측과 함께 실행되어 원본 커버리지 출력이 수집됨
- 원본 출력이 SPA 뷰어용 정규화 데이터로 가공되어 산출물 디렉토리에 쓰임
- 원본 출력과 빌드 / 테스트 로그가 산출물 디렉토리에 보존됨
- 커버리지 요약이 사용자에게 제시되고 산출물 경로가 확인됨

# 확정지식 형식 규격

`knowledge-promote` 의 `2. 형식 변환` 이 로드하는 하위 파일. wip 산문을 확정지식 마크다운으로 바꿀 때의 프론트매터 칸과 본문 표기 규칙을 정한다.

이 규격이 겨냥하는 렌더 대상은 overview 의 `렌더 surface 전제` 가 정한 Herbarium GitHub Pages 다.

---

## 프론트매터 칸

| 칸 | 내용 |
|----|------|
| kind | 지식 종류. `concept`(패턴·아키텍처·라이브러리) 또는 `code`(언어 문법/기능). 본문 템플릿을 가르는 기준 |
| id | 확정지식 고유 식별자 (kebab-case). 보통 파일명과 일치. relations 가 가리키는 주소 |
| title | 사람용 제목 |
| summary | 검색·중복판정의 1차 기준. 한 문장이 원칙이되 2문장 이상이면 블록 스칼라 `|` 로 마침표 단위 개행하고 각 문장은 간결하게(레이아웃이 pre-line 렌더). 이 파일의 `summary 표기` 참조 |
| category | 택일하는 대분류 한 개 |
| tags | 여러 개의 교차 색인 |
| relations | 다른 id 로의 타입드 엣지. `타입:대상` 문자열의 평탄 리스트 (overview `3. 관계 추출` 참조) |

- `concept` -- 핵심·오해·참고 같은 자유 구성 (패턴·아키텍처·라이브러리).
- `code` -- 아래 "코드 지식 본문" 구성 (언어 문법/기능). frontmatter 에 아래 두 칸을 더한다.

### kind 결정 규칙

kind 는 주제가 무엇이냐가 아니라 **노트가 답하는 질문** 으로 정한다.

- concept = "무엇·왜·언제" 에 답하는 노트 (개념·패턴·아키텍처·라이브러리).
- code = "어떻게 쓰나(구문·시그니처)" 에 답하는 노트 (언어 문법·기능의 사용법).

같은 주제라도 답하는 질문이 다르면 다른 노트다. 예: Ranges 라는 패러다임을 설명하면 concept, views 의 사용 구문을 보이면 code.

흔한 오해 -- "코드가 들어가니까 kind:code" 가 아니다. concept 노트도 예제 코드를 가질 수 있다. kind 는 본문 구성을 가르는 기준이지 코드 등장 여부가 아니다.

concept 과 code 가 둘 다 필요한 큰 주제는 제3의 hybrid kind 를 만들지 않고 concept 과 code 로 분리한다. 분리는 capture 단계에서 한다 -- 메인이 그런 주제를 concept wip 와 code wip 두 개로 나눠 캡처하므로(capture 의 묶음/분리 자율), promote 는 각 wip 를 1:1 로 승급하면 된다(한 wip 를 두 노드로 쪼개지 않는다). 두 노드는 relations 의 `part_of` 로 잇는다(code 노드가 concept 노드의 일부 -- `3. 관계 추출` 참조).

| code 전용 칸 | 내용 |
|----|----|
| language | 대상 언어. `python` / `rust` / `cpp` |
| since | 도입된 표준·언어 버전(예: `C++20`, `python-3.10`). 검색·필터용 정규 단일값. 무관하면 생략 |

`kind`·`language`·`since` 는 wip 맨 위 `<!-- wip-meta: ... -->` 주석에서 읽는다. writer 는 concept·code 가리지 않고 이 줄을 단다.
주석이 없으면 `kind: concept` 으로 본다.

wip-meta 에는 `triggered_by` 도 실려 온다. 이 값은 발동 기준을 개량하기 위한 기록이지 지식의 일부가 아니므로 frontmatter 로 올리지 않는다. wip-meta 줄 자체가 확정지식에 남지 않으므로 별도로 지울 것은 없다.

wip-meta 의 `since` 가 복합값(예: `C++11 (constexpr) / C++20 (consteval)`)으로 와도 frontmatter `since` 는 단일 정규값으로 만든다 -- 가장 이른 도입 버전 하나만 남기고 괄호 주석·기능별 병기를 뗀다. 떨어져 나온 기능별 도입 버전 세부는 본문 `버전·지원` 이 담는다(아래 코드 지식 본문의 `since` vs 버전·지원 참조).

본문은 wip 산문을 정제해 옮긴다. 산문 "관련 개념" 섹션은 본문에 두지 않고 relations 로 올린다. 관계의 단일 출처는 프론트매터다.

### summary 표기

summary 는 검색·중복판정의 1차 기준이자 사람이 가장 먼저 읽는 줄이다. 한 문장으로 간결한 것이 원칙이다. 한 문장에 다 못 담아 2문장 이상이 되면 YAML 블록 스칼라 `|` 로 마침표 단위로 끊어 한 문장씩 줄을 나누고, 각 문장은 최대한 짧게 다듬는다.

레이아웃이 summary 를 `white-space: pre-line` 으로 출력하므로(overview 의 `렌더 surface 전제`), 블록 스칼라의 줄바꿈이 웹 화면에서 그대로 줄바꿈으로 보인다. 본문에서 쓰는 `<br>`·두 칸 공백은 summary 에 쓰지 않는다 -- 프론트매터 값에서 `<br>` 는 글자 그대로 노출되고 두 칸 공백은 YAML 이 접어 없앤다.

```
# 한 문장이면 평문
summary: std::span 은 소유 없는 연속 메모리 구간의 경량 뷰다.

# 2문장 이상이면 블록 스칼라로 문장별 개행
summary: |
  std::span 은 소유 없는 연속 메모리 구간의 경량 뷰다.
  포인터와 길이를 한 객체로 묶어 넘겨, 배열과 vector 를 같은 함수로 받는다.
```

### 본문 표기 규칙

확정지식은 GitHub Pages 로 렌더해 읽으므로(overview 의 `렌더 surface 전제`), 렌더링했을 때 한눈에 들어오는 구조로 정제한다. wip 산문이 아래 형태이면 목록으로 편다.

- 콤마로 나열 가능한 항목(2개 이상)을 한 문장에 이어 붙여 가독성이 떨어지면, 리드 문장 한 줄만 남기고 나머지를 목록으로 뺀다.
- 순서·단계가 있으면 번호 목록(`1.`), 병렬 항목이면 불릿(`-`)을 쓴다. 둘 중 무엇이 맞는지는 내용의 성격을 보고 그때그때 판단한다.
- 라벨이 붙는 항목은 라벨만 상위 줄에 두고, 설명은 개행해 하위 불릿으로 내린다. 설명 안에 구분되는 점이 2개 이상이면 하위 불릿으로 각각 쪼갠다. 한 덩어리면 하위 불릿 하나로 둔다.
- 들여쓰기는 상위 마커 폭에 맞춘다. 번호 목록(`1. `) 아래 하위 불릿은 3칸, `-` 불릿 아래는 2칸 들여쓴다. 칸수가 어긋나면 렌더링이 깨진다.
- 마침표로 여러 문장을 한 덩어리로 이어 놓으면 문장 단위로 개행한다. 불릿/설명 맥락이면 각 문장을 하위 불릿으로 내리고, 정의·배경·귀속처럼 문장끼리 느슨하게 나열되는 산문 문단도 문장 단위로 끊거나 불릿로 편다. 어디서 끊을지의 감각은 사람과 다를 수 있으므로, 일단 문장 단위로 펴두고 세부 조정은 사람이 읽으며 한다.
- 산문 문단 안에서 문장 단위로 줄바꿈할 때는 마크다운 특성상 그냥 개행이 안 먹으므로, 문장 끝에 `<br>` 또는 두 칸 공백을 붙인다. `<br>`만 많이 쓰면 원본(raw)이 지저분해지니 두 칸 공백과 적절히 섞는다. 최종 확인·미세 조정은 사람이 한다.
- 흐름·관계 다이어그램은 Mermaid(```mermaid 블록)로 그린다. 좌우 정렬이 필요한 ASCII art 는 쓰지 않는다. Mermaid 는 Pages 레이아웃이 포함한 클라이언트측 mermaid.js 가 렌더한다(렌더 surface 전제 참조). 좌우 대조면 마크다운 표도 폰트 무관하게 자동 정렬되니 대안이다.
- Mermaid 노드 라벨은 짧게 유지하고, 단계·상세 설명은 노드 안에 욱여넣지 말고 그림 아래 목록으로 뺀다. 그림은 흐름(누가 누구로 가나)만 담는다.
- `참고 자료` 섹션의 URL 은 꺾쇠(`<url>`) 또는 `[라벨](url)` 형식으로 쓴다. bare URL 은 Herbarium Pages(kramdown GFM)에서 자동 링크되지 않는다.

단, 콤마가 단순 연결어로 쓰였거나 "A다, 그래서 B다"처럼 한 논지가 이어지는 서술은 쪼개지 않는다. 나열·단계·독립된 사실의 핵심일 때만 목록화한다.

콤마 나열을 펴는 예:

```
# before
테스트를 먼저 쓰고, 그 테스트가 실패하는 것을 눈으로 확인한 뒤, 통과시키는 최소 코드를 쓴다.

# after
이 순서가 RED-GREEN-REFACTOR 사이클이다:

1. 테스트를 먼저 쓴다.
2. 그 테스트가 실패하는 것을 눈으로 확인한다.
3. 통과시키는 최소 코드를 쓴다.
```

라벨 항목의 설명을 하위로 내리는 예:

```
# before
1. RED -- 테스트를 먼저 작성하고 실행한다. 테스트는 실패해야 한다. 이 실패를 눈으로 확인하는 것이 핵심이다.

# after
1. **RED**
   - 테스트를 먼저 작성하고 실행한다.
   - 테스트는 실패해야 한다. 이 실패를 눈으로 확인하는 것이 핵심이다.
```

### 대조·반박 항목 (흔한 오해 / 반례 등)

틀린 주장과 그 반증을 나열하는 섹션은 각 묶음을 blockquote(`>`)로 묶는다.

- 한 묶음 전체를 blockquote(`>`)로 감싼다. blockquote 가 묶음 경계를 만들어 주므로 `---` 같은 구분선은 쓰지 않는다.
- 틀린 주장은 `> **오해:**` 줄에, 설명·근거는 `> -` 불릿로 문장 단위로 나열한다.
- 주장을 깨는 구체 예가 있으면 그 blockquote 안에서 한 단 더 들여 `> > **반례:**` (중첩 blockquote)로 둔다. 중첩 앞에는 `>` 만 있는 빈 줄을 둬 분리한다.
- `반례:`는 깔끔한 반례가 있을 때만 쓴다. 설명형이라 반례가 없으면 `오해:` 묶음만 둔다.
- 라벨이 이미 "틀렸다"를 뜻하므로 원문 첫머리의 판정어("아니다", "다르다")는 뺀다.
- 묶음 사이는 `>` 없는 완전한 빈 줄로 띄워 서로 나뉘게 한다.

예:

```
> **오해:** "CQRS = 이벤트소싱"
> - 자주 함께 쓰여 한 덩어리로 보이지만 독립적인 두 패턴이다.
>
> > **반례:** CQRS 없이 ES만, ES 없이 CQRS만 쓸 수도 있다.

> **오해:** "CQRS를 쓰면 코드가 두 배라 항상 손해"
> - 비용은 채택 레벨에 비례한다.
> - 비용이 폭증하는 것은 L3/L4다.
```

### 코드 지식 본문 (kind: code)

언어 문법·기능 지식은 아래 구성으로 정제한다. 권장 구성이며, 언어에 해당 없는 섹션은 N/A 로 두거나 생략한다.

| 섹션 | 내용 |
|------|------|
| 한 줄 정의 | 이 문법/기능이 무엇을 하나 |
| 문법 형태 | 어떻게 쓰는가 (시그니처·구문) |
| 최소 예제 | 돌아가는 짧은 코드 (`language` 로 작성). 완결 코드는 본문 끝 `전체 예제` 로 (아래 예제 완결성) |
| 이전 방식과의 차이 | before/after. 선행 방식이 없으면 N/A |
| 주의점 | 그 기능에 실제로 있는 것만 (갈래는 아래) |
| 흔한 오해 / 통념 정정 | 널리 퍼진 잘못된 통념과 그 정정. 있을 때만 두는 선택적 슬롯. 포맷은 concept 의 대조·반박 포맷 재사용 (아래) |
| 버전·지원 | 언어·표준 버전 기준 지원 현황. 문법·함수별 도입 버전, deprecated 변동. `since` 와 역할이 다름(아래) |
| 참고 자료 | 공식 문서·표준 |
| 전체 예제 | 복붙 빌드되는 완결 코드. 본문 끝 `## 전체 예제` 섹션 (아래 예제 완결성) |

예제는 중간 snippet(부분 코드 OK)과 전체 예제(복붙 빌드되는 완결 코드)로 구분한다. 전체 예제는 본문 끝에 `## 전체 예제` 제목의 독립 섹션으로 둔다(제목·헤딩 레벨 고정). 상세 요건은 writer 의 `예제 완결성` 과 같고, 코드 예제를 넣는 concept 노트에도 적용한다. 실행할 API 가 아닌 순수 illustration 코드는 풀빌드 N/A. 전체 예제의 실제 컴파일·실행 확인은 overview 의 `5. 검증` 이 책임진다.

주의점은 한 종류가 아니라서 아래 갈래 중 해당되는 것만 점검해 적는다. 없는 갈래는 적지 않는다.

- 수명·소유권 -- 예: view 가 임시 객체를 참조하면 dangling (GC 언어면 보통 N/A)
- 동작·안전성 -- 예: thread-safe 하지 않다, 재진입 불가, UB 조건
- 성능 -- 예: 숨은 복사·할당
- 문법·파싱 -- 예: 모호한 구문, 우선순위 혼동
- 호환·지원 -- 예: 컴파일러별 미구현, ABI 차이

`since`(frontmatter)와 "버전·지원"(본문)은 역할이 다르다. `since` 는 "언제부터"의 정규 단일값(가장 이른 도입 버전, 검색·필터 축)이고, 본문 "버전·지원"은 문법·함수별 도입 표준 버전과 deprecated 변동 같은 세부다. 복합 `since` 를 단일값으로 정규화할 때 떨어져 나온 기능별 버전 병기가 여기로 온다. 본문이 `since` 를 그대로 반복하지 않고, 구체 컴파일러·툴체인 최소 버전 수치는 단정하지 않는다(writer 의 `버전·지원 작성 형식` 과 같다). 디테일이 없으면 본문 "버전·지원"은 N/A 로 두고 `since` 만 남긴다.

"흔한 오해 / 통념 정정"은 그 기능에 널리 퍼진 잘못된 통념이 있을 때만 두는 선택적 슬롯이다(없으면 생략). 포맷은 이 파일 `대조·반박 항목` 의 blockquote 형식(`> **오해:**` ...)을 그대로 재사용하고, code 전용 포맷을 새로 만들지 않는다.

반증이 코드인 경우(이 코드가 되면 통념이 틀린 것) `> > **반례:**` 자리에 코드블록을 둘 수 있다. 단 중첩 blockquote 안에서 렌더가 깨지지 않아야 한다. 깨지면 코드를 그 blockquote 바로 아래 일반 코드블록으로 빼고, 그 안 반례는 말로 가리킨다(예: "아래 코드가 컴파일된다 = 통념이 틀림").

"주의점" 과 이 슬롯은 가른다 -- "맞게 알아도 빠질 실제 함정"(수명·안전성·성능 등)이면 주의점, "널리 잘못 믿는 통념을 바로잡음"이면 흔한 오해다. 한 사안이 헷갈리면 틀린 믿음을 교정하는 성격인지로 판단해 오해 슬롯에 둔다.

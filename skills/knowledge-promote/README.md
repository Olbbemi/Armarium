# knowledge-promote

캡처 스킬들([`knowledge-capture`](../knowledge-capture/README.md) · [`knowledge-scan`](../knowledge-scan/README.md) · [`knowledge-study`](../knowledge-study/README.md))이 쌓은 wip 초안을 확정지식으로 가공해 전역 지식 저장소에 올리는 스킬.

## 무엇을 하나

wip 산문 한 건을 골라 확정지식 형식(프론트매터 + 정제 본문)으로 변환하고, 관계 추출·일반화·검증·중복 점검을 거쳐 사용자 승인 후 `knowledge/` 에 저장한다.<br>
main 에 직접 넣지 않고 브랜치에서 격리해 커밋하며, 푸시·머지는 사용자가 한다.<br>
캡처(wip 누적)와 별개의 독립 스킬이다.

## 언제 쓰나

`/knowledge-promote` 슬래시 명령으로 호출했을 때만 동작한다. 자연어 발화로는 뜨지 않도록 description 을 슬래시 호출로 닫아 두었다.<br>
승급은 사용자가 시점을 고르는 단발 작업이라 자동 호출 대상이 아니다.

## 구조

- `overview.md` -- 진입점. 경로 설정 · 렌더 대상 전제 · 10단계 실행 순서
- `format/format.md` -- 확정지식 형식 규격. 프론트매터 칸 · 언어별 공식 문서 · 본문 표기 규칙 · 코드 지식 구성. 2단계에서 로드한다
- [`references/knowledge-repos.md`](../../references/knowledge-repos.md) -- 네 knowledge 스킬 공용. 등록 저장소 표와 경로 판정 절차
- [`references/knowledge-wip-sections.md`](../../references/knowledge-wip-sections.md) -- `knowledge-writer` 와 공용. wip 섹션의 제목·앵커·강제 여부. 2단계에서 함께 로드한다

## 경로

wip 폴더와 확정지식 디렉토리는 등록된 지식 저장소 하위에 있다.<br>
경로를 코드에 고정하지 않고, 활성 직후 사용자에게 저장소 루트를 입력받아 git origin remote 로 판정한 뒤 `<루트>/wip` 와 `<루트>/knowledge` 를 도출한다. 판정 규약과 등록 저장소 목록은 캡처 스킬 셋과 공유하는 [`references/knowledge-repos.md`](../../references/knowledge-repos.md) 가 단일 출처다 -- 표에 행을 더하면 대상 저장소가 늘고, 한 곳만 고치면 네 스킬이 함께 따라온다.

## wip 섹션을 앵커로 찾는다

wip 본문의 섹션에는 제목 옆에 `<!-- wip:relations -->` 같은 앵커가 붙어 있다. `knowledge-writer` 가 작성할 때 달고, 승급이 그 앵커로 섹션을 찾는다.<br>
제목이 아니라 앵커를 기준으로 삼는 이유는 `본문` 이 자유 Markdown 이라 writer 가 그 안에 헤딩을 만들 수 있어서다. 앵커가 없는 헤딩은 본문 안 헤딩이므로 섹션으로 보지 않는다.<br>
앵커는 wip 전용이라 확정지식으로 옮길 때 뗀다.

## 동작 흐름 (10단계)

1. **대상 선택** — `wip/` 를 Glob 해 목록을 보여주고 사용자가 하나를 고름. 한 번에 하나만. 목록이 비면 승급할 초안이 없는 것이라 여기서 끝냄. 이어서 **미해결 질문 선행 게이트** — 고른 wip 의 `미해결 질문` 항목에 `[해결 완료]` 마커가 없으면 사용자와 함께 해소한 뒤 진행. 사람 판단이 필요한 사안은 승급 전에 닫는다
2. **형식 변환** — 산문을 프론트매터(kind/id/title/category/tags) + 정제 본문으로. 형식 규격은 `format/format.md`, 섹션 계약은 `references/knowledge-wip-sections.md` 가 단일 출처다. `kind`(concept/code)가 본문 구성을 가른다 — concept은 핵심·오해·참고 자유 구성, code는 문법·예제·주의점·통념 정정 구성(`language`·`since` 칸 추가). "노트가 답하는 질문"으로 kind 결정(무엇·왜=concept / 어떻게 쓰나=code). `relations` 와 `summary` 는 뒤 단계가 채운다
3. **관계 추출** — `wip:relations` 섹션을 relations 타입드 엣지로. 종류 4개: `contrasts_with`(반대/경쟁), `same_family`(동료), `part_of`(부분-전체), `related`(그 외). `타입:대상` 문자열 평탄 리스트로 저장
4. **일반화** — 특정 프로젝트에 종속된 부분(이름·언어·규모·결정)을 제거하고 조건 서술로 다듬음. `wip:project-context` 가 `[전제 없음]` 표식이면 제거할 게 없다는 신호. 본문이 여기서 최종 형태가 되므로 프론트매터 `summary` 도 이 단계에서 씀
5. **검증** — 참고 URL 생존 확인, 조사 보류 목록 fetch·대조·정정, 전체 예제 컴파일·실행 확인, 사실성 의심 항목 표시. 보류 항목의 `차단` 표기에 따라 갈림 — 권한 거부는 사용자 일회 승인으로 fetch 되고, 서버 403 은 포그라운드여도 안 되므로 다른 출처나 WebSearch 로 확인
6. **중복·충돌 점검** — 기존 확정지식과 summary 비교, 병합/대체/별도를 사용자에게 질의. 고른 갈래가 8단계 대상 파일과 9단계 커밋 메시지를 가름 (병합·대체는 기존 id 를 그대로 씀)
7. **브랜치 생성·체크아웃** — main 에 직접 저장하지 않고 브랜치를 만들어 격리. 브랜치명과 재사용 여부는 대상 저장소의 규칙 파일(`CLAUDE.md` 등)이 정하고, 없으면 `promote/<YYYY-MM-DD>`
8. **초안 저장 후 검토·승인** — 7단계 브랜치 위 `knowledge/<id>.md` 에 먼저 저장하고, 그 경로와 검증·중복 이슈를 알려 사용자가 파일을 직접 열어 검토·승인. 승인이 9단계 커밋의 게이트
9. **커밋** — 승급 산출을 그 브랜치에 커밋. 메시지는 갈래별로 다름(`Promote` / `Merge` / `Replace`). 푸시·머지는 사용자가 함
10. **종료 보고** — 저장 경로와 브랜치명, 미해결로 남은 이슈를 알리고 끝냄

## `since` 는 승급이 정한다

`since`(도입된 표준·언어 버전)는 wip 에 실려 오지 않는다. 본문 `버전·지원` 의 항목 중 가장 이른 도입 표준을 뽑아 승급이 채운다.<br>
값이 비었거나 미심쩍으면 `format/format.md` 의 언어별 공식 문서 표로 확인한다. 언어·표준 버전만 근거이며, 같은 페이지의 컴파일러·런타임 지원 표는 근거로 쓰지 않는다.<br>
캡처가 아니라 승급이 정하는 이유는 승급이 포그라운드라 사용자 승인을 받아 외부 문서를 열 수 있어서다.

## 주의

- 관계 정보는 프론트매터 relations가 단일 출처다. 본문에 산문으로 중복하지 않는다.
- 가리키는 id 파일이 아직 없어도 그 관계를 빼지 않는다.
- 초안은 브랜치에 먼저 저장하고 사용자 승인을 받는다. 승인 없이 커밋으로 넘어가지 않는다.
- 한 wip 는 확정지식 노드 하나로 승급한다. 큰 주제의 concept/code 분리는 캡처 단계에서 이미 끝나 있다.
- 원본 wip 를 지우지 않는다. 승급이 끝난 wip 의 정리는 사람이 필요할 때 직접 한다.

## 다루지 않는 것

- 마크다운 -> SQLite/벡터 빌드, 임베딩, 그래프 시각화 (범위 밖)
- 여러 wip 동시 승급(배치) (범위 밖)
- 승급이 끝난 원본 wip 정리 (사람이 직접)

# 지식 승급 (promote)

`knowledge-capture` 가 쌓은 wip 초안을 확정지식으로 가공해 전역 지식 저장소에 올리는 스킬.
캡처(wip 누적)와 별개의 독립 스킬이며, 사용자가 직접 호출할 때만 동작한다.

wip 폴더와 확정지식 디렉토리는 모두 Herbarium 저장소 하위에 있다. Herbarium 의 실제 경로는 고정이 아니므로, 활성 직후 사용자에게 저장소 루트를 입력받아 git origin remote 로 검증하고 wip/ 와 knowledge/ 를 그 하위로 도출한다 (아래 "경로 설정" 참조).

---

## 활성 조건

`knowledge-promote` 는 사용자가 `/knowledge-promote` 슬래시 명령으로 호출했을 때만 활성된다.

<RICOCHET>
사용자 호출 없이 자가판단으로 승급을 시작하지 않는다.
</RICOCHET>

## 경로 설정

활성 직후, Herbarium 저장소 루트 경로를 사용자에게 입력받는다.
경로를 코드에 고정하지 않으며, 매 활성마다 새로 입력받는다.
입력받은 루트 하위에서 wip 폴더(`<루트>/wip`)와 확정지식 디렉토리(`<루트>/knowledge`)를 도출한다.

디렉토리명은 동명 저장소가 있을 수 있어 신뢰할 수 없으므로, 검증은 git origin remote 조회로 한다. 이 검증 기준은 capture 의 "저장 경로 설정" 과 같다.

### 검증 절차

1. 입력 루트에서 origin remote 를 조회한다. `git -C <입력루트> remote get-url origin`
2. 결과가 아래 기대 remote URL 과 정확히 일치하면 채택한다.
3. 일치하지 않거나 조회에 실패하면(존재하지 않는 경로 포함) 사유를 한 줄로 알리고 경로를 다시 입력받는다. 일치할 때까지 반복한다.

#### 기대 remote URL

이 값이 경로 검증의 단일 기준이다.

```
git@github.com:Olbbemi/Herbarium.git
```

채택한 wip · knowledge 경로는 메인 LLM 컨텍스트에만 유지하며(세션 휘발), 별도 파일 · 인덱스에 저장하지 않는다.

</PENETRATE>

## 렌더 surface 전제

확정지식의 1차이자 유일한 설계 타겟 렌더 surface 는 Herbarium 의 GitHub Pages 다. GitHub 블롭 뷰나 다른 마크다운 뷰어로도 열 수는 있으나 포맷을 그쪽에 맞추지 않는다.

빌드는 Jekyll 을 GitHub Actions 커스텀 워크플로(`actions/configure-pages` -> `ruby/setup-ruby`(3.2, bundler-cache) -> `bundle exec jekyll build`(Gemfile 의 Jekyll 4.3) -> `actions/upload-pages-artifact` -> `actions/deploy-pages`, Pages Source = "GitHub Actions")로 돌린다. Gemfile/Gemfile.lock 은 레포에 커밋돼 있어 CI 가 동일 Jekyll 4.3 버전을 쓴다. 플러그인 화이트리스트 제약이 없는 것은 `jekyll-build-pages` 를 쓰지 않는 커스텀 빌드 덕이다. 마크다운이 단일 진실원천이고, `knowledge/<id>.md` 가 푸시될 때마다 워크플로가 사이트 전체를 자동 재빌드·배포한다. 그래서 promote 는 노트별 HTML 을 만들거나 별도 빌드를 호출하지 않는다 -- md 저장이 곧 산출이고 렌더는 CI 가 맡는다.

사이트 골격(`_config.yml`·`_layouts`·`assets/css`·인덱스·워크플로)은 Herbarium 레포에 실제 파일로 존재하며 이 스킬의 범위 밖이다. 스킬은 그 골격이 렌더하기 좋은 깨끗한 마크다운만 산출한다.

골격이 전제하는 계약(스킬이 맞춰 산출할 것):

- 레이아웃은 골격의 `_config.yml` `defaults` 로 `knowledge/` 전체에 일괄 부여한다. 노트 frontmatter 에 `layout` 을 개별로 두지 않아 md 를 지식 내용만으로 깨끗이 유지한다.
- `summary` 는 레이아웃이 `white-space: pre-line` 으로 출력한다. 그래서 값의 줄바꿈이 화면 줄바꿈으로 보인다(아래 summary 표기).
- Mermaid 는 레이아웃이 포함한 클라이언트측 `mermaid.js` 가 렌더한다. Jekyll 플러그인은 쓰지 않는다.

<RICOCHET>
노트 frontmatter 에 layout 필드를 개별로 두지 않는다.
</RICOCHET>

## 실행 순서

활성 직후 위 "경로 설정" 을 먼저 수행해 wip · knowledge 경로를 확정한 뒤, 아래 순서로 진행한다.

1. 대상 선택
2. 형식 변환
3. 관계 추출
4. 일반화
5. 검증
6. 중복·충돌 점검
7. 브랜치 생성·체크아웃
8. 사용자 확인 후 저장
9. 원본 wip 처리
10. 커밋

### 1. 대상 선택

TaskCreate 로 "1. 대상 선택" task 를 등록하고 in_progress 로 설정한다. 대상 wip 가 결정되면 completed 로 닫는다.

인자로 topic 또는 파일명이 오면 그 wip 를 대상으로 한다. 인자가 없으면 채택한 wip 디렉토리 목록을 보여주고 사용자가 고르게 한다. 한 번에 하나의 wip 만 승급한다.

### 2. 형식 변환

TaskCreate 로 "2. 형식 변환" task 를 등록하고 in_progress 로 설정한다. 형식 변환이 완료되면 completed 로 닫는다.

wip 산문을 확정지식 형식(프론트매터 + 정제 본문)으로 바꾼다. 프론트매터 칸:

| 칸 | 내용 |
|----|------|
| kind | 지식 종류. `concept`(패턴·아키텍처·라이브러리) 또는 `code`(언어 문법/기능). 본문 템플릿을 가르는 기준 |
| id | 확정지식 고유 식별자 (kebab-case). 보통 파일명과 일치. relations 가 가리키는 주소 |
| title | 사람용 제목 |
| summary | 검색·중복판정의 1차 기준. 한 문장이 원칙이되 2문장 이상이면 블록 스칼라 `|` 로 마침표 단위 개행하고 각 문장은 간결하게(레이아웃이 pre-line 렌더). 아래 summary 표기 참조 |
| category | 택일하는 대분류 한 개 |
| tags | 여러 개의 교차 색인 |
| relations | 다른 id 로의 타입드 엣지. `타입:대상` 문자열의 평탄 리스트 (아래 관계 추출 참조) |

`kind` 가 본문 섹션 구성을 가른다. 마크다운 포맷 규칙(아래 본문 표기 규칙)은 두 종류 공통이고, 어떤 섹션을 두느냐만 갈린다.

- `concept` -- 핵심·오해·참고 같은 자유 골격 (패턴·아키텍처·라이브러리).
- `code` -- 아래 "코드 지식 본문" 골격 (언어 문법/기능). frontmatter 에 아래 두 칸을 더한다.

#### kind 결정 규칙

kind 는 주제가 무엇이냐가 아니라 **노트가 답하는 질문** 으로 정한다.

- concept = "무엇·왜·언제" 에 답하는 노트 (개념·패턴·아키텍처·라이브러리).
- code = "어떻게 쓰나(구문·시그니처)" 에 답하는 노트 (언어 문법·기능의 사용법).

같은 주제라도 답하는 질문이 다르면 다른 노트다. 예: Ranges 라는 패러다임을 설명하면 concept, views 의 사용 구문을 보이면 code.

흔한 오해 -- "코드가 들어가니까 kind:code" 가 아니다. concept 노트도 예제 코드를 가질 수 있다. kind 는 본문 골격을 가르는 기준이지 코드 등장 여부가 아니다.

concept 과 code 가 둘 다 필요한 큰 주제는 제3의 hybrid kind 를 만들지 않고 concept 과 code 로 분리한다. 분리는 capture 단계에서 한다 -- 메인이 그런 주제를 concept wip 와 code wip 두 개로 나눠 캡처하므로(capture 의 묶음/분리 자율), promote 는 각 wip 를 1:1 로 승급하면 된다(한 wip 를 두 노드로 쪼개지 않는다). 두 노드는 relations 의 `part_of` 로 잇는다(code 노드가 concept 노드의 일부 -- `3. 관계 추출` 참조).

<RICOCHET>
concept 과 code 외의 제3의 hybrid kind 를 만들지 않는다.
</RICOCHET>

<RICOCHET>
코드 예제가 들어 있다는 이유만으로 concept 노트를 kind:code 로 분류하지 않는다.
</RICOCHET>

| code 전용 칸 | 내용 |
|----|----|
| language | 대상 언어. `python` / `rust` / `cpp` |
| since | 도입된 표준·언어 버전(예: `C++20`, `python-3.10`). 검색·필터용 정규 단일값. 무관하면 생략 |

`kind`·`language`·`since` 는 wip 맨 위 `<!-- wip-meta: kind=code | language=... | since=... -->` 주석에서 읽는다.
주석이 없으면 `kind: concept` 으로 본다. (코드 wip 에는 capture 의 writer 가 이 주석을 단다.)

wip-meta 의 `since` 가 복합값(예: `C++11 (constexpr) / C++20 (consteval)`)으로 와도 frontmatter `since` 는 단일 정규값으로 만든다 -- 가장 이른 도입 버전 하나만 남기고 괄호 주석·기능별 병기를 뗀다. 떨어져 나온 기능별 도입 버전 세부는 본문 `버전·지원` 이 담는다(아래 코드 지식 본문의 `since` vs 버전·지원 참조).

본문은 wip 산문을 정제해 옮긴다. 산문 "관련 개념" 섹션은 본문에 두지 않고 relations 로 올린다. 관계의 단일 출처는 프론트매터다.

<RICOCHET>
관계 정보를 확정지식 본문에 산문으로 중복해 남기지 않는다.
</RICOCHET>

#### summary 표기

summary 는 검색·중복판정의 1차 기준이자 사람이 가장 먼저 읽는 줄이다. 한 문장으로 간결한 것이 원칙이다. 한 문장에 다 못 담아 2문장 이상이 되면 YAML 블록 스칼라 `|` 로 마침표 단위로 끊어 한 문장씩 줄을 나누고, 각 문장은 최대한 짧게 다듬는다.

레이아웃이 summary 를 `white-space: pre-line` 으로 출력하므로(위 렌더 surface 전제), 블록 스칼라의 줄바꿈이 웹 화면에서 그대로 줄바꿈으로 보인다. 본문에서 쓰는 `<br>`·두 칸 공백은 summary 에 쓰지 않는다 -- 프론트매터 값에서 `<br>` 는 글자 그대로 노출되고 두 칸 공백은 YAML 이 접어 없앤다.

```
# 한 문장이면 평문
summary: std::span 은 소유 없는 연속 메모리 구간의 경량 뷰다.

# 2문장 이상이면 블록 스칼라로 문장별 개행
summary: |
  std::span 은 소유 없는 연속 메모리 구간의 경량 뷰다.
  포인터와 길이를 한 객체로 묶어 넘겨, 배열과 vector 를 같은 함수로 받는다.
```

<PENETRATE>
summary 가 2문장 이상이면 YAML 블록 스칼라 | 로 마침표 단위 문장별 개행한다.
</PENETRATE>

<RICOCHET>
summary 값에 HTML 줄바꿈 태그나 두 칸 공백 줄바꿈을 쓰지 않는다.
</RICOCHET>

#### 본문 표기 규칙

확정지식은 GitHub Pages 로 렌더해 읽으므로(위 렌더 surface 전제), 렌더링했을 때 한눈에 들어오는 구조로 정제한다. wip 산문이 아래 형태이면 목록으로 편다.

- 콤마로 나열 가능한 항목(2개 이상)을 한 문장에 이어 붙여 가독성이 떨어지면, 리드 문장 한 줄만 남기고 나머지를 목록으로 뺀다.
- 순서·단계가 있으면 번호 목록(`1.`), 병렬 항목이면 불릿(`-`)을 쓴다. 둘 중 무엇이 맞는지는 내용의 성격을 보고 그때그때 판단한다.
- 라벨이 붙는 항목은 라벨만 상위 줄에 두고, 설명은 개행해 하위 불릿으로 내린다. 설명 안에 구분되는 점이 2개 이상이면 하위 불릿으로 각각 쪼갠다. 한 덩어리면 하위 불릿 하나로 둔다.
- 들여쓰기는 상위 마커 폭에 맞춘다. 번호 목록(`1. `) 아래 하위 불릿은 3칸, `-` 불릿 아래는 2칸 들여쓴다. 칸수가 어긋나면 렌더링이 깨진다.
- 마침표로 여러 문장을 한 덩어리로 이어 놓으면 문장 단위로 개행한다. 불릿/설명 맥락이면 각 문장을 하위 불릿으로 내리고, 정의·배경·귀속처럼 문장끼리 느슨하게 나열되는 산문 문단도 문장 단위로 끊거나 불릿로 편다. 어디서 끊을지의 감각은 사람과 다를 수 있으므로, 일단 문장 단위로 펴두고 세부 조정은 사람이 읽으며 한다.
- 산문 문단 안에서 문장 단위로 줄바꿈할 때는 마크다운 특성상 그냥 개행이 안 먹으므로, 문장 끝에 `<br>` 또는 두 칸 공백을 붙인다. `<br>`만 많이 쓰면 원본(raw)이 지저분해지니 두 칸 공백과 적절히 섞는다. 최종 확인·미세 조정은 사람이 한다.
- 흐름·관계 다이어그램은 Mermaid(```mermaid 블록)로 그린다. 좌우 정렬이 필요한 ASCII art 는 쓰지 않는다. 전각(한글) 폭이 폰트마다 달라 ASCII art 열이 밀려 깨지고, 작성자가 뷰어 폰트를 통제할 수 없기 때문이다. Mermaid 는 Pages 레이아웃이 포함한 클라이언트측 mermaid.js 가 렌더한다(렌더 surface 전제 참조). 좌우 대조면 마크다운 표도 폰트 무관하게 자동 정렬되니 대안이다.
- Mermaid 노드 라벨은 짧게 유지하고, 단계·상세 설명은 노드 안에 욱여넣지 말고 그림 아래 목록으로 뺀다. 노드에 텍스트가 많으면 박스가 작아 글자가 강제 개행돼 지저분해진다. 그림은 흐름(누가 누구로 가나)만 담는다.
- `참고 자료` 섹션의 URL 은 꺾쇠(`<url>`) 또는 `[라벨](url)` 형식으로 쓴다. bare URL 은 Herbarium Pages(kramdown GFM)에서 자동 링크되지 않는다.

단, 콤마가 단순 연결어로 쓰였거나 "A다, 그래서 B다"처럼 한 논지가 이어지는 서술은 쪼개지 않는다. 나열·단계·독립된 사실의 핵심일 때만 목록화한다. 전부 쪼개면 글이 부서진다.

콤마 나열을 펴는 예:

```
# before
테스트를 먼저 쓰고, 그 테스트가 실패하는 것을 눈으로 확인한 뒤, 통과시키는 최소 코드를 쓴다.

# after
이 순서가 RED-GREEN-REFACTOR 사이클이다:

1. 테스트를 먼저 쓴다.
2. 그 테스트가 실패하는 것을 눈으로 확인한다.
3. 통과시키는 최소 코드를 쓴다.
```

라벨 항목의 설명을 하위로 내리는 예:

```
# before
1. RED -- 테스트를 먼저 작성하고 실행한다. 테스트는 실패해야 한다. 이 실패를 눈으로 확인하는 것이 핵심이다.

# after
1. **RED**
   - 테스트를 먼저 작성하고 실행한다.
   - 테스트는 실패해야 한다. 이 실패를 눈으로 확인하는 것이 핵심이다.
```

##### 대조·반박 항목 (흔한 오해 / 반례 등)

틀린 주장과 그 반증을 나열하는 섹션은 각 묶음을 blockquote 카드로 둔다.

- 한 묶음 전체를 blockquote(`>`)로 감싼다. 박스가 묶음 경계를 만들어 주므로 `---` 같은 구분선은 쓰지 않는다.
- 틀린 주장은 `> **오해:**` 줄에, 설명·근거는 `> -` 불릿로 문장 단위로 나열한다.
- 주장을 깨는 구체 예가 있으면 카드 안에서 한 단 더 들여 `> > **반례:**` (중첩 blockquote)로 둔다. 중첩 앞에는 `>` 만 있는 빈 줄을 둬 분리한다.
- `반례:`는 깔끔한 반례가 있을 때만 쓴다. 설명형이라 반례가 없으면 `오해:` 카드만 둔다.
- 라벨이 이미 "틀렸다"를 뜻하므로 원문 첫머리의 판정어("아니다", "다르다")는 뺀다.
- 카드 사이는 `>` 없는 완전한 빈 줄로 띄워 별개 박스가 되게 한다.

예:

```
> **오해:** "CQRS = 이벤트소싱"
> - 자주 함께 쓰여 한 덩어리로 보이지만 독립적인 두 패턴이다.
>
> > **반례:** CQRS 없이 ES만, ES 없이 CQRS만 쓸 수도 있다.

> **오해:** "CQRS를 쓰면 코드가 두 배라 항상 손해"
> - 비용은 채택 레벨에 비례한다.
> - 비용이 폭증하는 것은 L3/L4다.
```

#### 코드 지식 본문 (kind: code)

언어 문법·기능 지식은 아래 골격으로 정제한다. 권장 골격이며, 언어에 해당 없는 섹션은 N/A 로 두거나 생략한다.

| 섹션 | 내용 |
|------|------|
| 한 줄 정의 | 이 문법/기능이 무엇을 하나 |
| 문법 형태 | 어떻게 쓰는가 (시그니처·구문) |
| 최소 예제 | 돌아가는 짧은 코드 (`language` 로 작성). 완결 코드는 본문 끝 `전체 예제` 로 (아래 예제 완결성) |
| 이전 방식과의 차이 | before/after. 선행 방식이 없으면 N/A |
| 주의점 | 그 기능에 실제로 있는 것만 (갈래는 아래) |
| 흔한 오해 / 통념 정정 | 널리 퍼진 잘못된 통념과 그 정정. 있을 때만 두는 선택적 슬롯. 포맷은 concept 의 대조·반박 카드 재사용 (아래) |
| 버전·지원 | 언어·표준 버전 기준 지원 현황. 문법·함수별 도입 버전, deprecated 변동. `since` 와 역할이 다름(아래) |
| 참고 자료 | 공식 문서·표준 |
| 전체 예제 | 복붙 빌드되는 완결 코드. 본문 끝 `## 전체 예제` 섹션 (아래 예제 완결성) |

예제는 중간 snippet(부분 코드 OK)과 전체 예제(복붙 빌드되는 완결 코드)로 구분한다. 전체 예제는 본문 끝에 `## 전체 예제` 제목의 독립 섹션으로 둔다(제목·헤딩 레벨 고정). 상세 요건은 writer 의 `예제 완결성` 과 같고, 코드 예제를 넣는 concept 노트에도 적용한다. 실행할 API 가 아닌 순수 illustration 코드는 풀빌드 N/A. 전체 예제의 실제 컴파일·실행 확인은 `5. 검증` 이 책임진다.

주의점은 한 종류가 아니라서 아래 갈래 중 해당되는 것만 점검해 적는다. 없는 갈래는 적지 않는다.

- 수명·소유권 -- 예: view 가 임시 객체를 물면 dangling (GC 언어면 보통 N/A)
- 동작·안전성 -- 예: thread-safe 하지 않다, 재진입 불가, UB 조건
- 성능 -- 예: 숨은 복사·할당
- 문법·파싱 -- 예: 모호한 구문, 우선순위 혼동
- 호환·지원 -- 예: 컴파일러별 미구현, ABI 차이

`since`(frontmatter)와 "버전·지원"(본문)은 역할이 다르다. `since` 는 "언제부터"의 정규 단일값(가장 이른 도입 버전, 검색·필터 축)이고, 본문 "버전·지원"은 문법·함수별 도입 표준 버전과 deprecated 변동 같은 세부다. 복합 `since` 를 단일값으로 정규화할 때 떨어져 나온 기능별 버전 병기가 여기로 온다. 본문이 `since` 를 그대로 반복하지 않고, 구체 컴파일러·툴체인 최소 버전 수치는 단정하지 않는다(writer 의 `버전·지원 작성 형식` 과 같다). 디테일이 없으면 본문 "버전·지원"은 N/A 로 두고 `since` 만 남긴다.

"흔한 오해 / 통념 정정"은 그 기능에 널리 퍼진 잘못된 통념이 있을 때만 두는 선택적 슬롯이다(없으면 생략). 포맷은 위 `##### 대조·반박 항목` 의 blockquote 카드(`> **오해:**` ...)를 그대로 재사용하고, code 전용 포맷을 새로 만들지 않는다. 이 슬롯은 통념 정정이 핵심인 code 노트에서 writer 가 자리 없이 임의 절을 만들지 않도록 정해 둔 것이다.

반증이 코드인 경우(이 코드가 되면 통념이 틀린 것) `> > **반례:**` 자리에 코드블록을 둘 수 있다. 단 중첩 blockquote 안에서 렌더가 깨지지 않아야 한다. 깨지면 코드를 카드 바로 아래 일반 코드블록으로 빼고, 카드 반례는 말로 가리킨다(예: "아래 코드가 컴파일된다 = 통념이 틀림").

"주의점" 과 이 슬롯은 가른다 -- "맞게 알아도 빠질 실제 함정"(수명·안전성·성능 등)이면 주의점, "널리 잘못 믿는 통념을 바로잡음"이면 흔한 오해다. 한 사안이 헷갈리면 틀린 믿음을 교정하는 성격인지로 판단해 오해 슬롯에 둔다.

### 3. 관계 추출

TaskCreate 로 "3. 관계 추출" task 를 등록하고 in_progress 로 설정한다. 추출이 완료되면 completed 로 닫는다.

wip 의 "관련 개념"·본문 언급을 relations 타입드 엣지로 만든다. 현재 종류 4개:

- `contrasts_with` — 같은 역할의 반대/경쟁 선택지
- `same_family` — 같은 계열의 동료
- `part_of` — 부분-전체 종속 (하위가 상위의 일부). 예: views 는 Ranges 의 일부
- `related` — 그 밖에 엮인 연관 개념 (아직 종류 미분류)

대상은 다른 확정지식의 id 다. 채택한 knowledge 디렉토리를 Glob 으로 보고 실재 id 와 우선 연결하되, 아직 없는 id 도 그대로 적는다.

저장 포맷 -- relations 는 `타입:대상` 문자열의 평탄 리스트로 frontmatter 에 둔다. 중첩 맵을 쓰지 않는다. GitHub 의 frontmatter 표는 중첩 맵을 제대로 못 그리지만 평탄 리스트는 `tags` 처럼 칩으로 깔끔하게 보이기 때문이다.

```yaml
relations: [contrasts_with:characterization-test, same_family:bdd, part_of:ranges, related:unit-test]
```

타입이 문자열 prefix 라 새 종류 추가가 스키마 변경이 아니다. 그래도 종류 남발은 피하고, 위 4종으로 안 잡히는 더 세밀한 세분화는 노드가 쌓인 뒤로 미룬다.

<RICOCHET>
가리키는 id 파일이 아직 없다는 이유로 그 관계를 relations 에서 빼지 않는다.
</RICOCHET>

<RICOCHET>
relations 를 중첩 맵으로 저장하지 않는다.
</RICOCHET>

### 4. 일반화

TaskCreate 로 "4. 일반화" task 를 등록하고 in_progress 로 설정한다. 완료되면 completed 로 닫는다.

확정지식은 전역이라 특정 프로젝트 색을 걷어낸다. wip 의 "캡처 맥락" 격리 블록(프로젝트 이름·언어·규모·아키텍처·그 프로젝트의 결정)은 확정지식에서 들어내거나 압축한다. 보편 서술은 "본 프로젝트는 ..." 대신 조건 서술("...할 때")로 다듬는다. 미해결 질문은 그 주제에 보편적인 항목만 남기고 특정 프로젝트의 결정은 뺀다.

프로젝트색은 산문에만 있지 않다. 코드 예제·발췌(특히 code-scan 유래 wip)에 스캔 원본의 프로젝트 고유 식별자(함수·타입·변수명)가 남아 있으면 범용 이름으로 치환한다. writer 가 원천에서 걸러도 최종 일반화는 이 단계 책임이다.

캡처 맥락이 `[전제 없음]` 표식 한 줄이면, capture 의 writer 가 검토 후 걷어낼 프로젝트색이 없다고 판단한 것이다. 이때는 본문을 그대로 통과시키고 추가로 깎을 프로젝트색을 찾지 않는다(표식 줄만 strip). 반대로 캡처 맥락이 표식도 내용도 없이 진짜 비었거나 섹션 자체가 없으면 writer 누락을 의심해, 본문에 프로젝트색이 샜는지 한 번 더 점검하고 의심되면 사용자에게 확인한다.

<RICOCHET>
wip 의 "캡처 맥락" 격리 블록을 확정지식 본문에 그대로 남기지 않는다.
</RICOCHET>

<RICOCHET>
코드 예제·발췌에 스캔 원본 프로젝트의 고유 식별자를 그대로 남기지 않는다.
</RICOCHET>

### 5. 검증

TaskCreate 로 "5. 검증" task 를 등록하고 in_progress 로 설정한다. 검증이 완료되면 completed 로 닫는다.

- 참고 자료의 URL 이 살아있는지 WebFetch 로 확인한다. 죽은 링크는 사용자에게 보고한다. URL 이 꺾쇠(`<url>`) 또는 `[라벨](url)` 형식인지 함께 확인하고, bare URL 이면 교정한다.
- wip 의 `조사 보류 목록`(capture 의 백그라운드 writer 가 권한 제약으로 못 메운 항목)을 처리한다. 각 항목의 출처를 실제 WebFetch 로 가져와 본문의 대응 `[미검증 #N]` 마커 위치와 대조하고, 어긋나면 정정한다. promote 는 포그라운드라 도메인 미허용이어도 사용자 일회 승인(등록 없이)으로 fetch 할 수 있다. 검증으로 확정된 항목은 보류 목록에서 내리고 본문의 `[미검증 #N]` 마커를 지운다. 이 마커와 보류 목록은 wip 전용이라 확정지식 최종본에 남기지 않는다.
- 사용자가 fetch 승인을 거부하거나 출처로도 확정 못 한 항목은 `미해결 질문` 으로 옮겨 잔류시킨다(graceful).
- 전체 예제(코드 예제)를 실제로 컴파일·실행해 통과를 확인한다. promote 는 포그라운드라 가능하다. 순수 illustration 코드(실행할 API 가 아님)는 대상이 아니다. writer 는 도구가 없어 구조적 완결만 보장하므로, 실제 빌드 확인은 이 단계가 책임진다.
  - 컴파일러·런타임 부재 등으로 못 돌리면(검증 불가) "검증 불가" 로 사용자에게 보고한다(graceful).
  - 빌드는 됐는데 실패하면(검증 실패 = 코드 결함) 메인이 명백한 누락(빠진 include 등)을 정정해 재빌드한다. 몇 차례로도 통과 못 하면 8단계 이슈로 사용자에게 보고한다(자동 무한 정정은 하지 않는다).
- 사실성이 의심되는 서술은 표시해 사용자 확인 항목으로 남긴다.

<RICOCHET>
조사 보류 목록에서 검증되지 못한 미검증 서술을 확정지식 본문에 단정형으로 올리지 않는다.
</RICOCHET>

<RICOCHET>
참고 자료 URL 을 bare URL 로 두지 않는다.
</RICOCHET>

<PENETRATE>

### 6. 중복·충돌 점검

TaskCreate 로 "6. 중복·충돌 점검" task 를 등록하고 in_progress 로 설정한다. 점검이 완료되면 completed 로 닫는다.

`knowledge/` 의 기존 확정지식과 summary 를 비교해 의미적으로 겹치는 후보를 찾는다. 중복(같은 주제) 또는 충돌(같은 주제, 다른 서술)이 의심되면 병합·대체·별도 중 무엇이 맞는지 사용자에게 묻는다.

### 7. 브랜치 생성·체크아웃

TaskCreate 로 "7. 브랜치 생성·체크아웃" task 를 등록하고 in_progress 로 설정한다. 브랜치 생성 및 체크아웃이 완료되면 completed 로 닫는다.

승급 산출을 Herbarium main 에 직접 넣지 않고 브랜치에서 격리해, main 머지 시점에 CI 자동 배포가 일어나도록 한다.

1. 현재 브랜치가 main 인지 확인하고, main 이 아니면 먼저 main 으로 이동한다.
2. `git -C <herbarium루트> checkout -b promote/<id>` 로 신규 브랜치를 생성·체크아웃한다.

이후 8·9 단계(저장·원본 wip 처리)는 이 브랜치 위에서 수행한다.

<PENETRATE>
사용자 확인 후 저장 전, Herbarium 루트에서 `promote/<id>` 브랜치를 생성·체크아웃한 뒤 그 브랜치 위에서 저장·커밋한다.
</PENETRATE>

<RICOCHET>
브랜치를 만들지 않고 Herbarium main 에 직접 저장하지 않는다.
</RICOCHET>

### 8. 사용자 확인 후 저장

TaskCreate 로 "8. 사용자 확인" task 를 등록하고 in_progress 로 설정한다. 변환 결과와 이슈를 사용자에게 제시하기 직전 completed 로 닫는다. 사용자 승인 후 TaskCreate 로 "8. 확정지식 저장" task 를 등록하고 in_progress 로 설정한 뒤 저장을 진행한다. 저장이 완료되면 completed 로 닫는다.

변환 결과 본문과 5·6 단계의 이슈(죽은 링크, 사실성 의심, 중복·충돌 후보)를 사용자에게 함께 제시하고 승인받는다. 승인 시 메인이 채택한 `<knowledge>/<id>.md` 로 저장한다.

<PENETRATE>
확정지식 저장 전 변환 결과와 검증·중복 이슈를 사용자에게 제시하고 승인받는다.
</PENETRATE>

### 9. 원본 wip 처리

TaskCreate 로 "9. 원본 wip 처리" task 를 등록하고 in_progress 로 설정한다. 처리가 완료되면 completed 로 닫는다.

승급 후 원본 wip 를 삭제할지 남길지 사용자에게 확인한다.

<RICOCHET>
사용자 확인 없이 원본 wip 파일을 삭제하지 않는다.
</RICOCHET>

### 10. 커밋

TaskCreate 로 "10. 커밋" task 를 등록하고 in_progress 로 설정한다. 커밋이 완료되면 completed 로 닫는다.

승급 산출(`knowledge/<id>.md`)과 원본 wip 처리 결과를 7단계에서 만든 브랜치에 커밋한다. 커밋 메시지 형식: `Promote <id> to knowledge`. 푸시·머지는 사용자가 한다.

<PENETRATE>
저장과 원본 wip 처리가 완료된 뒤 그 브랜치에 커밋한다. 커밋 메시지는 `Promote <id> to knowledge` 형식으로 한다. 푸시·머지는 사용자에게 맡긴다.
</PENETRATE>

`knowledge-capture` 가 쌓은 wip 초안을 확정지식으로 가공해 전역 지식 저장소에 올리는 스킬.
캡처(wip 누적)와 별개의 독립 스킬이며, 사용자가 직접 호출할 때만 동작한다.

- 확정지식: `/home/olbbemi/Project/Herbarium/knowledge/`

## 실행 순서

1. 대상 선택
2. 형식 변환
3. 관계 추출
4. 일반화
5. 검증
6. 중복·충돌 점검
7. 사용자 확인 후 저장
8. 원본 wip 처리

### 1. 대상 선택

인자로 topic 또는 파일명이 오면 그 wip 를 대상으로 한다. 인자가 없으면 `wip/` 목록을 보여주고 사용자가 고르게 한다. 한 번에 하나의 wip 만 승급한다.

### 2. 형식 변환

wip 산문을 확정지식 형식(프론트매터 + 정제 본문)으로 바꾼다. 프론트매터 칸:

| 칸 | 내용 |
|----|------|
| id | 확정지식 고유 식별자 (kebab-case). 보통 파일명과 일치. relations 가 가리키는 주소 |
| title | 사람용 제목 |
| summary | 한 줄 요약. 검색·중복판정의 1차 잣대 |
| category | 택일하는 대분류 한 개 |
| tags | 여러 개의 교차 색인 |
| relations | 다른 id 로의 타입드 엣지 (아래 관계 추출 참조) |

본문은 wip 산문을 정제해 옮긴다. 산문 "관련 개념" 섹션은 본문에 두지 않고 relations 로 올린다. 관계의 단일 출처는 프론트매터다.

<RICOCHET>
관계 정보를 확정지식 본문에 산문으로 중복해 남기지 않는다.
</RICOCHET>

#### 본문 표기 규칙

확정지식은 마크다운 뷰어(Obsidian 등)로 읽으므로, 렌더링했을 때 한눈에 들어오는 구조로 정제한다. wip 산문이 아래 형태이면 목록으로 편다.

- 콤마로 나열 가능한 항목(2개 이상)을 한 문장에 이어 붙여 가독성이 떨어지면, 리드 문장 한 줄만 남기고 나머지를 목록으로 뺀다.
- 순서·단계가 있으면 번호 목록(`1.`), 병렬 항목이면 불릿(`-`)을 쓴다. 둘 중 무엇이 맞는지는 내용의 성격을 보고 그때그때 판단한다.
- 라벨이 붙는 항목은 라벨만 상위 줄에 두고, 설명은 개행해 하위 불릿으로 내린다. 설명 안에 구분되는 점이 2개 이상이면 하위 불릿으로 각각 쪼갠다. 한 덩어리면 하위 불릿 하나로 둔다.
- 들여쓰기는 상위 마커 폭에 맞춘다. 번호 목록(`1. `) 아래 하위 불릿은 3칸, `-` 불릿 아래는 2칸 들여쓴다. 칸수가 어긋나면 렌더링이 깨진다.
- 마침표로 여러 문장을 한 덩어리로 이어 놓으면 문장 단위로 개행한다. 불릿/설명 맥락이면 각 문장을 하위 불릿으로 내리고, 정의·배경·귀속처럼 문장끼리 느슨하게 나열되는 산문 문단도 문장 단위로 끊거나 불릿로 편다. 어디서 끊을지의 감각은 사람과 다를 수 있으므로, 일단 문장 단위로 펴두고 세부 조정은 사람이 읽으며 한다.
- 흐름·관계 다이어그램은 Mermaid(```mermaid 블록)로 그린다. 좌우 정렬이 필요한 ASCII art 는 쓰지 않는다. GitHub 등 뷰어에서 한글(전각) 폭이 영문 2배로 보장되지 않아 열이 밀려 깨지고, 작성자가 뷰어 폰트를 통제할 수 없기 때문이다. 좌우 대조면 마크다운 표도 폰트 무관하게 자동 정렬되니 대안이다.
- Mermaid 노드 라벨은 짧게 유지하고, 단계·상세 설명은 노드 안에 욱여넣지 말고 그림 아래 목록으로 뺀다. 노드에 텍스트가 많으면 박스가 작아 글자가 강제 개행돼 지저분해진다. 그림은 흐름(누가 누구로 가나)만 담는다.

단, 콤마가 단순 연결어로 쓰였거나 "A다, 그래서 B다"처럼 한 논지가 이어지는 서술은 쪼개지 않는다. 나열·단계·독립된 사실의 알맹이일 때만 목록화한다. 전부 쪼개면 글이 부서진다.

콤마 나열을 펴는 예:

```
# before
테스트를 먼저 쓰고, 그 테스트가 실패하는 것을 눈으로 확인한 뒤, 통과시키는 최소 코드를 쓴다.

# after
이 순서가 RED-GREEN-REFACTOR 사이클이다:

1. 테스트를 먼저 쓴다.
2. 그 테스트가 실패하는 것을 눈으로 확인한다.
3. 통과시키는 최소 코드를 쓴다.
```

라벨 항목의 설명을 하위로 내리는 예:

```
# before
1. RED -- 테스트를 먼저 작성하고 실행한다. 테스트는 실패해야 한다. 이 실패를 눈으로 확인하는 것이 핵심이다.

# after
1. **RED**
   - 테스트를 먼저 작성하고 실행한다.
   - 테스트는 실패해야 한다. 이 실패를 눈으로 확인하는 것이 핵심이다.
```

##### 대조·반박 항목 (흔한 오해 / 반례 등)

틀린 주장과 그 반증을 나열하는 섹션은 각 묶음을 blockquote 카드로 둔다.

- 한 묶음 전체를 blockquote(`>`)로 감싼다. 박스가 묶음 경계를 만들어 주므로 `---` 같은 구분선은 쓰지 않는다.
- 틀린 주장은 `> **오해:**` 줄에, 설명·근거는 `> -` 불릿로 문장 단위로 나열한다.
- 주장을 깨는 구체 예가 있으면 카드 안에서 한 단 더 들여 `> > **반례:**` (중첩 blockquote)로 둔다. 중첩 앞에는 `>` 만 있는 빈 줄을 둬 분리한다.
- `반례:`는 깔끔한 반례가 있을 때만 쓴다. 설명형이라 반례가 없으면 `오해:` 카드만 둔다.
- 라벨이 이미 "틀렸다"를 뜻하므로 원문 첫머리의 판정어("아니다", "다르다")는 뺀다.
- 카드 사이는 `>` 없는 완전한 빈 줄로 띄워 별개 박스가 되게 한다.

예:

```
> **오해:** "CQRS = 이벤트소싱"
> - 자주 함께 쓰여 한 덩어리로 보이지만 독립적인 두 패턴이다.
>
> > **반례:** CQRS 없이 ES만, ES 없이 CQRS만 쓸 수도 있다.

> **오해:** "CQRS를 쓰면 코드가 두 배라 항상 손해"
> - 비용은 채택 레벨에 비례한다.
> - 비용이 폭증하는 것은 L3/L4다.
```

### 3. 관계 추출

wip 의 "관련 개념"·본문 언급을 relations 타입드 엣지로 만든다. 현재 종류 3개:

- `contrasts_with` — 같은 역할의 반대/경쟁 선택지
- `same_family` — 같은 계열의 동료
- `related` — 그 밖에 엮인 연관 개념 (아직 종류 미분류)

대상은 다른 확정지식의 id 다. `knowledge/` 를 Glob 으로 보고 실재 id 와 우선 연결하되, 아직 없는 id 도 그대로 적는다. 종류 세분화는 노드가 쌓인 뒤로 미룬다.

<RICOCHET>
가리키는 id 파일이 아직 없다는 이유로 그 관계를 relations 에서 빼지 않는다.
</RICOCHET>

### 4. 일반화

확정지식은 전역이라 특정 프로젝트 색을 걷어낸다. wip 의 "캡처 맥락" 격리 블록(프로젝트 이름·언어·규모·아키텍처·그 프로젝트의 결정)은 확정지식에서 들어내거나 압축한다. 보편 서술은 "본 프로젝트는 ..." 대신 조건 서술("...할 때")로 다듬는다. 미해결 질문은 그 주제에 보편적인 항목만 남기고 특정 프로젝트의 결정은 뺀다.

<RICOCHET>
wip 의 "캡처 맥락" 격리 블록을 확정지식 본문에 그대로 남기지 않는다.
</RICOCHET>

### 5. 검증

- 참고 자료의 URL 이 살아있는지 WebFetch 로 확인한다. 죽은 링크는 사용자에게 보고한다.
- 사실성이 의심되는 서술은 표시해 사용자 확인 항목으로 남긴다.

### 6. 중복·충돌 점검

`knowledge/` 의 기존 확정지식과 summary 를 비교해 의미적으로 겹치는 후보를 찾는다. 중복(같은 주제) 또는 충돌(같은 주제, 다른 서술)이 의심되면 병합·대체·별도 중 무엇이 맞는지 사용자에게 묻는다.

### 7. 사용자 확인 후 저장

변환 결과 본문과 5·6 단계의 이슈(죽은 링크, 사실성 의심, 중복·충돌 후보)를 사용자에게 함께 제시하고 승인받는다. 승인 시 메인이 `/home/olbbemi/Project/Herbarium/knowledge/<id>.md` 로 저장한다.
